Decision and first repair

The smallest independently useful first repair is a caller-owned service creation lease. Today start_session returns its random session ID only after GdbManager.create completes. A cancelled or lost response can therefore hide a process from the caller. Implement and qualify this contract first in separate copied service files; do not install or deploy it as part of this preparation.

Proposed additive API: start_owned_session(owner_id, binary, args, cwd) and stop_session_by_owner(owner_id). Keep existing start_session and stop_session(session_id) signatures and responses unchanged. The lease key covers only the existing binary, args, and cwd inputs; keep the manager-owned fixed gdb --interpreter=mi2 --quiet launch and add no executable, argv, or environment launch controls. Register the single-use owner lease synchronously before the first spawn await. Repeating the same owner and identical immutable launch tuple returns the same lease without a second spawn; a changed tuple returns OWNER_CONFLICT. Stop is idempotent. Stop before delayed start records a cancellation tombstone; a later start with that token returns CANCELLED_BEFORE_START without spawning. Do not recover by listing processes, killing unrelated sessions, or relying on a client-side race.

Lease states are PENDING_START, ACTIVE, STOP_REQUESTED, EXITED, UNRESOLVED, and the pre-start tombstone CANCELLED_BEFORE_START. Retain the process/session owner until proc.wait() returns a return code. Only that observation may produce EXITED. If termination cannot be confirmed, keep the lease and report UNRESOLVED; do not remove the registry entry or claim cleanup. Tokens are never reused within an attempt.

One service-monotonic send deadline must cover lock acquisition, stdin write/drain, and response collection. The current implementation starts its collection timeout after lock and drain. A deadline hit while drain is unresponsive must stop later command admission and retain unresolved ownership; do not assume cancelling a drain cancels transport work. Close uses one absolute service-monotonic deadline, proposed at 7,000 ms, covering quit write/drain and every wait. Graceful and terminate waits may retain 3,000 ms and 2,000 ms caps; final wait receives only the time remaining on the same deadline. If quit/drain consumes that budget or final wait does not confirm exit, retain the task and lease as UNRESOLVED. Remove only after confirmed exit. A 7,000 ms service close cap does not establish that it fits the existing controller's 8-second cleanup reserve; no child/GDB/finalization partition or independent concurrency proof is frozen.
