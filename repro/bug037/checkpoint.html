Confirmed source cause and caller bounds

mainloop has one AUDIO_ENGINE_EXEC callsite after the presentation dispatcher and normal gameplay work. When STAGE_PENDING is set, the presentation branch calls PRES_MAIN_NEXT_STAGE, starts the next-level screen, returns retain, and loops before the audio service. Thus the last service can publish cue 9, then the next presentation frame freezes its sequencer while replacing the maze. This confirms the source mechanism; the user artifact, live bytes, queue state, and audible manifestation remain unverified.

audio_poll_gameplay currently requests music IDs 9, 10, 11, and 13 for stage completion, extra completion, special completion, and death. audio_init_impl queues cue 6. The current source therefore has five distinct reachable music IDs: 6, 9, 10, 11, 13. Cue 7 and cue 14 are anchor-pending; cue 8 is an alias without a separate producer. The current producer inventory must be rechecked before implementation.

Music currently enters the same four-entry FIFO as effects. Poll order can fill that FIFO before late stage/death events reach admission. Cue class must come from the manifest: cue 16 is class system despite its exclusive bit and is specified to preempt cue 13 at strictly higher priority, then play two ticks of silence. Cue 17 is its system alias. AUDIO_INIT_EXEC clears queue/slot state and writes silence before reinitializing; it is an explicit reset path.

Candidate direction and unresolved obligations

  1. Keep one clock, gated by the live owner. The early-return and gameplay paths can converge on one callsite, but only when the code at $0300 is still the audio engine. AUDIO_INSTALLED is not sufficient evidence because instruction/high-score phase swaps can reuse low RAM while that flag remains set. Before any service call, the implementation assignment must name and prove the existing owner discriminator and prove that the current live bytes at the entry match the installed audio image. If no existing discriminator suffices, the design requires renewed architectural/approval review.
  2. Reserve capacity for every distinct current music request. A four-ID pending queue is insufficient: while no cue is active, all five distinct IDs can be transiently pending before the selector chooses one. A five-ID queue is the safe bounded storage candidate. While music is active, at most four different IDs can wait because the active ID is deduplicated. Music must bypass the effect FIFO, active music must not restart, duplicate active/pending requests coalesce, and dequeue chooses highest priority with FIFO ties. This bound is limited to the current five caller IDs and must fail closed if a new source is added.
  3. Resolve cue 16 without violating nonpreemption. Its current manifest semantics explicitly stop cue 13 before natural completion, while BUG-037's approved policy forbids another cue from truncating active music and requires preservation of the final-silence effect. A conservative candidate would defer cue 16 until cue 13 naturally ends, then honor its two-tick silence and hold the handoff through it. That changes the current immediate-stop timing; the parent must decide whether this satisfies the approved wording or returns the ticket for renewed approval. Do not implement an exception that truncates cue 13.
  4. Gate both exits. Once the owner and stop semantics are settled, the existing stage and terminal-death branches must retain the maze before state reset/screen publication while music is active or pending. Effects do not hold this barrier. Explicit audio reset may abort and silence immediately.

The candidate stays inside src/main.s, src/audio_runtime.s, and src/presentation_runtime.s plus the existing verifier. It adds no module, loader, or separate scheduler. It is not yet a Ready design because owner identity and cue-16 semantics remain unresolved.
