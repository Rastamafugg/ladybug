Settled omission cause

Source evidence distinguishes BUG-038 from BUG-005. A legal gate push updates authoritative GATE_STATE and queues a render. The frame renderer clears current RENDER_GATE_ID/RENDER_GATE2_ID after rendering. On a later RF_ENTITIES pass, erase_entity_footprints restores each entity's four maze cells from MAZE_STATE and, when no dot remains, the authored screen_map tile. draw_entities then paints the live objects. Gate composition occurs afterward only for nonzero current render IDs; it does not enumerate settled GATE_STATE. Collision continues to read GATE_STATE. Therefore a settled rotated gate's pixels can be overwritten while collision retains the rotated orientation. This is the confirmed source cause. The exact reported one-wall pixel result remains unobserved.

Evidence locations: src/main.s gate state update and render queue around 2698–2707, entity restore at 1543–1590 and 3709–3748, gate list construction/replay at 3113–3308; src/enemy_runtime.s background order at 752–836 and current gate ID clearing at 585–616. RSCH-010 independently recorded this same source chain. No hardware, loader, mapping, or emulator defect is indicated.

Bounded-design assessment

The existing GATE_ENTITY_LISTS table has 20 records of 77 bytes and associates entity footprints with each gate-plus-neighbor redraw rectangle. It can avoid scanning the whole maze, but it does not prove that replaying only associated gates is narrower than all gates. A read-only calculation over the copied generated maze found 117 legal initial dot cells, up to three associated gate rectangles for one 2×2 entity footprint, and a 12-cell witness covering all 20 gate records. The witness uses unique legal positions (6,4),(14,6),(8,14),(18,14),(18,2),(2,6),(20,6),(8,8),(8,18),(14,18),(4,20),(18,20). At high stages the source permits 12 entities. This is a geometric placement envelope; the deterministic RNG's reachability of that exact witness was not established. Thus a repair that replays every nonempty gate association has a 20-gate worst case and cannot be accepted as satisfying the no-wholesale-all-gates-redraw constraint.

A cell-local direction could restore a cell from current MAZE_STATE, then reconstruct only the dynamic gate overlay for that cell from GATE_STATE, before live entities are drawn. This avoids replaying whole gate unions and handles a consumed entity's underlay in principle. It is not a viable design yet: current maze_gate_owner is documented as a five-cell collision cross, while the state-specific overlay data spans four orientations and does not provide a proven complete cell-to-all-overlay-owner map. Neighbor overlap ownership, the correct overlay tile selection, and interactions with pending diagonal/final intents have not been established. Reapplying settled orientation before the existing pending gate phase may change transient rendering. Existing gate/entity metadata also does not by itself resolve that ordering.

Capacity is consequently unproven. A cell-local implementation would need a complete owner lookup or equivalent scan and pending-intent guard. The unchanged-size option of repurposing existing generated metadata has not been shown to encode all simultaneous visual owners. No defensible exact byte estimate or frame-cycle estimate can be assigned without crossing the checkpoint into implementation or additional experiments. Current headroom is only 117 resident bytes, 1 enemy byte, and 128 asset bytes; the design must demonstrate fit against all three before Ready.
