# Direct-page overall effort assessment

**Recommendation.** Treat the bounded 32-site recovery as the first capacity step. Do not authorize a repository-wide pass yet. Once a fresh combined candidate builds, take a lightweight census of emitted extended operands that target existing `$00` state, then propose a separately bounded next batch if its measured benefit justifies the review and runtime cost.

**Evidence and limits.** This is a read-only estimate, not an audit or implementation plan. At HEAD `beb9b29` the source inventory is 34 assembly/include files recursively (28 `.s`, 6 `.inc`), with 22 root-level files; that count includes test, benchmark, and prototype files and does not equal the normal build closure. The build tree has listings, but the available generated evidence is not a complete, provenance-qualified census of current combined source. The retained FEAT010 attempt06 keyboard/adaptive presentation measurement is 1303/1280 bytes. Its independently checked 32-site allowlist projects 1271/1280 and 9 bytes free; this is not a post-edit build result. The current combined build is blocked when the TMX compiler encounters the user-edited high-score map without its old Coin Positions layer, so no current integrated baseline, candidate count, total savings, or gameplay improvement is established.

The release DP guidance supports an explicit `<` only when the operand resolves to the existing runtime page. Main establishes game DP=$00 after bootstrap temporarily uses DP=$02; normal runtime and IRQ share $00. Such operands can save one instruction byte (and often one cycle per execution) without changing DP ownership. This does not establish frame-time savings. Moving definitions earlier can shorten many uses due to assembler forward-reference policy; changing variables' addresses, changing DP, or broadly changing assembler sizing policy is a different and substantially riskier task. The internal coding-conventions page still says DP is set once at boot and implies per-file `setdp` is unnecessary; reconcile that stale wording before using it as implementation guidance (small documentation task, about 0.5–1h).

**Advisory hands-on estimates.** These are conservative planning assumptions in hands-on person-hours, not measured executor time or a fixed commitment. The rough sum is 16–32 person-hours (2–4 person-days of hands-on effort); it is not a guaranteed elapsed-time forecast. Unknown eligible-site counts and the missing current combined build make confidence low, approximately ±50%, until a fresh build supports a real census.

- Inventory the normal-build module closure and candidate operands from fresh, profile-specific listings: 2–4h. Exclude immediate operands, non-state/data references, non-$00 targets, and timing-sensitive sequences pending separate review.
- Prove each candidate against source, listing and emitted bytes; verify runtime page, source context, included/copied-module boundaries, fixed entry constraints and conditional/profile behavior; prepare a bounded allowlist: 4–8h. Do not infer a site count from file count.
- Apply explicit operand prefixes and run ordered capacity builds: 3–6h, assuming changes stay operand-only and fit remains within existing caps. Begin with the 32-site recovery and keyboard/adaptive fit; only after a pass continue to the already required joystick/adaptive and keyboard/nonadaptive profiles. A hard miss returns for reassessment.
- Run the already-approved scenarios affected by the changed subsystems against a buildable candidate, including relevant input/menu/wake/ranking acceptance and byte/pixel checks: 5–10h. This is not a blanket full-suite rerun and adds no gate or fixture. Actual QA effort depends on which modules and behaviors change. New DP ownership, new scenarios or state-write authority are excluded.
- Parent integration, combined rebuild, source/listing/artifact review and retained evidence: 2–4h after the build input issue is resolved. Any TMX compiler repair is separate and unestimated here.

**Priority and exclusions.** Highest immediate capacity value is the exact, parent-reviewed 32-site presentation recovery because it addresses a measured 23-byte hard-cap miss and has a bounded byte-level equivalence argument. Beyond that, inspect only emitted operands in modules with measured hard-cap pressure, then consider repeated high-frequency state accesses where execution frequency can be established. Do not include audio acceptance/delay loops in the initial sweep: `audio_runtime.s` contains SN write spacing whose exact reference-clock timing is part of the behavior. A timing-sensitive candidate needs its own evidence and effort estimate. No total byte savings or performance benefit can be estimated from this inventory.

Definition reordering, `noforwardrefmax`, state relocation, a new DP value/context, or changing runtime DP/IRQ behavior are excluded from the 16–32h estimate. Those changes broaden emitted-code effects or runtime ownership, so they require a separate High-risk proposal and explicit acceptance/verification scope.
