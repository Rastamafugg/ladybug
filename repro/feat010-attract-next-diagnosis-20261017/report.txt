FEAT-010 Attract pending-at-actor diagnostic
Date: 2026-10-17
Status: Proposed, non-gating; preparation only

Question and scope

Determine whether a naturally reached Attract actor phase-change boundary has a framebuffer publication already pending before the actor overlay calls prepare. The leading source-specific hypothesis is that the page-23 logo callback queues its BACK publication, then the outer Attract path enters actor preparation without checking PENDING. This diagnostic does not prove the producer of PENDING, an IRQ commit during ACTIVE, a FRONT pixel write, or the cause of the visible stutter. It does not test the separately reproduced selection rollback (A2), high-score defects, or an owner-causality claim.

Current evidence and pins

Manual evidence is the isolated candidate ROM `repro/feat010-frontend-dispatch-repair-20261016/candidate/build/ladybug.rom`, SHA-256 `6b2181bfba91869fcfe304524ecdd965d30c7b5ad6c560c0b00da67439282b08`, receipt SHA-256 `cf861fcaeb95c1c905d758d0d7a191a128dd4c56ecf2a6a00e4e643db464c0e0`. The user confirmed Attract actor stutter and selection rollback. The manual record lacks the exact input sequence, observation duration, and first-publication time. No live FRONT capture or qualified PC-to-byte identity exists.

Relevant candidate source/map anchors are `attract_tick=$1C56`, page-23 `highscore_attract_tick=$B830`, logo callback `$B49B`, menu paths `$B67C/$B6EE`, actor overlay `$0786` with phase-change label `$078D`, and framebuffer prepare/finish/IRQ `$0DDF/$0E49/$0E97`. Source order is logo tick, then menu tick, then actor overlay. `highscore_logo_tick` can finish a BACK transaction; the actor helper has no PENDING guard before prepare. These are source facts only, not evidence that the path ran in the reported session.

Proposed card

- Test type: one-attempt, non-gating native GDB state diagnostic for A1 only. No guest-memory/register writes, injected input, forced phase, monitor endpoint, or retries. The user provides no input during the observation.
- Independent expected result: the diagnostic samples PENDING at page-23 callback entry and later at actor phase-change entry `$078D`, before the following prepare instruction. These stops may occur in different Attract dispatches. Retain `PRES_TIMER` and `FRAMES` at both boundaries; never infer a same-callback 0-to-1 transition from their values. PENDING=1 at `$078D` proves a queued-admission opportunity at that actor boundary only. It does not identify which routine set PENDING, prove that the subsequent prepare executed, or show an IRQ commit during its copy. At each stop record ACTIVE, front/back IDs, commit sequence, missed count, write-front fault, actor phase, logo desired phase and selected BACK-owner cache, mode/screen, and menu selection/dirty. Read only unbanked direct-page RAM state; do not read GIME/PIA MMIO unless its debug-read side effects are independently proven absent.
- In-session control: at the initial resident Attract stop, require Attract mode/screen, PENDING=0, and no menu input/dirty state. At `$B830`, capture the same queue state before the logo callback. If either starting state is already pending or dirty, stop and mark the sample non-discriminating. PENDING remaining 0 at `$078D`, or failing to reach that label once, is inconclusive, not a pass.
- Live-byte qualification: before interpreting the resident stop, compare source, staged, and destination bytes for the relevant `$1C56` path through its page-23 call and return. At `$B830`, compare the live mapped code bytes at `$B830/$B49B` and the relevant menu callback spans with the staged page-23 helper payload and authored source; this byte match is the mapping evidence, so do not read PAR/GIME/PIA MMIO. At `$078D`, compare copied actor bytes around `$0786/$078D` and the live framebuffer-module entry at `$0DDF` with staged payloads and source. Any mismatch stops the run without PC interpretation. `$0E49/$0E97` are identity references only if their live bytes are separately compared; this card does not claim execution reached them.
- Procedure, after approval and setup qualification: launch one fresh XRoar process from the pinned candidate with the normal native UI and the same reviewed CoCo 3/6809/512-KiB/RGB/random-RAM/empty-joystick settings: `shell cd /mnt/e/projects/ladybug/repro/feat010-frontend-dispatch-repair-20261016/candidate && nohup /mnt/e/projects/ladybug/docs/reference/xroar/src/xroar -ui gtk3 -ao pulse -machine coco3 -machine-cpu 6809 -ram 512 -ram-init random -cart-type gmc -cart-rom /mnt/e/projects/ladybug/repro/feat010-frontend-dispatch-repair-20261016/candidate/build/ladybug.rom -cart-autorun -tv-input rgb -joy-right "" -joy-left "" -gdb -gdb-ip 127.0.0.1 -gdb-port 65521 > /tmp/feat010-attract-pending.log 2>&1 & echo $!`. Parent must first confirm the port is unused and record the new process PID, executable, argv, and start time. Leave every existing emulator process untouched. From a fresh GDB-MCP session run `show architecture`, `set remote supported-packets-packet off`, then `target remote :65521`; require m6809. Arm only unconditional one-shot breaks: `tbreak *0x1C56`, continue once (maximum 5 seconds), qualify resident bytes and the initial control; then `tbreak *0xB830`, continue once (maximum 5 seconds), qualify page-23 code bytes and read PENDING before logo; then `tbreak *0x078D`, continue once (maximum 5 seconds), qualify copied/module bytes and capture the fixed state set. Because the last stop can be in a later dispatch, retain `PRES_TIMER` and `FRAMES` at all three stops. No conditional breakpoints or additional successor stops.
- Deadline and stop cap: hard cap 45 seconds from launch through process cleanup, including attach, byte comparisons, state reads, and cleanup; reserve the final 8 seconds for normal cleanup. Maximum three intended breakpoint stops and three continues. The per-continue 5-second bounds and total-phase estimate are proposed limits, not prior measurements; parent must confirm they fit the chosen GDB-MCP call costs before dispatch. On timeout, preserve the tool result and last proven boundary; take a synchronized listed-state snapshot only if the target is still stopped and time remains. Do not continue, retry, or claim absence. Clean up only the verified owned process, normal termination first and bounded force only if required.
- Failure evidence: retain ROM/receipt pins, process identity, GDB architecture/attach result, each stop PC and mapping, source/staged/live byte comparisons, fixed reads, timeout boundary, and cleanup result. No large trace retention is needed. A1 result remains a manual symptom result unless a live marker is captured; no acceptance gate is added.

Readiness and reassessment

The current GDB setup is not qualified for this candidate/Attract path. Historical Options round trips and the two observation-tool timeouts do not qualify it. No GDB-enabled process should start until the parent reviews the proposed card, independently confirms pinned artifact/source/receipt consistency and the static byte spans, and qualifies a fresh non-mutating GDB-MCP attach/architecture/read path against this candidate. Since this is a new diagnostic after the documented two-timeout boundary, this card remains Proposed and requires explicit user approval before execution. If attach or byte qualification fails, stop; do not repair the observer or add another capture path. A manual screenshot or user timestamp can document visible coincidence but cannot prove the past PENDING transition or actor call ordering, so it is not an equivalent substitute.
