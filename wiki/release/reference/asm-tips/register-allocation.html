Register allocation release

Give registers useful roles, then make each routine's contract explicit.

Start with the interface

The 6809 has no universal register-preservation convention. A routine can use A, B, D, X, Y, or U according to its interface and callers. State which registers carry inputs and results, which are clobbered, and whether condition codes are meaningful on return.

D is the 16-bit accumulator formed by A as its high byte and B as its low byte. The 16-bit index registers X, Y, and U are useful for independent bases, cursors, and temporary pointers. S is the hardware stack pointer used by subroutine calls and saved registers; do not use it as an ordinary cursor unless the stack discipline explicitly permits it.

Preserve only what the caller needs

PSHS and PULS save and restore selected registers on the system stack. Saving fewer registers reduces stack traffic, but only when the interface permits the routine to overwrite the others. A save list is part of the contract, not a substitute for documenting it. 

; Preserve U while using it as a temporary table pointer.
        ; D is a table-relative offset on entry.
        pshs    u
        leau    colour_lut,pcr
        leau    d,u
        ; use the selected lookup entries
        puls    u,pc

This pattern appears in Ladybug's shared_mask renderer: it saves U because that register holds the caller's value across lookup setup. Other registers are scratch for this routine's contract. See src/shared_text_runtime.inc for the complete routine.

Keep hot values in registers

If a value is used several times in one short routine, keeping it in a register can avoid repeated loads and stores. Reserve direct-page variables for values that must survive a call or be shared across routines. When a call can overwrite a live register, save the value, move it to another available register, or reload it after the call.

The best register role is local to the call chain. A useful contract says what remains live across each call instead of assuming that X is always a destination or that Y is always preserved. The 6809 pages for TFR, PSHS, and PULS describe the transfer and stack instructions.

Tradeoffs

  • A save/restore pair costs two instructions; each saved register adds stack traffic and cycles, but protects the caller's live value.
  • Keeping more values in registers can reduce memory traffic, but leaves fewer registers for nested calls and addressing.
  • Register allocation must account for flags: a load, arithmetic operation, or loop branch may replace condition codes needed by the caller.

Confirm the instruction's flag behavior in the 6809 instruction reference before relying on a condition-code result.
