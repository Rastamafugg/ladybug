Asset Packing and Sparse Streams release

Move immutable graphics from authored data to compact, indexed runtime streams.

Keep build encoding separate from runtime encoding

A graphics asset can pass through three different representations. Authored pixels and maps are the editor-friendly input. A sparse frame stream is the runtime representation: it identifies destination deltas and carries opaque or partial pixel runs while omitting transparent bytes. A transport-compressed payload is the storage representation used to fit immutable data in the cartridge banks. Boot expands that payload before the runtime decoder reads the sparse stream.

The encodings solve different problems. LZSS reduces the bytes stored in the boot image and costs startup expansion work. Sparse commands reduce work and bytes associated with transparent regions during a frame, while retaining a small decoder. Do not pass LZSS bytes to the sprite decoder or assume every dense image benefits from sparse encoding.

Generate the index after packing

Ladybug's sparse-sprite builder emits a three-byte index entry for each frame: a physical page and a 16-bit CPU-visible stream address. It can pad a stream so one indexed frame does not cross an 8 KiB page boundary. The page and address are resolved from the final layout, so a source offset or a previously observed address is not a stable runtime pointer.

The packer checks that compressed data expands to the original stream and that page allocations fit their assigned destinations. Keep those checks close to the packing step. A hand-maintained index can silently point at another frame after a palette change, deduplication, or payload reordering.

Resolve once, then decode to the selected destination

The player path combines the facing and animation into a frame ordinal, resolves its generated index, and passes the selected BACK destination to the sparse blitter. The resolver owns page selection; the blitter consumes the frame while that mapping is valid. See MMU-aware pointer lifetimes for the mapping contract and sprite blitting for the pixel operations.

; Source pattern from player_draw_impl in src/enemy_runtime.s
        lda     PLAYER_FACE
        lsla
        lsla
        adda    PLAYER_ANIM
        bsr     sparse_player_stream
        bsr     sparse_blit_fb

The input X remains the framebuffer destination while the resolver returns the stream in U. This separation lets one decoder target the framebuffer or another defined destination without storing absolute per-frame addresses in each actor record.

Choose formats for the whole path

  • Use a shared sparse command format when the same decoded frame can serve multiple runtime destinations.
  • Use generated indexes for page relocation and frame selection; do not embed packed payload offsets in actor state.
  • Count index tables, page padding, relocation records, and boot scratch along with the compressed payload.
  • Keep dense fixed-size data when sparse command overhead or per-frame decode cost outweighs the skipped pixels.
  • Measure a complete render worklist before describing a format as faster. Smaller source files do not prove lower frame cost.
