Assembly tips

Direct-page conventions release

Using the 6809's DP register and direct-mode addressing to save bytes and cycles on frequently used variables.

Why direct page matters

The 6809's DP register holds the upper byte of every direct-mode effective address. When the assembler emits direct mode (an 8-bit operand byte), the CPU combines DP with that byte to form the 16-bit address. For common 8-bit loads and stores, direct mode uses two instruction bytes instead of three and typically saves one cycle. Check the chosen instruction's page for its exact encoding and timing. Compare the LDA and STA pages for the selected form.

The savings compound when a frequently executed routine accesses direct-page state many times. The total frame-time benefit still depends on how often that routine runs and what else it does.

Choose and set the page

Choose a page that contains the variables addressed directly. Set DP before executing code that uses them, then keep it stable while that code and its interrupt handlers run. This example uses $02 to show the mechanism; it is not the Ladybug gameplay runtime's value. 

        setdp $02          ; lwasm: assemble matching labels in direct mode
        lda   #$02
        tfr   a,dp          ; runtime: DP = $02

The assembler directive describes which addresses may use direct-mode encodings. It does not change the CPU register. The program must set DP at runtime, and the runtime value must match the assembled operands.

Force an addressing mode when needed

The < prefix asks lwasm for direct-mode encoding when the label is in the selected direct page. The > prefix asks for extended mode when the assembler could otherwise select a shorter form. 

        lda   <score       * direct form, if score is in the selected page
        lda   >score       * extended form
        sta   <$05         * store at address DP:$05

Direct-mode operands contain only the low address byte. Changing DP changes which page that instruction accesses; it does not change the encoded operand. Restore the expected page before code using those operands runs again.

What belongs in direct page

Direct-page space is 256 bytes. Give it to frequently used state, counters, flags, and pointers whose lifetime and ownership are clear. Cold data and one-time setup state can remain in extended-addressed memory. Direct-page placement is a shared resource: document each variable and avoid overlapping live values.

Ladybug runtime example

Ladybug uses separate startup phases. src/gmc_bootstrap.s sets DP=$02 for bootstrap scratch. The game entry in src/main.s then sets DP=$00 before entering normal runtime work; runtime variables such as LAST_FRAME occupy that page. Normal runtime code and its IRQ handler share DP=$00. Do not treat the loader's value as the game's runtime convention.

The CPU value and each module's assembler directive must agree at the point of use. See the CoCo 3 memory map for the low-RAM mapping context.

Pitfalls

  • Assembler state is not CPU state. SETDP guides encoding; TFR A,DP changes the live register.
  • Direct mode uses the active page. A mismatched DP can direct reads and writes to the wrong variables.
  • Interrupts inherit the runtime context. An IRQ routine using direct operands must see the page expected by those operands.
  • Changing DP needs a boundary. Save, change, and restore it if code contexts genuinely require different pages.
