Beginner Glossary: Assembly and Cartridge Terms release

Plain-language definitions for reading 6809 assembly, build settings, graphics data, and CoCo 3 cartridge code.

The big picture

A programmer writes source text. The assembler reads that text and the selected build settings, then translates the chosen instructions into machine-code bytes for the cartridge image. Later, the CoCo 3 reads and executes those bytes. The assembler prepares the game; it does not run the game.

Computer, cartridge, and addresses

  • Tandy Color Computer 3 (CoCo 3): the computer that runs this game. Its central processing unit (CPU), or processor, executes 6809 instructions.
  • 6809: the processor family and instruction set used by the CoCo 3. An instruction is one operation for the processor to perform. Assembly mnemonics such as JSR name these operations.
  • GMC: Game Master Cartridge, the cartridge used by this project. A cartridge can hold more code and data than the computer can expose at once by dividing it into banks.
  • Bank: one selectable part of cartridge memory. Selecting a bank makes that part available in the cartridge's address window: the range of addresses the computer uses to access cartridge content.
  • ROM: read-only memory. A ROM image is the built file containing the bytes intended for the cartridge; it holds the game's code and data.
  • Address: a number the processor uses to select a memory location or hardware destination. The range of numbers it can use is its address space. A leading dollar sign means the number is hexadecimal, or base 16: $FF40 is an example.
  • Processor register: a small storage location inside the CPU, such as its A or B register, used while instructions calculate or move values. This is different from a hardware register.
  • Hardware register: a special address used to control or communicate with a device. When a register is memory-mapped, the processor reaches it using an address, but a read or write talks to hardware instead of ordinary RAM. The GMC documentation identifies $FF40 as its write-only bank-select register: software writes a bank choice there and cannot read that register back to discover the choice.

See the CoCo 3 memory map and cartridge connector. The GMC programming notes are the source for the $FF40 register description.

Source code and assembly

  • Source file: the human-written text that describes a program. Ladybug's 6809 assembly source includes files such as src/main.s.
  • Assembly language: short names called mnemonics that describe processor instructions, plus directives for the assembler. For example, JSR is a mnemonic. Directives guide the assembler and are not instructions executed by the CoCo's processor.
  • Assembler and machine code: an assembler translates assembly source into machine code: the bytes representing instructions and data that the processor can execute or use. Ladybug uses lwasm, part of LWTOOLS. Assembling is the translation step and happens before the game runs.
  • Label and symbol: a name attached to a location or value in the assembled program. A call that names a label lets the assembler calculate where the target code is. An undefined symbol error means the selected source did not provide a definition for a name that was referenced.
  • Subroutine: a reusable block of instructions. “Helper” is an informal name for a small subroutine that performs one task.
  • JSR and RTS: 6809 instructions for calling and returning from a subroutine. JSR life_marker_position calls code with that label; RTS returns to the instruction after the call. Read the JSR and RTS pages for their processor-level details.
  • Include file: another source file inserted by an assembler directive such as INCLUDE. The assembler processes its contents as part of the current build; the running game does not open the file.

Build settings and runtime

  • Build profile: a named set of build settings that selects which code and data are assembled into an image. Ladybug's COMPLETE_PROFILE setting controls complete-profile source blocks. Here, HST is shorthand for the project's highscore-test profile; the build system uses the full name. A profile is a build choice, not a processor mode or a game screen.
  • Compile-time conditional: an assembler directive that includes or skips source text while assembling. LWASM's IFNE value includes the following text when the value is nonzero; IFEQ value includes it when the value is zero; ELSE selects the other branch; ENDC closes the conditional.
  • Runtime: the period after the finished image starts executing on the CoCo 3. An emulator is a program that imitates another computer so its software can run on the current computer. A code path is the sequence of instructions the game follows for one situation.

A historical source example shows why assembly-time and runtime are different. These excerpts come from separate areas of src/main.s and src/shared_text_runtime.inc at the source revision when BUG-114 was first reproduced: 

; A call site uses the label life_marker_position.
marker_entry_begin
        jsr     life_marker_position

; Elsewhere, this file supplies the label for the complete profile.
        ifne    COMPLETE_PROFILE
        include "shared_text_runtime.inc"
        endc

At that revision, the highscore-test build set COMPLETE_PROFILE to zero, so the conditional skipped the include. The call still remained in the source selected for assembly. The assembler needed to find life_marker_position and assign it an address, but no selected source defined that label. It stopped with an undefined-symbol error while building the image; the CoCo had not tried to run the subroutine. BUG-114 later resolved this by excluding the unused live marker-entry code from HST. The current src/main.s has that profile guard. The LWTOOLS manual documents the INCLUDE and conditional directives. The build script selects the highscore-test profile and sets COMPLETE_PROFILE to zero for that build.

In the routine name life_marker_position, “life marker” means a life icon in the game's HUD. That differs from a “high-score marker” in a test report, which means a recognizable screen used to confirm that a test reached the high-score state.

Graphics data

  • Byte: a group of eight binary digits, called bits. Each bit is either 0 or 1; together the eight bits can represent 256 different values.
  • Tile: a small rectangular graphic reused to build a screen.
  • Tile atlas: a collection of unique tiles. A tile ID is the number used to refer to one tile in that collection.
  • One-byte tile ID: a tile number stored in one byte can hold values 0 through 255, or 256 distinct values. An atlas that needs 257 distinct IDs exceeds that limit.
