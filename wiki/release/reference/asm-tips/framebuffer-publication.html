Persistent Framebuffer Publication release

Pair each persistent image with its own history and publish only a completed hidden buffer.

Keep display ownership separate from drawing

Ladybug keeps two persistent framebuffer surfaces. The display scans FRONT while foreground rendering prepares the other surface, BACK. Before drawing, the renderer maps BACK and hydrates its owner-local metadata, including actor save-under validity and prior positions. This lets the game update only the affected regions instead of copying an entire shadow image every frame.

Pixels and the metadata that explains those pixels form one owner. A save-under captured for buffer A is not valid for buffer B, even when both buffers represent the same logical actors. Keep each history with its physical framebuffer and restore it when that framebuffer becomes BACK again.

Publish as one completed transaction

  1. Verify that the selected BACK owner differs from FRONT.
  2. Restore the affected actors and structural layers to a clean underlay.
  3. Draw current work into BACK and capture its matching owner metadata.
  4. Set the pending-ready flag only after the complete image and history are coherent.
  5. At Vbord, let the IRQ change the display offset and exchange FRONT/BACK ownership.

If no complete BACK image is ready, the IRQ keeps the current FRONT. A partial renderer must not arm publication just because its own layer is finished; all cooperating dynamic layers for that transaction must be closed first.

Use the interrupt as the sole display commit point

The foreground owns pixel updates and may prepare the pending flag. The Vbord IRQ owns the display-offset write and successful owner swap. Keeping one publication point prevents a display from switching midway through a draw and makes commit counters meaningful. Do not let a helper write the display offset as a shortcut around the transaction.

Persistent A/B buffers trade full-image copies for owner-specific history and closure work. This is efficient when the damage bookkeeping is correct; an unbounded restore or an incomplete owner history can cost more than a copy or can publish stale pixels.

Measure the rendered work, not just the buffer name

Record the phase and executed worklist first when comparing render cost. FRONT/BACK owner is supporting metadata because each owner has different retained pixels and history. An owner-specific timing claim needs a controlled crossover with identical starting pixels, metadata, and render intents.

For the hardware display offset and Vbord registers, see the GIME reference. For mapped windows, see the CoCo 3 memory map. For pixel writes and save-under rules, see packed-pixel and sprite blitting.
