Assembly tips · timing

Hot loops and code size release

Reduce repeated work, then compare loop overhead with the bytes used to remove it.

Move invariant setup outside the loop

If a base pointer, table row, or constant does not change during an iteration, prepare it once before the loop. Keep the changing index or pixel value in a register and use indexed loads and stores for the repeated part. Do not hoist a value if a call or interrupt can change its source while the loop is active.

Ladybug's shared_mask prepares the font and colour-table pointers, then processes a fixed number of rows. This keeps table selection outside the per-row path while retaining one compact row loop. The full routine is in src/shared_text_runtime.inc.

Count the loop work

A small counted loop usually saves code bytes because one body handles each element. Its repeated work includes the counter update and the branch. For a very small fixed count, those instructions may cost more than spelling out each iteration. Compare the whole path, including setup and exit, and account for whether the branch is taken. 

; X/Y and ROWS_LEFT are initialized before this loop.
row_loop
        ldd     ,y++
        std     ,x++
        ldd     ,y++
        std     ,x++
        leax    156,x           ; four output bytes plus 156 = next 160-byte row
        dec     ROWS_LEFT
        bne     row_loop

Use the instruction pages for DEC, BNE, and LEAX to account for the chosen instructions. Exact time also depends on the target memory and the complete executed worklist.

Unroll only a fixed, worthwhile path

Loop unrolling writes multiple copies of the body and removes some per-iteration counter and branch work. It also increases code size and can make later changes harder to keep consistent. Unroll when the count is fixed, the path is hot enough to matter, and the added bytes fit the target's code region.

Ladybug's presentation_fast_blit writes the eight rows of an 8×8 graphic with straight-line loads and stores. The sibling shared_mask uses a row loop because it also expands each mask through a colour lookup. These are two different work shapes, not proof that one structure is always faster. Their assembled code size and complete workload should decide whether a change is useful. 

; One row of the straight-line graphic path:
        ldd     ,y++
        std     ,x++
        ldd     ,y++
        std     ,x++
        leax    156,x

Measure the right boundary

Instruction-cycle totals answer how much CPU time an instruction sequence uses; they do not alone establish that a game frame meets its budget. Measure the complete routine or worklist that matters, compare the same inputs and state, and record the assembled code-size change separately. Keep projected savings separate from observed results.

A game's cycle budget is a program requirement, not a universal 6809 limit. See the CoCo 3 timing reference and the individual 6809 instruction pages for the instruction-level basis.
