Assembly tips · source organization

Source order and instruction encoding release

Define state before use, make encoding requirements explicit, and verify the emitted program.

Define state before the instructions that use it

Place fixed addresses and record-field constants before their first use. A small shared include is appropriate when several modules use the same definitions. Keep profile-dependent definitions inside the correct conditional context and after the configuration symbols they depend on. Keep one authoritative definition for each shared address.

This organization makes dependencies visible and lets the assembler choose an encoding from an already-known value. A forward reference is a symbol used before its definition; even when its final value is small, the assembler may reserve a larger encoding.

STATE_SCREEN equ $00A6       ; resolved before the instruction

        setdp $00           ; assembler assumption
        clra
        tfr   a,dp          ; CPU state: DP = $00
        lda   STATE_SCREEN

This example establishes DP locally for illustration. A real module should obey its caller's documented DP contract; inserting new DP changes requires reviewing callers and interrupt handlers.

Know the assembler's forward-reference policy

LWASM's forwardrefmax pragma selects the maximum address or offset size for unresolved forward references unless an operand prefix explicitly selects a size. The LWTOOLS manual documents it as the default since version 4.14. Consequently, a later definition in page zero does not necessarily cause an earlier instruction to shrink.

SETDP $00 describes the page the assembler may assume. It neither sets the CPU's DP register nor overrides forwardrefmax. Disabling that policy with noforwardrefmax is a broader assembly-policy change: it can alter other inferred address and offset sizes. Review its complete output rather than using it as an unmeasured size fix.

Make required encodings explicit

Use < on a memory operand when direct-page encoding is an intentional requirement. Use > when extended encoding is required. The prefixes override automatic size selection; they do not establish the runtime DP value.

        lda   <STATE_SCREEN ; direct encoding:   96 A6
        lda   >STATE_SCREEN ; extended encoding: B6 00 A6

These hexadecimal bytes are the specified 6809 LDA encodings for STATE_SCREEN=$00A6, not a measured project build. With DP=$00, both load the same byte and have the same register and condition-code behavior. The direct form uses two instruction bytes instead of three. With another DP value, the direct form accesses a different address; the extended form still accesses $00A6.

Check each instruction's opcode, prefixes, width and timing. A prefixed instruction such as LDY retains its opcode prefix when changing address mode. A one-byte encoding saving does not establish a whole-frame performance improvement. See LDA, LDY and hot loops and code size.

Separate source cleanup from bounded size recovery

For long-term maintenance, define constants before use and document direct-page requirements where they matter. Moving a definition block earlier can improve readability and remove unnecessary forward references, but it may shorten every affected use, not only a selected instruction. Check conditional definitions, include dependencies and the complete changed listing.

For a narrowly scoped recovery, an audited allowlist of explicit direct operands gives a smaller review surface. Retain the routine, operation, target address, previous bytes and expected replacement for each site. Apply the change by source context; addresses and line numbers from an older listing may move. Keep broader reorganization separate from that repair.

Verify the program that was emitted

  1. Record source, profile, assembler options and baseline listing or artifact identities before editing.
  2. Prove the operand resolves to the intended page in every affected profile. Establish the runtime DP precondition on all relevant callers, interrupt paths and returns. Assembler directives alone are insufficient.
  3. Assemble with a listing. Compare actual opcodes, address widths, effective addresses and retained prefixes at each changed site; inspect additional encoding changes caused by moved definitions.
  4. Review relocated branches, calls, PC-relative operands, fixed entry points, copied code and generated symbol consumers. Smaller code moves labels; absolute entry contracts and copy boundaries still have to hold.
  5. Run the existing build and capacity guards for the affected profiles. Measure final region sizes and remaining space; projected byte savings are not a successful build.
  6. Use focused behavior or runtime checks for the identified risks. Verify changed timing where exact cycles matter. When interpreting banked or copied code, establish live-byte and mapping identity before using a source symbol as evidence.

Encoding equivalence requires the same effective address and operation; instruction lengths and timings can differ. Reaching a smaller binary size alone does not establish behavioral or timing equivalence.
