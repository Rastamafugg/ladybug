MAME cart-ROM-to-RAM comparison test internal

Run the same cart-ROM-to-RAM self-copy under MAME's CoCo 3 driver and compare against XRoar 1.10's broken cart-window write path.

Context

XRoar 1.10 does not write RAM-under-ROM for CPU-space writes in $C000-$FDFF when TY=0. Root cause is source-confirmed at coco3.c:1170-1240 — the RAS=0 gate skips the RAM-overlay write while S=1 routes the write to the read-only cart bank. See lessons-learned §XRoar cart-window write decode.

The documented real-hardware contract is that writes pass through to DRAM regardless of TY. Before locking that interpretation we want a second-emulator opinion. MAME's CoCo 3 driver is the most thorough open-source model in active use.

Test plan

Goal: replay the boot-time self-copy and observe whether the underlying RAM page is written.

  1. Build a minimal cart (~16 KB) with:
    • "DK" magic + entry stub at $C000.
    • Code that, with TY=0 still in effect, writes a known sentinel (e.g. $5A) to $C100, then flips TY=1 via STA $FFDF, then reads $C100 and stores the result at a known RAM observation address.
    • Halt loop afterward.
  2. Run under MAME: mame coco3 -cart <path>.rom. Use MAME's debugger (-debug) to inspect.
  3. Run the same ROM under XRoar for direct A/B comparison — expected to show the sentinel not present in RAM.
  4. Record outcome:
    • If MAME shows the sentinel landed in RAM: confirms XRoar is the outlier; the hardware-contract interpretation in xroar-monitor (physical-space write is the right primitive) stands unchanged.
    • If MAME also drops the write: re-open the question. Update memory map and the monitor design accordingly.

Effort

Small. Cart build reuses existing lwasm + scripts/build.sh pipeline; MAME debug session is interactive. Estimate: 1-2 hours.

Priority

Not blocking the XRoar monitor Phase 2 implementation plan. But the result feeds the eventual Phase 10 hardware bring-up.
