Internal · backlog · superseded

Build a purpose-built mcp-xroar server internal

Cost/benefit of replacing gdb-mcp + m6809-gdb + XRoar GDB stub with a direct XRoar control plane. Superseded by xroar-monitor.

Why this might be worth doing

The current debug stack — gdb-mcp driving m6809-gdb connected to XRoar's built-in GDB remote stub — gives us CPU-visible memory, register reads, breakpoints, and instruction stepping. That's sufficient for ~80% of bring-up debugging.

The remaining 20% is genuinely hard to reach via the GDB protocol:

  • GIME internal state. MC3, MMUEN, mmu_bank[0..15], TR, the current S and RAS decode signals, IRQ-source masks. None exposed as memory-mapped reads.
  • Cycle-accurate stepping. GDB stub steps per-instruction.
  • Deterministic re-runs. Without snapshots, every gdb session re-runs the full BASIC boot + cart-autorun handshake.
  • Framebuffer / video state dumps.

The cart-RAM-corruption investigation hit exactly this wall.

Why we're not doing it yet

XRoar is a substantial C codebase. A purpose-built MCP server would either:

  1. Fork XRoar and add a JSON-RPC / stdio control plane. Pro: full access. Con: divergent fork.
  2. Patch XRoar with a small instrumentation socket. Pro: minimal diff, can upstream. Con: still a C build to maintain.
  3. LD_PRELOAD-style shim. Pro: no XRoar fork. Con: fragile.

All three are a multi-day project.

Current-stack improvements that defer this work

  1. Use XRoar's -trap <addr> -trap-snap <file> flags to save a snapshot at a known boot point, then re-launch with -load <file>.
  2. Insert temporary SWI opcodes in src/main.s at inspection points. (Updated: use bra . — see tooling/xroar.)
  3. Pass explicit timeout: 60 or higher on mcp__gdb-mcp__continue_exec calls.
  4. Sentinel probes for GIME state. Write a known byte to $FExx, read it back, infer.

Concrete trigger for revisiting this

Build the MCP server when all three are true:

  • An investigation requires direct GIME / MMU / cycle-level inspection that sentinel probes cannot answer.
  • That investigation has blocked progress for >1 day.
  • The investigation is on the critical path of a milestone.

Status (2026-05-16)

This sketch is superseded. The requirements document is now xroar-monitor, and Phase 3 milestones M1–M6a have landed (2026-05-17).
