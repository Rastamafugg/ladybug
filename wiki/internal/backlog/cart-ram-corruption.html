Troubleshoot cartridge RAM corruption after IRQ install internal

After removing the Phase 2.4 isolation halt, the boot path through IRQ install + Vbord enable derails the CPU. Wild PC overwrites the cart's RAM image.

Resolution 2026-07-16

The same-address cart self-copy was removed from src/main.s. Ladybug now selects the cartridge ROM map before clearing TY and executes directly from $C000-$DFFF with PAR6 mapped to physical page $3E. This avoids XRoar's discarded cart-window writes. The related framebuffer regression also required replacing a non-emitting raw-output org gap with explicit fill bytes. The automated screen probe is green.

Symptoms

Filed 2026-05-14 during the Phase 2.4 "three tile" build-out.

When the Phase 2.4 isolation halt (post_blit: bra post_blit) is removed so execution flows into the carried-forward Phase 2.3 IRQ-install + Vbord-enable code, the CPU goes off the rails within milliseconds of mainloop:

  • $FEF7 (JT_IRQ slot) reads back 16 02 12 16 — not the 7E xx xx we wrote.
  • First Vbord IRQ vectors via $FFF8 = FE F7 to $FEF7, executes the garbage there, PC lands in cleared FB RAM.
  • The wild PC writes to $C000+ and $2000+, corrupting both the cart RAM image and the framebuffer.

What's already known

  • The Phase 2.4 isolation halt was added before the IRQ install code, so every build since Phase 2.4 started has skipped that code path entirely.
  • The current phase24_halt in src/main.s is a workaround.
  • ROM image, .lst, and .map look correct.
  • The build script does not pass -tv-input rgb; unrelated to corruption.
  • The historical $C0D9-$C0DB / $C8B4-$C8BE / $E000-$E042 mismatches are CoCo 3 reset-ROM all-RAM copy/patch behavior, not a separate XRoar cartridge-reader bug. See lessons learned.

2026-05-14 reframing — XRoar source review (H6 investigation)

  • No XRoar fix between 1.10 and HEAD/1.11 touches GIME force-$FExx, MMU PAR, or IRQ vector dispatch. Upgrading will not fix this.
  • XRoar's coco3.c read/write paths for $FE00-$FEFF are symmetric for -cart-type rom. There is no emulator path that would produce "write $7E, read $16" under our cart configuration.
  • The observation "$FEF7 reads back 16 02 12 16" was taken at SIGINT-time, after wild-PC corruption had occurred. It is therefore not evidence that the original STA $FEF7 failed.

Reframed question

"Why does the first IRQ go wild despite a correctly-installed vector?" — not "why is $FEF7 garbage?".

Corrected architecture model

The real GIME MMU is fully implemented in tcc1014/tcc1014.c, independent of the dat struct in coco3.c. For A=$FEF7 with MC3=1, bank = $3F regardless of MMU/PAR. Reads and writes use this same decoder → symmetric.

New leads (L1–L4)

  • L1. Does XRoar provide a SECB-equivalent ROM at boot?
  • L2. PIA1 vsync IRQ may fire concurrently with (or instead of) the Vbord IRQ.
  • L3. Cart-shadow self-copy at lines 102-118 may not populate $FE00-$FEFF correctly.
  • L4. The MC3 bit in the GIME may not be persistently set when STA $FEF7 executes.

2026-05-14 — second gdb-mcp pass: cart-shadow self-copy non-functional

Used the new SWI-trap + snapshot workflow. swi opcodes in the cart cause XRoar 1.10 to segfault — switched to bra . halt loop.

Inserted a probe block immediately before phase24_halt. State at attach: PC=$B977 (wild PC), A=$68, B=$1E, $1000 reads 0x00 0x00 (probe never executed). The CPU is wandering uninitialized memory.

The deeper finding: the cart-shadow self-copy doesn't populate RAM

Cart-window region shows XRoar's default DRAM-init fill pattern (00 00 00 00 FF FF FF FF repeating). RAM at the cart-shadow addresses was never written by the boot.

Tracing XRoar's source:

  1. Pre-SAM_ALLRAM, with our Init0 = %10101000 (MMUEN=0, MC3=1): for A in $C000-$DFFF, bank = 0x38 | (A>>13) = $3E. The condition !TY && bank >= 0x3c is TRUE → ROM mode, S=1 (CTS). RAS is NOT set.
  2. In coco3.c:1170+ write_byte: the if (RAS) block at line 1227 is skipped. The cart's write callback IS called, but cart.c:955-959 cart_rom_write only calls rombank_d8, which is read-only.
  3. Net effect: the std ,x writes inside the cart-shadow loop go to nowhere observable.

2026-05-14 — third pass: discriminating reads at copy_done halt

What this actually means

  • $C000-$FDFF: RAS=0; reads bypass the RAS RAM-overlay and return cart-ROM bytes via cart_rom_read. gdb-mcp reads here return cart-ROM bytes, NOT RAM.
  • $FE00-$FEFF: MC3=1 forces RAS=1; reads/writes hit RAM. gdb-mcp reads here return RAM contents.

The cart-shadow self-copy is a no-op on XRoar 1.10. It never populates RAM at $C000-$FEFF.

2026-05-14 — fourth pass: cold-start verification + post-SAM_ALLRAM probe

Probe 1 (cold-start): Cleared ~/.xroar/, clean Phase 2.4 build with -trap pc=0xC0BE -trap-snap. Trap fired; snapshot was written. Phase 2.4 reaches phase24_halt from cold start.

Probe 2 (post-SAM_ALLRAM): Inserted bra . halt at line 147 ($C05E in built ROM), immediately after sta SAM_ALLRAM. $C000-$C05F returns cart bytes matching the cart ROM file exactly.

Probe 3 (pre-cart-shadow): Moved halt to line 99, BEFORE the cart-shadow loop runs. $C000 already shows cart bytes — the cart-shadow self-copy is irrelevant to whether the cart is accessible.

What this conclusively proves

  • The boot works correctly under XRoar 1.10. Phase 2.4 reaches phase24_halt reliably from cold start.
  • Cart bytes at $C000-$FDFF are accessible throughout the boot, both pre- and post-SAM_ALLRAM.
  • My source-review has a gap. My decode trace predicts $E000 should return cart-ROM bytes via case 1 / cart_rom_read; empirically returns SECB-style vector-table bytes.

Pivoting back to the IRQ-vector question

Cart-shadow architecture confirmed working in practice. The IRQ-install bug is a real, isolated problem. Next debugger session should pivot back to L4: probe MC3 / MMU / PAR state at the exact moment of STA $FEF7.

Implications

The "cart-to-shadow-RAM self-copy → all-RAM execution" boot model is not actually how XRoar runs our cart. We've been running directly from cart ROM the whole time. Worth a wiki update to memory-map and lessons-learned.

Conclusions

  1. The probe at $C0BE-$C0CD did not execute. The STA $FEF7 was never reached. The boot derails before the IRQ-install code path.
  2. A=$68 at every attach = exactly the byte loaded by LDA #%01101000 at $C078. Boot consistently executes through $C078, then derails — most likely at the MMU-enable store at $C07A.
  3. gdb-mcp reads at $C000+ now return DRAM init pattern, contradicting the 2026-05-14 fourth-pass finding. gdb-mcp memory reads in the cart window cannot be trusted as a model of CPU instruction-fetch behavior.
  4. The 2026-05-14 cold-start verification via -trap pc=0xC0BE -trap-snap is now suspect: a wandering CPU naturally parks at the first 20 FE byte pair (= BRA self) it encounters.

Reframed problem statement

The actual question is: does our boot execute legitimately past $C07A (the MMU-enable point)? Evidence says no: PAR6 → phys $3E is uninitialised DRAM, the cart-shadow copy having been a no-op.

Implications for cart development going forward

  1. Disable MMU enable entirely on XRoar — pragmatic short-term.
  2. Replace the cart-shadow self-copy with explicit RAM population through a known-mapped window (e.g., copy via $FE00-$FEFF).
  3. Move execution to a different physical page reachable without the cart-shadow trick.
  4. Move to real hardware sooner.
