Phase 2.x main.s FB render regression — resolved internal

Resolved 2026-07-16. XRoar discarded cartridge-window writes and an unfilled lwasm ORG gap shifted ROM data by 19 bytes.

Observed facts

Building src/main.s at main HEAD (commit 57333f0) under either -tv-input rgb or -tv-input cmp:

  • Expected: black FB with three identical arcade-char-432 tiles spaced across the top row.
  • Observed: tight 2-colour grid pattern (red+green under RGB, pink+green under composite) over the entire FB area, with a magenta border. Three tiny lighter spots barely visible mid-screen.

The pattern is stable, not transient: same image after the cart halts on phase24_halt: bra phase24_halt. The pattern is independent of FB content: replacing the 3-tile render with a stripe diagnostic or a solid $11 fill produces visually identical noise, so writes to the FB are not landing where the GIME reads from.

Discriminating test that isolates the bug

src/diag_minimal.s — a from-scratch hi-res diagnostic with no MMU, no cart self-copy, no PARs:

  • $FF90 Init0 = %00001000 (CoCo3 mode, MMU OFF, force $FExx)
  • $FF98 BP=1, $FF99 = $1E (VRES=0, HRES=7, CRES=2 — 320×192×16)
  • VOFF = phys $072000 (= virt $2000 because MMU-off maps the 64 K virtual range onto the topmost 64 K physical)
  • Load 16 distinct palette codes
  • Fill FB with 16 horizontal stripes (12 rows each)
  • Unblank → halt

Result under -tv-input rgb: 16 clean horizontal stripes, all distinct colours, exactly as drawn. Confirmed the empirical RGB palette mapping now recorded in lessons-learned §"XRoar RGB monitor palette mapping".

So:

  • GIME 320×192×16 mode works.
  • XRoar -tv-input rgb rendering works.
  • Palette load to $FFB0-$FFBF works.
  • FB writes to phys $072000 work.
  • Something between diag_minimal.s and main.s breaks FB display.

Resolved 2026-07-16

Two failures combined. First, the boot incorrectly assumed writes beneath selected cartridge ROM would populate physical page $3E; XRoar and the hardware documentation both indicate that internal RAM is not selected in this state. Second, lwasm raw output did not emit bytes for org $C0DC; labels after the gap were 19 bytes ahead of their ROM file offsets, so par_table loaded palette/tile bytes as PAR values. The fix executes directly from cartridge ROM, keeps TY=0, maps writable state below page $3C, and emits the gap with fill $FF,$C0DC-*. After the reset-ROM patch source was identified, that historical address gap was removed on 2026-07-17.

web/scripts/probe_ladybug_screen.py verifies the halt PC, liveness bytes 55 AA, exact PAR/palette state, and the complete three-tile framebuffer.

Historical candidate causes

  1. Cart self-copy is corrupting the FB or executing wrong code. Historical hypothesis, later corrected: the $C0D9-$C0DB bytes came from the CoCo 3 reset ROM's patched all-RAM shadow, not XRoar cart-window corruption. The actual XRoar issue was that same-address writes under selected cartridge ROM did not populate physical RAM.
  2. MMU PAR setup or order has a hole. Current main.s sets clr $FF91 (force exec PAR set) after the cart copy but before loading the par_table into $FFA0-$FFA7. If the PARs aren't reaching the executive bank, virtual $2000 writes go to whatever RAM the (possibly uninitialised) PAR1 points at.
  3. VOFF + PAR mismatch. main.s configures VOFF for phys $060000 AND PAR1 = $30. Both point at phys $060000. But VOFF is written before Init0 enables the MMU. Sequencing issue possible.
  4. The wiki claim that Phase 2.4 "renders 3 tiles" was never empirically verified. Possibility that lessons-learned tables describe intended-but-unobserved behaviour.

Historical investigation plan

  1. Reproduce the noise pattern on commit 2593d36 (Phase 2.3 close). If 2.3 also shows noise, the regression has been latent the entire time.
  2. Bisect: from diag_minimal.s (works), add features one at a time until display breaks. Order: enable MMU → add PAR load → add cart self-copy → move FB to phys $060000. The breaking change is the bug.
  3. Once the breaking change is identified, fix it minimally — don't refactor surrounding code.

Acceptance evidence

  • ./scripts/build.sh run boots main.s and shows three clean tiles on a black background, in palette indices 0-3 under -tv-input rgb.
  • Root cause is captured in lessons-learned.
  • The "Phase 2.4 isolation build renders 3 tiles correctly under RGB" acceptance criterion in rgb-tv-input-palette is now satisfiable.
