Cartridge — boot strategy internal

How Ladybug as a ROM cartridge takes control on power-on, current cart-size decision, and the boot-time sequence.

The 40-pin cartridge edge pinout and the CART → PIA2 CB1 → FIRQ auto-start handshake are reference content — see release/reference/coco3/cartridge. This page records project-specific decisions on top of that.

Boot handshake — verified

Verified Phase 0 (2026-05-08) — FCC "DK" followed by entry code at $C002 works as written under XRoar with -cart-autorun. See lessons-learned §Phase 0.

Cart size — 64 K GMC image implemented

Decision (2026-07-19): four-bank 64 K GMC cartridge for development.

The former 16 K direct-ROM image remains the runtime payload in bank 1. Bank 0 contains the low-RAM bootstrap at offsets $0000-$07FF and a fixed overflow source pool at $0800-$3DFF; banks 2 and 3 remain the primary expansion sources. The bootstrap selects banks through the GMC SCS register at $FF50, copies manifest-described payloads from banks 2, 3, and 0, copies bank 1 into physical pages $3E/$3F, switches TY to all-RAM mode, and enters the unchanged virtual runtime. This avoids gameplay-time bank switching.

scripts/build.sh verify-gmc proves both expansion-bank signatures, a bank-0 source copy into always-mapped low RAM, bank-1 selection, the TY=1 handoff, and repeated relocated main-loop execution under XRoar 1.10. Physical GMC-compatible hardware remains unverified.

The ingested GMC programming guide agrees with the 64 K maximum and almost-16 K bank windows. It names the primary bank register as $FF40; Ladybug currently writes the redundant CoCo 3 SCS alias $FF50. Local XRoar accepts the alias, while the existing MAME 0.220 evidence requires $FF40. The alias choice remains a compatibility decision pending physical GMC proof and is not changed by this ingest.

Manifest-driven loader: candidate source-bank images and a copy table are generated separately from the delivered image. Every source interval is below bank offset $3E00; the final 512 bytes of each nominal 16 KiB bank are not loader capacity because the CPU sees forced RAM and I/O at $FE00-$FFFF. Banks 2 and 3 are allocated first, followed by bank 0 overflow. The current layout has 14,731 CPU-readable source bytes free across the complete cartridge after its two-byte bank-0 execution proof.

Capacity rule (2026-08-02): a cycle-performance change is not rejected solely because its source payload exceeds the remaining space in bank 1, 2, or 3. The build may place an explicit relocatable payload in bank 0's overflow pool when the complete 64 K image still fits and every runtime destination, resident, asset, low-RAM, direct-page, stack, ABI, timing, and behavioral guard passes. Bank-0 overflow does not make flat resident or enemy code automatically relocatable; executable spill requires a separately assembled segment, an explicit destination, and an unchanged or deliberately versioned ABI.

Initially retargeted to 32 K (Init0 b1-b0 = 11) when ROM-budget analysis suggested 4bpp sprite data would push past 16 K, but reverted after Phase 2.1 testing showed XRoar's -cart-rom handling of 32 K files is unverified — -cart-rom is documented only as "mapped from $C000" and our experimental 32 K cart didn't autostart, consistent with XRoar truncating to the lower 16 K of the file. Rather than detour into XRoar source-code investigation or XRoar -cart-type gmc rework now, we proceed at 16 K until we have real ROM-size numbers.

The expansion path is documented and held in reserve:

  • 32 K via Init0 b1-b0 = 11. GIME-native 32 K cart mode. Cart visible at $8000-$FEFF after our boot enables it. Requires (a) cart hardware that decodes the wider range, and (b) emulator support that we haven't confirmed. This is not the immediate expansion path because it overlaps the current framebuffer mapping.
  • Software bank-switched cart. Two or more 16 K banks of ROM, standard $C000-$FEFF window. Software writes a bank-select register to swap. XRoar supports the GMC model, but physical CoCoSDC/custom-hardware compatibility must be selected and verified. Because current code executes from ROM, this requires a low-RAM loader, explicit copies to different physical pages, and a TY=1 handoff. It is the fallback after the 16 K split is exhausted.

Trigger for the banked pivot: the Phase 6 packed-asset inventory exceeds the 7,680-byte $E000-$FDFF static-data region after curation/compression, or resident code exceeds the separate 8,192-byte $C000-$DFFF region.

Cart layout in the 16 K image:

file offset   virtual    purpose
$0000-$1FFF   $C000-$DFFF   "DK" magic, entry, resident code/hot constants
$2000-$3DFF   $E000-$FDFF   immutable graphics, maze, and static tables
$3E00-$3EFF   $FE00-$FEFF   forced RAM jump-table window; cart byte unused
$3F00-$3FFF   $FF00-$FFFF   dedicated I/O; cart byte unused

Cart hardware: standard 16 K EPROM cart shell. CoCoSDC and similar work natively. Init0 bit 3 forces $FE00-$FEFF to RAM and $FF00-$FFFF is dedicated I/O, so the final 512 file bytes are deliberately unused.

Immediate split layout — implemented 2026-07-18

The build continues using one plain 16 K ROM. Entry and executable code remain in $C000-$DFFF; relocate immutable data beginning with palette_table to $E000-$FDFF. This yields 15,872 usable cartridge bytes without changing cartridge hardware, runtime MMU ownership, or the output format.

Local XRoar 1.10 source confirms that a single 16 K -cart-type rom -cart-rom image is loaded as one 16 K ROM slot and addressed with a $3FFF mask. Its second 8 K is therefore read at $E000 without -cart-rom2. A cold emulator test read the complete relocated block exactly and rendered the expected framebuffer.

Separate assembler labels and build guards enforce the resident and asset boundaries. This ownership split also prepares a later banked loader without committing the release cartridge to GMC hardware now.

What our boot must do

Current decision (2026-07-16): direct-ROM execution. Boot writes Init0 first to select the 16 K cartridge map, explicitly clears TY through $FFDE, loads executive PARs 38 30 31 32 33 34 3E 3F, and enables the MMU while code remains cartridge-backed through PAR6. This removes the discarded XRoar shadow-write dependency and limits current code to $C000-$DFFF.

Historical Phase 2 sequence (superseded):

  1. ORCC #$50 — mask IRQ and FIRQ.
  2. Set S to the top of our work RAM.
  3. Disable PIA-driven interrupts and bleed any pending flags.
  4. Configure GIME Init0: clear bit 7 (hi-res), enable MMU, set bit 3 so $FE00-$FEFF is always reachable, set bit 5 to enable ACVC IRQs. Then clear/blank the screen buffer with CRES=11 while we initialise.
  5. Attempt to self-copy $C000-$FEFF to shadow RAM beneath the cart. The original sentinel test was non-discriminating; TY=0 selects the cartridge without selecting internal RAM, so the writes do not populate the shadow. This was removed from the active path. See memory-map §Boot execution.
  6. Switch to all-RAM mode (write to $FFDF). Cart ROM disconnects; phys $3E-$3F becomes visible, but it was not populated by the preceding writes.
  7. Switch to fast clock (write to $FFD9).
  8. Load our palette ($FFB0-$FFBF).
  9. Install our IRQ handler in the primary jump table at $FEF7 (JMP extended), write $FF92 bit 3 to enable Vbord.
  10. ANDCC #$EF — unmask IRQ. Enter main loop.

Historically, Phase 1 implemented steps 1-3 and 6-10 (with a Phase-1 simplification of step 4: no MMU, no hi-res, no palette). Phase 2.2 added the attempted copy. This sequence is retained only as history.

Every step has a citation in coco3-asm-tepolt chapters 6-7.
