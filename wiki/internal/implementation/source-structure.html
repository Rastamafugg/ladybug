Source Code Structure internal

Working map of modules, generated interfaces, memory ownership, game-loop flow, and review boundaries.

Purpose and reading order

Use this page before changing or reviewing runtime code. It identifies where behavior belongs, which files are generated, which interfaces cross independently assembled modules, and which state may be touched during rendering or IRQ service. Detailed facts remain canonical in memory-map, ping-pong-framebuffer, platform/timing, and build-workflow.

  1. Locate the owning source or generator in the source inventory.
  2. Check the module boundary and memory owner before editing state.
  3. Trace the affected game-loop and framebuffer transaction phases.
  4. Select verification from the change-impact table.

The three assembly files are assembled separately. They do not share linker relocation. Their contract consists of fixed entry addresses, generated absolute resident symbols, identical direct-page addresses, and agreed MMU mappings.

Source inventory and ownership

PathRoleSafe change boundary
src/main.s Resident entry, hardware initialization, main loop, player/gameplay state machines, HUD/entities, resident render primitives, immutable tables. Owns authoritative gameplay state and publishes compact render intents. Normal gameplay mutation must not call framebuffer writers directly.
src/enemy_runtime.s Fixed jump table, enemy logic, central frame renderer, A/B framebuffer protocol, sparse decoders, actor closure, save-under and damage projection. Must fit $0800-$17FF. Code may temporarily map PAR5, but must restore page $34 before accessing game-state data or returning.
src/gmc_bootstrap.s Bank-0 cold loader. Copies runtime, bank-3 module, sparse/gate payloads, and mirrored indexes into physical RAM before TY=1 handoff. Runs partly from $0300. Every temporary PAR5 destination mapping is explicit. No frame-time cartridge banking is allowed.
src/tester/ Independent display/input tester ROM and patterns. Diagnostic target only. It is not linked into the game image.
src/diag_minimal.s, src/rom_probe.s Focused hardware and cartridge probes. Do not treat probe assumptions as production ABI.
scripts/build.sh Canonical build, guard, packaging, run, and GMC verification entry point. Keep the full build authoritative. Incremental commands must not bypass layout or pixel-exact verification.
scripts/derive_maze.py Derives semantic maze, gate, ownership, navigation, and generated maze include data. Edit the capture or derivation rule, not build/ladybug_maze.inc.
scripts/build_screen.py Compiles TMX tiles, resident presentation sprites, object masks, HUD data, and six gate transition streams. Generated screen/resident includes and gate payload are outputs, never hand-edited sources.
scripts/build_sparse_sprites.py Encodes indexed enemy/player streams, packs banks 2/3, and emits the fragmented loader table and layout manifest. Preserve page containment, inaccessible GMC-tail exclusion, signatures, and bank-3 module reservation.
scripts/verify_*.py Structural, pixel, ownership, boot, timing, and scenario proofs. A source change is incomplete when it invalidates the independent model instead of updating both implementation and intended contract.

      |
      v

  - mask interrupts, establish stack/MMU
  - relocate loader to $0300
  - prove bank signatures
  - copy bank-3 module to $0800-$17FF
  - copy sparse/gate segments to pages $35-$37/$39

      |

Cross-module jump-table ABI

The first 36 bytes of enemy_runtime.s are twelve three-byte absolute JMP entries. Resident code calls fixed addresses; internal bank-3 labels may move without changing callers.

AddressEntryPurpose
$0800enemy_init_implInitialize enemies and nest ownership.
$0803enemy_tick_implMutate enemy movement, AI, animation, and lifecycle state.
$0806enemy_release_implRelease one enemy from the den.
$0809enemy_collect_implResolve player/enemy collectible interaction.
$080Cplayer_compose_implCompose staged player presentation.
$080Fgate_compose_implRender gate transition work into BACK.
$0812player_draw_implDecode the selected sparse player stream.
$0815enemy_render_implConsume enemy render intents and compose nest/roaming state.
$0818frame_render_implSingle complete-frame renderer and ownership boundary.
$081Bframebuffer_init_implCold A/B image and restoration-state convergence.
$081Eframebuffer_irq_implVbord acknowledge, commit, ownership exchange, counters.

Adding, removing, or reordering an entry is a protocol change. Update constants in main.s, structural verification, generated maps, and this table together.

Game-loop process flow

mainloop
  |
  +-- SYNC until IRQ
  +-- wait while FB_RENDER_PENDING != 0
  +-- require a new Vbord frame count
  +-- set FB_RENDER_ACTIVE
  |
  +-- finish_gate_animation
  +-- pickup_tick
  +-- player_animation_tick
  +-- enemy_tick
  +-- if alive and queued: player_tick -> enemy_collect
  +-- read_joystick
  +-- if alive: bonus_color_tick -> perimeter_timer_tick
  +-- rng_next
  +-- death_tick OR queue next 30 Hz player step / stage transition
  |
  +-- render_frame -> $0818 frame_render_impl
  |     |
  |     +-- framebuffer_prepare_back
  |     +-- actor_closure_restore
  |     +-- queue current damage for the other owner
  |     +-- project this BACK owner's pending damage
  |     +-- frame_render_pass
  |     |     +-- background/HUD/entity/gate/nest intents
  |     |     +-- capture clean actor destinations
  |     |     +-- draw roaming enemies
  |     |     +-- draw player/popup/death presentation last
  |     +-- framebuffer_finish_back
  |           +-- capture owner-local metadata
  |           +-- atomically set FB_RENDER_PENDING
  |
  +-- repeat

Logical cadence is commit-driven. The free-running Vbord counter wakes the loop, but FB_SIM_SEQ controls committed epoch parity. When a render misses Vbord, the same logical epoch remains frozen until it commits.

IRQ and commit flow

ACVC Vbord IRQ
      |
      v
irq_handler (resident jump target at $FEF7)
      |
      v
$081E framebuffer_irq_impl
  - read $FF92 to acknowledge
  - increment raw FRAMES counter
  - FB_RENDER_PENDING?
       no  -> if render active, increment FB_MISSED_COMMIT
       yes -> select $C0 (A) or $B0 (B)
              write $FF9D
              exchange FB_FRONT_ID / FB_BACK_ID
              clear pending
              increment FB_COMMIT_SEQ and FB_SIM_SEQ
      |
      v
RTI; mainloop resumes after SYNC

IRQ-visible fields live in always-mapped page $38. The handler does not read framebuffer metadata or game state behind PAR5, so an interrupt during sparse decoding cannot redirect ownership reads.

Code-review checklist

  1. Ownership: does the change mutate authoritative state, render intent, BACK pixels, or owner-local history in the correct phase?
  2. ABI: are fixed jump addresses, generated resident symbols, DP variables, and record offsets unchanged or updated everywhere?
  3. MMU scope: can any path access page-$34 state while PAR5 maps a payload, and does every exit restore PAR5?
  4. Interrupt safety: can Vbord interrupt the path without observing partially published ownership state?
  5. A/B symmetry: was the change tested with both owners and distinct per-buffer history?
  6. Layering: are all selected actors restored before damage, clean destinations captured before drawing, enemies drawn before the player?
  7. Memory: do resident, assets, bank-3 code, direct page, loader intervals, and stack remain within guarded limits?
  8. Timing: is the claim based on cycles for a complete active interval rather than instruction count or a partial routine?
  9. Generated data: was the generator changed instead of its output, and does an independent verifier reconstruct the result?
  10. Compatibility: if shared framebuffer code changed, does PERSISTENT_FB=0 still assemble and retain its explicit fallback semantics?

Canonical commands

# Full generated build and static/pixel proofs
scripts/build.sh build

# Build plus bounded boot/runtime execution proofs
scripts/build.sh verify-gmc

# Canonical emulator launch
scripts/build.sh run

Use the GDB-MCP round trip for live machine inspection. Timing or scenario work must also run the relevant verify_*_profile.py or arcade-fidelity verifier; the build alone does not prove every gameplay path.
