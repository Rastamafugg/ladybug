Working map of modules, generated interfaces, memory ownership, game-loop flow, and review boundaries.

Purpose and reading order

Use this page before changing or reviewing runtime code. It identifies where behavior belongs, which files are generated, which interfaces cross independently assembled modules, and which state may be touched during rendering or IRQ service. Detailed facts remain canonical in memory-map, ping-pong-framebuffer, platform/timing, and build-workflow.

  1. Locate the owning source or generator in the source inventory.
  2. Check the module boundary and memory owner before editing state.
  3. Trace the affected game-loop and framebuffer transaction phases.
  4. Select verification from the change-impact table.

Proposed presentation and documentation revisions

Revised FEAT-002 is Proposed, not current architecture. It would retain a thin low-RAM presentation director while replacing synchronous six-map inflation with bounded direct decoding of only the selected screen. Static screens would reuse exact resident gameplay tiles through generated resolver data; applicable outer-wall layers would share one build-time definition; title and instruction actors would invoke existing actor services; and demo mode would run normal gameplay with a compact deterministic input route and muted sound dispatch. Until approval and implementation, the module inventory and call flow below describe the current working tree.

Completed DOC-002 provides the controlled glossary, normalized memory atlas, routine and data catalogs, requirement-to-source traceability, and generated lwasm source/listing browser under build/source-reference/. Semantic rationale remains hand-authored in the wiki; generated addresses, bytes, and source-line relationships remain build artifacts.

Module boundaries exchange frozen records for modules, source lines, emitted spans, symbols, routines, basic blocks, memory references, call edges, relocations, and evidence. Configuration dictionaries are converted at ingress; generated JSON and HTML are serialization outputs, not the internal model. The generation path is parse, normalize, apply coverage and link policy, then render. Verification may reuse the typed records and raw parsers, but it re-derives required sets and inspects emitted anchors, links, hashes, and evidence states instead of trusting the renderer's conclusions.

Hand-authored wiki HTML owns semantic meaning and stable IDs. Concise source headers mirror local register, memory, and side-effect contracts. Generated pages own revision-specific addresses, bytes, and source/listing/map relationships. The approved semantic hubs remain bounded pages and split only after measured size or navigation failure. Generated output contains one line browser per assembled module plus global address, symbol, routine, and source-file indexes.

Coverage fails closed. Every exported, called, hardware-touching, shared-state-mutating, or otherwise non-trivial routine requires a canonical contract. Every global label must be documented, explicitly excluded with a reason, or classified as a basic block. Direct calls are extracted; fixed jumps, indirect calls, and relocation/copy relationships are declared in configuration. Each relationship distinguishes assembled/source, cartridge-staged, and runtime-destination address identities.

Evidence is multidimensional rather than a single pass flag. Structural, representation, delivery, runtime-reachability, visible-output, and timing evidence each has an independent pass, fail, missing, or stale state bound to an artifact hash. A passing structural or runtime-reachability check therefore cannot imply visible-output or timing proof.

BUG-012 full-coverage demo route architecture

BUG-012 selects an explicit uncompressed 147-action CoCo node walk plus a $FF terminator. The build retains the original 188-byte arcade control-call stream as immutable provenance, while assets/arcade/demo_walk.json owns the deployed node actions, backbone relationship, four return-to-anchor detours, and exact coverage/hash metadata. Runtime consumes one action only at a new even/even semantic maze cell and delegates legality, gate rotation, collection, collision, and rendering to the normal player/gameplay services.

This separation is deliberate. The arcade pointer can advance twice at a turning node and its mapped path covers only 104 of the adapted maze's 117 placement cells; replaying those bytes as a legality-buffered queue deadlocks. An explicit node walk is deterministic and machine-verifiable without adding frame-time pathfinding. Uncompressed storage is selected because 148 bytes are 39 bytes smaller than the current deployed stream, the cold-data margin exceeds three kilobytes, and a two-bit decoder would add unnecessary code and bank-boundary risk.

The release auxiliary remains copied at $0300 within the existing $0300-$06A9 allocation. Final implementation commit 763381a measures 143/938 auxiliary bytes, 1234/1280 presentation-module bytes, and 7636/10874 cold-payload bytes. A last-cell latch is required because presentation can tick twice before movement leaves a semantic node; route consumption otherwise remains aligned-node driven. The route-index initialization is the only flow-module change; no new direct-page byte, module boundary, or resident gameplay interface is introduced.

Build and verification architecture

scripts/build.sh is an ordered dependency graph, not a single assembly command. Authored Tiled maps, captured arcade data, route records, and assembly source are the inputs. Python generators produce semantic JSON, generated includes, encoded payloads, module manifests, source-bank images, and the loader plan. Six independent lwasm invocations then establish the resident, enemy, profile-selected auxiliary, presentation, perimeter-helper, and bootstrap address spaces. The delivery composer overlays only manifest-owned bank-0 intervals and concatenates four exact 16 KiB banks into the 65,536-byte GMC image.

Assembly and generated-ABI ordering

The resident is assembled first because its map supplies absolute service and data addresses to enemy_runtime.s and presentation_runtime.s. The enemy map then contributes framebuffer-ownership entries to the presentation symbol include. A release build assembles its demo auxiliary before the presentation module and passes the exact byte count. A development build passes the fixed auxiliary reservation first, then assembles and pads its instruction auxiliary after the presentation module. Presentation module symbols then bind the perimeter helper. Finally, the sparse packer can place all assembled modules and payloads and emit the copy records consumed by the bootstrap. Generated symbol includes are build interfaces between separately assembled modules; they are not stable hand-authored APIs and must never be edited directly.

Release and development profiles reuse output paths but assemble different auxiliary owners at $0300. Release builds place demo_runtime.s there; development builds reserve the whole $0300-$06A9 interval, assemble instruction_runtime.s, and pad it to that reservation. A reproducible artifact identity therefore requires the profile as well as source, generator, tool, and input hashes.

Fail-closed delivery guards

The build stops on the first failing command. It rejects resident code beyond $E000, misplaced or oversized assets beyond $FE00, inconsistent raw length, enemy code beyond 4096 bytes, presentation and helper interval overflow, boot code crossing the bank-0 overflow start, non-16-KiB bank inputs, bank-3 content that differs from the assembled enemy module, undeclared or nonblank bank-0 overlays, and a final image other than 65,536 bytes. The sparse packer separately excludes the CPU-inaccessible $3E00-$3FFF cartridge tail, prevents frame/page and destination crossings, and records every source segment in the layout manifest.

Bootstrap binary, listing, and map publication uses temporary files followed by replacement, and final bank-0/manifest replacement is also staged. Other generated files are written directly. The build directory is therefore disposable but not transactionally atomic as a whole: only a completely passing command establishes a mutually consistent artifact set. Running build also overwrites listings and maps, so a modified listing must be preserved or retired before certifying a new baseline. DOC-002 certified its baseline in a detached exact-revision worktree; future tickets must repeat that boundary when dirty artifacts are in scope.

Verification ladder and independence

Generator validation proves authored-input and encoding contracts. Build-time verifiers then decode sparse streams, reconstruct manifest segments, compare pixels and hashes, exercise exact-capacity and one-byte-overflow cases, inspect allocations, and enforce structural source/map contracts. Independence is per check, not per filename: sparse and presentation decoders are separate implementations, but several expected-frame compilers are imported from generator modules; the presentation verifier reuses substantial presentation compiler logic; and the GMC overflow proof calls the production packer with a constructed boundary payload. These checks strongly detect corrupted representations and contract drift, but shared producer logic can preserve the same semantic error on both sides.

scripts/build.sh verify-gmc first repeats the complete build. It then applies static presentation capacity/structure checks, runs bounded XRoar/GDB phases for loader handoff, resident startup, natural attract entry, forced gameplay renderer paths, and release-demo deaths, and finally applies the enemy-runtime structural and mathematical models. The runtime phase proves authored/staged/live delivery and required control-path reachability. Entry markers and successful hashes do not prove visible screen identity, full gameplay correctness, or timing outside the named phases; tickets requiring those properties must add explicit pixel, state-sequence, or cycle evidence.

Evidence and documentation boundary

Hand-authored wiki pages own meaning: terminology, rationale, behavior, ownership, invariants, data layouts, module contracts, and scenario intent. Listings, maps, binaries, manifests, generated includes, hashes, and the line-level browser are revision-derived evidence. The browser lives under build/source-reference/ and may be regenerated or discarded; it cannot become the canonical definition of an owner or contract. scripts/source_reference.json contains Ladybug-specific module inputs and policy, while the parser and renderer must remain generic and take all source/listing/map/relocation relationships explicitly.

A valid documentation baseline must bind material authored-source hashes, build profile, lwasm version, listings, maps, module binaries, layout manifests, and final ROM hash from the same passing build. Coverage verification must reject stale hashes, unresolved emitted addresses, undocumented owners, and missing required scenarios. Fixture and mutation tests are necessary because a generated page that merely renders successfully proves neither parser coverage nor semantic completeness.

The certified DOC-002 exact-revision release artifact records final ROM SHA-256 74ccb023d967037e4cba92e043eba5973f65877f54d3dc18965b13dcefc9a751, 15 loader segments, 3965 readable GMC source bytes spare, and six cold presentation maps in 7636 bytes. These values are retained as baseline evidence; later source, listing, or map changes require a fresh build and regenerated browser.

Why bank 1 uses a two-hop copy

With the cartridge selected, bank 1 is readable through the CPU cartridge window: resident bytes at $C000-$DFFF and asset bytes at $E000-$FDFF. The current delivery path does not assume that a write to those same CPU addresses can reach the underlying RAM while the cartridge owns the read window. The loader therefore executes from always-mapped low RAM and uses PAR5's separate $A000-$BFFF window for temporary storage.

  1. Select physical page $21 in PAR5 and GMC bank 1, then copy exactly 8192 resident bytes from cartridge $C000-$DFFF to staging window $A000-$BFFF.
  2. Select physical page $22 in PAR5, then copy the 7680-byte usable asset interval from cartridge $E000-$FDFF to $A000-$BDFF. Cartridge addresses $FE00-$FFFF are not payload: forced RAM occupies $FE00-$FEFF and I/O occupies $FF00-$FFFF.
  3. Keep bank 1 selected while the low-RAM loader synthesizes the perimeter reset program from the authored asset tables into physical page $20.
  4. Strobe SAM all-RAM mode. PAR6 and PAR7 already select final physical pages $3E and $3F, so CPU destinations $C000-$DFFF and $E000-$FDFF now refer to RAM, not the GMC cartridge window.
  5. Remap PAR5 to staging page $21 and copy $A000-$BFFF to final resident destination $C000-$DFFF. Remap PAR5 to page $22 and copy $A000-$BDFF to final asset destination $E000-$FDFF.
  6. Expand the attract bundle staged in page $23 into physical page $3C, set BOOT_FLAG=$A5, restore PAR5 to authoritative game-state page $34, and jump to $C002. The two-byte DK cartridge header remains at $C000-$C001 and is data, not an instruction entry.

Pages $21 and $22 are boot-only staging owners, not runtime ABI regions. After publication, the stable virtual ABI is resident code at $C000-$DFFF through PAR6/page $3E, immutable assets at $E000-$FDFF through PAR7/page $3F, and normal game state at $A000-$BFFF through PAR5/page $34. See memory-map for the complete physical and virtual allocation and lessons-learned for the cart-shadow self-copy evidence and scoped-PAR rule.

Other control ABIs

  • Resident entry $C002: both direct-cartridge autorun and the GMC loader skip the two-byte DK header and enter the resident initialization sequence here.
  • Presentation entry $1900: mainloop calls one fixed dispatcher. An A/condition-code result of zero releases the interval to gameplay; nonzero means presentation owns the interval and foreground gameplay must not run.
  • Profile-selected auxiliary $0300: the release build installs demo_runtime_tick; the development profile installs instruction_runtime_tick. They are mutually exclusive implementations of one low-RAM slot, not simultaneous modules.
  • Presentation helper entries: $06B2 is the perimeter-program gateway; $06C5/$06C7/$06C9 are fixed hold-begin, hold-tick, and attract-overlay jumps.
  • Generated absolute bindings: presentation and auxiliary modules call resident, enemy-runtime, and presentation-internal routines through build/ladybug_presentation_symbols.inc. These addresses are regenerated from current maps and are not stable hand-authored entry slots.

Control ownership and dispatch contract

Ladybug has two control domains. Foreground code owns presentation dispatch, gameplay mutation, and BACK construction. The Vbord IRQ owns only time observation and display publication. The IRQ never invokes gameplay logic, presentation logic, or a framebuffer compositor.

cartridge autorun -> $C002
  GMC image: bank-0 bootstrap -> relocated loader -> all-RAM publication -> $C002
  direct image: resident entry at $C002

$C002 resident startup
  mask IRQ/FIRQ, set S=$1FFE and DP=$00
  install PARs, video mode, palette, and initial framebuffer
  initialize persistent A/B ownership while display is blanked
  install JMP irq_handler at forced-RAM slot $FEF7
  enable only ACVC Vbord in $FF92, unmask IRQ
  enter mainloop

mainloop foreground interval
  SYNC -> reject pending/unseen Vbord -> call $1900 presentation dispatcher
    nonzero -> presentation owned the interval; return to SYNC
    zero    -> set FB_RENDER_ACTIVE; run gameplay mutation and BACK rendering
  renderer captures owner-local state, clears ACTIVE, sets PENDING atomically

Vbord IRQ interval
  acknowledge $FF92 and increment FRAMES
  if PENDING: publish BACK, swap IDs, increment commit/simulation sequences
  otherwise: leave FRONT unchanged; count a miss only if ACTIVE is set
  RTI to the interrupted foreground instruction

The presentation dispatcher is itself a state machine. MODE_LOAD incrementally constructs a screen; attract, credit, level-start, game-over, and name modes normally return nonzero and retain the foreground interval. In the default release profile, demo mode first calls the auxiliary director at $0300 to supply ordinary joystick-direction state, then returns zero so the normal gameplay mutation and renderer execute. Normal live mode also returns zero unless it initiates a presentation transition.

Gameplay re-entry is an explicit cross-domain handoff. Presentation restores PAR5 to page $34, maps the current logical BACK into PAR1-PAR4, invalidates both framebuffer ledgers, calls generated resident initialization bindings in dependency order, marks ownership initialized, and raises a full-stage render intent. It does not bypass the ordinary gameplay renderer after returning zero.

The only installed runtime hardware service in current authored source is the ACVC Vbord IRQ. Cartridge FIRQ participates in the ROM autorun path before Ladybug takes control, but the resident runtime masks FIRQ and installs no authored FIRQ or NMI handler. SWI is not implemented as the proposed syscall layer: the single current SWI is a fail-stop cache-overflow diagnostic, and no authored SWI service handler is installed.

Rendering representations and data-flow contract

Rendering crosses five representations. Authoritative gameplay state records the maze, gates, entities, actors, score, and timers. The renderer copies a 16-byte direct-page transfer window beginning at RENDER_FLAGS=$007F. Its render fields form a compact transaction of flag classes plus snapshots such as the affected cell, perimeter box, recolored letter, and gate identities and modes. The window also spans renderer working state, so the damage queue filters and replaces fields rather than treating all 16 bytes as persistent intent. Each physical framebuffer retains its own reconstruction history and damage ledger. Generated dense or sparse asset streams supply encoded pixel operations. The final projection is the persistent image in physical framebuffer A or B. Pixels and intent flags are projections; neither replaces authoritative gameplay state. 

authoritative gameplay mutation

  -> framebuffer_prepare_back maps and hydrates BACK's private history
  -> actor_closure_restore removes BACK's old player and four enemies
  -> framebuffer_queue_damage copies filtered persistent coverage to the other owner
  -> framebuffer_project_damage redraws this BACK's older coverage from current state

Intent and damage lifetimes

Gameplay routines mutate logical records and OR render flags; they do not directly redraw the final moving-actor layer. When a payload can change again before rendering, the intent block freezes the old coverage or drawing parameters. The current transaction is consumed only after the complete BACK render. Before that happens, framebuffer_queue_damage copies it to the metadata of the framebuffer that is not currently BACK, then retains only persistent background classes: HUD, lives, entities, changed maze cell, stage, perimeter, multiplier, letter, nest, and gate coverage. Player, popup, death, and roaming-enemy presentation are excluded because actors use buffer-local reconstruction instead.

When an owner next becomes BACK, framebuffer_project_damage temporarily replaces the live intent block with that owner's pending record, redraws the affected background from the latest authoritative state, clears only that owner's ledger, and restores the live transaction. This is an idempotent state projection, not a replay of historical drawing commands. Background work intersecting a roaming footprint invalidates strip reuse and forces a safe capture path.

Actor closure and owner-local history

A and B can contain different prior world epochs, so each owner keeps private player and enemy positions, valid bits, save-under pixels, and enemy ring phases. The conservative closure restores the old player and all four old enemy footprints before any new destination is captured. It then captures clean current destinations, draws roaming enemies, and draws popup, death, or the live player last. The ordering makes player-layer ownership explicit and prevents one actor's pixels from being captured as another actor's background.

Enemy save-under storage is a circular 8-by-16-byte representation. An unchanged destination reuses its clean capture; a one-byte horizontal move or two-row vertical move captures only the exposed strip; discontinuous motion or intersecting background damage falls back to a full 128-byte capture. This changes the cost of maintaining history, not its ownership.

Encoded asset boundary

Sparse player and enemy indexes are page-local three-byte page/address entries. The resolver first maps the index page through PAR5, then maps the selected payload page and returns its stream pointer. A stream contains destination deltas, opaque byte runs, masked partial-byte runs, and an extended-delta command; the $FF,$0000 terminator restores PAR5 to state page $34. sparse_blit_fb decodes directly into the mapped BACK, while sparse_blit_stage expands the same representation into the always-mapped actor stage at $1800. Sprite or frame selection occurs before decoding; the stream itself is a sequence of destination operations rather than semantic actor state.

Presentation as an alternate BACK producer

Presentation screens bypass gameplay render intents. In MODE_LOAD, presentation_runtime.s maps BACK, reads the run-length encoded map from cold page $3A, and expands 32 cells per foreground tick. Each tile ID selects either a cold-atlas tile or a gameplay-tile lookup before the ordinary tile blitter writes BACK. Optional sparse overlays use the fixed $0821 draw service. Completion restores PAR5 to $34, performs any required owner hydration, atomically sets FB_RENDER_PENDING, and advances the presentation mode. Gameplay composition and presentation streaming therefore produce the same publication object, a complete hidden BACK image, through different upstream data paths.

Logical cadence is commit-driven. The free-running Vbord counter wakes the loop, but FB_SIM_SEQ controls committed epoch parity. When a render misses Vbord, the same logical epoch remains frozen until it commits.

IRQ and commit flow

ACVC Vbord IRQ
      |
      v
irq_handler (resident jump target at $FEF7)
      |
      v
$081E framebuffer_irq_impl
  - read $FF92 to acknowledge
  - increment raw FRAMES counter
  - FB_RENDER_PENDING?
       no  -> if render active, increment FB_MISSED_COMMIT
       yes -> select $C0 (A) or $B0 (B)
              write $FF9D
              exchange FB_FRONT_ID / FB_BACK_ID
              clear pending
              increment FB_COMMIT_SEQ and FB_SIM_SEQ
      |
      v
RTI; mainloop resumes after SYNC

IRQ-visible fields live in always-mapped page $38. The handler does not read framebuffer metadata or game state behind PAR5, so an interrupt during sparse decoding cannot redirect ownership reads.

The IRQ is deliberately a publication service rather than a game-tick callback. It can interrupt any foreground phase, but it changes visible ownership only when FB_RENDER_PENDING proves a complete BACK transaction. A Vbord that arrives while FB_RENDER_ACTIVE is set records a missed commit and leaves both the visible FRONT and logical epoch unchanged.

Code-review checklist

  1. Ownership: does the change mutate authoritative state, render intent, BACK pixels, or owner-local history in the correct phase?
  2. ABI: are fixed jump addresses, generated resident symbols, DP variables, and record offsets unchanged or updated everywhere?
  3. MMU scope: can any path access page-$34 state while PAR5 maps a payload, and does every exit restore PAR5?
  4. Interrupt safety: can Vbord interrupt the path without observing partially published ownership state?
  5. A/B symmetry: was the change tested with both owners and distinct per-buffer history?
  6. Layering: are all selected actors restored before damage, clean destinations captured before drawing, enemies drawn before the player?
  7. Memory: do resident, assets, bank-3 code, direct page, loader intervals, and stack remain within guarded limits?
  8. Timing: is the claim based on cycles for a complete active interval rather than instruction count or a partial routine?
  9. Generated data: was the generator changed instead of its output, and does an independent verifier reconstruct the result?
  10. Compatibility: if shared framebuffer code changed, does PERSISTENT_FB=0 still assemble and retain its explicit fallback semantics?
