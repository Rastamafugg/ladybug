Implementation · data ownership

Data Layout Catalog internal

Canonical record, array, table, and protocol layouts; addresses remain normalized in the memory atlas and generated browser.

Controlled vocabulary

Basic block, assembled address, cartridge-staged address, runtime destination, authoritative state, publication, and evidence dimension use the glossary definitions throughout this catalog.

Render transaction

The always-mapped direct page owns BACK selection, ACTIVE/PENDING state, commit and simulation sequences, missed-commit count, and render flags. Gameplay mutates authoritative state before composition. The selected framebuffer owns pixels and its local actor/save-under history. IRQ owns only final publication.

Reset clears both owner histories and protocol state. A completed compositor transaction atomically converts ACTIVE to PENDING with interrupts masked; Vbord converts PENDING into visible FRONT ownership.

Presentation flow state

The presentation runtime owns the always-mapped mode, screen, timer, phase, and hold-state bytes. PRES_MODE selects the director branch, PRES_SCREEN selects the streamed authored map, PRES_TIMER is the state-local 16-bit interval count, and phase/hold fields retain bounded producer progress across Vbords. Reset or a state transition initializes these fields; the resident foreground loop calls presentation_flow_tick, and presentation helpers are the only normal producers.

Bank-1 resident publication

The GMC bootstrap owns the resident image while it is cartridge-selected and while it is staged at virtual $A000-$DDFF. It copies the exact 15,872-byte interval into the final all-RAM $C000-$FDFF destination, sets BOOT_FLAG at $02F0, and transfers control to the resident entry. After handoff, the resident runtime owns the destination; the staging window is no longer authoritative.

Copied modules

Every configured relocation record carries one assembled identity, optional cartridge-staged identity, runtime destination, physical page when applicable, exact byte length, bootstrap owner through copy/validation, and runtime owner after handoff. The source-reference verifier derives the complete copied-module set from these records and rejects an omitted, duplicate, or ownerless record.

Persistent records

The exhaustive persistent families are the render transaction, presentation flow, authoritative gameplay state, entity table, A/B player and enemy histories, A/B damage ledgers, and session score state. Each family has one phase-qualified owner, reset rule, producer set, consumer set, lifetime, and canonical detailed page. Lifecycle aliases are one allocation with mutually exclusive meanings, not free or duplicate storage.

Framebuffer structures

The complete set is the compatibility hold surface, persistent framebuffer A, persistent framebuffer B, direct-page render metadata, A/B player save-under histories, A/B enemy ring histories, and A/B pending-damage ledgers. A physical framebuffer owns its pixels and local histories. The direct-page protocol owns ACTIVE, PENDING, FRONT/BACK selection, and publication sequencing but never owns completed pixels.

Structured tables

Every authored data label is assigned to its declaring module through the typed data-label inventory. Required field schemas cover sparse index records, sparse command streams, loader copy records, address identities, call edges, label classifications, evidence records, presentation screen records, demo route records, entity records, and render-intent records. A schema definition owns field offset, width, encoding, range or sentinel, producer, consumer, reset/lifetime rule, and capacity formula; generated instances remain revision-bound build output.

Address identity record

Every copied or relocated payload records an assembled address, optional cartridge-staged address, runtime virtual destination, optional physical page, byte length, owning module, and stable relationship ID. These identities must not be collapsed into one unqualified address.

Call-edge record

A call edge records source module, file, line, caller, target, and one of direct, tail-jump, fixed-jump, or indirect kind. Direct calls are extracted from active source. Fixed and indirect relationships are declared because absence of static inference is not absence of control flow.

Global-label classification

Every authored global label resolves to exactly one routine, inferred or declared basic block, typed data label, or boundary label. Assembly-time uppercase aliases are classified as constants with a recorded rule; labels originating in build/ includes are classified as generated interfaces whose semantic owner is the producing build step. A rule is expanded into concrete typed records for the current symbol set, so a new unmatched label remains a verification failure.

Data identifies an immutable table or packed record. Boundary identifies a start, end, size, or publication marker. Constant has no storage at its label. Generated is imported from a build-produced interface. Basic blocks carry a concise control-purpose record and inherit the complete contract of their enclosing routine.

Evidence record

Each record has a stable ID, one evidence dimension, one state, an artifact path, SHA-256 hash, and optional note. Valid dimensions are structural, representation, delivery, runtime reachability, visible output, and timing. Valid states are pass, fail, missing, and stale.

Detailed current layouts

Memory map is canonical for direct-page bytes, virtual ranges, physical pages, cartridge intervals, framebuffer pages, and stack. This catalog is canonical for copied-module, persistent-record, framebuffer-history, and structured-table schemas. Persistent ping-pong framebuffer supplies the detailed owner-local history and damage-ledger behavior. The machine-readable ownership inventory assigns every derived fixed-address symbol, typed data label, relocation, and enumerated nonsymbol allocation to exactly one of these definitions.

Initial DOC-002 data schema. Every added record requires owner, width, encoding, reset rule, lifetime, producers, consumers, and capacity rule.
