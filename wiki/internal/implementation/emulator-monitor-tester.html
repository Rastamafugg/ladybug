Implementation · decision

Emulator-Monitor Tester — requirements internal

Four-workstream initiative pairing a switchable 6809 tester ROM with web-app features (live FB rendering, mapped memory regions, step-synchronized panels) to drive emulator/hardware bring-up and palette/mode experiments.

A development platform — not the Ladybug game — for exercising the CoCo 3 hardware envelope and the web-app monitor in parallel. Seeded from src/diag_minimal.s (the working 16-stripe minimal hi-res cart from 2026-05-16). Lives alongside the game ROM; does not modify it.

Why a separate tester

  • Phase 2.x main.s has a confirmed FB-render regression (backlog/phase2-fb-render-regression). A clean minimal cart side-steps that while we iterate on the web app.
  • The mode/palette/pattern space is large and not arcade-relevant for most of it. Exercising it inside main.s would bloat the game ROM.
  • The web app needs a reliable, known-state target to validate live FB rendering, mode resolution, and the regions feature against.

Workstreams

WS-A — Tester ROM v0 + GIME-state visibility probe

DECIDED.

  • Input: keyboard, key-per-option (number row for modes, letter row for patterns).
  • HUD: none on-screen. Current selection visible only in the web app.
  • Run model: continuous main loop + 60 Hz Vbord IRQ.
  • v0 pattern catalogue: horizontal bars + checkerboard.
  • v0 mode: 320×192×16 only (CRES=10, HRES=7, VRES=00). The mode matrix expands in WS-D.

GIME-state visibility — three options:

OptionIf probe says...Cost
1. Direct read of $FF9x via gdb-mcpXRoar returns last-written values for write-only regsfree; XRoar-only
2. Read tester program state (mode-index + table at known symbol)XRoar returns garbagesmall; real-hardware-compatible
3. Software shadow block(always available)most invasive; real-hardware-compatible

Resolved 2026-05-16: Option 2 (ProgramStateStrategy). XRoar's gdb stub returns sentinel $1B for every read of $FF90 and $FF98..$FF9E regardless of writes; palette and PARs read back correctly so the channel is sound. Probe artifact: web/scripts/probe_gime_readback.py.

WS-B — Live framebuffer renderer (done 2026-05-17)

See log entry 2026-05-17 "Phase 4 WS-B". Two architect-pass decisions revised at landing time:

  • ReadStrategy protocol collapsed. M3's read_gime_state returns the GIME shadow directly; the three-strategy abstraction is moot.
  • FB read path changed from virtual to physical. FB is now read via space="physical" from ($FF9D<<11) | ($FF9E<<3), matching the GIME's actual hardware video pointer.

WS-B — original requirements (preserved for traceability)

  • Palette decode: RGB monitor (palette.decode_rgb_monitor).
  • New backend module: web/backend/gime_state.py.
  • Trigger: on ws:halt, frontend already polls /api/instances/{id}/framebuffer.png.
  • Free-run rendering: optional poll at ~500 ms during free-run. Default off.
  • Unsupported modes: return placeholder PNG.

WS-C — Mapped memory regions (done 2026-05-17)

See log entry 2026-05-17 "Phase 4 WS-C". Two decisions taken at landing time:

  • Naming-collision resolution. The existing web/backend/regions.py (static 6809 hardware-region map) was renamed to web/backend/memory_map.py. The architect-approved name regions.py is now the user-defined region module. The /api/regions URL is preserved for frontend back-compat.
  • Config identity. config_id derives from the rom_path filename stem. All instances of the same ROM share a region set.

v0 ships hex-dump viewer only.

WS-C — original requirements (preserved for traceability)

  • Persistence: per-config (regions attach to web/configs/<id>.json).
  • Definition modes: fixed addr + length; Symbol + offset + length; Follow pointer at addr.
  • Auto-refresh: every halt (visible regions only).
  • Max size: 32 KB per region.
  • Viewer formats: extensible plugin convention. Hex dump is the always-on baseline.

WS-D — Tester mode/pattern matrix expansion (partial 2026-05-18)

v0 landed: mode-switch infrastructure + 320×192×4 hi-res 4-color mode (mode 1). No new patterns this round.

Mode-table schema extension. Record grew 5 → 8 bytes:

  • TM_BPR (bytes per row, u8)
  • TM_LINES (lines per frame)
  • TM_BPP (bits per pixel: 1, 2, or 4)

Pattern-renderer contract change. draw_current_pattern now receives X = pointer to the active mode record. Inside each pattern handler, an internal bpp dispatcher (pat_<name>_draw → pat_<name>_4bpp / pat_<name>_2bpp) selects the variant.

Key binding. Number-row '2' → select mode 1. Mode 0 remains '1'.

What's NOT in v0: hi-res 4-color at 640 wide, hi-res monochrome, hi-res text, the 16-color stripe diagnostic, per-color solid fill sweep.

WS-D — original requirements (preserved for traceability)

  • Mode families in scope: hi-res 16-color (CRES=10), hi-res 4-color (CRES=01), hi-res monochrome (CRES=00), hi-res text (BP=0).
  • Resolution sweep: HRES 4-7, VRES 192/200/225 where applicable.
  • Mode-switch atomicity: blank via CRES=11 during reconfiguration.

Cross-cutting — step-sync

All reactive panels refresh on every ws:halt, including each -exec-step. The 30 KB FB read per step is accepted.

Scope approvals (granted by user)

  • New build target: build/tester.rom via a tester action in scripts/build.sh.
  • New backend module: web/backend/regions.py.
  • New backend module: web/backend/gime_state.py.
  • New frontend component: web/frontend/components/memory-regions.js.

Explicitly out of scope

  • Modifications to Ladybug game ROM behavior.
  • Composite-NTSC palette rendering (closed; RGB is canonical).
  • Time-travel / reverse-step.
  • Native-hardware verification of the tester (XRoar-only for v1).
  • Snapshot save/load integration with the tester.
  • Project-wide application of the shadow-register convention to Ladybug-proper.

Sequencing

  1. Probe (gates everything): empirical $FF98/9 read test. Resolved 2026-05-16: Option 2.
  2. WS-A: tester v0 ROM.
  3. WS-B: live FB renderer.
  4. WS-C: regions feature. Can parallelize with WS-D after WS-A.
  5. WS-D: mode-matrix expansion.

Each WS closes in qa-reviewer.

WS-A architect-pass decisions (2026-05-16)

Probe

  • Tool: web/scripts/probe_gime_readback.py (~50 lines). Migrated 2026-05-17 to MonitorSession against xroar-monitor; verdict reproduces identically.
  • Stimulus: an already-running diag_minimal.rom instance.
  • Reads: $FF98-$FF9E (the question), $FFB0-$FFBF palette and $FFA0-$FFA7 PARs (controls).

Build target

  • cmd_tester_run — cmd_tester then xroar.
