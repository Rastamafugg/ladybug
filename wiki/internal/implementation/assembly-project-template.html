Implementation · reusable template

Assembly Documentation Project Template internal

Minimum structure for reusing DOC-002 with another lwasm bare-metal project.

Controlled vocabulary

Routine contract, basic block, runtime destination, and evidence dimension use the glossary definitions throughout this template.

Required inputs

  • One configuration file declaring modules, top-level sources, listings, maps, optional binaries, include roots, profile-inactive source units, relocations, fixed or indirect calls, exclusions, semantic IDs, and evidence.
  • One lwasm listing and map for every active assembled module. Profile-inactive modules may be source-only and must state that representation evidence is missing.
  • Hand-authored HTML definitions for controlled terms, routine contracts, data layouts, memory ownership, and architectural rationale.
  • Concise source headers mirroring local inputs, returns, clobbers, and side effects without duplicating revision-specific addresses.

The parser package contains no project address constants. Configuration and serialization are the only untyped boundaries. Internal records are immutable and typed.

Adoption sequence

  1. Build one revision and retain source, listing, map, binary, tool-version, profile, and final-image hashes.
  2. Declare every active and profile-inactive module plus every delivery identity.
  3. Generate module pages and global address, symbol, routine, and source indexes.
  4. Classify every global label as routine, basic block, data/constant exclusion, or failure.
  5. Add canonical routine, memory, and scenario evidence definitions until the verifier passes without broad exclusions.
  6. Run the reusable fixture and mutation suite before adopting the output as a navigation aid.

Reusable proof

scripts/fixtures/source-reference/project.json supplies two modules, one include, emitted instructions and data, a cross-module call, a copied runtime destination, all six evidence dimensions, and nine mutation failures. The mutations remove required routine, symbol, memory-owner, scenario-evidence, and required-scenario records; stale the revision; materially change a listing and a map; and break a generated link. It contains no Ladybug address requirement.

Memory and scenario records

Each memory definition declares a stable ID, one canonical owner, one semantic HTML anchor, and every assembly symbol alias that resolves to that definition. Normalization expands those aliases into immutable reference records containing module, file, line, symbol, and definition/read/write/read-write access.

Each required scenario declares its criterion, behavior, state, module, owning routine, memory-definition IDs, exact source records, verifier description, and one or more passing evidence IDs. A separate required-scenario ID set makes an omitted scenario fail verification. A missing field, unresolved source line, unknown routine or memory ID, or non-passing evidence record also fails.

Every intentionally omitted source path has one manifest exclusion record containing the exact path and a non-empty reason. Exclusions do not reduce a required coverage set.

Generated HTML remains disposable. The host project's hand-authored documentation remains the semantic authority.
