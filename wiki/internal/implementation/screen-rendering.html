Reading this page

Rendering has four separate concerns. Authoritative state says what the game believes is true. Render intents say which layers must be reconsidered. Composition turns that state into pixels in the hidden BACK framebuffer. Publication makes the completed BACK image visible at Vbord. A bug in one concern must not be hidden by changing another. The related architecture pages are source structure for module ownership, video mode for the pixel format, and persistent ping-pong framebuffer for the A/B transaction.

Coordinate and storage model

The screen is 320×192 pixels in 16-colour mode. Two pixels occupy one framebuffer byte, so each scanline is 160 bytes. The CPU sees the current BACK image at virtual $2000-$97FF; FB_VIRT is $2000 and FB_END is $9800. A 16×16 actor therefore occupies eight framebuffer bytes per row and 128 bytes total. The row-to-row advance inside that rectangle is 152 bytes after the eight written bytes. 

framebuffer byte = $2000 + (pixel_y * 160) + (pixel_x / 2)
PLAYER_FB        = top-left byte of the current 16×16 player rectangle
PLAYER_OLD_FB    = top-left byte of the rectangle whose background is saved
PLAYER_BG_PTR    = A- or B-owned 128-byte clean background
semantic cell    = maze coordinates used by collision and dot state

PLAYER_FB is a visual destination, not the collision origin. Movement updates it by one byte horizontally or 320 bytes vertically for each two-CoCo-pixel step, while PLAYER_CELL_X/Y advance only when the player reaches a semantic cell centre. The authored sprite anchor is seven pixels left and seven pixels above that semantic origin; the byte-aligned save rectangle begins eight pixels left. The one-pixel source adjustment described below keeps artwork aligned inside that rectangle.

One gameplay frame, end to end

The main loop samples one Vbord epoch, waits if a completed BACK image is still pending, and then runs game logic. Gameplay routines do not publish pixels directly. They mutate records such as player position, death state, gate state, entities, and HUD values, then set compact flags such as RF_PLAYER, RF_DEATH, or RF_ENTITIES.

  1. Dispatch and simulation: mainloop calls the presentation dispatcher, then runs gate, pickup, player-animation, enemy, input, timer, and death logic. If death is active, death_tick selects the phase and may update PLAYER_FB for the angel movement.
  2. Choose BACK: frame_render_impl calls framebuffer_prepare_back. It verifies BACK is not FRONT, maps PAR1–PAR4 to BACK, selects the owner-local player save-under, and hydrates old actor pointers and metadata.
  3. Remove old actors: actor_closure_restore restores the prior player rectangle and every old enemy footprint from that BACK owner’s clean backgrounds.
  4. Project background state: queued maze, entity, gate, perimeter, HUD, nest, and other persistent damage is applied by frame_render_background. Damage replay is background-only; it does not draw the player or death presentation prematurely.
  5. Capture and draw: actor_closure_draw captures clean destinations, draws enemies, then draws popup, death, or the live player last. This order preserves player-over-enemy ownership and prevents later layers from covering the selected presentation.
  6. Publish readiness: framebuffer_finish_back records owner-local state and sets FB_RENDER_PENDING with interrupts briefly masked. Main code does not change the displayed owner.
  7. Commit: the Vbord IRQ acknowledges the interrupt, writes GIME_VOFF1 for BACK, exchanges FRONT/BACK IDs, clears pending, and advances the commit and simulation sequences. Until this point the old FRONT image remains visible.

This is why a visible rendering correction should usually be made at the layer that creates the wrong pixels. Moving a destination address changes the whole composition contract; changing an authored/generated frame preserves movement, collision, ownership, and publication behavior.

How the player and death layers are drawn

The live player path uses player_compose_impl during persistent rendering. It starts from the owner-local clean background, accounts for the old-to-new rectangle delta, builds the clean new rectangle, saves that clean rectangle, overlays the selected sparse player stream, writes the complete new rectangle to BACK, and restores old-only strips. A first or discontinuous draw uses the direct draw_player path, which saves the rectangle and calls PLAYER_MODULE_DRAW.

Death uses the same rectangle and the same save-under boundary. On entry, death_tick records PLAYER_OLD_FB, exposes the old player background when valid, and sets RF_DEATH. The renderer later calls draw_death_frame, which saves the current PLAYER_FB rectangle, selects the generated death stream, and calls PRESENTATION_MODULE_DRAW. Popup presentation follows the same final-layer rule. The renderer does not infer a separate death origin.

The death state machine is independent of composition: state 1 selects the initial shrink frames, state 2 selects the stationary angel and moving angel phase, state 3 holds the blank interval, and state 4 holds game over. The current timing and movement are in src/main.s; the pixel streams are generated data. A timeout or wrong phase is therefore a different problem from a consistently shifted death sprite.

Generated sprite pipeline

assets/arcade/sprites.json stores 16×16 raw 2bpp source grids. scripts/build_screen.py rotates the selected arcade sprite into runtime orientation, packs four 2bpp pixels per byte, expands the selected pen map to native 4bpp, and encodes non-transparent destination runs as sparse streams. The generated resident include contains the death stream pointer table and the individual death_sparse_frame_N streams; src/enemy_runtime.s decodes those streams into BACK and restores PAR5 to page $34 when decoding ends. 

raw 16×16 2bpp grid
        ↓ rotate_ccw / rotate_cw
oriented 16×16 source grid
        ↓ pack_sprite_2bpp
64-byte packed source frame
        ↓ expand_sprite + encode_sparse_native
native 4bpp sparse destination stream
        ↓ sparse_blit_fb / PRESENTATION_MODULE_DRAW
16×16 pixels in the current BACK framebuffer

Normal player frames are generated by compile_player_sprites. After orientation and rotation derivation, each row becomes [0] + row[:15]: one transparent source pixel is inserted at the left and the old rightmost source column is dropped. This is the established one-pixel right-alignment transform for the player rectangle. Enemy and attract-extra frames use the same transform.

Death frames are generated by compile_death_sprites, which calls compile_sprite_codes without that transform. They are rotated and packed at their original 16-column source positions. Runtime then draws live and death streams at the same PLAYER_FB address. The result is a one-source-pixel left shift of every death frame relative to the live player origin. This is the confirmed BUG-020 cause.

High-score name-entry presentation

FEAT-003 extends the existing presentation owner for the terminal GAME OVER → qualification → name-entry → ranked-list → high-score → attract sequence. Authored Sprite Locations metadata supplies the cursor's starting cell and generated metadata supplies the cursor stream, dynamic character cells, CL cells, END, and HUD patch destinations. The map compiler keeps the shared one-byte atlas bounded; any authored tile that cannot enter that atlas is emitted as a screen-local literal patch rather than changing the existing map-cell protocol.

Session records remain authoritative in page $34 at $AF84-$AFDD: each record contains a three-byte packed-BCD score followed by seven name bytes. The pending name occupies the adjacent seven-byte buffer. Presentation initializes the records once per cold session, compares scores most-significant byte first, and shifts lower records exactly once when END commits the entry.

Name-entry rendering is persistent-owner safe. Both A and B presentation surfaces are hydrated at the screen boundary. Each owner has a 128-byte cursor save-under and validity state in free page-$34 RAM. A cursor move restores the current owner's old footprint, captures the clean destination, draws the generated 16×16 cursor stream, and publishes through the normal PENDING/Vbord transaction. Presentation code never selects FRONT directly.

What BUG-020 does and does not change

The approved BUG-020 contract is to apply the established normal-player alignment transform to death source rows, with an opaque-edge and width oracle. It keeps the current PLAYER_FB, movement and collision coordinates, death timing, artwork selection, A/B ownership, and sparse decoder unchanged. The rightmost source column must be checked before it is truncated; a runtime address offset is explicitly the wrong abstraction because it would make the visual rectangle disagree with collision and save-under reasoning.

The smallest useful proof is build-time: decode generated live and death pixels into a common 16-column grid, verify the declared origin and width, reject opaque-pixel loss, and mutate the death generator to omit the leading transparent column. The mutation must fail before runtime capture. Runtime evidence then covers every death phase, enemy and skull causes, natural demo/live flow, both BACK owners, and the existing BUG-012 and BUG-017 boundaries. The full acceptance contract remains in the BUG-020 ticket.

Debugging checklist

  1. First decide whether the wrong pixels are in the authored source, the generated stream, the runtime destination, or the displayed owner.
  2. For a fixed offset, compare source and generated grids before inspecting MMU or Vbord behavior. Confirm the live and death streams use the same 16-column origin.
  3. For trails or restored scenery, inspect PLAYER_OLD_FB, PLAYER_BG_PTR, owner-local validity, and actor-closure order.
  4. For a one-frame or mixed-image artifact, inspect FB_RENDER_PENDING, the commit sequence, and FRONT/BACK ownership. Do not attribute it to A or B without identical starting metadata and a reversed crossover.
  5. For a missing death frame, inspect DEATH_STATE, DEATH_FRAME, the RF_DEATH intent, stream selection, and the blank/game-over guards separately.

The source ownership map and verification boundaries are maintained in source-structure. Hardware register behavior is documented in the linked GIME reference; this page records only the project-specific rendering contract.
