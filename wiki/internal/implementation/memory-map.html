Implementation · design

Memory Map internal

Physical-page allocation, virtual MMU layout, cart ROM image structure, and the boot data-copy procedure. Phase 2 base; Phase 4 will refine the data-table half once sprite count is concrete.

Constraints recap

  • 8 MMU PARs, each maps an 8 K virtual page to a 6-bit physical-page number (see CoCo 3 memory map, GIME).
  • 64 physical pages of RAM on a 512 K machine, numbered $00-$3F. RAM is populated top-down — $3F is highest.
  • Framebuffer = 30 720 bytes = 4 pages (3.75 actually used). GIME reads it via physical address, bypassing the MMU.
  • Hidden gate framebuffer = physical pages $2C-$2F. The sixth bank-3 ABI entry maps these pages only while composing a gate region; GIME continues scanning live pages $30-$33.
  • Resident code is copied from GMC bank 1 into physical page $3E. The enemy runtime is copied once from bank 3 offset $0800 to low RAM $0800-$17FF.
  • Delivery cartridge is a 64 K GMC image containing four 16 K banks. Bank 0 is the loader, bank 1 is the resident runtime/assets, bank 2 holds eight four-direction enemy animation sets, and bank 3 owns the enemy module.
  • $FF00-$FFFF is dedicated I/O, not cart-visible. $FE00-$FEFF is forced to phys $3F regardless of PAR7 when Init0 b3 is set — the primary jump table stays reachable.

GIME $FF9D/$FF9E (vertical-offset) points at physical address of phys page $30 = $30 << 13 = $060000. So the framebuffer's first byte is physical $060000. The CPU writes to the FB through virtual $2000-$9FFF, accessing the same physical bytes through the MMU.

$9800-$9FFF is the 2 K of slack at the end of FB page 3 (192 rows × 160 bytes/row = 30 720 = $7800; FB occupies virtual $2000-$97FF). Free for use as scratch / sprite save-restore buffer.

Physical pages $2C-$2F form a second, non-scanned framebuffer used only by the gate-region compositor. Bank 3 copies the gate union and player rectangle from live RAM, invokes the resident gate/player renderer against the hidden mapping, then publishes only those completed rectangles back to pages $30-$33.

Build script pads the resulting raw output to 16384 bytes (see build-workflow).

If 16 K becomes insufficient, expansion options are documented in platform/cartridge §"Cart size — 16 K split layout implemented". Expansion requires an explicit bank-switch or copy design because the current runtime executes directly from cartridge ROM.

Boot execution and legacy data-copy procedure

Current procedure (resolved 2026-07-16)

Ladybug now executes directly from the 8 K cartridge code window. Boot writes Init0 first to select the 16 K cartridge map, explicitly clears TY through $FFDE, loads PAR0-PAR7 as 38 30 31 32 33 34 3E 3F, then enables the MMU. Writable state uses physical pages below $3C; the forced $FE00-$FEFF jump-table window remains RAM-backed.

This removes the XRoar dependency on writes beneath a selected ROM cartridge. It also constrains executable cartridge code to $C000-$DFFF until a later bank/copy design is approved. The historical self-copy procedure below is retained only as the investigation record and is no longer implemented by src/main.s.

Legacy procedure (superseded and based on a false assumption)

Goal (on real hardware): get cart ROM contents into RAM at the same physical pages, so all-RAM mode is transparent.

The old design assumed physical RAM at $3C-$3F accepted writes while TY=0 supplied reads from ROM. The manuals do not support that write-through semantic: TY=0 selects ROM or cartridge hardware, and cartridge writes are delivered to the selected cartridge device. XRoar models this by leaving RAS inactive. The Phase 2.1 "wrote $5A to $C000, flipped TY=1, read it back" test passed under XRoar, but see the important caveat below — that test result is consistent with both "shadow-RAM-during-write works" AND with "XRoar serves cart bytes through the cart-window read path regardless of TY". The two are indistinguishable from CPU-visible behavior alone.

Important: under XRoar 1.10 the self-copy is a no-op

Empirically established 2026-05-14 (four-pass gdb-mcp investigation, see backlog/cart-ram-corruption). Under XRoar 1.10's GIME emulation:

  • Pre-SAM_ALLRAM (MC3=1, MMUEN=0, TY=0), the GIME's address decoder routes $C000-$FDFF through S=1/CTS (cart ROM) with RAS=0. coco3.c read_byte's if (RAS) RAM-overlay block is skipped → reads return cart-ROM bytes. coco3.c write_byte calls cart_rom_write (read-only no-op) and likewise skips the RAS RAM-write block → writes go nowhere. std ,x in the self-copy loop neither populates RAM nor errors.
  • Post-SAM_ALLRAM (TY=1), reads at $C000-$FDFF come from physical RAM. The CoCo 3 reset ROM has already copied and patched that shadow: notably $C0D9-$C0DB = 7E E2 9D and $C8B4-$C8BE = $12. Earlier probes mistook the mostly matching shadow for direct cartridge reads.
  • $FE00-$FEFF is different: MC3=1 forces RAS=1 in the inner decode, so reads/writes hit bank 0 RAM symmetrically. The jump-table region IS RAM-backed.

Net: with TY=0, XRoar reads cartridge ROM but discards same-address writes, so the former self-copy could not populate the shadow. With TY=1, reads switch to the reset-ROM- initialized RAM shadow. The active Ladybug boot avoids both dependencies by keeping TY=0 and executing directly from the cartridge. The manuals and the CoCo 1/2-compatible decode strongly suggest this is hardware-faithful; physical CoCo 3 and CoCoSDC verification remains deferred until Phase 10.

Implications for code that assumes RAM-shadowing

  • Self-modifying code at $C000-$FDFF will silently fail on XRoar (writes don't land; subsequent reads return the original cart byte).
  • Runtime data tables at $C000-$FDFF are read-only on XRoar. The jump table at $FE00-$FEFF is the only RAM-backed window inside the cart range under emulation.
  • Game-state RAM at $A000-$BFFF is below the cart window; once PAR5 maps it to a normal phys page, ordinary read/write works on both XRoar and hardware.
  • The obsolete $C0DC fill was removed on 2026-07-17. Under the active TY=0 boot, $C0D9-$C0DB read directly from the cartridge. See lessons learned.

Sequence:

1. (Cart entered at $C002, ORCC #$50, LDS, DP setup — Phase 1 base.)

2. Self-copy $C000-$FEFF:
        ldx     #$C000
   loop ldd     ,x
        std     ,x
        leax    2,x
        cmpx    #$FF00
        blo     loop
   Reads come from cart ROM; writes are presented to the cartridge and do not
   populate internal RAM.

3. Switch TY = 1 (write $FFDF). Cart hardware disconnects.
   Virtual $C000-$FEFF now reads RAM at phys $3E-$3F. Because the preceding
   writes did not populate it, execution cannot continue safely there.

4. (Phase 2 continues: configure GIME hi-res mode, MMU + PARs, palette,
   framebuffer clear, render.)

Approximate cost: 16 K bytes copied two-at-a-time = ~8 K iterations × ~10 cycles ≈ 80 K cycles ≈ 45 ms at 1.78 MHz. Boot-time-only, never observed by the player.

Phase 3 maze budget

The current Phase 3 screen format uses a 960-byte 40×24 map plus 3,072 bytes for 96 deduplicated packed graphics. The current build contains 15,848 meaningful and alignment bytes before 16 KB padding. Executable code stays in $C000-$DFFF and static data now occupies $E000-$FDFF. The generated semantic maze, writable dot state, and 20 gate-state bytes are integrated.

Phase 4 problem: sprite ROM at full 4bpp likely doesn't fit in 16 K cart

Current Phase 4 resolution: curate arcade sprite 0 for the player, rotate it into four directions, and store four frames as 128 packed pixel bytes with source colour zero treated as transparent. These 512 bytes avoid a separate preserve mask. The full-set decision remains open until Phase 6 enemy integration.

Sprite ROM at full 4bpp: ~120 sprites × 128 B = 15 K. Plus tile gfx (~1.6 K), font (~3 K), code (~6-8 K), maze (~1 K), palette (~0.5 K), sound (~1-3 K) ≈ 28-31 K total — overflows the 16 K cart window. Decide at the Phase 4 review gate against measured numbers:

  1. Compress sprites to 2bpp + per-sprite attribute byte — halves sprite ROM to ~7.5 K. Inline expand during blit (~30% cost). Closest to arcade hardware's native layout. Default plan.
  2. Curate the sprite set — drop direction-flip frames; mirror at blit time. Probably reduces 120 → 60-80 frames.
  3. Pivot to a software bank-switched cart — see platform/cartridge §"Cart size — 16 K split layout implemented; banked fallback deferred". Requires a low-RAM loader, explicit copies to other physical pages, a TY=1 handoff, and a separately selected physical cartridge target.

Once a cart holds enough data, the in-RAM data layout still has the same constraint: 8 PARs vs 8-10 wanted (1 system + 4 FB + 1 game state + 2 data + 2 code). Resolution options for that, in increasing cost:

  1. Bank-switch the data PAR — map phys $34 for "common" sprites, phys $35 for "rare"; switch PAR5 between as needed. ~10 cycles per switch.
  2. Drop one FB page, use a sliding write window — frees one PAR for data; renderer gets more complex.
  3. Move some code out of $E000-$FFFF — frees PAR7. Code lives only in $C000-$DFFF (8 K). Tight.

Cartridge-capacity split — implemented 2026-07-18

The immediate limit was the active 8 K code window, not the physical 16 K cartridge. The plain ROM is now split into two guarded regions: 

Virtual          Capacity  Planned owner
$C000-$DFFF      8,192 B   resident executable code and hot constants
$E000-$FDFF      7,680 B   immutable graphics, maze, and other static data
$FE00-$FEFF        256 B   forced physical-page-$3F jump table; never cart data
$FF00-$FFFF        256 B   I/O; never cart data

The current immutable block begins at palette_table=$E000 and ends at asset_end=$FDE8. The build uses 8,175 resident bytes and 7,656 asset bytes, leaving 17 bytes for resident-code growth and 24 bytes for additional static data, subject to the independent region limits. The resident total includes twelve curated 128-byte death frames because the static asset window cannot hold them. All current 6809 PC-relative references remain within signed 16-bit reach.

Cold-start entity placement samples untouched game-state RAM at $BFFE-$BFFF before that free range is otherwise used, mixes it with the joystick sample, and forces a nonzero LFSR seed. Physical hardware supplies power-on RAM variation; the canonical XRoar run uses -ram-init random to provide the emulator equivalent.

The authored LADYBUG top-score name added four unique 32-byte screen glyphs. To retain them inside the asset window, the screen compiler interns the twenty seven-byte contextual gate background records. A twenty-byte gate-to-record index selects four unique records, reducing this table from 140 to 48 bytes without changing the gate renderer's seven-cell record format or visuals.

src/main.s now emits resident_end, aligns with explicit $FF bytes to asset_start=$E000, and emits asset_end. scripts/build.sh fails the build for resident_end > $E000 or asset_end > $FE00, and also rejects a raw-file length that disagrees with asset_end-$C000. Cold XRoar/gdb-mcp read the relocated block exactly from $E000-$FAA3; the live framebuffer matched the generated screen plus initial player pixel-for-pixel. Cartridge type, runtime MMU ownership, and the 16 K output size are unchanged.

Banked loader implemented for Phase 6+

The GMC-compatible banked image uses a low-RAM bootstrap to select each 16 K source bank and copy its payload through a temporary $A000-$BFFF destination mapping into unused physical RAM. It must also copy the resident code page explicitly; same-address writes beneath TY=0 cartridge ROM remain invalid. After loading, switch TY=1, map one resident code page at PAR6 and one swappable asset page at PAR7, restore PAR5 to game state, then enter the runtime. Normal gameplay will not bank-switch cartridge ROM.

XRoar trace verification confirms bank selection, low-RAM execution, bank-1 multi-page copying, TY=1 handoff, and relocated main-loop execution. Bank 2 offset $0800 supplies the eight packed enemy type/direction animation sets copied to physical page $35; bank 3 offset $0800 supplies the low-RAM enemy module. Runtime temporarily maps page $35 through PAR5 only to refresh a selected low-RAM frame cache, then restores page $34. The loader restores PAR5 to physical page $3E before reusing $A000-$BFFF as the resident-copy destination. Physical cartridge/CoCoSDC compatibility remains a separate release decision.

Stack

Top of stack at $1FFE (in PAR0, phys $38). Grows down. Max realistic depth a few hundred bytes — interrupts push 12 (IRQ) or 3 (FIRQ) bytes plus whatever the handler reserves. The approved 4 K bank-3 copy ends at $17FF, leaving 2 K below the stack top. IRQ nesting and current call depth remain within that margin.
