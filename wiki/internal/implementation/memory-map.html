Implementation · design

Memory Map internal

Current CPU address map, physical RAM ownership, cartridge source windows, and boot-time publication.

Three address spaces

The memory map uses three different coordinates. The 6809 addresses the 64 KiB CPU space. With the GIME MMU enabled, each 8 KiB PAR slot selects a physical 8 KiB RAM page. The GMC cartridge exposes a banked source window through CPU addresses while its ROM is selected; bytes read there are not RAM destinations. The bootstrap copies or expands those source bytes into physical pages before handing the runtime to RAM. A CPU address, a physical page number, and a cartridge bank offset therefore describe different locations.

The project targets a 512 KiB CoCo 3 memory configuration. scripts/build.sh defaults to the complete profile; explicitly selected profiles can change which presentation helpers and payloads are built. The tables below describe fixed source assignments and the runtime mapping; exact packed extents and profile-specific overlays come from the current generators and their manifests. An address or page assignment does not by itself establish that every byte in its containing interval is occupied.

Cartridge source and boot publication

The build assembles a four-bank, 16 KiB-per-bank GMC image. While cartridge reads are selected, each bank is visible through CPU $C000-$FDFF, corresponding to bank offsets $0000-$3DFF. Offsets $3E00-$3FFF are not readable cartridge payload because CPU $FE00-$FEFF is forced to RAM and $FF00-$FFFF is dedicated I/O/control space. Bank offsets identify ROM source positions; they are not physical RAM page numbers.

Bank 0 begins with the bootstrap at offset $0000; the linker/build may place overflow source in $0800-$3DFF. Bank 1 supplies the runtime image: its first 8 KiB is staged as resident code and its following window supplies immutable assets. Banks 2 and 3 carry generated compressed and sparse source payloads; bank 3 also contains the enemy module at offset $0800, which the loader copies into low RAM at $0800. The exact source intervals are generated for the selected profile by scripts/build.sh and scripts/build_sparse_sprites.py; use the corresponding manifests for packed extents and hashes. See the GMC cartridge account and build workflow.

On the complete-profile path, execution begins in bank 0. src/gmc_bootstrap.s establishes bootstrap mappings, copies its loader to low RAM at $0300, and transfers control there before switching cartridge banks. The loader checks the bank signatures, copies the bank-3 enemy module to low RAM, expands generated streams to their specified RAM destinations, and stages the bank-1 resident and asset windows in ordinary RAM pages $21 and $22. The compressed audio stream is staged separately in physical page $24.

After staging, the bootstrap switches the SAM to all-RAM operation. It publishes the resident image at CPU $C000 through physical page $3E and assets at $E000 through physical page $3F, then expands the audio image into page $3D. Only after audio expansion has consumed its compressed source does the low-RAM loader briefly reselect GMC ROM, copy the delayed presentation auxiliary into page $24, and restore all-RAM mode. It then expands the attract surfaces into page $3C, writes $A5 to BOOT_FLAG, restores game-state page $34 in PAR5, and jumps to $C002. In this path, the runtime executes from RAM; it does not self-copy the currently selected cartridge window.

src/main.s retains a plain-cartridge fallback for entry without the bootstrap flag; that branch selects TY=0. It is separate from the default complete GMC boot and must not be used to describe the complete-profile runtime. The earlier same-address shadow-RAM copy model was disproven and is recorded in lessons learned. The forced $FE00-$FEFF and dedicated $FF00-$FFFF regions are described in the CoCo 3 hardware map.

The owner describes its source-defined purpose; “staging” means a boot-time copy/decompression destination, while “runtime” means the page remains available after handoff. The presentation generators and selected build profile determine exact extents within their assigned pages. The table deliberately identifies overlapping page roles where the source has distinct staging, presentation, or runtime phases. It does not make those owners concurrent: use the active PAR mapping, the call/phase lifetime, and the selected profile's generated manifests together. The $25-$26 FEAT-011 row records a candidate source-preparation destination only; it does not establish final ownership or runtime safety. The source ownership audit checks declared owners, ranges, and lifetimes; it complements rather than replaces path-level runtime verification.

Fixed addresses and low-RAM overlays

The assembly assigns several fixed locations that connect the map's phases. $FF40 selects a GMC bank, $FF90-$FF91 control GIME initialization/MMU state, $FFA0-$FFA7 are executive PAR registers, and the SAM commands at $FFD9, $FFDE, and $FFDF select fast clock, cartridge/RAM mode, and all-RAM mode. The IRQ jump slot at $FEF7 is software code in the forced-RAM region. Hardware-register addresses and software allocations are logical CPU addresses, not physical-page identities.

The boot descriptor table now uses low RAM $1800-$187E, with a maximum of 127 bytes for nine 14-byte descriptors plus the terminator. The loader copies and reads it through the unchanged low-RAM mapping. The same bytes later form the first 128-byte half of the runtime actor staging area at $1800-$18FF; descriptors retire at boot_streams_retired before runtime handoff, so the two uses are phase-exclusive. Enemy executable code occupies $0800-$17FF, and the second actor-stage half remains at $1880-$18FF. BOOT_FLAG remains at $02F0, and the loader begins at $0300. Existing keybinding and audio state may continue reusing the old $0287 area after descriptor retirement.

The complete-profile HUD provider owns low RAM $02A0-$02BF after boot-stream retirement. It stores an eight-byte player-one value block at $02A0-$02A7, an unused reserved player-two block at $02A8-$02AF, the ten-byte TOP row-one record at $02B0-$02B9, and a gameplay-values-valid flag at $02BA; $02BB-$02BF remain unassigned. The provider clears all 32 bytes before its first read and seeds TOP from the boot ranking row. Audio guards continue to begin at $02C0.

Low-RAM execution windows are also reused. The bootstrap loader, presentation auxiliaries, and copied audio routines have distinct owners and handoff points; build-generated profile maps provide their exact fitted ends. Do not add maxima for phase-exclusive modules as if they were resident together. The 6809 stack begins with SP=$1FFE and owns $1E00-$1FFF after runtime publication. The source-qualified stack boundary is maintained by the source-reference audit.

Direct page

The runtime sets the 6809 DP register to $00, so direct-page operands address $0000-$00FF in low RAM. Those bytes are shared component state and scratch with declared owners; they are not a general-purpose free pool. In particular, the audio module owns its declared queue and mixer bytes, while gameplay, input, presentation, and interrupt code use their own source-defined fields and phase aliases. Check the current symbol declarations and ownership records before changing an allocation. See data layouts and the ownership audit.

System stack

Boot and runtime initialize the 6809 system stack pointer to $1FFE in low RAM. The project reserves $1E00-$1FFF as its stack window after copied-module publication. The boundary is a protected allocation: low-RAM module staging and generated copy destinations must remain below it. Current hard limits and stack ownership are checked by the source-reference configuration and build guards, not by historical free-byte snapshots.

Compressed source and expanded RAM are separate budgets

Compression changes how many bytes a payload occupies in the cartridge source window; it does not reduce the destination pages required after expansion. Boot descriptors identify source bank intervals and physical destinations, and the loader expands those streams before runtime. Cartridge source headroom, expanded RAM capacity, low-RAM helper space, and framebuffer storage are independent constraints. A result for one cannot be used as spare capacity in another. The historical compression investigation and its ticket evidence remain in BUG-058.

Framebuffer pixels and retained state

Each persistent framebuffer has its own pixel history and owner metadata. Player save-under, enemy rings, pending damage, and other retained records are associated with the framebuffer whose pixels they describe. When rendering switches to the other buffer, restore data is valid only if it belongs to that selected buffer and the recorded background has not been invalidated. A surface clear or an intervening redraw can invalidate saved pixels even if an actor did not move.

For a retained redraw, select and hydrate the chosen buffer's metadata, restore affected actors, capture clean backgrounds, draw, and publish the resulting owner state. The operation order is part of the retained-rendering contract. See framebuffer structures, ownership examples, and lessons learned.
