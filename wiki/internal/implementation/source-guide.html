Source Traceability Guide internal

Navigation from behavior and memory ownership to current source lines, and back from an address to its semantic owner.

Controlled vocabulary

Authored source, generated reference, publication, and evidence dimension use the glossary definitions throughout this guide.

Authority boundary

This wiki owns meaning, rationale, ownership, and stable semantic IDs. Concise assembly headers mirror local register and side-effect contracts. The generated browser owns current addresses, emitted bytes, source-line relationships, symbols, and artifact hashes. A generated page is current only when its manifest hashes match the authored source, listing, map, and binary from one build.

Top-down trace

  1. Start with source structure for the owning module and control phase.
  2. Use routine catalog for inputs, side effects, state ownership, callers, and callees.
  3. Use data layouts and memory map for record fields and virtual, physical, and cartridge identities.
  4. Regenerate build/source-reference/ and follow the routine or symbol link to the exact current line, address, and bytes.
  5. Confirm the required evidence dimension. Structural reachability does not prove delivery, visible output, or timing.

Bottom-up trace

  1. Start from the observed PC, address, symbol, or direct-page byte.
  2. Use the generated address or symbol index to identify the assembled module and source line.
  3. If the module is copied or banked, follow its declared assembled, cartridge-staged, and runtime-destination relationship before interpreting live bytes.
  4. Follow the stable semantic link to the routine, structure, or memory owner in this wiki.
  5. Verify that the live artifact hash matches the generated manifest before drawing a runtime conclusion.
