Implementation Roadmap internal

Phased plan from empty src/ to finished game. Each phase has a proof-of-concept exit criterion and a review gate. Living document — adjust at every gate.

How to use this document

  • Phases are sequential by default — each one's exit criterion gates the next.
  • Each phase ends with a review gate where we re-read this roadmap, update it from what we learned, and decide whether the next phase still makes sense as written.
  • Every gate also triggers an append to lessons-learned. New conventions go to coding-conventions. Anti-patterns go to lessons-learned.
  • A POC is "minimum thing that proves the phase works." It's allowed to be ugly.

Current state — Phase 5 collectible loop implemented

  • Phases 0–4 are implemented. MAME measurement fixed movement at one pixel per 60 Hz frame and confirmed persistent early-turn requests. The Up-as-Left fault was traced to MC6821 C2 strobe configuration and corrected to static axis selection.
  • src/gmc_bootstrap.s starts in GMC bank 0, proves banks 2 and 3, loads manifest-described sources from banks 2, 3, and bank 0 overflow, selects bank 1, copies the existing runtime into its RAM execution pages, switches to TY=1 all-RAM mode, and enters src/main.s. XRoar verifies the complete handoff.
  • Tooling: lwasm 4.24 and XRoar 1.10 in WSL. The active automated verification path is gdb-mcp; the web app and patched monitor are deferred.
  • The screen compiler emits 96 transformed tiles, packed curated sprite groups, canonical named maze/HUD colours, the TMX-authored LADYBUG top-score name and life markers, interned contextual gate backgrounds, and both diagonal transition styles.
  • Vbord input, two-pixel movement every second frame, arcade-style persistent direction requests, blocked-turn stop at an aligned junction, mid-cell reversal, measured three-step late-turn/gate diagonal correction, eight-pixel cell centres, dots, and four-state endpoint-pushed rotation with a one-Vbord diagonal gate frame are implemented.
  • The runtime retains its guarded 8 KB resident and 7.5 KB asset windows inside bank 1. The delivered image is four 16 KB GMC banks: bootstrap, runtime, and two sparse-expansion banks, with the bank-3 enemy module embedded in the latter. Current use is 7,466 resident bytes, 7,432 asset bytes, and 4,057 of 4,096 copied bank-3 module bytes. Persistent rendering uses five-actor closure, pointer-selected per-buffer player history, circular enemy save-under with phase-dispatched restore and segmented horizontal capture, shared destination-delta enemy/player streams resolved through always-mapped index mirrors, and generated gate transition streams; shadow-region code is omitted from the active image and remains only in the build-time compatibility path.
  • Automated acceptance includes versioned MAME captures for 60 px/s movement, a request held 35 frames before a legal turn, a six-pixel late-corner window, a 30-frame pickup popup, and a complete gate-17 traversal.

Phase 0 — Hello cart (boot handshake) — DONE 2026-05-08

Goal: smallest possible cartridge that takes control from BASIC and proves we own the machine.

POC tasks:

  1. Create src/main.s with a 3-line stub: ORG $C000, an entry vector compatible with the BASIC CART/FIRQ handshake, an infinite BRA * (or write a known byte to a known screen address before the loop).
  2. Build, autorun under XRoar, confirm the screen shows our marker.

Exit criterion: scripts/build.sh run boots straight to our stub on XRoar without dropping to the BASIC OK prompt.

Review gate Q's:

  • Did the FIRQ handshake work as documented in platform/cartridge? Any gotchas to record?
  • Is scripts/build.sh ergonomic for daily edit-build-run, or does it need a watch mode?
  • Does our cartridge header layout match what we expect to flash to a 16K EPROM later?

Phase 1 — Boot init: all-RAM, DP, vsync IRQ — DONE 2026-05-08

Goal: establish the runtime environment our code will assume forever afterward.

POC tasks:

  1. Set MMU to all-RAM mode (no ROM in the address space).
  2. Set DP to the chosen page (decision: pick the page now and document in coding-conventions §1).
  3. Switch CPU to 1.78 MHz.
  4. Initialise PIA1/PIA2 ourselves (don't trust BASIC's leftovers).
  5. Install Vbord IRQ handler that does nothing but increment a frame counter. Print/poke the counter to a fixed memory location so we can watch it tick on screen.
  6. BRA * main loop.

Exit criterion: XRoar shows the frame counter incrementing at 60 Hz. Confirm in the trace log that no FIRQ/IRQ from any other source fires.

Review gate Q's:

  • Is our IRQ enable mask actually masking everything but Vbord? (Re-check against platform/timing.)
  • Does SWI collide with anything we'll need later? — pending question from coding-conventions §4. Resolve at this gate before any further code uses SWI.
  • Capacity check: how many bytes did we burn on init? Project that against the 16 KB cart budget.

The instructions map remains reference/authoring material but is removed from deployed emission and runtime. High scores remain session-only with no battery-backed RAM.

Approved wiring plan:

  1. Compile cold screens: extend the screen compiler with a presentation-map input list and emit one common character atlas plus per-screen tile-index / palette records. Place these cold records in unused GMC expansion-bank space; do not consume the resident window, which has less than one cache line of headroom.
  2. Own flow in one state machine: the deployed unattended states are boot → attract title → demo level start → demo gameplay → death presentation → attract title. The prior automatic instructions state is removed. Coin or start pre-empts every attract/demo state through one edge-tested input path.

The module maps only the selected cold-data page through PAR5, expands the static tile map into the hidden framebuffer, restores PAR ownership, then publishes a complete frame. Existing gameplay and enemy compositors retain ownership only in gameplay states.
  4. Script animations as data: each non-game screen uses compact frame-count / operation records for flashes, cursor movement, colour changes, and sprite overlays. The 60 Hz Vbord counter is the sole clock. No presentation animation may busy-wait or run a private timer loop.

  • Cart-shell compatibility check. Does the target cart shell (CoCoSDC, RetroCloud, custom 32 K PCB, etc.) actually respond to the GIME's $8000-$BFFF accesses when Init0 b1-b0 = 11 is set? If not, pivot to a software bank-switched cart (~half-day refactor). See platform/cartridge §"Cart size — 32 K".

Standing review checklist (every gate)

  1. Wiki updates. Any new lesson, decision, hardware quirk, or convention discovered → file it. Don't let it stay in chat history.
  2. Roadmap drift check. Re-read this document. Does the next phase's POC and exit criterion still describe the right next step? If not, edit this file and append a log entry explaining the change.
  3. Budget check. ROM bytes used / 16384. Cycles per frame used / ~29800 (1.78 MHz / 60 Hz).
  4. Scope check. Anything we added that wasn't in the design doc? Anything we cut? Update game/overview decisions block.

Risks the plan won't surface on its own

  • GIME mode choice in Phase 2 is load-bearing for everything visual. Don't rush the review at that gate.
  • Tile vs sprite format coupling in Phase 3/4 — getting the boundary wrong forces a rewrite later. Sketch both formats together, not sequentially.
  • Per-frame budget under enemy load in Phase 6 is the most likely place we discover we need the TCB scheduler or dirty-rect tracking. Plan a contingency phase at that gate, not after.
  • EPROM/cart-shell hardware logistics in Phase 10 — sourcing a programmer, blank EPROM, and a working cart shell is not a code task. CoCoSDC removes most of this. Start sourcing in parallel during Phase 6 or 7.
