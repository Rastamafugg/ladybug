Implementation Roadmap internal

Phased plan from empty src/ to finished game. Each phase has a proof-of-concept exit criterion and a review gate. Living document — adjust at every gate.

How to use this document

  • Phases are sequential by default — each one's exit criterion gates the next.
  • Each phase ends with a review gate where we re-read this roadmap, update it from what we learned, and decide whether the next phase still makes sense as written.
  • Every gate also triggers an append to lessons-learned. New conventions go to coding-conventions. Anti-patterns go to lessons-learned.
  • A POC is "minimum thing that proves the phase works." It's allowed to be ugly.

Current state — Phase 5 collectible loop implemented

  • Phases 0–4 are implemented. MAME measurement fixed movement at one pixel per 60 Hz frame and confirmed persistent early-turn requests. The Up-as-Left fault was traced to MC6821 C2 strobe configuration and corrected to static axis selection.
  • src/gmc_bootstrap.s starts in GMC bank 0, proves banks 2 and 3, selects bank 1, copies the existing runtime into its RAM execution pages, switches to TY=1 all-RAM mode, and enters src/main.s. XRoar verifies the complete handoff.
  • Tooling: lwasm 4.24 and XRoar 1.10 in WSL. The active automated verification path is gdb-mcp; the web app and patched monitor are deferred.
  • The screen compiler emits 92 transformed tiles, packed curated sprite groups, canonical named maze/HUD colours, TMX-authored life markers, contextual gate backgrounds, and both diagonal transition styles.
  • Vbord input, two-pixel movement every second frame, arcade-style persistent direction requests, blocked-turn stop at an aligned junction, mid-cell reversal, measured three-step late-turn/gate diagonal correction, eight-pixel cell centres, dots, and four-state endpoint-pushed rotation with a one-Vbord diagonal gate frame are implemented.
  • The runtime retains its guarded 8 KB resident and 7.5 KB asset windows inside bank 1. The delivered image is four 16 KB GMC banks: bootstrap, runtime, and two expansion banks. Current use is 8,172 resident bytes and 7,672 asset bytes.
  • Automated acceptance includes versioned MAME captures for 60 px/s movement, a request held 35 frames before a legal turn, a six-pixel late-corner window, a 30-frame pickup popup, and a complete gate-17 traversal.

Phase 0 — Hello cart (boot handshake) — DONE 2026-05-08

Goal: smallest possible cartridge that takes control from BASIC and proves we own the machine.

POC tasks:

  1. Create src/main.s with a 3-line stub: ORG $C000, an entry vector compatible with the BASIC CART/FIRQ handshake, an infinite BRA * (or write a known byte to a known screen address before the loop).
  2. Build, autorun under XRoar, confirm the screen shows our marker.

Exit criterion: scripts/build.sh run boots straight to our stub on XRoar without dropping to the BASIC OK prompt.

Review gate Q's:

  • Did the FIRQ handshake work as documented in platform/cartridge? Any gotchas to record?
  • Is scripts/build.sh ergonomic for daily edit-build-run, or does it need a watch mode?
  • Does our cartridge header layout match what we expect to flash to a 16K EPROM later?

Phase 1 — Boot init: all-RAM, DP, vsync IRQ — DONE 2026-05-08

Goal: establish the runtime environment our code will assume forever afterward.

POC tasks:

  1. Set MMU to all-RAM mode (no ROM in the address space).
  2. Set DP to the chosen page (decision: pick the page now and document in coding-conventions §1).
  3. Switch CPU to 1.78 MHz.
  4. Initialise PIA1/PIA2 ourselves (don't trust BASIC's leftovers).
  5. Install Vbord IRQ handler that does nothing but increment a frame counter. Print/poke the counter to a fixed memory location so we can watch it tick on screen.
  6. BRA * main loop.

Exit criterion: XRoar shows the frame counter incrementing at 60 Hz. Confirm in the trace log that no FIRQ/IRQ from any other source fires.

Review gate Q's:

  • Is our IRQ enable mask actually masking everything but Vbord? (Re-check against platform/timing.)
  • Does SWI collide with anything we'll need later? — pending question from coding-conventions §4. Resolve at this gate before any further code uses SWI.
  • Capacity check: how many bytes did we burn on init? Project that against the 16 KB cart budget.

Phase 2 — Display foundation: video mode + char output — DONE 2026-07-16

Substep status:

  • 2.1 — shadow-RAM-during-write at phys $3E verified
  • 2.2 — cart self-copy + all-RAM transition; IRQ ticks from RAM
  • 2.3 — GIME hi-res 320×192×16 + MMU + PARs + framebuffer writes + palette load + IRQ-driven FB writes from mainloop
  • 2.4 — hand-converted arcade char #432 (dense tile exercising all four pixvals 0/1/2/3 → black/yellow/blue/white) to 4bpp GIME bytes; blit_tile (8 rows × 4 bytes, stride 160); three-tile framebuffer verified after the 2026-07-16 fix
  • 2.5 — automated selected-tile and target-palette generation with scripts/build_gfx.py; generated character 432 reproduces the Phase 2.4 bytes without embedding the full 512-tile set (done 2026-07-16)
  • 2.6 — selected arcade glyphs 21/10/13/34/11/30/16 for LADYBUG, rotated them counter-clockwise for the unrotated CoCo framebuffer, implemented put_char, and verified every title row through gdb-mcp (done 2026-07-16)

Goal: pick the GIME video mode, get a stable framebuffer, render text reliably.

POC tasks:

  1. Pick a video mode (decision point — write the chosen mode + rationale to video-mode). Candidates per GIME: 320×192 16-color, 256×192 16-color, or a hi-res text mode.
  2. Configure GIME to that mode in init; clear the framebuffer to a known colour.
  3. Implement SVC_PUTC (or a regular JSR equivalent) — render a single character glyph from a font table at a tile coordinate.
  4. Print "LADYBUG" at the top of the screen.

Exit criterion: stable picture in XRoar, no flicker, "LADYBUG" visible.

Exit result: passed. The title is drawn once while blanked and then displayed statically. A cold gdb-mcp run verified the exact seven-glyph framebuffer region, black bytes on both sides, palette/PAR state, liveness markers, and the halt-loop PC.

Review gate Q's:

  • Does the chosen mode have enough resolution and palette for the playfield + HUD as described in game/overview?
  • Memory cost of the framebuffer — does it fit comfortably alongside our code?
  • Is our font/glyph format what we want for the HUD numbers and letters too, or do we need separate large/small fonts?

Review gate: retain 320×192×16 and the 30,720-byte framebuffer. The generated 8×8/32-byte glyph format is accepted for HUD letters and digits; any larger score font remains deferred until HUD implementation. Phase 3 may build on put_char and blit_tile without an SWI layer.

Phase 3 — Tile renderer + static maze

Goal: render the playfield from data, no entities yet. Validates the data-driven approach.

POC tasks:

  1. Done 2026-07-16: define the 8×8 tile, layered maze, gate, dot, navigation, renderer, and memory contracts in maze-format.
  2. Done 2026-07-17: capture an authoritative level-one start state from MAME background RAM, apply ROT270, and crop the complete maze at arcade rows 2–25 into the 24×24 target grid.
  3. Done 2026-07-18: derive the semantic maze and deterministic validator/generator: 25 styles, 117 food-placement candidates, all 20 initial gate footprints, and a connected 249-cell navigation graph. Six bonuses and 2–6 skulls replace candidates at runtime.
  4. Done 2026-07-17: compile the authored layered 40×24 TMX into a 960-byte map and 53-tile packed atlas, then render it row-major once at boot before the deterministic halt.

Exit criterion: the full Lady Bug playfield is visible and correct against the design doc — outer walls, inner walls, turnstiles, all 20 gates, dots in their starting positions.

Exit result: passed. A cold gdb-mcp run stopped at $C096, preserved the $55AA liveness marker, and produced a 30,720-byte framebuffer whose SHA-256 exactly matched the build-time TMX render: cf52d7cde30fee0df12b39a35416628f7d4e75b7bf1c5961d17acf474d3661ad.

Review gate Q's:

  • Render time budget — how many cycles did the full maze take? Project that against the 60 Hz frame budget if we re-render every frame vs only dirty tiles.
  • Does the maze layout look right at this resolution? (User judgement call.)
  • Is the tile format tractable for both static maze tiles and animated entities, or do we need a separate sprite format?

Phase 4 — Input + Lady Bug sprite (joystick walking) — IMPLEMENTED 2026-07-17

Goal: a controllable Lady Bug sprite walks the maze, no AI yet.

POC tasks:

  1. Done: right-joystick X/Y read via PIA2 DAC + comparator (input reference), with centred dead zone and dominant-axis four-way resolution.
  2. Done: one authored north-facing four-frame Lady Bug animation sequence is packed with source-zero transparency; east, south, and west are derived by clockwise rotation rather than separate source sequences.
  3. Done: single-sprite 128-byte background save/restore plus transparent 16×16 blit.
  4. Done: two-pixel movement every second Vbord, four updates per semantic cell, navigation collision, and dot removal through writable maze cells.

Exit criterion: Lady Bug walks the maze under joystick control, walls block movement, and entered dots disappear without scoring.

Exit result: the first playtest defects were corrected, then calibrated against MAME 0.220. Arcade stage-one motion is exactly one pixel on every 60 Hz frame. An east request issued at frame 620 is retained until the first legal centre at frame 655, where direction changes without a stopped frame. The CoCo uses the collision-safe (-7,-7) anchor and the same 60 px/s cadence through two-pixel updates every second Vbord. A 2026-07-19 follow-up made PLAYER_WANT persist through neutral analog samples and made mid-cell/gate decisions consume it while continuing toward a not-yet-legal junction. Opposite input still reverses immediately with partial-cell rebasing, and an aligned blocked request stops. Startup auto-travel remains intact. The Up-as-Left defect was traced to MC6821 C2 strobe values $24/$2C and corrected to static-output values $34/$3C. Build and static control-flow checks passed; the user hardware retest reported substantially improved gate feel.

Review gate Q's:

  • Does the movement feel right against arcade footage? Record the finding.
  • Sprite renderer cost — sustainable when we have skulls + bugs + letters all moving?
  • Decision point: do we still want the scheduler TCB pattern, or is the flat main loop fine?

Phase 7 — Enemies: bug spawner + skull AI

Goal: the game becomes Lady Bug.

POC tasks:

  1. First pass implemented 2026-07-19: four compact enemy records release sequentially, one per completed 92-box timer circuit. Active enemies advance at 60 px/s in eight-pixel cell steps, select a pseudo-random legal direction at each junction, consume current gate orientation without rotating gates, kill the player on contact, and are removed with only the contacted skull when they hit one. Smooth two-pixel interpolation, directional animation, pursuit bias, and arcade den re-release remain follow-ups.
  2. Bug entity record (BUG.X, BUG.Y, BUG.STATE, BUG.LEN); fixed-size pool.
  3. Border-circuit spawn timer driving four initial den occupants; measure the claimed speed changes on stages 2 and 5.
  4. Bug AI — semi-random corridor wandering outside detection range, steady pursuit inside it, and no gate rotation; verify detection and den-safety rules in MAME.
  5. Player-side skull behavior is done: stage table 2 / 3 / 4 / 5 / 6 at stages 1 / 2–4 / 5–8 / 9–17 / 18+, with all skulls removed after player contact.
  6. Refine skull-killed enemies from first-pass removal to the arcade den return and delayed re-release sequence.
  7. Collision → life lost; reset positions.

Exit criterion: playable. You can lose the game. Multiple bugs on screen at once.

Review gate Q's:

  • ROM size — runtime resident and asset use against their independent guards, plus total use of the two GMC expansion banks. If a runtime window overflows, move cold payloads into an expansion bank and extend the bootstrap copy contract.

Phase 10 — Real hardware bring-up

Goal: runs on a physical CoCo 3 from a 16K EPROM in a cart shell.

POC tasks:

  1. Burn the ROM to EPROM.
  2. Boot on real hardware.
  3. Compare against XRoar — note any divergences (timing, palette, sound).

Exit criterion: hardware run matches XRoar. Any divergences are explained or fixed.

Review gate Q's:

  • Emulator-vs-hardware divergences — file each one to lessons-learned with the cause.
  • Cart-shell compatibility check. Does the target cart shell (CoCoSDC, RetroCloud, custom 32 K PCB, etc.) actually respond to the GIME's $8000-$BFFF accesses when Init0 b1-b0 = 11 is set? If not, pivot to a software bank-switched cart (~half-day refactor). See platform/cartridge §"Cart size — 32 K".

Standing review checklist (every gate)

  1. Wiki updates. Any new lesson, decision, hardware quirk, or convention discovered → file it. Don't let it stay in chat history.
  2. Roadmap drift check. Re-read this document. Does the next phase's POC and exit criterion still describe the right next step? If not, edit this file and append a log entry explaining the change.
  3. Budget check. ROM bytes used / 16384. Cycles per frame used / ~29800 (1.78 MHz / 60 Hz).
  4. Scope check. Anything we added that wasn't in the design doc? Anything we cut? Update game/overview decisions block.

Risks the plan won't surface on its own

  • GIME mode choice in Phase 2 is load-bearing for everything visual. Don't rush the review at that gate.
  • Tile vs sprite format coupling in Phase 3/4 — getting the boundary wrong forces a rewrite later. Sketch both formats together, not sequentially.
  • Per-frame budget under enemy load in Phase 6 is the most likely place we discover we need the TCB scheduler or dirty-rect tracking. Plan a contingency phase at that gate, not after.
  • EPROM/cart-shell hardware logistics in Phase 10 — sourcing a programmer, blank EPROM, and a working cart shell is not a code task. CoCoSDC removes most of this. Start sourcing in parallel during Phase 6 or 7.
