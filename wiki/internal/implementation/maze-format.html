Implementation · Phase 3 design

Tile format and static maze internal

Approved architecture and generated semantic tables for the 24×24 playfield and the completed static-rendering pipeline.

Decision

  • Visual unit: retain the Phase 2 packed 8×8, 4-bpp tile: 32 bytes, four bytes per row.
  • Playfield: 24×24 cells (576 cells), rendered at framebuffer character columns 8–31 and rows 0–23.
  • Layers: base visual style, navigation topology, dots, and turnstile gates remain separate. A rendered tile is a composition result, not the game-state record.
  • Ownership: canonical maze and tile metadata are immutable cartridge data. Collected-dot bits and gate orientation are writable game state.
  • Rendering: draw the full static field once at boot in Phase 3; later phases redraw only cells changed by a dot, gate, or moving entity.

The MAME capture confirms that the arcade's complete rotated display is 24×30 tiles and its complete maze occupies rows 2–25 inclusive. The CoCo grid keeps those 24 rows unchanged, including both horizontal and vertical frame tiles. The maze therefore fits the 192-pixel height exactly; corridor cells and their 8×8 scale remain unchanged.

Why the layers are separate

A single array of displayed tile numbers would couple collision to art and would require maze mutation for dot collection and gate rotation. That is unsafe while cartridge data is read-only under the active XRoar path. Separate layers also let a cell restore its clean background after a dot or sprite disappears without reconstructing maze semantics from a graphic number.

Compiled data contract

TableFormatSizePurpose
maze_cells 576 bytes, row-major. Bits 0–6 = logical visual-style ID; bit 7 = dot initially present. 576 B Static appearance and initial dot seed.
maze_nav 576 bytes. Bits 0–3 = passable N/E/S/W; bit 4 = gate-affected; bit 5 = nest; bit 6 = perimeter track; bit 7 reserved. 576 B Movement topology independent of the selected artwork.
tile_styles Two graphic IDs per logical style: clean and dotted. $FF means no dotted form. 2 B/style Selects a precomposed 32-byte graphic without requiring a transparent tile blitter.
tile_gfx Contiguous 32-byte packed graphics; graphic ID × 32 gives its offset. 32 B/graphic Uses the format already verified by blit_tile.
maze_gates 20 three-byte records: pivot X, pivot Y, initial passage state. 60 B Identifies every turnstile pivot and its captured north/west initial passage.
maze_gate_owner / gate_state_tiles 576 owner bytes plus four states of four signed-offset tile records. 624 B Maps each five-cell collision cross to a gate and supplies four directional states using two arcade visual orientations.

Logical style IDs are capped at 128 by maze_cells. The Phase 3 generator must fail if the authored maze exceeds that limit or references a dotted style without a dotted graphic.

Writable state

  • Dots: Phase 4 copies all 576 maze_cells bytes to $A000-$A23F and clears bit 7 in place when a dot is collected. A later phase may compact this to the planned 72-byte bitmap if RAM pressure requires it.
  • Gates: one byte per gate at $A240-$A253. Values 0/1/2/3 mean the passage is north/west/south/east of the pivot. Opposite passage states reuse the same horizontal or vertical arcade tile set; only the logical opening differs after a 180-degree turn.
  • Dynamic topology: regular cells use maze_nav. States 0/2 admit east-west travel through the north/south passage cell; states 1/3 admit north-south travel through the west/east passage cell. Pushing a bar endpoint perpendicularly rotates that endpoint into the new segment before movement proceeds.
  • Potential gate edges: generation adds reciprocal external edges for all four possible passage segments because the MAME start capture contains only the initial orientation. Runtime state still permits only one segment.

The current runtime cost is 576 bytes for writable maze cells. Adding the implemented 20 gate bytes fits comfortably in the $A000-$BFFF game-state page; bitmap compaction is deferred until pressure is measured.

Renderer boundary

Phase 3 implemented a row-major renderer for the compiled 40×24 screen. Phase 4 keeps semantic navigation separate and uses the single-tile blitter only for dirty cells after dot collection.

  1. At boot, render the complete authored 40×24 map while blanked.
  2. Before moving the player, restore its prior 16×16 background.
  3. When entering a dotted semantic cell, clear bit 7 in writable state and blit the clean corridor tile at screen column maze_x+8.
  4. Save the new 16×16 background and apply the transparent player frame.

Keep the existing single-tile routine for character output and correctness tests. The full-maze path may add a row-major fast path that carries its destination pointer instead of recomputing row * 160 + col * 4 576 times. It must retain the established rule that an LDD-loaded data register is not also a loop counter.

Authoring and generation workflow

scripts/capture_mame_maze.py now produces the immutable assets/arcade/maze_capture.bin and derived maze_capture.json provenance files. scripts/derive_maze.py normalizes the captured stage-object overlays and emits semantic assets/arcade/maze.json plus build/ladybug_maze.inc. The source records dimensions, per-cell style and movement mask, dots, nest and perimeter flags, and the 20 gate definitions. The generator validates the invariants below. The build runs this derivation before assembly.

scripts/update_tiled_maze.py converts all 720 rotated visible-sheet indices into Tiled GIDs and replaces layer 1 of tiled/black-and-whitte-screen.tmx. This map represents background RAM only; arcade sprites are not missing tiles. Tiled CSV requires exactly 720 non-empty GID fields for this layer. The generator separates fields with 719 commas and does not emit a terminal comma.

The semantic source must be derived from the capture, not from the incomplete Tiled experiment or screenshot inference.

scripts/create_tiled_coco_screen.py combines the normalized semantic maze with HUD placeholders in a separate 40×24 map. The map has a complete background layer and a transparent HUD layer so the side-panel design can be edited without changing maze GIDs.

After initial creation, tiled/coco-screen.tmx is a hand-authored source file. The scaffold generator refuses to replace an existing map unless --force is supplied. scripts/build_screen.py flattens visible tile layers in order, applies Tiled horizontal and vertical flip flags, rejects diagonal flips and active non-8×8 tilesets, and deduplicates the transformed packed graphics. The current authored screen compiles to a 960-byte map and 92 graphics after semantic colour, gate-state, and diagonal gate-frame expansion.

Derived result: 25 logical styles, 117 food-placement candidates, 20 gates split evenly between horizontal and vertical initial orientations, 249 connected walkable cells, a two-cell central nest release lane, and a 92-cell perimeter circuit. Every gate owns a non-overlapping five-cell collision cross around its pivot. Gate-state parity selects the two parallel passages for the current horizontal or vertical orientation; the centre remains blocked.

Exact maze source — resolved 2026-07-17

MAME 0.220 and the installed ladybug ROM now provide the authoritative start-state background. The capture helper samples $D000-$D7FF until it finds a stable complete-maze state. The accepted run is frames 2545–2558 with SHA-256 d8129bb9f57ce51b0355101115af7eab538b854d31771f6f51917fa072f686f3.

MAME's raw background is 32×32 tiles. Its visible raw rectangle is columns 1–30 and rows 4–27; applying the driver's ROT270 produces the 24×30 arcade display. The JSON records all visible nine-bit tile codes, colour attributes, indices for the whole-sheet counter-clockwise rotation, and the 24×24 CoCo crop. The binary file is the unchanged 2,048-byte RAM dump and remains the final provenance source. A screenshot validates orientation but does not define topology.

Gate transition frame

A pushed gate displays one slash or backslash diagonal frame for exactly one Vbord before the final perpendicular frame. The seven opaque records reproduce arcade character tables at CPU ROM $0CD5 and $0CDE. Two diagonal corner records temporarily cover dot cells; finalization redraws each corner from writable MAZE_STATE, preserving collected-dot state.

MAME movement capture adds a positional rule around both ordinary wall ends and gate pushes. A perpendicular turn remains legal at offsets 2, 4, and 6 pixels after the aligned path; 8 pixels is too late. The CoCo stores the old direction plus a three-step countdown and corrects two pixels on the old axis while advancing two on the new axis. Gate collision is tested from the last aligned cell before this correction, so the existing owner table and endpoint-push rules remain authoritative.

Validation gates

  • The raw capture is exactly 2,048 bytes and matches its recorded SHA-256.
  • The rotated display is exactly 30 rows × 24 cells; the CoCo crop is arcade rows 2–25 inclusive and is exactly 24×24.
  • Every semantic style and graphic reference is in range.
  • Exactly 20 gates; every gate footprint is inside the grid and maps only to cells marked gate-affected.
  • N/E/S/W movement is reciprocal between adjacent non-gate cells; no passable edge exits the grid.
  • Runtime regular-cell collision tests the destination cell's reciprocal entrance bit for the requested direction; a nonzero navigation mask alone is insufficient.
  • The generator restores eight captured object-overlay nodes as ordinary candidates and requires exactly 117; stage load replaces unique candidates with six bonuses and 2–6 skulls.
  • Nest and perimeter-track cells form the captured connected regions.
  • The generator validates 20 non-overlapping five-cell collision crosses with no dots. Each orientation transparently overlays five arcade tiles after restoring seven contextual background cells; four overlapping gate pairs trigger a reciprocal neighbour overlay. Versioned MAME evidence verifies gate-17 rotation and traversal; the four-state runtime rule is exercised by cold gdb-mcp.
  • Live gdb-mcp verification compares all 192 rendered rows, the 64-pixel side margins, palette/PAR state, halt PC, and reported ROM size.

Deferred

  • Two-frame visual interpolation of the arcade rotation remains deferred; navigation state changes atomically on the triggering CoCo frame.
  • Per-frame full-maze rendering is not planned; Phase 3 uses a verified one-time boot render.
  • The generated owner table avoids a per-collision scan of all 20 gate records.
