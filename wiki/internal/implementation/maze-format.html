Implementation · Phase 3 design

Tile format and static maze internal

Approved architecture for the 24×24 playfield. Exact maze capture and implementation remain the next Phase 3 increment.

Decision

  • Visual unit: retain the Phase 2 packed 8×8, 4-bpp tile: 32 bytes, four bytes per row.
  • Playfield: 24×24 cells (576 cells), rendered at framebuffer character columns 8–31 and rows 0–23.
  • Layers: base visual style, navigation topology, dots, and turnstile gates remain separate. A rendered tile is a composition result, not the game-state record.
  • Ownership: canonical maze and tile metadata are immutable cartridge data. Collected-dot bits and gate orientation are writable game state.
  • Rendering: draw the full static field once at boot in Phase 3; later phases redraw only cells changed by a dot, gate, or moving entity.

The MAME capture confirms that the arcade's complete rotated display is 24×30 tiles and its maze frame occupies rows 2–27. The CoCo grid keeps arcade rows 3–26: 24 rows including the vertical side walls. The omitted horizontal frame rows become top and bottom edge pixels in the first and last rendered rows. This is the documented 192-pixel-height adaptation; corridor cells and their 8×8 scale remain unchanged.

Why the layers are separate

A single array of displayed tile numbers would couple collision to art and would require maze mutation for dot collection and gate rotation. That is unsafe while cartridge data is read-only under the active XRoar path. Separate layers also let a cell restore its clean background after a dot or sprite disappears without reconstructing maze semantics from a graphic number.

Compiled data contract

TableFormatSizePurpose
maze_cells 576 bytes, row-major. Bits 0–6 = logical visual-style ID; bit 7 = dot initially present. 576 B Static appearance and initial dot seed.
maze_nav 576 bytes. Bits 0–3 = passable N/E/S/W; bit 4 = gate-affected; bit 5 = nest; bit 6 = perimeter track; bit 7 reserved. 576 B Movement topology independent of the selected artwork.
tile_styles Two graphic IDs per logical style: clean and dotted. $FF means no dotted form. 2 B/style Selects a precomposed 32-byte graphic without requiring a transparent tile blitter.
tile_gfx Contiguous 32-byte packed graphics; graphic ID × 32 gives its offset. 32 B/graphic Uses the format already verified by blit_tile.
maze_gates 20 four-byte records: 16-bit anchor-cell offset, footprint ID, initial orientation. 80 B Identifies every turnstile without embedding mutable state in the map.
gate_footprints Variable records listing each affected cell and its horizontal/vertical graphic and navigation forms. Target ≤128 B Supports the arcade footprint after capture, including a footprint larger than one cell.

Logical style IDs are capped at 128 by maze_cells. The Phase 3 generator must fail if the authored maze exceeds that limit or references a dotted style without a dotted graphic.

Writable state

  • Dots: a 576-bit bitmap, 72 bytes. It is initialized by scanning bit 7 of maze_cells at stage reset; clearing a dot changes only this RAM bitmap.
  • Gates: one byte per gate in the initial implementation, 20 bytes. Values are horizontal or vertical; bit-packing can be considered only if RAM pressure becomes measured.
  • Static topology: remains in ROM. A collision query reads maze_nav; only cells marked gate-affected consult the owning gate record and its orientation-specific footprint.

The runtime cost is 92 bytes before later entity state. This preserves the planned $A000-$BFFF game-state page and avoids copying either 576-byte map at boot.

Renderer boundary

Phase 3 should add a maze renderer, not expand put_char into a general game-state API. Its input is the immutable maze tables and its output is the centre 192×192 framebuffer region.

  1. For each row, set the destination to framebuffer byte offset row * 160 + 32.
  2. For each of 24 cells, resolve logical style plus current dot state to a graphic ID and blit 32 bytes.
  3. Advance 4 bytes between cells and 64 bytes after the final cell to reach the next framebuffer row start.
  4. Overlay the 20 gates from their initial orientation records.

Keep the existing single-tile routine for character output and correctness tests. The full-maze path may add a row-major fast path that carries its destination pointer instead of recomputing row * 160 + col * 4 576 times. It must retain the established rule that an LDD-loaded data register is not also a loop counter.

Authoring and generation workflow

scripts/capture_mame_maze.py now produces the immutable assets/arcade/maze_capture.bin and derived maze_capture.json provenance files. The next implementation step adds a semantic assets/arcade/maze.json source and a deterministic generator that emits an assembly include under build/. The source records dimensions, per-cell style and movement mask, dots, nest and perimeter flags, and the 20 gate definitions. The generator validates the invariants below and selects only referenced graphics.

scripts/update_tiled_maze.py converts all 720 rotated visible-sheet indices into Tiled GIDs and replaces layer 1 of tiled/black-and-whitte-screen.tmx. This map represents background RAM only; arcade sprites are not missing tiles.

The semantic source must be derived from the capture, not from the incomplete Tiled experiment or screenshot inference.

Exact maze source — resolved 2026-07-17

MAME 0.220 and the installed ladybug ROM now provide the authoritative start-state background. The capture helper samples $D000-$D7FF until it finds a stable complete-maze state. The accepted run is frames 2545–2558 with SHA-256 d8129bb9f57ce51b0355101115af7eab538b854d31771f6f51917fa072f686f3.

MAME's raw background is 32×32 tiles. Its visible raw rectangle is columns 1–30 and rows 4–27; applying the driver's ROT270 produces the 24×30 arcade display. The JSON records all visible nine-bit tile codes, colour attributes, indices for the whole-sheet counter-clockwise rotation, and the 24×24 CoCo crop. The binary file is the unchanged 2,048-byte RAM dump and remains the final provenance source. A screenshot validates orientation but does not define topology.

The 48-graphic figure is a planning ceiling, not a claimed arcade count. The generator must report actual unique styles, graphics, and ROM bytes. With the Phase 2.6 image at 557 bytes before padding, this ceiling leaves more than 12 KB of the 16 KB cartridge image before later phases, excluding new renderer code.

Validation gates

  • The raw capture is exactly 2,048 bytes and matches its recorded SHA-256.
  • The rotated display is exactly 30 rows × 24 cells; the CoCo crop is arcade rows 3–26 and is exactly 24×24.
  • Every semantic style and graphic reference is in range.
  • Exactly 20 gates; every gate footprint is inside the grid and maps only to cells marked gate-affected.
  • N/E/S/W movement is reciprocal between adjacent non-gate cells; no passable edge exits the grid.
  • Initial dot count is emitted and checked against the captured source.
  • Nest and perimeter-track cells form the captured connected regions.
  • Phase 3 validates the arcade initial state and each single-gate rotation. Before Phase 5 gate interaction is accepted, validate the no-isolated-region rule by exhaustive state checking or a documented structural proof.
  • Live gdb-mcp verification compares all 192 rendered rows, the 64-pixel side margins, palette/PAR state, halt PC, and reported ROM size.

Deferred

  • Logical-style count, dot classification, navigation masks, gate footprint shapes, and semantic cell topology still require derivation from the authoritative capture.
  • Animated entities and sprite/background restoration remain Phase 4.
  • Gate interaction and collision implementation remain Phase 5.
  • Per-frame full-maze rendering is not planned; Phase 3 will measure the one-time boot render for reference.
  • A gate-affected collision query may scan the 20 gate records initially. Add a generated cell-to-gate lookup only if Phase 5 measurements require it.
