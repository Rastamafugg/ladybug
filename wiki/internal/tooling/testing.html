Internal · testing

Testing and verification internal

A risk-directed test strategy, the routine build gates, and the current verifier inventory.

Approach

Ladybug uses layered checks around a bare-metal 6809 program. Python tools validate authored data, generate compact representations, and compare generated bytes against independent expectations. The normal build assembles the selected profile and rejects invalid artifacts or hard-boundary overruns. Focused verifiers cover ticket-specific behavior. XRoar with GDB-MCP observes the running ROM for natural sequences, controlled rare paths, visible output, and timing.

There is no single command that runs every verifier. Each ticket selects the smallest set that covers its distinct risks. A passing build proves that its build gates passed; it does not prove every gameplay path, natural transition, pixel result, timing target, audible output, or physical CoCo 3 behavior.

The Python build and oracles page defines source authorities and independent expected-result models. The build workflow documents artifact generation and emulator launch. The XRoar/GDB-MCP round trip describes the active runtime observation path.

Types of testing

  • Source and contract checks: inspect annotations, module ownership, profile selection, generated source references, data bounds, and declared producer/consumer relationships without requiring an emulator.
  • Generator and artifact-oracle checks: independently decode generated maps, pixels, sparse streams, payloads, loader tables, and manifests; compare identities, hashes, reconstructed bytes, and authored expectations.
  • Build and capacity checks: assemble and compose the selected ROM while enforcing resident, module, bank, destination, stack, and other declared hard boundaries. A successful assembly that exceeds a guard is a failure.
  • Runtime integration checks: boot the built ROM in XRoar, verify artifact identity before interpreting live symbols, then observe natural flows and force rare states only for the separate risk they cover.
  • Behavior and regression checks: exercise input ownership, movement, scoring, collisions, level and attract transitions, audio dispatch, framebuffer history, and neighboring behavior affected by a ticket.
  • Performance checks: measure complete worklists and named phases against the ticket’s cycle or deadline target. A probe timeout describes the observation boundary; it is not a cycle measurement.
  • Human acceptance: user-observed play or visual feedback is recorded against the launched artifact and the paths actually exercised. It supplements technical evidence and does not silently waive unmet project targets.

Static source checks, pixel comparisons, emulator behavior, measured performance, and user observations answer different questions. Tickets state which result is required and how a pass is decided.

Routine commands

scripts/build.sh build

This is the normal compile and artifact gate. It regenerates semantic and presentation data, assembles the runtime and boot modules, builds indexed sparse payloads and the loader plan, checks profile/layout contracts, proves capacity boundaries, composes the four-bank image, and runs build-integrated verifiers. The exact conditional set depends on the selected profile. In the complete profile, verify_shared_text.py checks shared text; other profiles use verify_presentation.py and run the FEAT-003 profile-isolation guard. The build runs verify_bug016_presentation_layers.py, verify_sparse_sprites.py, verify_gmc_overflow.py, verify_presentation_sparse.py, and verify_perimeter_allocation.py. Complete builds also generate and run the source-reference audit. These checks are part of the build contract.

scripts/build.sh verify-gmc

This command runs the full build first, then adds profile-specific verification. All profiles run the audio placement, entry-point, and loader-coverage check. The complete profile runs the FEAT-007 checkpoint, static, and refreshed runtime gates. Other profiles run dynamic-presentation checks; the high-score-test profile then follows its isolated startup and ranking path, while release and development follow the boot/resident, natural attract, forced gameplay/demo, and enemy-module checks. Required runtime phases have deadlines; a missing phase fails the verification.

Focused checks

Ticket verifiers are run directly when their acceptance contract requires them. Some are source or asset checks; others require a built ROM, XRoar, GDB-MCP, reference captures, or a specific profile. Use the ticket for exact prerequisites, forced states, phase markers, deadlines, expected visible output, and retained evidence. scripts/test_source_audit.py runs the standalone standard-library unit suite and is not called by the normal build.

How to interpret runtime evidence

  • Identify the exact source revision, profile, ROM hash, and relevant payload hashes. Before interpreting a live symbol or PC, prove that live bytes match the built artifact. When data is staged or copied, compare authored, staged, and destination bytes first.
  • Run the natural user-visible sequence from the delivered cold artifact. Add forced states for rare-path reachability or a distinct failure risk; a forced fixture does not replace natural startup, handoff, input pre-emption, or first visible output.
  • For persistent framebuffers, pair pixels with the metadata and owner history that produced them. Cover natural sequence behavior and isolated owners when those paths can differ. Do not infer an owner-specific timing cause without a controlled crossover.
  • State a marker and deadline for each runtime phase. A timeout is evidence about that probe boundary, not proof that game code is slow. Missing required coverage is incomplete or failed, never a pass.
  • Report behavior, pixel correctness, performance, capacity, diagnostic-tool validity, and physical-hardware results separately. XRoar execution is emulator evidence, not native CoCo 3 hardware acceptance.

Standalone source-audit unit tests

python3 scripts/test_source_audit.py runs 24 standard-library unit cases. They use temporary fixtures and do not start an emulator or mutate game state.

Relocation tests

  • test_current_binary_size_replaces_old_copied_length — confirms relocation length follows the current binary size as that file changes.

Operand and memory-overlap tests

  • test_width_and_address — checks operand width, byte offset, indirect/indexed access handling, expressions, and writes.
  • test_collision_and_permitted_sharing — rejects overlapping live ranges and allows sharing only across distinct mappings, phases, or justified aliases.

Source-contract tests

  • test_good_index_and_shifted_lines — accepts a valid annotated index and keeps its address/line data correct when source lines shift.
  • test_literal_index_rejected — rejects a literal that bypasses the declared generated index.
  • test_bounds_rejected — rejects a generated value outside its declared bounds.
  • test_missing_producer — rejects an annotation whose producer source is missing.
  • test_missing_consumer_annotation — rejects a declared index with no matching source consumer annotation.
  • test_missing_producer_function — rejects a producer file that lacks its declared function.
  • test_wrong_producer_symbol — rejects a producer that does not declare the expected symbol.
  • test_duplicate_identity — rejects duplicate contract identities.
  • test_generated_mirror_mismatch — rejects a generated mirror whose symbol identity differs from the source contract.
  • test_scratch_allocation_and_access_extent — accepts a matching scratch allocation and rejects over-extent access or a mismatched allocation size.
  • test_missing_required_record — rejects an absent required ownership record.
  • test_background_links_and_contract — accepts a complete background ownership contract and rejects dangling links or missing required fields.

Build-provenance tests

  • test_no_receipt — rejects a build with no provenance receipt.
  • test_unchanged — accepts a receipt whose inputs and artifacts still match.
  • test_stale_source_not_recertified — rejects source inputs changed after the recorded build.
  • test_changed_artifact — rejects a generated artifact whose bytes changed after the receipt.
  • test_unregistered_module — rejects a build invocation missing from the configured module inventory.
  • test_wrong_profile_mapping — rejects an invocation mapped to the wrong source identity.
  • test_wrong_conditional_profile — rejects invocation defines that disagree with the configured profile.
  • test_missing_output_hash — rejects a receipt missing required artifact provenance.
  • test_interrupted — rejects a receipt left in an incomplete build state.

Measurement and diagnostic tools

Capture scripts, benchmark programs, and diagnostic probes support test setup or explain observed behavior. They are not automatically pass/fail tests. A measurement becomes an acceptance check only when a ticket names its source artifact, scenario/worklist, target, and pass rule. For isolated processor comparisons, see 6309 benchmarks. For MAME capture tools and emulator controls, use the XRoar tooling page and the relevant ticket.

Keeping this inventory current

The catalog is a source-revision snapshot, not a claim that every listed verifier is part of the default build. When verifier entry points are added, removed, renamed, or change purpose, compare this list with top-level scripts/verify_*.py, scripts/test_*.py, and the command branches in scripts/build.sh. Update the build/focused labels from actual call sites and note the new source revision. Keep new scenario requirements and acceptance criteria in their canonical work ticket.
