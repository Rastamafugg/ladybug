Internal · diagnostic tooling

Cartridge-Window ROM Probe internal

A non-shipped ROM for checking bytes read through the CoCo 3 cartridge window.

Purpose and project status

src/rom_probe.s is a standalone diagnostic ROM. It reads the CPU-visible cartridge window and records bytes that differ from the probe's expected program and fill pattern. It is not gameplay code and is excluded from the shipped module set in scripts/source_reference.json. The standard scripts/build.sh game build assembles src/main.s; the probe requires a separate one-off assemble, 16 KiB padding, and emulator launch. See the build workflow.

Git history records the probe's addition on 2026-05-10 and a full-window scan update on 2026-05-12. The lessons-learned record documents an XRoar/GDB run on 2026-05-12. The exact command line and ROM hash for that historical run were not retained in the reviewed project records.

How the scan works

The source starts at $C000, sets the stack to $1FFE, and reads upward through $FEFF. The loop stops at $FF00, which is outside the cartridge read window. It does not write to the scanned cartridge window.

  • Bytes from $C000 up to the probe_code_end label are the probe's own executable code and are not compared.
  • The next $0100 bytes are assembled as $00; those addresses are expected to read as zero.
  • From probe_ff_start through $FEFF, the padded ROM is expected to read as $FF.

For each mismatch, the probe saves the observed address, expected byte, and actual byte in low RAM. At the end it loops forever at probe_done; it does not print a screen message or return to a menu. A debugger is used to inspect the results.

Fixed settings and output format

The source has no command-line parameters or runtime options. The scan bounds, expected fill pattern, and output addresses are assembly constants and labels:

  • org $C000: ROM entry and scan start.
  • $FF00: exclusive scan end; the final scanned address is $FEFF.
  • fill $00,$100: a 256-byte expected-zero region after the probe code; the remaining ROM padding is expected to be $FF.
  • $01FE: one-byte scratch field holding the expected value for the current mismatch.
  • $01FF: one-byte mismatch count. It increments for each record and has no overflow handling, so it wraps after 255.
  • $0200: start of the mismatch log. Each record is four bytes: address high, address low, expected byte, actual byte.

Output-capacity warning: the log pointer advances by four for every mismatch and the source has no record limit. It can overwrite unrelated low-RAM data. Record n begins at $0200 + 4 × (n − 1). The 41st record begins at $02A0; 50 records span $0200-$02C7. A zero count means no mismatches only when fewer than 256 were found, because the one-byte counter wraps. Do not interpret the output as safely bounded.

This output is produced by a separate diagnostic ROM, not concurrently with the game. Its overlap with a proposed game address still matters when assessing whether that address is globally unused or when running the probe itself.

Recorded project use

The May 12, 2026 investigation used a 16 KiB probe image padded with $FF, then inspected it in XRoar with GDB. The recorded full-window scan found 50 mismatches: the known $C0D9-$C0DB bytes, $C8B4-$C8BE reading $12 rather than $FF, and $E000-$E042 reading non-cartridge ROM bytes rather than $FF. A live snapshot showed the Tandy BASIC reset ROM had installed these bytes in RAM. The project conclusion was that these findings came from reset-ROM behavior, not an address-specific XRoar cartridge-reader defect. See the full evidence and reasoning in lessons learned.

The evidence records the result and method, but not the exact assembler invocation, complete ROM hash, or a retained dump of the probe's low-RAM result area. The 50-record output span above is therefore calculated from the recorded count and current four-byte record layout, not confirmed from a retained RAM dump.

Reproduction boundary

For a new run, use the documented one-off process: assemble src/rom_probe.s in WSL, pad its ROM image to 16 KiB with $FF, launch it in XRoar as a ROM cartridge, and inspect $01FF and the corresponding records beginning at $0200 through GDB. This is a procedure summary, not a copy-paste command; the historical exact command was not retained. Because the current source has no output cap, first use a separately bounded result destination or add an approved cap before running it where low-RAM contents must be preserved.

The probe is an investigation aid, not a routine game test. It should not be included in the normal cartridge build or treated as evidence about the current game ROM unless the probe source, padded ROM, emulator, and captured results are identified.
