6309 benchmark harnesses RSCH-003

Isolated 6809/HD6309 instruction measurements with host-side correctness checks and XRoar monitor evidence.

Purpose

scripts/benchmark_6309.py assembles and runs a portable 6809 baseline, the same baseline under the 6309 CPU model, and a 6309-only candidate ROM. It does not modify Ladybug production source, the runtime ABI, MMU ownership, or release ROM output.

The assembly source is src/bench/6309_benchmark.s. Baseline 6809 and baseline 6309 binaries must be byte-identical. The candidate build is expected to fail in 6809-only assembler mode.

Run command

wsl -d Ubuntu -- bash -lc 'cd /mnt/e/projects/ladybug && python3 scripts/benchmark_6309.py --timeout 10'

The command writes build/rsch003-6309/rsch003-6309-benchmark.json, plus ROM, listing, and map files for each variant. Every marker has the supplied timeout as its observation deadline. A timeout means that the requested emulator stop was not observed before that boundary.

Harness contract

  • TFM: 64-byte contiguous copy with source and destination guards.
  • LDQ/STQ: four-byte state copy with source and destination preservation.
  • OIM: masked byte update preserving the adjacent guard byte.
  • LDW/STW: 16-bit state transfer with both destination guards.

Each operation has separate start and end markers. The host oracle compares expected source and destination bytes, guard bytes, mask result, variant marker, and correctness across all three runs. Verification is intentionally host-side so the tested instruction window is not mixed with a subroutine oracle.

Measured result at RSCH-003 completion

Toolchain: lwtools 4.24 and the repository XRoar monitor build. Source revision hash: d1d2adbc01ebcee72cc086cc4b163e2b32d005f1ab222d7efd92be9f19156601. The following values are single-run XRoar cpu_cycles observations from the retained JSON; negative percentages are candidate reductions relative to the 6309 baseline, and positive percentages are regressions.

  • TFM: 282 candidate cycles versus 364,937 baseline cycles, measured delta −99.92%.
  • LDQ/STQ: 18 versus 40, delta −55.00%.
  • OIM: 7 versus 12, delta −41.67%.
  • LDW/STW: 14 versus 12, delta +16.67%; reject for production consideration on this measurement.

All correctness checks passed. The two baseline ROMs were byte-identical. Candidate assembly under lwasm -9 failed on the 6309-only instructions as required. The absolute TFM baseline is unusually large relative to the other isolated windows; treat the relative result as emulator evidence requiring a production-hotspot benchmark before adoption.

Non-applicable and rejected cases

  • Strided framebuffer rows: one TFM cannot express Ladybug’s 156-byte row stride without copying intervening bytes, so the contiguous result does not transfer to that renderer path.
  • PAR5 remap boundary: one TFM cannot preserve the loader’s mapping contract across an 8 KiB physical-page transition; remap and restore must remain explicit.
  • Separate production ROM: excluded from RSCH-003. A 6309-only release would require a new High-risk ticket covering distribution, loader assumptions, hardware qualification, and fallback behavior.

Recommendation

Keep the production source 6809-compatible. The corrected evidence supports no immediate production opcode change. LDQ/STQ is the strongest candidate for a later hotspot-specific implementation ticket, but its 6309 result remains a fixture measurement until exact production routines, alignment, register contracts, interrupt boundaries, and frame impact are tested. OIM remains limited to nibble-compatible merges; retain the existing merge path for mixed transparency. Do not pursue LDW/STW from the measured regression. RSCH-006 now reconciles the TFM XRoar evidence: the old 364937-cycle baseline is invalidated as a launch/marker-boundary artifact, while the repaired fixed and source-aligned controls are valid and repeatable. TFM remains a research candidate only; exact production worklists and frame impact still require evaluation. The earlier source/executable read_cycles mismatch hypothesis is not confirmed at the current revision.

RSCH-004 hot-path runner

src/bench/6309_hotpath_benchmark.s mirrors the eight-byte contiguous row work in save_player, restore_player, roam_capture_ring_row, and phase-zero roam_copy_bg_to_fb. It preserves the 152-byte outer stride, compares LDQ/STQ four-byte pairs, and tests OIM only for nibble-compatible merges. Mixed transparency is an explicit rejection case.

wsl -d Ubuntu -- bash -lc 'cd /mnt/e/projects/ladybug && python3 scripts/benchmark_6309_hotpaths.py --rows 1 2 4 8 16 --repeats 3 --timeout 5 --output build/bug024-6309'

The runner assembles 1/2/4/8/16-row variants and repeats each cold launch. It records event ticks, CPU cycles, marker addresses, source and ROM hashes, live execution marker, live benchmark window, guards, source preservation, repeatability, and normalized row slopes. It rejects constant or non-scaling LDQ/STQ evidence, waits for live ROM identity within the five-second deadline, and treats a timeout, stale marker, unexpected stop, live-window mismatch, non-scaling series, or repeatability failure as invalid evidence.

RSCH-004 also adds read_cycles to the tracked XRoar monitor source. The source-aligned runner passes both CPU variants and all correctness checks. TFM and OIM are measured candidates for later hotspot-specific work; the 11,119-cycle LDQ/STQ result is a repeatable XRoar outlier and is rejected for production decisions. Native-mode entry was tested separately and remains unqualified.

RSCH-005 LDQ/STQ diagnosis

src/bench/6309_ldq_stq_timing.s and scripts/benchmark_6309_ldq_stq_timing.py isolate one boundary NOP, one LDQ, one STQ, one LDQ/STQ pair, and the equivalent four-byte copy. Each case is assembled into its own cold ROM so setup and loop control cannot enter the measured window.

wsl -d Ubuntu -- bash -lc 'cd /mnt/e/projects/ladybug && python3 scripts/benchmark_6309_ldq_stq_timing.py --repeats 3 --timeout 5 --output build/rsch005-6309'

Three identical samples measured 2 cycles for the boundary NOP, 8 for LDQ, 8 for STQ, 16 for the pair, and 38 for the byte-equivalent copy under both the 6309 and 6809 control. BUG-024 corrected the RSCH-004 row loop to use a direct-memory counter; its source proof is now accepted and the unchanged controls pass. The original 11119-cycle value was not an XRoar instruction-timing defect: RSCH-004 loaded Q_ROWS into B, then executed LDQ before DECB, so copied data controlled unintended extra iterations. LDQ/STQ remains research evidence only; no production opcode or separate ROM is authorized by this result.

Potential 6309 optimizations after correction

  • LDQ/STQ — investigate next: the corrected source-aligned sweep measures candidate medians 74/134/254/494/974 cycles for 1/2/4/8/16 rows versus baseline 118/222/430/846/1678. Both series have zero normalized slope spread; candidate slope is 60 cycles per row versus baseline 104. This establishes a valid benchmark result, not a production speedup claim.
  • OIM — constrained candidate: retain only for masks that do not alter the opposite destination nibble. Mixed-transparency cases must continue to use the existing merge logic.
  • TFM — repaired measurement: RSCH-006 records a 2-cycle/32-event-tick NOP boundary, fixed 8-byte medians of 103 baseline versus 41 candidate cycles, and source-aligned medians of 126/243/477/945/1881 versus 64/119/229/449/889. Three samples per case were identical, startup identity passed on the first attempt, and every event-tick delta was exactly 16 times its CPU-cycle delta. The old 364937-cycle baseline is rejected as launch/marker-boundary contamination. TFM remains research-only until exact production worklists and frame impact are measured.
  • LDW/STW — reject: the measured candidate regressed and has no current implementation case.
  • Separate ROM builds — defer: no separate 6309 ROM is justified. A production 6309 path would require a new High-risk ticket covering distribution, loader assumptions, fallback behavior, hardware qualification, capacity, and runtime selection.

Remaining evaluation gates

  1. Benchmark LDQ/STQ and TFM against the exact production save-under and roaming routines, including alignment, stride, source preservation, register/ABI, interrupt, and framebuffer ownership contracts.
  2. Translate candidate savings into complete-frame and named-worklist impact under the real phase sequence; isolated row slopes are insufficient.
  3. Keep production source 6809-compatible until a separate approved implementation ticket passes correctness, capacity, native-hardware, and 6809 regression gates.

RSCH-006 TFM timing reconciliation

scripts/benchmark_6309_tfm_timing.py and src/bench/6309_tfm_timing.s use an explicit entry synchronization, then poll the C000 prefix and 64-byte benchmark window before installing timing breakpoints. The fixed controls are a single NOP boundary and one 8-byte transfer; the source-aligned control models eight visible bytes per row with the 152-byte Ladybug stride. The command is wsl -d Ubuntu -- bash -lc 'cd /mnt/e/projects/ladybug && make -C docs/reference/xroar -j2 && python3 scripts/benchmark_6309_tfm_timing.py --rows 1 2 4 8 16 --repeats 3 --timeout 5 --output build/rsch006-tfm'.

The monitor method remains read_cycles with integer event_ticks and cpu_cycles, using event_ticks / 16 as the exposed conversion and marker-to-marker deltas for measurement. Current monitor source and executable identity are retained in the evidence JSON. All current controls pass correctness, guard preservation, event-tick conversion, and repeatability; no production, ROM, native-mode, hardware, or separate-ROM behavior changed.

RSCH-007 exact production-shape result

The exact one-sided-stride controls replace the earlier proxy baseline. Three identical cold samples show TFM reductions of 288 cycles for player save, player restore, phase-zero restore, and split phase-zero restore; 480 cycles for roaming full capture; and 36 cycles for a two-row vertical capture. Phase-four restore favors LDQ/STQ by 336 cycles. Odd phase one remains non-applicable. Correctness, guards, source preservation, final required pointers, owner-local storage, FRONT preservation, event/cycle conversion, portable baseline byte identity, and 6809 candidate rejection pass.

BUG-026 rejects incompatible profile artifacts before launch and proves complete-profile requests 0/3/2 through first frame_render_impl. BUG-027’s static dual-exit proof remains valid, but Done BUG-028 rejects its abort-exit explanation for the timeout. Natural frame zero and hydration frame one reached normal RTS. Hydration frame two began with 50,917 ms remaining; at recovery, XRoar was already halted at configured restore_player=$D612/ID 26 while the primary still waited. Breakpoint inventory, live bytes, and FRONT preservation pass. XRoar source documents a compatible nonblocking subscriber-event drop path; a later approved runner repair should evaluate stateful wait_for_stop rather than relying solely on breakpoint notifications. Invocation counts, frame projections, and the 1,000-cycle/5% materiality gate remain unresolved. RSCH-007, BUG-026, and BUG-027 remain Blocked. Production remains 6809-compatible and separate 6309 ROMs remain deferred.
