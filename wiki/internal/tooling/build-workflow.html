Internal · tooling

Build & deploy runbook internal

End-to-end: source → ROM → emulator. Driven by scripts/build.sh; every step is also documented as a manual command.

Active workflow 2026-07-19: use this build path and gdb-mcp for automated execution checks. The web app and patched -monitor stack are preserved but deferred.

For the distinction between authored inputs, Python generators, independent oracles, verifiers, and delivered ROM artifacts, see Python build and oracles.

One-command interface

scripts/build.sh is the entry point. Run from anywhere — it routes to WSL automatically when invoked from the Windows host.

An unset LADYBUG_PROFILE selects highscore-test. Explicit release, development, and complete retain their prior ownership; complete stages both instruction and demo auxiliaries with phase-swapped use of $0300.

Defaults are 10/10/10/20/10 seconds. For startup-only diagnosis, run python3 scripts/verify_gmc_boot.py --startup-only. The loader handoff uses XRoar trace evidence to avoid a one-shot breakpoint race; resident startup stops at the repeating $1900 boundary and compares all 15,872 resident bytes exactly. The full verifier checks bank signatures, generated source-bank selections including bank 0, the bank-0 proof copy, boot-only pages $21/$22, bank-3 low-RAM copy, bank-1 staging and all-RAM publication, sparse framebuffer/stage decoders, repeated main-loop execution, and enemy-module contracts. Assembly source-reference generation

DOC-002 adds a read-only documentation stage after a passing assembly build. Hand-authored wiki pages remain the semantic authority. The generated browser under build/source-reference/ binds source lines, assembled addresses, emitted bytes, symbols, routines, delivery identities, and evidence states to current artifact hashes. 

python3 scripts/build_source_reference.py \
  --config scripts/source_reference.json \
  --output build/source-reference

python3 scripts/verify_source_documentation.py \
  --config scripts/source_reference.json \
  --wiki-root wiki \
  --generated-root build/source-reference \
  --all

A dirty workspace may use explicit --source-root and --artifact-root paths from a detached canonical build. This prevents documentation work from overwriting retained failure evidence. The configuration records profile-inactive authored modules as source-only; their lines remain visible while emitted addresses and representation evidence remain explicitly absent until that profile is assembled.

The reusable proof is python3 scripts/verify_source_documentation.py --fixture scripts/fixtures/source-reference/project.json --generated-root build/source-reference-fixture --all. Add --mutation-suite to require all nine independent rejections: missing routine, symbol, memory owner, scenario evidence, or required scenario; stale revision; materially changed listing or map; and broken link. The generated manifest also records each intentionally omitted source path and its reason.

Manual equivalents

1. Assemble

mkdir -p build
python3 scripts/derive_maze.py
python3 scripts/build_screen.py \
  --map tiled/coco-screen.tmx \
  --maze assets/arcade/maze.json \
  --chars assets/arcade/chars.json \
  --sprites assets/arcade/sprites.json \
  --output build/ladybug_screen.inc \
  --resident-output build/ladybug_resident.inc \
  --gate-output build/ladybug-gate-transitions.bin \
  --presentation-output build/ladybug-presentation-sparse.bin
lwasm -9 --format=raw \
      --output=build/ladybug.rom \
      --list=build/ladybug.lst \
      --symbols \
      --map=build/ladybug.map \
      -I build \
      src/main.s

The canonical script then reads resident_end, asset_start, and asset_end from the lwasm map. It rejects resident code beyond $E000, an asset start other than $E000, assets beyond $FE00, or a raw-file length inconsistent with asset_end-$C000. A successful current integrated build reports resident 8190/8192 and assets 7144/7680 before padding. The copied bank-3 module reports 4089/4096; its fixed jump table includes direct sparse player draw plus framebuffer/stage decoders. The approved module copy spans $0800-$17FF; a shared actor stage occupies $1800-$18FF, with the copied presentation module at $1900-$1DFF and the stack reserved at $1E00-$1FFF. Generated enemy streams occupy physical pages $35-$37; player, gate, and popup presentation streams share page $39.

After assembling the enemy module, phase 1 also runs build_sparse_sprites.py and verify_sparse_sprites.py. The outputs are ladybug-enemy-sparse.bin, ladybug-player-sparse.bin, ladybug-gate-transitions.bin, ladybug-presentation-sparse.bin, ladybug-sparse-bank2.bin, ladybug-sparse-bank3.bin, ladybug-gmc-bank0-overflow.bin, ladybug-sparse-loader.inc, and ladybug-sparse-layout.json. The proof decodes every frame, checks physical-page containment and signatures, excludes inaccessible GMC offsets $3E00-$3FFF, and reconstructs all physical payloads from all ten copy records. A separate boundary proof fills the exact source capacity across banks 2, 3, and 0 and requires one additional byte to fail. The generated banks and loader are the delivered path, with 14,731 CPU-readable source bytes spare. The loader keeps enemy/player indexes at the start of their loaded sparse pages, $35:$A000 and $39:$A000, so their copies cannot overlap the relocated loader before handoff.

2. Pad source banks to 16 KB and compose the 64 KB GMC image

python3 -c "
data = open('build/ladybug.rom','rb').read()
pad  = 16384 - len(data)
assert pad >= 0, f'ROM is {len(data)} bytes — exceeds 16 KB'
open('build/ladybug.rom','wb').write(data + b'\xff'*pad)
print(f'padded {16384-pad} → 16384 bytes')
"

3. Run

xroar -machine coco3 -ram 512 \
      -ram-init random \
      -cart-type gmc \
      -cart-rom build/ladybug.rom \
      -cart-autorun \
      -tv-input rgb \
      -joy-right kjoy0

-tv-input rgb selects the GIME's digital RGB output (canonical RGBrgb 2-bit-per-channel mapping). XRoar's default is composite NTSC, which aliases several 6-bit palette codes. See xroar and lessons-learned §"XRoar RGB monitor palette mapping".

MAME 0.220 GMC launch

From the repository root in WSL, use the GMC slot explicitly and ask Color BASIC to enter the cartridge payload at $C002: 

mame coco3 \
      -ext games_master \
      -cart build/ladybug.rom \
      -autoboot_delay 1 \
      -autoboot_command 'EXEC &HC002\n'

This is the deterministic MAME 0.220 launch command for Ladybug. The games_master extension supplies the four-bank GMC mapper; plain -cart does not select that hardware. The ROM begins with the expected DK signature at $C000, while executable bootstrap code begins at $C002.

This command is a BASIC-mediated entry fallback, not proof that MAME reproduced the physical CART/FIRQ auto-start handshake. On local MAME 0.220, the GMC Cart Auto-Start field read as on and the mapped bytes at $C000 read 44 4B, but an unassisted launch remained in BASIC. The command above left BASIC and entered the Ladybug display path within four emulated seconds. Do not combine this launch check with -autoboot_script on this version: the observed script invocation suppressed -autoboot_command. Use a separate MAME plugin, debugger session, or video capture for observation.

Current-image limitation: Ladybug selects GMC banks at even SCS address $FF50. MAME 0.220's GMC model accepts its bank register only at $FF40 and its PSG only at $FF41. Under the command above, the unmodified image enters the bootstrap but fails its bank-signature checks and leaves a striped, corrupted display. A controlled ROM changing only the five bootstrap STA $FF50 operands to STA $FF40 produced a coherent Ladybug high-score screen under the same four-emulated-second deadline. Until the SCS-address compatibility decision is resolved, this MAME command proves cartridge mapping and entry only; it is not a valid BUG-008 gameplay/framebuffer verifier for the shipped image.

Cross-platform invocation

If PowerShell wsl.exe works, a Windows-side session can launch the normal run flow with: 

wsl -d Ubuntu -- bash -lc 'cd /mnt/d/retro/ladybug && ./scripts/build.sh run'

Inside WSL, paths to the project work via /mnt/d/retro/ladybug.

If PowerShell reports no WSL distributions, do not conclude that runtime launch is impossible. Use the GDB-MCP-hosted Linux shell instead: 

shell cd /mnt/d/retro/ladybug && ./scripts/build.sh build
shell cd /mnt/d/retro/ladybug && nohup /usr/local/bin/xroar -machine coco3 -ram 512 -ram-init random -cart-type gmc -cart-rom build/ladybug.rom -cart-autorun -joy-right kjoy0 -gdb -gdb-ip 127.0.0.1 -gdb-port 65520 > /tmp/ladybug-xroar.log 2>&1 & echo $!

Then start a fresh GDB-MCP session and attach with:

target remote :65520

Probe ROM variant

scripts/build.sh always builds src/main.s into build/ladybug.rom. To run a one-off diagnostic source such as src/rom_probe.s, use the same WSL-hosted assemble, pad, and xroar sequence with the input and output names changed.

If XRoar runs on Windows and gdb-mcp runs under WSL, use -gdb-ip 0.0.0.0 instead of 127.0.0.1.

Reproducibility artifacts

The reproducibility authority is the committed source tree, the selected LADYBUG_PROFILE, the build and verification scripts, and the identified assembler/XRoar toolchain. The repository-wide /build directory is disposable and ignored by default; it contains generated ROMs, binaries, maps, listings, manifests, loader tables, and verifier evidence. Recreate it with the profile-specific build command before running a verifier.

Historical generated files that are already tracked under build/ are legacy snapshots, not the canonical build result. Do not update or add individual generated files there. A tracked reproducibility bundle is permitted only under a dedicated path outside build/, with one exact profile and source revision per bundle. It must contain the deliverable ROM, every non-regenerable or profile-specific payload required to interpret it, the relevant maps and manifests, a provenance record containing the source revision, profile, build command, assembler/toolchain identity, and a complete SHA-256 file.

Listing-only changes, mixed-profile outputs, partial auxiliary payloads, and evidence copied from an unrecorded dirty tree are not reproducibility artifacts. Natural XRoar evidence is normally retained as a concise ticket record and an ignored JSON capture; it is promoted into a tracked bundle only when later inspection or independent reproduction is an explicit acceptance requirement.

When this runbook breaks

  • lwasm: command not found — WSL ~/coco-tools/lwtools not built/installed. Reinstall: cd ~/coco-tools/lwtools && make && sudo make install.
  • xroar: command not found — same pattern under ~/coco-tools/xroar; check its INSTALL for SDL/GTK build deps.
  • build: resident region ends... / build: asset region ends... — one guarded runtime-bank region overflowed before final padding. Move new payloads into GMC expansion banks or revise the loader contract documented in platform/cartridge.
  • No xroar window from Windows host — WSLg should hand off automatically on Win 11. Test with wsl -d Ubuntu -- bash -lc "xeyes" to confirm GUI passthrough; if blank, restart WSL: wsl --shutdown.
  • xroar boots to BASIC OK prompt instead of our cart — -cart-autorun missing, or our JMP at $C000 isn't where BASIC's FIRQ handler expects (see boot handshake in platform/cartridge).

See also: lwtools, xroar, toolshed; platform/cartridge — boot handshake; memory map — cart window placement.
