What the commands do

scripts/ladybug.py gives the build, artifact validation, manual launch and bounded read-only observation one interface. Run production commands with WSL Python 3.8 or later. There is no MCP result serializer, PowerShell data transport, copied attempt-specific launcher, or model-administered runtime clock in this path. Existing scripts/build.sh remains the assembler/packager and retains all its guards.

A build description (build.json) identifies the profile, source snapshot, original revision, tool versions, artifact sizes/hashes and emitted symbols. Relative paths resolve from that description's directory. Move the complete bundle to move a build; source listings can retain historical absolute text, but locating artifacts never depends on that text. Validation records its own checker and policy hashes separately from the ROM's build identity. Editing today's checker or main worktree does not invent a new build or invalidate an intact archived ROM.

Commands

These are usage examples, not game-run acceptance evidence. Replace the returned paths below with paths printed by your operation. Global --root and --runs options precede the operation. No command implicitly runs another game scenario or retries.

# Record actual executable paths, versions, hashes and 6809 debugger capability.
python3 -B scripts/ladybug.py doctor

# Doctor --scope build or --scope runtime can qualify only the needed tools.
# Build each profile into its own fresh source/output bundle.
python3 -B scripts/ladybug.py build --profile keyboard-adaptive --environment /path/from/doctor/environment.json
python3 -B scripts/ladybug.py build --profile joystick-adaptive --environment /path/from/doctor/environment.json
python3 -B scripts/ladybug.py build --profile keyboard-nonadaptive --environment /path/from/doctor/environment.json

# Optional: qualify retained sources without editing that source tree.
python3 -B scripts/ladybug.py build --profile keyboard-adaptive --inputs /path/to/retained/candidate-src --environment /path/from/doctor/environment.json

# Verify one build's recorded artifacts and the initial explicit capacity policy.
python3 -B scripts/ladybug.py validate --description /path/from/build/build.json

# Launch that ROM in RGB for a user-owned session, with no session time limit.
python3 -B scripts/ladybug.py launch --description /path/from/build/build.json --environment /path/from/doctor/environment.json

# Observe one named read-only startup scenario, maximum 60 seconds.
python3 -B scripts/ladybug.py observe --description /path/from/build/build.json --environment /path/from/doctor/environment.json --scenario scripts/engineering/scenarios/resident-entry.json

# Inventory every top-level verifier without executing it.
python3 -B scripts/ladybug.py audit

# Offline qualification: fake tools and temporary fixtures, no game execution.
python3 -B scripts/test_engineering.py

From Windows, invoke WSL explicitly, for example wsl -e bash -lc 'cd /mnt/e/projects/ladybug && python3 -B scripts/ladybug.py doctor'. The debugger path is selected by doctor --debugger, never by a parameter describing a program being debugged. Doctor checks versions and selecting the m6809 architecture; it does not certify a live stub, hardware watchpoints or input delivery.

Isolation, identities and deadlines

The runner allocates a unique directory beneath repro/engineering/. Builds copy only authored src/, scripts/, assets/, tiled/ and authored wiki HTML, excluding wiki evidence and bytecode caches. They do not copy old build outputs. Source and wiki hashes before/after copying must match. Each copied source root retains the legacy conventional build/ path. This deliberately contains alternate-directory assumptions without patching existing dirty scripts. Build runs must be beneath the project, outside authored input directories, so legacy Git revision discovery can still find the originating repository.

TOOL-016 writes the snapshot's LF-only checksum manifest. Other generated JSON and GDB files use explicit UTF-8/LF bytes. No normalization is applied to historical packages or authored files. TOOL-017 remains separate. Source snapshots are conservative rather than an unproven minimal dependency closure; no incremental compilation or shorter build-time claim is made.

One detached supervisor owns each automated job's process group, monotonic deadline, log and result.json. Closing the controller pipe, including controller death, triggers cleanup. Build's default and maximum job bound is 600 seconds, covering source copying, legacy construction and description collection together. Validation's default/maximum is 60 seconds. Observe takes a scenario bound of at most 60 seconds, including its reads and child cleanup. A small cleanup reserve lies inside the worker deadline. The caller allows bounded host-handshake overhead and reports it separately; it never labels extra host time as a game timing result. Doctor uses at most five five-second tool jobs. No ports, emulator instances or manual sessions are used by offline qualification.

Manual launch verifies the ROM and tool identities, writes its launch record, and replaces the launcher process with XRoar. The user owns the session, without a test timer or acceptance claim. No game is built automatically. Automated runtime jobs use an explicit GDB executable and a fresh owned loopback listener; ownership is checked from Linux socket descriptors without making a probe connection to the stub.

Normal deadline, cancellation, process-exit and controller-loss cases are covered by fixtures. No software can guarantee cleanup or result persistence if the OS/disk fails, the supervisor itself is forcibly killed, or a process remains uninterruptible in the kernel. Cleanup failure is an explicit outcome, not a pass.

What validation and observation prove

The initial capacity policy preserves the existing complete-profile limits: presentation module 1,280 bytes; perimeter-reset helper 334; High Score runtime 920; cold payload 16,384; ROM exactly 65,536. Those are policy maxima/exact size, not values inferred from the generated files. Other loader/stack/mapping/packing and behavioral checks remain in the legacy build and approved test cards. This validator does not replace the complete existing acceptance suite.

Full validation hashes only artifacts explicitly recorded in this bundle, so sibling profile outputs do not contaminate it. Manual launch hashes the ROM; observation hashes the ROM plus its scenario's code/map artifacts. It does not repeat a whole source-tree inventory during a short runtime window. Parsed symbol records are checked against their hashed map before use. The scenario binds an artifact/map/symbol, image origin, expected physical pages and bounded read ranges. The emitted debugger commands check the stopped PC, masked page values and actual code bytes before dumping declared data. It sends no guest-memory/register writes, remapping, reset, keyboard input or private-monitor command.

resident-entry is a repeating presentation-entry observation. It does not diagnose the menu flicker or qualify either framebuffer's displayed menu selection. Future scenarios require their own stated purpose and controlled fixture/card; this generic runner is not blanket runtime authority.

Results and migration

Results distinguish passed (the named operation), observed (a byte-qualified capture), command_failed (child exit status), product_failure (an explicit capacity assertion), harness_failure, timeout, cancelled, cleanup_failure and incomplete. No result sets release acceptance true. The construction summary separately reports ROM existence and recognized source-documentation success/failure; absence of a known marker is not_established. Legacy source-documentation failure still makes the build command fail, even if it produced a ROM.

The current gate-purpose inventory retains every top-level verifier's source identity, module purpose, prior catalogue description, recurrence recommendation and coupling flags. Flags are explicitly heuristic review aids. No existing approved gate is retired or newly authorized by that inventory. Source-text/label-order predicates and legacy monitor consumers remain migration work; replace them only against independent good/broken fixtures and their approved behavior contract. PROFILE-FIT qualification is relevant when its checker, limit or fixture changes, or valid evidence is absent; actual artifact size remains checked for every produced build.

First migration slice: artifact identity and capacity now have source-format-independent validation. The source/map readers, frozen-source practice, build receipt semantics and checksum writer are reused. Wholesale verifier rewriting and a project-independent framework were rejected. TOOL-014 remains broader design work; TOOL-009's legacy alternate-root problem is contained by isolated conventional build roots rather than declared fixed globally.

Qualified initial integration and current limitations

Completion evidence records 31 offline cases, a real retained-source build in 402.42 seconds, final validation in 2.12 seconds and live startup in 4.02 seconds. The ROM matches its prior 64 KiB positive control exactly. A separate current-E build failed on a High Score colour override targeting a non-text cell; that game-data failure was correctly retained and downstream dispatch stopped. The harness does not fix or adopt game source as a side effect.

build --inputs selects a read-only authored tree to copy, with outputs still allocated in the execution project's ignored run root. source_origin identifies the selected tree. The recorded Git revision is the enclosing execution repository HEAD, not an inferred original commit for an imported historical candidate; exact snapshot hashes identify the actual contents.

GDB uses fixed validated relative dump filenames in its explicit run directory because the tested native dump parser treated quoted absolute filenames literally. Doctor's target-free write of byte 0x5A qualifies that mechanism before target dispatch. The scenario hash fingerprints the normalized execution JSON copy; source-file whitespace has a separate byte identity and must not be compared blindly to that normalized hash.

The first presentation-entry breakpoint occurs before presentation initialization. The shipped resident-entry scenario therefore captures no menu-state bytes and makes no claim that Attract is initialized or visible. Menu and framebuffer scenarios require an appropriate later phase and their own data expectations. The existing 75 gates remain inventoried, not globally migrated or certified; continue semantic migration using their relevant cards. Historical implementation records saying integration was pending are superseded by the completion record.

The observer seeds its counter, proves a visible Attract baseline, then disables publication stops while the user supplies one normal Down press. A release must be observed before held-input anomalies become product conclusions. Two repainted owners and one follow-up per owner complete machine coverage.
