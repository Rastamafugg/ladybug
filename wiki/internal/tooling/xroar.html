XRoar — CoCo 3 emulator internal

By Ciaran Anscomb. Installed at /usr/local/bin/xroar. Version: 1.10. Reference: xroar.shtml.

XRoar emulates the GIME, MMU, PIAs, ACVC IRQs, and the cartridge port — everything the boot sequence in platform/cartridge depends on.

Canonical invocation (Ladybug cart)

xroar \
  -machine coco3 \
  -ram 512 \
  -cart-type gmc \
  -cart-rom build/ladybug.rom \
  -cart-autorun \
  -tv-input rgb
FlagWhy
-machine coco3NTSC CoCo 3, 1.78 MHz fast clock available, GIME present.
-ram 512512 KB — matches our target hardware spec.
-cart-type gmcGame Master Cartridge banking: writes to an even SCS address select a 16 KB bank. Ladybug uses $FF50.
-cart-rom FILEPath to the 64 KB four-bank ROM image.
-cart-autorunTriggers the CART → FIRQ handshake on startup so BASIC dispatches into our JMP entry at $C000.
-tv-input rgbDecode the GIME's digital RGB output directly. XRoar's default is composite NTSC, which aliases several palette codes. Empirical RGB-mode 6-bit→colour table in lessons-learned §"XRoar RGB monitor palette mapping".

Automated banking proof: scripts/build.sh verify-gmc uses XRoar's instruction trace to prove bank-2 and bank-3 reads, selection and copying of bank 1, the all-RAM handoff, and execution of the relocated runtime main loop.

Attract-flow timing constraint: when a presentation module owns the initial Vbord sequence, scripts/verify_gmc_boot.py uses two phases. The natural trace proves loader, MMU, presentation entry, frame ownership, and normal attract-flow evidence. A separate GDB-stub phase stops at $1900, patches CPU-visible presentation state to an expired live level, and requires actor restore, damage queue/projection, both sparse decoders, actor draw, and four alternating Vbord commits. A missing required phase fails verification; increasing the natural trace timeout is not a substitute for forced rare-path coverage.

Sound-cartridge emulation status

  • GMC SN76489: implemented and already active. XRoar's gmc part contains a 4 MHz SN76489 and connects it to cartridge audio. Even SCS writes select the ROM bank; odd SCS writes program the sound chip. The current invocation therefore needs no MPI or additional option for GMC sound.
  • Multi-Pak: implemented. Define named cartridge profiles, make mpi the machine cartridge, populate slots with -mpi-load-cart SLOT=NAME, and choose the boot slot with -mpi-slot. XRoar models independent CTS/CART and SCS routing through $FF7F.
  • Tandy Speech/Sound Cartridge: not implemented as an XRoar cartridge type. A full model needs the TMS7040 firmware, 2 K RAM, existing AY891x synthesis, SP0256 speech, status/timing at $FF7D-$FF7E, serialization, and audio attachment. A Ladybug-only compatibility model can omit speech and interpret the documented buffered sound command protocol directly.
  • SuperSprite FM+: not implemented as an XRoar cartridge type. A sound-only model needs MPI-mode registers $FF56-$FF57 for YM2413 and $FF5C-$FF5D for YM2149. XRoar already has an AY891x core but no YM2413 part. Full-board fidelity additionally requires the V9958, 128 K VRAM, video switching, NMI, and alternate native $FF7x decode.

MAME's BSD-licensed coco_ssc.cpp and dragon_msx2.cpp provide primary reference implementations for both missing devices. The lowest-risk progression is GMC sound first, then a sound-only SuperSprite or Speech/Sound compatibility part only if real-hardware backend testing still requires it.

MPI configuration shape for future named devices:

xroar -machine coco3 -ram 512 \
  -cart ladybug -cart-type gmc -cart-rom build/ladybug.rom -cart-autorun \
  -cart external-sound -cart-type DEVICE_TYPE \
  -cart mpi -mpi-load-cart 0=external-sound -mpi-load-cart 1=ladybug \
  -mpi-slot 1 -machine-cart mpi -tv-input rgb

Placing the sound cartridge before the GMC also works around the current MPI sound-interface attachment rule, which attaches the first sound-capable slot to XRoar's single cartridge-audio callback. After bootstrap, Ladybug would write $10 to $FF7F to retain CTS/CART on slot 1 and route SCS to slot 0. A Speech/Sound model at $FF7D-$FF7E is broadcast outside SCS and does not require that final SCS route.

GDB-MCP round trip — active workflow

Use this workflow for automated Ladybug execution checks. The web app and private XRoar monitor are deferred.

1. Build the cartridge

cd /mnt/d/retro/ladybug
./scripts/build.sh build

2. Start XRoar with the GDB stub

There are three launch contexts to keep separate:

  • PowerShell sandbox — may report that no WSL distributions are installed.
  • GDB-MCP Linux host — the already-running gdb-mcp process can run Linux shell commands through GDB's shell command.
  • Windows desktop XRoar — useful for manual visual runs.

Preferred Codex path: start XRoar from a GDB-MCP session using GDB's shell command:

shell cd /mnt/d/retro/ladybug && nohup /usr/local/bin/xroar -machine coco3 -ram 512 -cart-type gmc -cart-rom build/ladybug.rom -cart-autorun -gdb -gdb-ip 127.0.0.1 -gdb-port 65520 > /tmp/ladybug-xroar.log 2>&1 & echo $!

Then attach from a fresh GDB-MCP session with target remote :65520.

If XRoar is launched on Windows and gdb-mcp runs under its Linux host, bind the stub to all interfaces (-gdb-ip 0.0.0.0).

3. Attach through GDB-MCP

The Codex MCP config starts gdb-mcp through WSL. gdb should resolve to the 6809 GDB:

/home/rastamafugg/.local/bin/gdb -> /usr/local/bin/m6809-gdb

Start a GDB-MCP session, then run:

show architecture
target remote :65520

Expected: The target architecture is set to "auto" (currently "m6809").

Useful first commands: info registers, x/8i $pc, x/16xb $pc.

Reaching specific boot points reliably

The cart-autorun handshake fires on a 100 ms cart-FIRQ schedule and is gated by BASIC's keyboard-polling latency, so several wall-clock seconds elapse before our cart entry at $C000 runs. That clashes with gdb-mcp's default 30 s per-command timeout. Three workarounds:

1. Bump per-command timeouts

Pass timeout: 60 (or higher) explicitly on mcp__gdb-mcp__continue_exec and mcp__gdb-mcp__exec_command calls.

2. Insert a temporary halt loop in source

Software breakpoints set via break *0xC0xx are unreliable during early boot. The cheapest deterministic-stop pattern is a self-branch:

inspect_halt
        bra     inspect_halt    ; gdb-mcp attaches; PC parks here

Do NOT use swi for this purpose. Empirically, XRoar 1.10 segfaults when it tries to snapshot at a swi trap point (see backlog/cart-ram-corruption). bra . is safer.

3. Snapshot a stable boot state, then re-launch from it

XRoar supports save/restore via -trap, -trap-snap, and -load:

xroar -machine coco3 -ram 512 \
      -cart ladybug -cart-type rom -cart-rom build/ladybug.rom -cart-autorun \
      -trap 0xC096 \
      -trap-snap /tmp/ladybug-phase26.sna \
      -trap-timeout 1

At the current phase26_halt symbol ($C096 in the 2026-07-17 build), XRoar writes a snapshot and exits. Recheck build/ladybug.map after source changes. Subsequent debug sessions skip the autorun entirely:

xroar -machine coco3 -ram 512 \
      -cart ladybug -cart-type rom -cart-rom build/ladybug.rom \
      -load /tmp/ladybug-phase26.sna \
      -gdb -gdb-ip 127.0.0.1 -gdb-port 65520

Note: snapshots are tied to the ROM image. Rebuild the ROM → re-capture the snapshot.

Limits of the current GDB-stub workflow

XRoar's gdb stub exposes the CPU view: registers, memory, breakpoints, single-step. It does not expose:

  • GIME internal state. MC3, MMUEN, mmu_bank[], TR, S, RAS are not memory-mapped readable. Use sentinel probes through $FExx.
  • Cycle-level stepping. GDB-stub step is per-instruction.
  • Video / palette state. Not addressable through CPU memory.

Concrete inspection of GIME state is the largest current gap; if it becomes a blocker, see backlog/mcp-xroar-server for the implemented private monitor and the still-missing outward MCP bridge. Both are deferred; see xroar-monitor and MCP bridge backlog.

Reverse execution / record full — not viable on this stack

Probed 2026-05-15. gdb's record full does not work for the m6809 + XRoar stack, and the failure is in two independent layers — both would have to be addressed to fix it:

  • gdb side. record full refuses to start with Process record: the current architecture doesn't support record function. m6809 is not in gdb's list of architectures with a record-mode implementation.
  • stub side. reverse-stepi and reverse-continue return Target remote does not support this command. XRoar's stub doesn't speak the reverse-protocol packets.

Forward stepping (stepi) works as expected.

Iteration workflow

scripts/build.sh run builds the ROM and launches xroar with the canonical invocation above. To kill: close the xroar window or Ctrl-C the script.

Known XRoar 1.10 limitations

  • -load <snapshot> + -gdb together fails to bind the gdb listener. XRoar logs [gdb] WARNING: bind 127.0.0.1:PORT failed. Root cause: gdb_interface_new runs twice when -load is given and the listening socket lacks SO_REUSEADDR. Fix is a single-line patch documented in backlog/xroar-load-gdb-patch.
  • swi (opcode $3F) at a -trap point makes XRoar segfault when it tries to write the snapshot. Use bra . halt loops instead.
  • -trap succeeds at writing the snapshot, but XRoar segfaults right after. The snapshot file is fully valid and usable for reload. The segfault is post-write.
  • The stub answers vMustReplyEmpty with the literal string "timeout". Modern gdb (14.x) considers this a fatal protocol error when reported via MI. The plain CLI target remote … path works; MI paths surface it as ^error.
  • The stub gets wedged by probe-connect+disconnect. A TCP connect() immediately followed by close() drives the stub into the degraded state. Do not probe the GDB port — sleep ~4 s after launching XRoar and connect with gdb directly.
  • info registers always trails with ^error,msg="Register 12 is not available". m6809-gdb knows 13 registers; the stub exposes 12. The trailing error must be tolerated by any consumer.

Gotchas

  • Cart ROM must be a power of 2. XRoar will load any size but mapping behaviour for non-pow2 ROMs is undefined.
  • Plain 16 K ROM mapping is source-confirmed. XRoar 1.10 cart_rom_finish() creates one slot sized to a lone ROM file, and rombank_a8() masks a 16 K slot address with $3FFF. A single 16 K -cart-rom therefore covers $C000-$FFFF address offsets, including the usable $E000-$FDFF half. Native 32 K Init0=11 behaviour remains unverified; use a separately validated banked type such as GMC if capacity later exceeds the plain 16 K image.
  • The split-ROM acceptance run passed 2026-07-18. Cold gdb-mcp reads matched file offsets for palette_table=$E000, screen_map=$E010, maze_cells=$F256, and maze_gates=$F916. The live framebuffer matched the generated 40×24 screen plus initial player pixel-for-pixel.
  • Default machine config carries state across runs. If a previous session changed PAR/palette in a weird way, clear ~/.xroar/.
  • WSL display — XRoar opens an X11/Wayland window. WSL2 with WSLg (Win11 default) handles this transparently.
