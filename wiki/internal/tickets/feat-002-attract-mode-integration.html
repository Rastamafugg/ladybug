Revised architecture approval brief — 2026-08-08

Recommendation and intended outcome

Replace the separate presentation-game implementation with a thin, data-driven presentation director. The director selects states, handles deadlines and credit/start edges, streams static screen records into the hidden framebuffer, and supplies deterministic demo input. Existing gameplay services remain authoritative for actor animation, player movement, gates, enemies, collision, death, and rendering. Approval authorizes this architecture and its measurable targets; it does not authorize implementation until the assignment contract is refreshed and the ticket returns to Ready.

Terms, evidence revision, and measurement rules

  • Cartridge source byte: one byte stored in the 65,536-byte GMC image, whether executable code or immutable data.
  • Cold payload: cartridge-stored presentation data copied at boot to physical RAM pages $3A-$3D.
  • Direct streaming: decode the selected screen record directly into the hidden BACK framebuffer over bounded Vbord work units; do not first inflate all six tile-index maps into RAM.
  • Presentation director: the low-RAM flow owner that chooses state and invokes services but does not implement a second actor, movement, collision, maze, or death engine.
  • Exact gameplay-tile reuse: a presentation tile whose complete 32-byte packed native representation equals a tile already stored in screen_tiles. Palette-remappable similarity is reported separately and is not counted as exact reuse.
  • Complete presentation worklist: all decode, tile drawing, ownership bookkeeping, dynamic overlay, and publication work performed between two Vbord boundaries. The strict maximum is 29,666 active CPU cycles; the engineering target is 27,000 cycles.
  • Headroom: capacity limit minus measured use. Cartridge headroom after sound subtracts the proposed 1,536-byte sound allocation from measured CPU-readable GMC source spare.
  • Evidence revision: uncommitted working tree based on Git 3c9d780f7d4d3ff95a532000527cfe11209feec8, measured 2026-08-08. Inputs are build/ladybug-presentation.json SHA-256 798733b9342de3264a0a308c282f6a8e70b86727301c90404840bf02e1ab3e0c, cold payload SHA-256 e5112c81307c4d69f6e5839212799efd3cf31efde2dbb6fb245a2364346ee6c7, and build/ladybug_screen.inc SHA-256 4ce90afdbab8e2d02e0af15a10358ad56687441226626f64c41ece866eb0d390. Byte counts are exact measurements of these artifacts; proposed post-change capacities are projections until rebuilt.
  • Measurement method: a read-only Python probe decoded all count/value map streams from the cold payload, parsed the 97 packed gameplay tiles from screen_tiles, compared complete 32-byte tile values, constructed a per-cell modal base, and counted candidate encodings exactly. The one-off probe was rerun during review; implementation must convert these calculations into a retained generator/verifier before they can become acceptance evidence.

Observed baseline and reason for revision

  • The current build uses resident code 8192/8192, bank-3 runtime 4096/4096, presentation module 1278/1280, resident assets 7144/7680, cold presentation payload 11398, and 2,055 CPU-readable GMC source bytes spare. Reserving 1,536 sound bytes leaves 519 bytes against the required 512-byte final reserve.
  • The first call to presentation_flow_tick synchronously executes inflate_maps for all six maps. Runtime snapshots observed the CPU inside inflate_emit after approximately four seconds and returning to the main loop only after a second approximately four-second interval.
  • The delivered runtime does not satisfy visible acceptance: the user observed a mostly black attract sequence, odd non-animated sprites, and no successful 5-then-1 start. Source review confirms start handling is not global, the demo route is not a maze route, and presentation-specific actor behavior duplicates responsibilities already owned by gameplay.
  • The four cold presentation pages contain 32,768 physical bytes. The current source occupies offsets 0–11,397; a 4,986-byte gap precedes the expanded-map output at offset 16,384; six expanded maps occupy 5,760 bytes; and 10,624 trailing bytes remain. Total unoccupied space is therefore 15,610 bytes. RAM destination capacity is available, but it does not relax cartridge-source or fixed executable-module limits.

Measured tile and map-format comparison

  • The gameplay atlas contains 97 tiles; the presentation atlas contains 255 tiles or 8,160 bytes. Fifty-three presentation tiles are exact gameplay-tile matches, representing 1,696 duplicated tile bytes and 4,785 of 5,760 presentation cell references.
  • An exact-reuse resolver encoded as a 255-byte compact index plus a 32-byte source bitmap leaves 202 cold-only tiles. With unchanged map streams, the projected cold payload is 9,989 bytes, a 1,409-byte source reduction before decoder-code changes.
  • An additional 56 tiles are geometrically equivalent under one of 15 measured pen mappings. They cover another 548 cell references, but runtime recolouring or boot-time derivation adds code, descriptors, and cycles. This is an optional measured experiment, not part of the default design.
  • The current six independent count/value RLE maps occupy 3,238 bytes. A synthetic per-cell modal base encoded with RLE plus six 960-bit change masks and replacement values occupies 2,418 bytes, saving 820 bytes. It applies 1,364 overlays after drawing the base across one complete six-screen cycle, so it increases tile work by 23.7 percent relative to six direct 960-cell draws.
  • Among authored-screen bases, game-over plus skip/literal deltas is the smallest measured candidate at 2,524 bytes. It saves 714 bytes but couples unrelated screen definitions and still requires extra tile applications. It is rejected as the default.
  • The selected default keeps independent RLE screen streams, composes shared outer-wall definitions at build time, and decodes only the selected stream directly into BACK. Base-plus-delta remains a fallback only if the rebuilt shared-tile design cannot meet the cartridge engineering target.

Module and ownership design

  1. Build-time composition: define one canonical outer-maze-wall layer and require every applicable TMX screen to inherit or validate against it. The compiler may emit independent RLE streams after composition; source reuse does not require runtime redraw coupling.
  2. Direct screen stream: a screen descriptor supplies stream pointer, static duration, next state, input policy, and optional overlay script. The decoder retains source page/offset, run count, tile identifier, cell destination, and remaining cells between Vbords. Only the selected map is decoded.
  3. Shared tile resolver: map identifiers resolve through generated exact-reuse metadata to either resident screen_tiles or the compact cold-only atlas. The resolver must restore PAR5 before returning and must preserve framebuffer ownership rules.
  4. Shared actors: title and instruction records set actor destination, frame, colour/action, and duration, then invoke existing player/enemy sparse drawing and save-under services. Presentation code may sequence actors but may not own an independent movement, animation-frame, collision, or underlay implementation.
  5. Demo input provider: initialize the normal part-one gameplay path with a demo flag and deterministic seed. A compact sequence of {direction, duration} records writes the ordinary player input state; normal movement, enemy AI, gates, collision, death, and framebuffer rendering execute unchanged. Enemy navigation adapted for player control is rejected unless an assembled prototype is both smaller and no slower than the route driver.
  6. Sound boundary: gameplay emits the same future sound-event hooks in live and demo modes. FEAT-002 reserves the measured sound capacity but does not add synthesis, assets, or a dispatcher; no silent gameplay fork may be introduced to avoid the future sound boundary.
  7. Input policy: one edge scanner runs before state dispatch. Credit edges are accepted in every specified attract/demo presentation state. A valid start edge with available credit pre-empts the current presentation before its next animation or movement update, consumes exactly one credit, and enters level-start.
  8. Reset contract: boot and warm reset initialize presentation state from a reset-owned generation value or explicit boot flag. A retained magic byte alone cannot authorize restoration of an old mode.

Scope and exclusions

In scope: direct selected-screen streaming; exact gameplay-tile reuse; canonical outer-wall composition; thin presentation-state ownership; shared actor services; deterministic route-driven normal gameplay demo; global credit/start pre-emption; cold/warm attract initialization; title, instruction, level-start, demo, credit, and game-over behavior already assigned to FEAT-002; and current-revision capacity, timing, visual, and natural/forced verification.

Out of scope: FEAT-003 visible high-score records and name traversal; sound synthesis or sound assets; two-player gameplay; battery-backed scores; changes to normal maze, collision, scoring, or enemy rules; frame-time cartridge banking; deferred web/monitor work; and manual prose duplication of generated line listings.

Targets and pass/fail measurements

  • Cold and warm launch publish a complete attract title within 60 Vbords of the first presentation hook. Warm RAM containing the old magic value must still enter the title state.
  • Every complete presentation worklist is at most 29,666 active cycles; the engineering target is at most 27,000. Missing or timed-out screen phases fail rather than count as passing evidence.
  • Static frame hashes for all six authored maps remain exact. Shared-wall composition must fail generation when an applicable source screen diverges from the canonical wall layer without an explicit documented exception.
  • The presentation module remains within $1900-$1DFF. The engineering target is at least 32 module bytes free after all FEAT-002 behavior; zero to 31 bytes is a reported target miss requiring renewed capacity review even if the hard limit passes.
  • After reserving 1,536 cartridge bytes for sound, at least 512 CPU-readable GMC source bytes remain as a hard gate; the engineering target is at least 1,024 bytes. Every resident, asset, bank-3, direct-page, stack, physical-page, and PAR-scope guard remains independent and passing.
  • A complete natural attract loop visibly executes title, instructions, part-one level-start, normal-engine demo, normal death presentation, and return to title. Forced evidence separately covers every instruction outcome, both demo death causes, credit arrival in every state, start with and without credit, held/alternating/simultaneous keys, subsequent live part transition, and final live death.
  • The demo route uses normal player and enemy update services. Verification must fail if movement, collision, death, or rendering is replaced by presentation-only substitutes.

Options, risks, and decision required

Recommended: independent RLE streams, direct selected-screen decoding, exact resident-tile reuse, build-time shared-wall composition, and route-driven normal gameplay. This has the lowest architectural coupling and uses the measured 1,409-byte tile-duplication opportunity without accepting the additional draw work of runtime base overlays.

Conditional fallback: add modal-base bitmap/value overlays only if the implemented default misses the 1,024-byte post-sound engineering target and a complete-cycle profile proves every presentation worklist remains at most 27,000 cycles. Palette-remappable boot-time tile derivation is a later fallback under the same renewed measurement gate.

Rejected: synchronous six-map inflation; presentation-owned actor or movement logic; enemy-AI control of the player without a smaller/faster measured prototype; authored-screen coupling to game-over as a runtime base; full pre-rendered framebuffers in cartridge storage; and any result that treats available physical RAM as cartridge-source headroom.

Original approval brief — historical

Objective and motivation

Implement the runtime presentation flow requested for the CoCo port. The game currently boots directly into the gameplay renderer, despite the authored 40×24 presentation maps and the Phase 9 roadmap contract. The completed feature must provide an unattended attract loop, credit handling, and level-one start selection while preserving the existing gameplay compositor and native-hardware constraints.

Evidence and baseline

  • Current revision: repository state inspected 2026-08-07.
  • tiled/coco-attract-screen.tmx, coco-instructions-screen.tmx, coco-level-start-screen.tmx, and coco-high-score-screen.tmx are 40×24 maps with 960 cells each. The high-score map contains the updated authored coin locations.
  • scripts/build_screen.py currently compiles only tiled/coco-screen.tmx for the gameplay map and emits popup/multiplier presentation sprites, not full cold presentation maps or animation scripts.
  • src/main.s has no flow state, credit counter, keyboard scanner, or presentation-screen sequencing. src/tester/input.s demonstrates an 8-column PIA1 edge scanner, but it is not part of the game runtime.
  • Roadmap Phase 9 already specifies cold maps in GMC expansion storage, a Vbord-driven flow state, scripted animation records, input pre-emption, and a deterministic demo. Those requirements are the design baseline for this ticket.

Scope

In scope: compile and package the six named presentation TMX maps (attract, instructions, level-start, high-score, game-over, and enter-high-score); add a single Vbord-clocked presentation flow; animate the title actors using existing Lady Bug and enemy sprite data at arcade-reference locations; animate the instruction demonstrations and recolour the relevant authored HUD characters; show level-one and subsequent part values and vegetable sets; add deterministic demo gameplay ending by enemy contact or skull pickup; scan keyboard edge presses for 5, 6, and 1; maintain session credits; show the base high-score screen and authored coin locations; run live gameplay through each subsequent part; show game over after the final reserve expires; atomically publish cold screens through the hidden framebuffer; and verify build, capacity, input, transitions, and gameplay regression. FEAT-003 owns visible high-score records and name entry.

Out of scope: visible high-score record rendering, seven-character name traversal, score insertion presentation, sound, two-player mode, battery-backed high scores, the deferred web application, XRoar monitor/MCP work, and changes to the arcade-derived maze or enemy rules except where required to terminate the demo safely or support existing part progression.

Proposed user-visible behavior

  1. With no credit or start input, loop coco-attract-screen.tmx, then coco-instructions-screen.tmx, then coco-level-start-screen.tmx for part one, then a short level-one demo. After demo death, return to the attract title and repeat.
  2. The title phase displays the TMX artwork plus Lady Bug and enemy animation overlays in the measured arcade locations. The instruction phase demonstrates SPECIAL letters, EXTRA letters, three hearts, skulls, and the final flower/collectible value and multiplier rows. The bonus colour cycle is evenly distributed across red, yellow, and blue; Lady Bug collects each demonstration row; the resulting extra-life, extra-credit, and ×2/×3/×5 outcomes are shown.
  3. When a demonstration collectible is collected, the matching SPECIAL, EXTRA, or multiplier section characters are lit/recoloured for that item. Static authored rows remain unchanged outside the active demonstration.
  4. An edge press of 5 or 6 adds exactly one session credit, pre-empts the current attract/demo state, and displays the high-score screen with a coin icon at the next valid authored coin location. Repeated edge presses add further coins without requiring a release of unrelated keys. A held key does not add credits every frame.
  5. An edge press of 1 when a credit is available consumes one credit and displays the level-start screen with part one values and the level-one vegetable set, then enters normal level-one gameplay. A start without credit has no gameplay effect.
  6. The demo uses a deterministic replay and normal collision/rendering. It runs until a forced route causes enemy collision or skull pickup, then returns to attract after the death presentation. A credit or start edge aborts the demo before its next movement tick.
  7. Live play uses the existing game rules. Every successful part clear displays coco-level-start-screen.tmx before the next part, with the current part number, vegetable, value, skull count, enemy lineup, and GOOD LUCK values updated for that part.
  8. When the final replacement Lady Bug dies with no reserve remaining, display coco-game-over-screen.tmx and hand qualifying-score presentation to FEAT-003.

Scenarios, edge cases, and failure modes

  • Cold boot reaches the title without a partially published frame, then completes the full unattended sequence and returns to the title.
  • Credit arrives during each attract phase, each instruction phase, level-start, and demo gameplay. The current phase is abandoned atomically and the high-score presentation begins.
  • Multiple credits arrive while the high-score presentation is visible. Each valid edge advances the next authored coin location and the credit count remains consistent with the right-panel value.
  • 5 and 6 are held, released, alternated, or pressed simultaneously. Each physical key edge is counted once; simultaneous keys must not double-count one key edge or corrupt the scanner state.
  • 1 is pressed with zero credits, during high-score display, during level-start, and during gameplay. Only the authorized transition consumes a credit; attract/demo pre-emption remains deterministic.
  • A part clear occurs with every live reserve state and at the first and later part values. The next level-start screen must not briefly show the previous part's vegetable or score fields.
  • The instruction row completion paths are forced independently for SPECIAL, EXTRA, blue-heart multiplier progression, skull interaction, and the final flower/collectible row. Missing a required rare path is a verification failure.
  • Both demo death causes are forced in verification: enemy contact and skull pickup. The demo must not hang if the route reaches a wall, a missing entity, or a depleted life state.
  • Both framebuffer owners are tested at every screen boundary. No write-to-front, missed-commit, stale owner metadata, or gameplay A/B divergence is accepted.
  • All presentation maps remain bounded by the generated asset manifest. Resident, direct-page, stack, bank-3 runtime, and total GMC capacity guards must pass; cold screen payloads must not silently displace the enemy module.

Options and recommendation

  1. Recommended: one resident flow state machine with data-driven screen records and animation scripts, cold map/tile payloads in expansion-bank storage, and one edge-tested keyboard service shared by attract and gameplay. This matches the Phase 9 roadmap, keeps presentation timing on the 60 Hz Vbord clock, and preserves gameplay ownership boundaries.
  2. Rejected for this ticket: hard-wire each screen as a separate assembly routine. It minimizes initial design work but duplicates map data, consumes scarce resident bytes, and makes pre-emption and frame-hash verification inconsistent.
  3. Rejected for this ticket: use the deferred web app or XRoar monitor as the presentation controller. That does not satisfy native-hardware execution and would not prove the delivered ROM behavior.

Acceptance criteria

  • All six TMX maps compile from source, remain 40×24, and produce static framebuffer hashes matching an independent TMX renderer for every authored static layer.
  • The unattended sequence executes in the required order and repeats after demo death. Every transition is atomic, Vbord-clocked, and pre-emptible by the specified input edges.
  • Title actor positions and instruction animation ranges are recorded as data and verified against the available arcade-reference captures or explicitly marked as projected where no capture exists.
  • Instruction demonstrations visibly complete SPECIAL, EXTRA, blue-heart ×2/×3/×5, skull, and final flower/collectible value/multiplier cases, including the corresponding section-character lighting.
  • Credit/start keyboard behavior passes edge, held-key, alternating-key, simultaneous-key, no-credit, and multi-credit scenarios. Coin icons use only valid locations authored in coco-high-score-screen.tmx.
  • Level-one start shows the authored part-one values and vegetable set, consumes exactly one credit, and enters the existing gameplay path without changing normal collision, enemy, or framebuffer semantics.
  • Live part transitions show the level-start map for every subsequent part and preserve the current part's vegetable/value, skull, enemy, score, life, and flower state when gameplay resumes.
  • Forced demo verification passes both enemy-collision and skull-pickup death paths, and pre-emption interrupts the replay before the next movement update.
  • scripts/build.sh build, the generated manifest/capacity guards, arcade-fidelity checks, focused presentation checks, and the gdb-mcp round trip pass on the combined revision. Report resident/assets/bank use, worst presentation/gameplay frame, retained evidence, and residual risks.

Locked defaults

  • 5 and 6 are equivalent single-credit inputs; 1 is Player 1 start and consumes one credit.
  • The high-score screen remains visible until a start edge or the configured attract timeout; each new credit resets the timeout.
  • The shipped attract loop uses one deterministic route; verification forces both enemy-collision and skull-pickup demo death causes.

Superseded Plan A architecture — historical

  • Resident hook: add one seven-byte main-loop hook that calls PRESENTATION_FLOW_TICK at $1900, returns zero for normal gameplay, and returns nonzero when the presentation module owns the current Vbord. This avoids extending the full bank-3 enemy ABI.
  • Copied module: add src/presentation_runtime.s, assembled for $1900-$1DFF and copied during GMC boot. It owns the flow state machine, PIA1 keyboard edge scan, screen-chunk scheduler, scripted overlays, credit/high-score/name-entry logic, and live/demo transition decisions.   • Cold data: add scripts/build_presentation.py to flatten the six maps into six 960-byte tile-index maps sharing one transformed native tile atlas, then store bounded two-byte RLE streams plus coin-slot metadata in physical pages $3A-$3D. The build must reject a payload above 12939 bytes or a destination crossing four pages.
  • Framebuffer ownership: the module renders cold screens and dynamic overlays into the existing hidden BACK owner. It clears FB_RENDER_ACTIVE during multi-Vbord construction, sets FB_RENDER_PENDING only after a complete frame is ready, and restores PAR5 to page $34 before returning. Capacity and risk decision

The approved Plan A reserves the copied module at $1900-$1DFF, keeps the stack floor at $1E00, and limits the cold payload to 12939 bytes. The integrated build currently uses 1278/1280 module bytes, 11398 cold bytes, and 2055 CPU-readable GMC source bytes spare. After the proposed 1536-byte sound allocation, 519 bytes remain against the required 512-byte reserve. A module overflow, cold-payload overflow, destination-page overflow, or measured stack margin below 256 bytes remains a design failure.

Approved Plan A capacity revision

  • Module reservation: extend the copied presentation module from $1900-$1BFF to $1900-$1DFF (1280 bytes; the inclusive address range is the authority). Move the stack floor to $1E00 and require a measured stack high-water margin of at least 256 bytes in the combined runtime probe.
  • Cold format: retain the four-page physical destination at $3A-$3D, but encode each six-map tile-index stream with bounded run-length records. The module inflates the maps before the first frame, leaving the shared native atlas available at its generated offset. The current six-map data projects from 5760 raw bytes to approximately 3238 bytes with two-byte run records; this is a projection, not acceptance evidence.
  • Dynamic records: keep the cold payload unchanged for FEAT-002 dynamic actors. The module contains the six instruction destinations and colour phases, while title actors reuse the loader-mirrored sparse indexes. The generated cold payload must remain at or below 12939 bytes, the combined module-plus-cold budget remains 14219 bytes, and the measured GMC source margin must remain at least 512 bytes after the proposed sound allocation.
  • Verification gate: the compiler must report raw and encoded map sizes, the inflater must have an independent six-map hash proof, scripts/verify_presentation_flow.py must cover dynamic labels, phase rotation, actor traversal, death paths, and sound reserve, and the build must reject module overflow, stack margin below 256 bytes, cold payload above 12939 bytes, combined module-plus-cold usage above 14219 bytes, destination-page overflow, or any coin offset not present in the high-score TMX.

Rejected alternatives

  • Resident-only flow code: rejected because the current resident window has only seven bytes of headroom.
  • Additional bank-3 service: rejected because the current enemy module occupies its full 4 KiB reservation.
  • Frame-time GMC bank switching: rejected because it conflicts with the no-frame-time-cartridge-banking rule and complicates IRQ/PAR ownership.
  • Six pre-expanded 30,720-byte framebuffers: rejected because they exceed the GMC source budget; shared tile atlas plus tile-index maps remain within the intended cold-data budget.
