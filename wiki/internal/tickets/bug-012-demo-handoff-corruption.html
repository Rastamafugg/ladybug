Approval brief

Decision and outcome

On 2026-08-13 the user selected a replacement deployed flow: attract title → part-one level start → normal-engine demo → death presentation → attract title. The automatic instructions state is removed. This replaces the prior attract → instructions → level-start owner path in presentation_flow_tick.

Arcade evidence and selected route model

The installed arcade Z80 program proves that the demo uses a fixed direction stream, not algorithmic intersection choice. Demo initialization sets bit 4 at $605F and stores ROM pointer $0EF8 at $61D8. Player-control routine $35FF-$3642 reads the current table byte instead of input ports $9000/$9001, advances the pointer at the aligned decision boundary, and stops advancing when the next byte is $FF. The table contains 187 direction bytes plus the terminator. Ordinary arcade direction bits are Left/Down/Right/Up $01/$02/$04/$08.

Golden path

  1. Cold or warm boot publishes the complete attract title as the first visible frame.
  2. The title runs to its deadline while global credit/start edges remain active.
  3. The flow loads and publishes the part-one level-start map directly, with no instruction map or intervening blank frame.
  4. At the level-start deadline, shared gameplay initialization creates stage one exactly once.
  5. The demo director supplies the next arcade-derived requested direction at each aligned decision boundary. Normal player, gate, collectible, enemy, collision, render, and framebuffer services execute unchanged.
  6. A natural route collision enters ordinary death presentation without consuming session credits, persistent lives, score, or high-score state.
  7. Death completion returns directly to a fresh attract title and repeats.

Scope

In: remove the deployed instructions flow state, map emission, choreography payload, and copied instruction runtime; retain its TMX/reference material outside deployment; add the arcade route as generated or verified data; connect it to shared gameplay input ownership; preserve atomic credit/start pre-emption; add focused natural and forced verification; update build profiles and capacity evidence. Out: deleting authored instruction assets or historical evidence, new pathfinding AI, demo-only movement/collision/rendering, live gameplay rule changes, tile-ID widening, high-score/name implementation, sound, and final PERF-005 packing.

Input and state ownership

  • Credit keys remain global edge inputs and pre-empt attract, level-start, or demo before the next demo movement tick.
  • Player 1 start consumes one available credit through the existing credited flow; with no credit it has no gameplay effect.
  • Live joystick state must not overwrite demo PLAYER_WANT; simultaneous or held live directions are ignored in demo mode.
  • Cold and warm entry reset the route pointer, demo-only persistent effects, pending render ownership, and death cause.

Representation and packing

Build tooling owns the 188-byte arcade table and validates its SHA-256, byte count, legal values, terminator, and conversion to CoCo direction ordinals. The deployed route may be raw or losslessly packed only after measuring total source and decoder cost. Removing the measured 931-byte instruction runtime plus its map/choreography data is projected to exceed route cost, but only final build output may claim exact margin.

Edge cases and failure modes

  • A route request reaches a wall because initial gates, player alignment, or maze state differs from the arcade baseline.
  • The route ends before a natural collision, loops without progress, or advances more than once at one boundary.
  • A gate rotation changes the next legal passage; normal gate services retain legality and publication ownership.
  • No enemy reaches the route before the hard deadline. This fails natural acceptance; forced death is diagnostic only.
  • Credit/start arrives during map load, level-start hold, a pending framebuffer commit, or death presentation.
  • The removed instruction payload remains reachable, copied, emitted, or counted in the shipping manifest.
  • Framebuffer-owner starting order changes pixels, commits, or route state.

Acceptance criteria

  • The deployed natural sequence is exactly attract, level start, demo gameplay, death presentation, attract, with no instructions state or publication.
  • The shipping manifest and loader contain no instruction map, choreography streams, or copied instruction runtime; authored TMX/reference files remain intact and valid.
  • The converted route is derived byte-for-byte from arcade ROM $0EF8-$0FB3, contains 187 actions plus $FF, and advances only at the proven aligned decision boundary.
  • Normal game-engine movement, gates, collection, enemy updates, collision, death, rendering, and A/B publication execute during demo. No timer-forced DEATH=1 contributes to natural acceptance.
  • A complete unforced route reaches a real enemy or skull collision and returns directly to attract. Both causes remain separately forced for regression coverage.
  • Credit/start pre-emption passes every attract, level-start, demo, pending-commit, and death boundary; live joystick input never owns demo movement.
  • Both framebuffer starting owners converge with zero FRONT writes, zero missed accepted commits, exact route state, and exact presentation-boundary frame hashes.
  • Development and deployed builds, hard memory guards, applicable BUG-008 through BUG-011/BUG-016 regressions, and combined GMC runtime checks pass. Exact bytes recovered, route bytes added, final headroom, and worst worklist are reported.

Rejected alternatives

  • Intersection AI: rejected because arcade ROM inspection proves a fixed stream.
  • Skip but ship instructions: rejected because the user requested deployed removal and the unused payload consumes constrained capacity.
  • Timer-forced death: rejected as natural evidence because it bypasses collision ownership.
  • Run PERF-005 first: rejected because it follows functional closure and would create a dependency cycle.
