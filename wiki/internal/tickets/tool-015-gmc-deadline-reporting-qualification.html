Scenarios and edge cases

Four guard families each have r4-at-expiry, r5-at-expiry and r5-just-before cases: twelve actions. One r5 missing-GDB control and one receipt-writer canary bring the exact total to fourteen. Each guard distinguishes a different source boundary; this is not a mode/owner Cartesian matrix. D means the same absolute work deadline seen by the target guard. Expiry uses fake time equal to D; the before control uses D minus 0.001 seconds, a chosen exact fixture separation rather than a wall-clock tolerance. Exact predecessor markers, monotonic-read sequences and target read indices are TBD and must be frozen without adding production markers.

  1. Loader prelaunch, NATURAL: r4 SystemExit.code == "gmc proof: loader deadline expired before launch"; r5 marker NATURAL_LOADER_PHASE_TIMEOUT stage=prelaunch, summary phase NATURAL_LOADER_TRACE, direct-call SystemExit.code == 1. The target loader launch count is zero.
  2. GDB prelaunch, NATURAL_RUNTIME: r4 SystemExit.code == "gmc proof: GDB work deadline expired before launch"; r5 marker GDB_PHASE_TIMEOUT phase=NATURAL_RUNTIME stage=prelaunch, summary phase NATURAL_RUNTIME, direct-call code 1. The target GDB launch count is zero.
  3. Resident pre-setup, FORCED: r4 SystemExit.code == "gmc proof: resident work deadline expired before setup"; r5 marker FORCED_RESIDENT_PHASE_TIMEOUT stage=pre-setup, summary phase FORCED_RESIDENT_STARTUP, direct-call code 1. An initially live owned fake XRoar child exists; GDB does not launch; the real cleanup path must confirm that child's termination.
  4. Resident pre-GDB, DEMO: r4 SystemExit.code == "gmc proof: resident work deadline expired before GDB"; r5 marker DEMO_RESIDENT_PHASE_TIMEOUT stage=pre-gdb, summary phase DEMO_RESIDENT_STARTUP, direct-call code 1. Earlier resident guards stay below D; an initially live owned fake XRoar child exists; GDB does not launch; real cleanup must confirm termination.

Each r5 before control must reach the named continuation boundary exactly once without a timeout marker, then stop on an expected harness sentinel. The sentinel is neither product success nor a product exit code. Resident controls must leave no live fake child, record product cleanup separately from harness teardown, and keep earlier and nested guards below their deadlines as needed to reach the target. The r4 expiry cases are expected baseline observations that fail the r5 reporting oracle; they are not required product failures to preserve.
