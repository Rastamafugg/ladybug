Confirmed source-level mechanism for the maze-completion stuck note

  1. The completion event is emitted on the last gameplay service. audio_poll_gameplay aliases AUDIO_GAME_STAGE to direct-page $0026, which is STAGE_PENDING in src/main.s:214. When that field changes from zero to nonzero, and both dots and bonus objects are zero, src/audio_runtime.s:629-640 enqueues cue 9, all-flowers-complete. The service then processes the queue, advances the new slot, mixes it, and writes PSG registers in src/audio_runtime.s:44-62.
  2. If cue 9 is admitted, its first note is live before the handoff. The generated cue manifest identifies cue 9 as an exclusive priority-5 jingle with a 32-tick translated duration and stream gmc_cue_stream_09. Its stream begins with tone writes followed by waits in assets/arcade/audio/gmc_sound_data.inc:223-231. The source facts establish that the first note is published during the last gameplay service when the event reaches slot admission; they do not require a waveform capture to explain a sustained register state.
  3. The next-level path skips the only sequencer tick. On the following main-loop pass, mainloop calls the presentation dispatcher at src/main.s:612-621. The complete-profile normal_stage branch tests STAGE_PENDING, calls PRES_MAIN_NEXT_STAGE, starts the level-start screen, returns 1, and therefore takes the bne mainloop at src/presentation_runtime.s:315-328 and src/main.s:620-621. The sole AUDIO_ENGINE_EXEC call is later at src/main.s:670-677, so it is not reached for that retained presentation tick.
  4. The state transition has no audio completion barrier. next_stage clears STAGE_PENDING and reinitializes stage state at src/main.s:724-745. The presentation branch calls it before drawing the next level and never reads an audio slot-complete flag or waits on a cue boundary at src/presentation_runtime.s:315-328. The SN76489 is register-driven and sustains its last tone between writes; consequently, freezing the foreground service freezes the first note until a later service call. This is a confirmed source-level explanation for the reported “first note during next-level drawing” symptom.

Expected repair boundary: preserve the completion cue's register updates while the handoff is pending, or hold the stage transition until the required musical cue reports completion. The acceptance path must prove the natural last-dot → completion cue → level-start sequence and verify that no stale tone remains when the cue ends. The report does not choose an implementation because that would cross into the separately authorized repair work.

Arbitration findings

Active channel mixing does prioritize exclusive music over effects. Cue descriptors encode musical/exclusive status in the generated policy fields. audio_admit sends every descriptor with the high bit of descriptor offset 2 set to slot 0 at src/audio_runtime.s:165-180. audio_mix first scans active exclusive slots and selects the highest stored priority, then returns after mixing only that slot at src/audio_runtime.s:374-405. Thus the observed completion handoff is not explained by an effect winning the PSG channels while a jingle is active.

Admission is weaker than the channel mixer. Musical admission unconditionally resets slot 0 and copies the new cue at src/audio_runtime.s:224-254; it does not compare the incoming priority with the active musical cue and does not consult the policy's preemptible field. A later exclusive cue can therefore terminate an earlier music cue even when its priority is lower. This is a confirmed static arbitration defect, but it is a separate mechanism from the stage-handoff stuck note.

The event queue has no priority reservation. audio_enqueue_impl accepts at most four queued events and drops the next event while incrementing AUDIO_Q_OVERFLOW at src/audio_runtime.s:113-142. The polling order admits dots, bonus, box, gate, vegetable, release, special, extra, then stage at src/audio_runtime.s:548-643; a full queue can therefore drop the later stage or other musical event before it reaches the mixer. This is a confirmed static loss path. It is not proof that the user's particular completion cue was dropped, because the report says a first note was heard and no queue state was captured.

Existing audio verification does not cover these behaviors. scripts/verify_audio_runtime.py:198-241 validates descriptors, aliases, streams, waits, and event-map coverage; :349-380 validates bounded indexing, wait-pointer retention, loop bounds, write count, and placement. It contains no assertion for queue overflow priority, exclusive-cue replacement, presentation-retain service cadence, or a stage-cue completion barrier. The existing verifier can therefore pass while this source-level handoff defect remains.

Hypotheses and missing runtime evidence

  • Confirmed source cause: the stage-completion cue begins before normal_stage; the retained presentation return bypasses the only audio service call, and the handoff does not wait for cue completion.
  • Confirmed independent risks: an exclusive cue can replace slot 0 without priority/preemption arbitration; a full four-entry FIFO can drop any later musical event. These need separate regression coverage if the repair changes admission policy.
  • Unresolved runtime facts: the user artifact/profile, exact frame at which the first PSG write is heard, queue count/overflow at completion, actual slot-0 ID/wait/stream pointer, and whether any other cue is enqueued during the same completion frame. No runtime probe was authorized or run for this report.

Speculation: if an additional higher-priority cue is emitted on the same completion frame, slot-0 replacement could alter the audible result. Static source permits this, but no current evidence ties it to the reported maze-completion instance.

Smallest future discriminating checks

  1. Natural completion handoff: from a revision-identified complete-profile artifact, play the natural last-dot path until DOTS_LEFT=0 and BONUS_LEFT=0. Record a marker at cue-9 enqueue, a marker at the first PSG write, every subsequent audio-service entry, and the first level-start publication. Deadline: 60 seconds for the initial phase. A timeout means the marker was not proven, not that target code is slow. The discriminating result is whether audio-service ticks disappear while the first note remains selected.
  2. Forced reachability control: separately force the same terminal counters in a revision-identified artifact to test the handoff without depending on full gameplay. Record the same markers and label this as forced evidence; it cannot replace the natural completion sequence.
  3. Completion ownership: at the same handoff, capture STAGE_PENDING, slot-0 ID, slot wait, stream pointer, and PSG shadow values immediately before and after presentation release. This separates a frozen sequencer from a cue being repeatedly replaced. Prove authored/staged/live bytes before interpreting any stopped PC.
  4. Priority/queue isolation: exercise one active cue-9 plus one lower-priority and one higher-priority exclusive enqueue, then separately fill the four-entry FIFO before cue 9. The expected policy must be declared first. This distinguishes intentional replacement from the confirmed unconditional overwrite and queue-drop paths.
