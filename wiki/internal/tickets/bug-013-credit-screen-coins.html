Approval brief

Objective and motivation

The high-score/credit screen must appear only in response to a credit edge, initially show its base design without coins, and then show one complete coin per available credit at the TMX-authored locations in the required order.

Reproduction

  1. Launch without input and observe whether the high-score screen or any coins appear.
  2. Press 5 or 6 once and inspect the first coin.
  3. Add credits repeatedly through the maximum, then press 1.

Observed versus expected

Observed at 135b965: the base High Score Table and Branding layer is hidden for Tiled authoring and the Coin Positions layer is visible. The current compiler equates visibility with runtime inclusion, so it discards the base layer and flattens every authored coin into the initial map. The pre-update generator also hard-codes nine one-cell destinations in one column, and the runtime advances them by a constant delta; neither represents the committed twelve nonuniform 2×2 slots.

Expected: no high-score screen or coin appears before input. The first 5/6 edge opens the screen, publishes the base design, and shows exactly one complete coin. Each later edge adds the next coin left-to-right within the lower row and then left-to-right within the upper row, stopping at twelve authored locations and twelve credits. Player 1 start consumes one credit and leaves the credit flow for level start. The credit screen has no timeout; attract restarts only after a played game reaches game over and any qualifying high-score flow completes.

Scope

In: semantic high-score layer selection, credit-screen entry and exit policy, no-timeout hold, credit saturation, machine-readable 2×2 coin metadata in coco-high-score-screen.tmx, nonuniform destination records, complete coin drawing, coin order, clipping, and natural key-edge verification. Out: moving the authored coin slots, visible score/name records, name entry, two-player mode, battery-backed credits, and post-game timeout ownership.

Golden path

  1. Cold unattended boot remains in the attract sequence and publishes no credit screen.
  2. A new 5 or 6 edge increments credits from zero to one, selects the high-score map, streams only High Score Table and Branding, and overlays the first lower-row coin.
  3. Each later accepted edge increments once and republishes exactly one additional complete 2×2 coin according to the generated destination list.
  4. At twelve credits, further edges leave state and pixels unchanged.
  5. A valid Player 1 edge consumes exactly one credit and atomically selects level start before another credit-screen mutation.

Scenarios and edge cases

  • No input: no credit screen and no coins.
  • Held key: no repeated credits; alternating and simultaneous credit keys follow the approved edge policy.
  • Counts zero through twelve: exactly the corresponding prefix of complete coin slots is visible.
  • Maximum reached: no counter wrap, destination overrun, clipped draw, or thirteenth coin.
  • Start with zero credits is ignored; start with credits consumes one and enters level start.
  • Credit input while already on the screen adds one coin without resetting or timing out the screen.
  • A missing, renamed, duplicate, malformed, nonidentical, overlapping, clipped, or out-of-order 2×2 slot fails generation.

Discriminating test

Independently parse the two semantic layers, prove that the static map equals the base layer with zero coin pixels, derive the twelve ordered 2×2 slots from the coin layer, and force every credit count from zero through twelve while comparing decoded framebuffer cells. Separately trace boot, first credit, later credit, saturation, valid start, game over, and the later FEAT-003 handoff.

Acceptance criteria

  • The generated destination list exactly equals all twelve approved TMX coin anchors in left-to-right, bottom-to-top order.
  • For each credit count from zero through twelve, exactly that many complete authored 2×2 coin glyphs are visible and no pixels are clipped or written outside the authored footprints.
  • The high-score screen is entered only by a new credit edge before gameplay and is not part of unattended boot rotation.
  • Credits saturate at twelve; start consumes exactly one; the credit screen does not time out.
  • Attract resumes only after game over and the applicable FEAT-003 handoff, not from a credit-screen timer.
  • The current module remains at or below 1,280 bytes, helper at or below 334 bytes, cold payload at or below 10,874 bytes, module plus cold payload at or below 14,219 bytes, future-sound margin at or above 512 bytes, and every measured complete scheduled worklist at or below the 29,666-cycle hardware ceiling and 27,000-cycle engineering target.

Authored TMX layer contract

Layer names, not Tiled visibility, define build ownership. High Score Table and Branding is always the static runtime base even when hidden in Tiled. Coin Positions is always metadata/dynamic-overlay input even when visible in Tiled and must never appear in the zero-credit static map.

  • Slot shape: exactly twelve nonoverlapping slots exist. Each is the same authored 2×2 tile pattern; the upper-left nonzero cell is its anchor. The generator validates all four tile identities and transforms against the canonical first slot and emits the four tile IDs once.
  • Anchor order: zero-based lower-row anchors (1,21), (4,21), (7,21), (31,21), (34,21), and (37,21) precede upper-row anchors (1,18), (4,18), (7,18), (31,18), (34,18), and (37,18). Sorting is ascending X within descending Y.
  • Framebuffer conversion: an anchor (x,y) maps to byte address $2000 + y×1280 + x×4. The renderer draws the generated upper-left and upper-right tiles, then the lower-left and lower-right tiles one 1,280-byte scan-row block below; it does not use one constant destination delta or a synthesized one-cell coin.
  • Generated ownership: scripts/build_presentation.py emits the ordered anchors, framebuffer destinations, four glyph tile IDs, and slot count to build/ladybug-presentation.json and build/ladybug_presentation.inc. src/presentation_runtime.s consumes the generated table and count with no parallel nine-slot constants.

Design and capacity

The existing selected-screen cold stream and dynamic overlay path remain the owners. The compiler gains semantic per-role layer selection; no general visibility-based policy or new renderer is introduced. The runtime iterates a generated nonuniform destination table and draws the four authored quadrant tiles for each earned credit. The last successful pre-update artifact is a single historical observation, not current-source evidence: module 1,277/1,280 bytes, cold payload 9,659/10,874 bytes, combined 10,936/14,219 bytes, GMC source spare 2,084 bytes, and future-sound margin 548/512 bytes. No post-change size result is projected; failure of any hard guard requires a recorded follow-up or renewed design, not acceptance.

Rejected alternatives: named object points are superseded by the committed tile-layer contract because the full 2×2 glyph validates both location and completeness; Tiled visibility is rejected as runtime policy because the authoring view intentionally hides the base; hard-coded destinations and a constant stride are rejected because the twelve slots cross two distant column groups; the synthesized one-cell coin is rejected because it does not reproduce the authored footprint.
