BUG-069 — Match the level-start 1ST score to its label Draft

2026-10-01 · P2 · Standard · Draft · RSCH-014 Step A

Approval brief

Objective and motivation

Ensure the numeric first-player score uses the same light green as the “1ST” label on level-start.

Evidence, reproduction and cause

In the static level-start compiler image, the “1ST” label at row 1 uses LIGHT_GREEN pen 8 while the row-2 score placeholders compile WHITE pen 6. Current assets/arcade/text-colours.json already sets the global dynamic score field to pen 8. Therefore source inspection alone cannot confirm a runtime defect: SharedText may recolor the static placeholders before first publication. The current full build stops earlier in FEAT-005 parsing, so no delivered current-ROM frame proves either outcome. Static frame packed-pen hash is in snapshot.json.

Scope

In: the visible level-start first-player score after screen hydration, compared with the 1ST label. Out: gameplay score colors, score value/authority, TOP/high-score fields and unrelated label palette changes.

Design and prototype

First verify the first natural level-start frame with a nonzero score and current artifact identity. If the dynamic score is already pen 8, close the source cause without a production edit. If static white placeholders remain visible, add a screen-specific level-start run/ownership fix without changing the shared global score field for unrelated screens.

Scenarios and edge cases

  • The natural level-start frame shows all score glyph pixels in the same LIGHT_GREEN pen 8 as “1ST”, for zero and nonzero score; no one-frame white flash or stale prior score.
  • Both screen publication owners show the same value/color after ordinary replay; exact expected pixels derive from authored glyph masks.
  • If no mismatch reproduces after current SharedText initialization, document the current revision and close as no-change evidence; if it reproduces, propose the minimal owner-specific correction and return for approval if scope changes.
