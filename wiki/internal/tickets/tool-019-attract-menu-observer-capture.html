Scenarios and edge cases

  • Baseline is visible Attract: screen 0, mode 2, selection 0, dirty state 0 and no pending publication. The user confirms readiness outside the timed operation, then presses and releases Down once after the observer identifies this baseline.
  • Expected selection is START GAME (0) to OPTIONS (1). Retain every observed menu_down event, frame count, event/previous/selection/dirty state, screen and mode. A screen transition or repeated input is not evidence of selection corruption.
  • At fbiq_done, only a 16-bit commit-counter difference of one modulo 65,536 confirms the next consecutive publication. Zero is not a publication; a gap is incomplete coverage. $FFFF to $0000 is one publication.
  • Do not read $FF91 or $FF9D as configuration readback. These are write-only control addresses. Record readable PAR0-PAR5 values, mask only page bits, validate the relevant code and data image mappings, and bind the publication instruction span to the accepted image. Executive selection is inferred from the accepted startup write and the absence of a subsequent task-select write in the bound release path. Display selection is inferred from the byte-qualified publication path, the advancing counter and the exchanged owner IDs. Report these inferences explicitly; do not fabricate observed register values.
  • Before pixel reads, PAR1-PAR4 must match the newly published FRONT: owner A (0) uses pages $30-$33, owner B (1) uses $2C-$2F. The verified publication code writes offset $C0 or $B0 respectively before exchanging IDs and incrementing the counter, without remapping PAR1-PAR4. These expected offsets are derived evidence, not hardware readback. An unproved startup/publication path or inconsistent readable mapping is a harness failure.
  • MENU_DIRTY bit 1 requests A repaint and bit 2 requests B repaint. Assess an owner after its request clears and its new image publishes; an already queued pre-input image is not a display failure. Cover both owner updates and one subsequent publication from each. Limit captures to the baseline, input event and required publications; do not collect unrelated frame traces.

Options and recommendation

The current one-snapshot observer cannot establish the relationship between one input event and later A/B publications. Adding automated key injection would add an unnecessary input path. Recommended: keep Down as a normal manual keyboard action in the visible XRoar window, add only the user-readiness handoff and repeated, page-qualified read-only capture to TOOL-018, and keep the live observation as a separate user-authorized step.
