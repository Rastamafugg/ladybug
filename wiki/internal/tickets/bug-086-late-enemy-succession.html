BUG-086 — Later-level enemy succession and preview Draft

High-risk · P2 · created 2026-10-01 · source fe160ae389145d24083218ded05ba9cdca781474

Approval brief

Objective and motivation

After the initial enemy-type cycle, show and spawn the next enemy type in the requested order. A skull-killed enemy becomes the next preview and the timed replacement without advancing or losing the ordinary type cursor.

Observed behavior and source evidence

In src/enemy_runtime.s, enemy_release_impl selects the first empty eight-byte actor record and stores no enemy type there. enemy_frame_number derives type from stage and record index. Dormant nest composition sets ENEMY_WORK=0 before draw_enemy_stage, so the preview is tied to record zero rather than a separately recorded next-release identity. The examined flow has no explicit next-preview or pending-dead-type fields. This confirms the state-ownership gap in source; it does not prove the visible mismatch on every death/slot order.

The arcade source page documents parts 1–8 with their part-specific groups, part 9 with types 1–4, and later parts rotating adjacent four-type groups (part 10 uses 2–5). The user explicitly confirmed this documented arcade progression on 2026-10-01; the fixed-1–4-forever alternative is excluded.

Scope and proposed behavior

In: authoritative next-preview identity, normal succession cursor, one pending skull-death type, and reset/consume handoffs across stage, release, death, and nest rendering. Out: movement/AI, scoring, skull collision, initial type-cycle changes, life markers, animation cadence, and queueing multiple dead types.

Prototype: ordinary releases consume the current four-type group in order and preview the next item. A skull death replaces the preview with that type and uses the existing release deadline. A second death before that deadline overwrites the pending type with the newest processed death while preserving the original deadline and normal cursor. At expiry, release the latest type, then resume the saved cursor. This is a single latest-death override, not a queue.

Prototype, scenarios, and acceptance

The deterministic model in prototype_enemy_succession.py and its output covers the ordered four-type group, preview, two deaths before one deadline, latest-death replacement, and normal cursor resumption. Tick numbers are illustrative. The model does not establish arcade dwell, CoCo fit, or source behavior.

Acceptance must verify the post-eight initial four-type group in order and its next preview; a death in each relevant actor slot; death immediately before expiry; two deaths before one expiry; release of the latest dead type at the unchanged deadline; and normal cursor resumption. Pair cases only where record slot changes type selection. Natural stage progression and persistent nest replay are integration coverage after a current ROM exists.

Confirmed group policy, class, and design gates

The user confirmed arcade adjacent-group progression. Keep this ticket Draft for authoritative type-state storage, release/death/rendering proof and physical capacity. High-risk: authoritative type state crosses stage reset, timed release, skull death, record selection, nest preview, and persistent framebuffer publication.

Candidate logical state owner is src/enemy_runtime.s, with fields named ENEMY_NEXT_TYPE, ENEMY_PENDING_TYPE, and ENEMY_PENDING_VALID. Initialize/reset in enemy_init_impl/reset_enemy_state; select the stage group from next_stage in src/main.s; update the override in the skull-death path; consume it in enemy_release_impl; render ENEMY_NEXT_TYPE in the nest compositor. Physical addresses are unassigned: all eight bytes at $A470 in each actor record are used, and ENEMY_RELEASED=$0059 is an existing release counter that must not be repurposed. A direct-page/resident/cold ownership and capacity audit is required before Ready.

2026-10-01 — Source fit and allocation review; no implementation approval

The isolated candidate encodes type0–7 in bits4–6 of the enemy record state byte while retaining bit0 as active, and tests page-34 bytes $A89D-$A89F for the normal cursor, pending death type, and cache type. It preserves the confirmed arcade group formula and the one latest-death override policy in source. This is source-level behavior only; no runtime sequence or user-visible result has been verified.

Direct lwasm 4.24 assembly passes for the adaptive main and enemy sources and the nonadaptive main source. Adaptive resident end is $DFD4 (8148/8192 bytes, 44 free); nonadaptive resident end is $DFFE (8190/8192, 2 free). In both profiles the immutable helper pack ends at $FDFA, leaving 6 bytes before $FE00; the pre-placement zmb ENEMY_CACHE_GUARD_HELPER-* and final asset bound pass. The adaptive enemy module ends at $17FB, 5 bytes before active-stage RAM at $1800, with the fixed object-mask LUT still at $17A0. Nonadaptive enemy assembly fails the exact pre-LUT guard zmb $17A0-* with a negative block of 25 bytes. It emits no valid nonadaptive module map or executable. The evidence and output hashes are in RSCH-014-E fit evidence.

The allocation trial moves the 12-byte cache guard, 25-byte normal selector, and 13-byte preview packer into executable immutable tail bytes $FDC8-$FDFA. It also adds a 3-byte JMP build_enemy_nest_cache at fixed module address $0824. These changes expand the module ABI and assign executable ownership to the immutable ROM tail. They are a High-risk design candidate only, not an approved implementation. If retained, the approval and assignment must include both src/main.s and src/enemy_runtime.s; the earlier read-only-main assignment boundary no longer fits this candidate. A PM/coding-architect reassessment must select a viable all-profile allocation before any further allocation edits.

The bounded shrink pass found no safe 25-byte reduction. Packed live-frame selection already replaces stage/slot reconstruction and recovers about nine bytes by the cache-builder region. Sharing the normal selector does not remove the release cursor, packing, or cache-preservation work. The earlier supported LBSR-to-BSR reductions remain. No LUT relocation, copy-loop timing change, renderer cadence change, profile exclusion, or active-stage-boundary change is acceptable. A resident helper at $DFD4 is not cross-profile viable because the nonadaptive resident has only 2 bytes before $E000.

PERF-005 remains the broad future whole-tree release-capacity review; it does not replace BUG-086's local pre-LUT, resident, immutable, and active-stage gates. Keep BUG-086 Draft. No complete all-profile ROM or runtime probe exists, and the behavior contract is not approved for implementation.
