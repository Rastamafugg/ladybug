Objective and motivation

Provide one reusable way to write and verify SHA-256 checksum lists for generated candidate packages so a Windows-created package can be checked by the project's WSL/Linux sha256sum -c commands. The writer must emit LF line endings explicitly, and the verifier must reject a CRLF manifest before any build command starts. This prevents a formatting problem from consuming a bounded build attempt.

The exact program that wrote the earlier bad manifests is unknown. This ticket addresses the observable workflow gap: candidate packages have no shared writer or common preflight for generated checksum-list files.

Evidence and baseline

  • repro/feat010-only-candidate-20261031-r3/input-manifest.sha256 was recorded with CRLF endings.
  • repro/feat010-source-docs-candidate-20261101-01/control-fixtures.sha256 had seven CRLF-terminated records. The content hashes independently matched all seven fixture files, but sha256sum -c treated the trailing carriage return as part of each filename and failed.
  • Candidate packages are under ignored /repro. Current .gitattributes sets LF for *.sh only. A Git rule for tracked *.sha256 files therefore cannot by itself protect these generated package manifests.
  • Candidate feat010-source-docs-candidate-20261101-03 was prepared with an explicit LF manifest writer and pre-build LF/hash preflight. Its package is preserved and has not been qualified.
  • At the current worktree baseline, core.autocrlf=true; the tracked shared-verifier-base.sha256 has LF in the Git index but CRLF in the working tree. git check-attr reports no text or eol rule for it.

These are two occurrences in generated candidate manifests, not evidence that every checksum file is malformed. They do show that the format is not enforced consistently. No source or user editing tool has been identified as the author of the CRLF bytes.

Scope

In: add *.sha256 text eol=lf to .gitattributes for tracked checksum-list files; add scripts/candidate_manifest.py with write and verify operations for generated candidate packages; add focused tests in scripts/test_candidate_manifest.py; document use in wiki/internal/tooling/build-workflow.html.

Writer input: take an explicit UTF-8 JSON array of package-relative paths; do not discover inputs by glob. The command shape is write --root ROOT --manifest RELATIVE_MANIFEST --files-json RELATIVE_JSON_LIST. The manifest and listed files must resolve inside ROOT. Output paths use normalized forward slashes and are sorted lexically. Reject absolute paths, ./.. traversal, symlink escapes, backslashes, and control characters. The writer emits the standard GNU sha256sum -c record form as bytes: lowercase 64-character SHA-256, two spaces, relative path, and exactly one LF after each record.

Verifier: verify --root ROOT --manifest RELATIVE_MANIFEST is read-only. It rejects CR bytes, malformed or duplicate records, unsafe paths, missing files, and digest mismatches. It does not silently repair a malformed manifest. The command that consumes a package runs the verifier and GNU checksum consumer before its build phase using an &&-chained sequence; no new build wrapper or process-launch layer is added.

Out: changing hash algorithms or JSON receipts; changing global Git newline settings; normalizing every file under repro/; editing or re-identifying the frozen -01 or -03 candidates; rerunning FEAT-010 builds; emulator/runtime work; game-source changes; any additional implementation commit beyond the user-authorized four-file commit 3738b660ef27f5ec6b0bcf686a8fe50cfbd4eaac; adoption or release work.

Acceptance criteria

  1. Writing the same package manifest twice produces byte-identical, sorted, LF-only output.
  2. A valid generated manifest passes the Python verifier and the project's sha256sum -c consumer.
  3. Focused tests show that CRLF, malformed records, duplicate/unsafe paths, missing files, and incorrect digests are rejected before build dispatch; the valid LF control passes.
  4. .gitattributes reports text and eol=lf for tracked *.sha256 files without changing unrelated file attributes or global Git configuration.
  5. A documented candidate command sequence runs the Python verifier and sha256sum -c from the package root before the build command, chained with &&; a CRLF negative skips a harmless sentinel build command.
  6. Each offline command has a 30-second work limit plus up to a 1-second termination grace. The work limit is an estimate, not a measured requirement. Record first-attempt duration and result, including timeout or early failure; stop after the first failure pending reassessment.
  7. Retain concise test output, the helper and test hashes, Git attribute evidence, and one positive and one CRLF-negative manifest result. Do not retain duplicate package payloads.
