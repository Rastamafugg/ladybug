This report covers input sampling, cadence, turning, collision footprint, and generated name-entry geometry. No build, emulator probe, production edit, or shared wiki edit was performed. The checkout is dirty; relevant current working-tree hashes are src/demo_runtime.s 4463e5020a0ec62893a84fc11d5c745c33935d5d, src/presentation_runtime.s 70934e478c3954f8ba328a2eabda1e372ad8148b, src/main.s 046dbf7cd825dc77419352b89908b2944eb04720, scripts/build_presentation.py 215991a7d170c311331247afd78f9b4488d4120b, and scripts/verify_feat003_highscore_test.py 2b37abf60ea050b74a185f175326f41742a702ce. Confirmed source findings

  1. Input acquisition is shared. Main gameplay and the active complete name helper use the same direction resolver: src/main.s:2096-2180 and src/shared_text_ranking.inc:773-795 resolve/read JOY_DIR, while src/main.s:2174-2178 persists PLAYER_WANT.
  2. Movement granularity is structurally comparable, but scheduling is unverified. Main gameplay advances PLAYER_FB by 2 bytes horizontally or 320 bytes vertically per player_tick, increments PLAYER_STEP, and completes four updates for an 8-pixel tile (src/main.s:2439-2480). The active complete name helper uses the same 2-byte/320-byte deltas and initializes PRES_NAME_STEPS to 4 (src/shared_text_ranking.inc:773-825). Both paths contain alternating-phase gates, but source inspection does not prove their real runtime call cadence.
  3. Turning semantics differ materially. Gameplay buffers a requested direction, retries it at the approaching junction, and has explicit opposite-direction rebasing/late-turn snap (src/main.s:2270-2360). The active name helper chooses PLAYER_DIR only when PRES_NAME_STEPS is zero, then holds that direction for four 2-pixel updates (src/shared_text_ranking.inc:782-850). A new perpendicular request during a partial traversal is retained only in PLAYER_WANT and is not tested until arrival. This is a confirmed source discrepancy capable of producing a less responsive feel around letter-separating walls.
  4. Active name collision uses the authored 24×24 full-edge table. src/shared_text_ranking.inc:866-907 computes local X as screen-space PLAYER_CELL_X - 8, reads PRESENTATION_NAME_ENTRY_FULL_EDGE_MASK_TABLE, and tests the requested N/E/S/W bit. Arrival action lookup applies the same normalization at src/shared_text_ranking.inc:908-925. This path does not call gameplay can_move and therefore has no gameplay gate rotation or dynamic maze-state behavior, which is expected for the static entry screen.
  5. Generated footprint expansion applies to the perimeter only. scripts/build_presentation.py:472-539 parses authored inner-wall cells and adds the perimeter, then blocks every local column x==22 and row y==1 for the sprite’s right/above extent. Inner-wall cells themselves are cleared, but no neighboring cells around inner walls receive the same footprint expansion. Whether that permits visible internal-wall overlap is unresolved from source alone.
  6. The 9×5 node edge table is emitted but not consumed by the active helper. enter_high_score_edge_masks generates it at scripts/build_presentation.py:454-469; the active complete helper references only the full-maze table at src/shared_text_ranking.inc:866-907. The historical full-maze requirement supersedes the 9×5 graph; this report treats the unused table as context only.

Cause classification

Confirmed source defect: name-entry turning is cell-locked and omits the gameplay buffered/late-turn behavior. If the requirement is gameplay-like steering, this is the direct control-path discrepancy.

Unconfirmed runtime causes: the reported alternating or jumping ladybug, visible overlap, internal-wall overlap, and exact wall feel cannot be attributed from this source review. They require a current-artifact runtime trace proving helper bytes, player coordinates, step counter, destination pixels, and the authored internal-wall route. The perimeter-only footprint expansion may explain boundary behavior, but no live route was executed here.

Rejected explanations

Input hardware or joystick polarity is not the leading source explanation: both paths share the same direction resolver and dead zone. A one-pixel-per-update model is contradicted by source: both paths use 2-byte horizontal or 320-byte vertical deltas, four updates per 8-pixel tile. Actual cadence remains unverified. Gameplay collision code itself is not being accidentally reused by name entry; the active helper explicitly reads its generated full-edge table.

Repair direction and minimal future verification

Future approved repair should preserve the existing 2-byte/320-byte deltas and four-update 8-pixel traversal, then add a bounded name-entry turn policy equivalent to gameplay’s buffered request and junction retry, with explicit neutral-stop behavior. Preserve the active authored full-maze geometry. The smallest runtime check is one current-artifact high-score route forced through a perpendicular request during a partial four-update traversal, followed by an authored inner-wall approach and a perimeter approach. Record phase marker name_joy_ready, deadline ≤60 seconds, JOY_DIR/PLAYER_WANT, PRES_NAME_STEPS, screen-space and local coordinates, and both destination/visible-owner pixels. Success means neutral input freezes without losing progress, a legal buffered turn takes at the first eligible junction, wall and footprint edges remain blocked, and no prior cursor pixels remain. Timeout means the marker or expected return was not reached; it is not proof of target-code slowness.
