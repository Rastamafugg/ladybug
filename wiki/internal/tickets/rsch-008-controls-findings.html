RSCH-008 — Controls findings

Source diagnosis · controls owner · 2026-09-12

Scope and source identity

This report covers input sampling, cadence, turning, collision footprint, and generated name-entry geometry. No build, emulator probe, production edit, or shared wiki edit was performed. The checkout is dirty; relevant current working-tree hashes are src/demo_runtime.s 4463e5020a0ec62893a84fc11d5c745c33935d5d, src/presentation_runtime.s 70934e478c3954f8ba328a2eabda1e372ad8148b, src/main.s 046dbf7cd825dc77419352b89908b2944eb04720, scripts/build_presentation.py 215991a7d170c311331247afd78f9b4488d4120b, and scripts/verify_feat003_highscore_test.py 2b37abf60ea050b74a185f175326f41742a702ce. These hashes include existing dirty changes and are source evidence only.

Confirmed source findings

  1. Input acquisition is shared. Main gameplay and the name helper both use PRES_MAIN_READ_JOY/read_joystick. src/main.s:2096-2180 resolves a four-way direction, writes JOY_DIR and persists PLAYER_WANT; src/demo_runtime.s:782-805 samples the same state before name movement.
  2. Cadence matches the current gameplay schedule. Main gameplay sets PLAYER_TICK_PENDING on alternating simulation phases (src/main.s:654-663) and advances one pixel per player_tick call, completing four pixels per cell (src/main.s:2439-2480). Name entry gates on FRAMES+1 parity, then advances one pixel and uses PRES_NAME_STEPS=4 (src/demo_runtime.s:785-805, 814-858). Static source therefore supports approximately the same 30 Hz logical movement and four-pixel cell traversal; runtime timing remains unverified.
  3. Turning semantics differ materially. Gameplay buffers a requested direction, retries it at the approaching junction, and has explicit opposite-direction rebasing/late-turn snap (src/main.s:2270-2360). Name entry chooses PLAYER_DIR only when PRES_NAME_STEPS is zero, then holds that direction for all four pixels (src/demo_runtime.s:791-805). A new perpendicular request during a partial step is retained only in PLAYER_WANT and is not tested until arrival. This is a confirmed source discrepancy capable of producing a less responsive feel around letter-separating walls.
  4. Active name collision uses the authored 24×24 full-edge table. name_can_move computes local X as screen-space PLAYER_CELL_X - 8, reads PRESENTATION_NAME_ENTRY_FULL_EDGE_MASK_TABLE, and tests the requested N/E/S/W bit (src/demo_runtime.s:875-911). Arrival action lookup applies the same X normalization (src/demo_runtime.s:913-945). This path does not call gameplay can_move and therefore has no gameplay gate rotation or dynamic maze-state behavior, which is expected for the static entry screen.
  5. Generated geometry deliberately includes a broad footprint exclusion. scripts/build_presentation.py:472-539 parses authored inner-wall cells, adds the perimeter, then blocks every local column x==22 and row y==1 because the 16×16 sprite extends one tile right and one tile above its anchor. It clears both sides of every edge touching those cells. This matches the documented sprite-footprint intent, but it changes the walkable topology beyond the authored wall glyphs and must be checked against the desired letter routes.
  6. The 9×5 node edge table is emitted but not consumed by the active helper. enter_high_score_edge_masks generates the selectable-node masks at scripts/build_presentation.py:454-469 and emits their table constants at 1602-1618. The active src/demo_runtime.s references only PRESENTATION_NAME_ENTRY_FULL_EDGE_MASK_TABLE (875-884); no runtime reference to PRESENTATION_NAME_ENTRY_EDGE_MASK_TABLE exists. This is a confirmed stale/unused generated artifact, not by itself a movement failure.

Cause classification

Confirmed source defect: name-entry turning is cell-locked and omits the gameplay buffered/late-turn behavior. If the requirement is gameplay-like steering, this is the direct control-path discrepancy. The generated 9×5 edge table being unused is confirmed cleanup debt.

Unconfirmed runtime causes: the reported alternating or jumping ladybug, visible overlap, and exact wall feel cannot be attributed from this source review. They require a current-artifact runtime trace proving the helper bytes, player coordinates, step counter, and destination pixels. The footprint exclusion may explain blocked or unexpectedly long routes, but no live route was executed here.

Rejected explanations

Input hardware or joystick polarity is not the leading source explanation: both paths share the same direction resolver and dead zone. A simple cadence mismatch is not supported by source: both paths are scheduled at alternating frame phases with four one-pixel advances per cell. Gameplay collision code itself is not being accidentally reused by name entry; the name helper explicitly reads its generated full-edge table.

Repair direction and minimal future verification

Future approved repair should preserve the existing four-pixel cadence and full-edge footprint contract, then add a bounded name-entry turn policy equivalent to gameplay’s buffered request and junction retry, with explicit neutral-stop behavior. Decide whether the 9×5 edge generator should be removed or made authoritative; do not maintain two divergent geometry sources. The smallest runtime check is one current-artifact high-score route forced through a perpendicular request during a partial four-pixel step, followed by an authored inner-wall approach and a footprint perimeter approach. Record phase marker name_joy_ready, deadline ≤60 seconds, JOY_DIR/PLAYER_WANT, PRES_NAME_STEPS, screen-space and local coordinates, and both destination/visible-owner pixels. Success means neutral input freezes without losing progress, a legal buffered turn takes at the first eligible junction, wall and footprint edges remain blocked, and no prior cursor pixels remain. Timeout means the marker or expected return was not reached; it is not proof of target-code slowness.
