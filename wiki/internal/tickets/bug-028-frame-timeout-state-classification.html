Competing causes and discriminator

  1. Leading: shared phase-budget depletion. BUG-027 starts one 60-second deadline before complete-profile startup, then spends the remainder on a natural frame and four hydration frames. The primary socket timeout may therefore mean only that no wall-clock budget remained. Record monotonic elapsed and remaining milliseconds at every startup marker, frame entry, breakpoint hit, and pre-run boundary; reserve two seconds inside the same 60-second phase for timeout recovery.
  2. Target still running in the frame call tree. Hydrated state may enter a path that reaches neither return before the reserved recovery boundary. On primary timeout, an already-connected observer queries run state, pauses only if running, and records PC, registers, cycles, stack bytes, frame flags, FRONT-fault state, mapped symbol/range, and live bytes at PC.
  3. Breakpoint lifecycle mismatch. One or both exits or routine markers may not be installed when execution resumes. Before every run, query list_breakpoints and require an exact ID/address match with the journaled set; after every halt, correlate reported bp_id and PC.
  4. Monitor event-delivery mismatch. The target may already be halted at a configured exit while the primary client fails to receive or correlate the event. After primary timeout, the observer records get_run_state, last-stop reason, PC, and breakpoint ID before issuing any pause. A halted configured exit with matching live bytes confirms delivery/correlation failure.
  5. Artifact or mapping drift. BUG-027 passed the static contract and BUG-026 passed live enemy identity, making this lower probability. Recheck source/staged/live identity before interpreting any captured PC; mismatch fails before runtime diagnosis.

Scenarios, edge cases, and failure meanings

  • Pre-run identity and inventory: covers stale bytes and missing/wrong breakpoint IDs; any mismatch stops before target resume.
  • Natural frame then existing one-roamer hydration: reproduces the exact failing sequence without expanding mode, owner, phase, or actor coverage.
  • Primary receives a configured exit: durable evidence records the exit and remaining budget; no observer pause is needed.
  • Primary reaches the reserved recovery boundary: the observer snapshot classifies halted-at-exit, running-in-frame, running-outside-frame, or breakpoint-inventory failure within the same 60-second phase.
  • Observer unavailable or snapshot incomplete: fails the diagnostic and stops; do not reconnect, rerun, or extend the deadline.
  • Partial evidence write or process termination: the last complete journal record remains parseable through write-to-temporary plus atomic replacement. Missing required fields fail rather than becoming null passing evidence.

Acceptance criteria and target

  • Add a mutually exclusive --frame-timeout-diagnostic-only mode to the existing runner. Do not create another runner.
  • Persist a compact journal before and after every blocking monitor operation. Each record names phase, frame ordinal, monotonic elapsed/remaining milliseconds, requested operation, last mapped marker, breakpoint IDs/addresses, target state when known, registers/cycles when halted, FRONT-fault state, and source/staged/live hashes. The file must survive socket timeout and forced XRoar termination.
  • Use one 60-second total phase. Reserve at least two seconds from that same phase for the observer snapshot; neither the primary wait nor recovery may extend the phase.
  • Before each run, list_breakpoints must exactly match frame entry where applicable, five routine markers, normal RTS $0A07, and abort RTS $0A0A. Each received event must match both ID and PC.
  • After a primary timeout, the observer must classify the target within two seconds as halted at a configured breakpoint, running at a source-aligned frame-call-tree PC, running outside the source-aligned frame call tree, or inconsistent with the installed breakpoint inventory. Artifact mismatch remains a separate fail-closed result.
  • Success requires one evidence-backed cause classification with no unknown frame ordinal, last marker, remaining budget, target state, PC, or breakpoint inventory. Merely reproducing another unclassified timeout fails.
  • No production/build input, ROM, XRoar, runtime behavior, timeout ceiling, worklist, isolated result, projection, or memory-capacity value changes.

Dependencies, ordering, risks, and alternatives
