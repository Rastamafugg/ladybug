Approved test card

  1. Purpose and risk: name the behavior/defect and why the test is needed; distinguish unit, source/oracle, integration, performance, robustness and manual acceptance.
  2. Setup and repeatability: identify source/ROM/profile and fixture hashes; specify inputs, seed or chooser state, clocks/scheduling where relevant, and framebuffer history. Prove the setup reaches its start marker within bounds. Disclose all forced state. Do not require a randomly chosen enemy route to discover the fixture.
  3. Expected result: define the independent oracle, observed marker/output, tolerance and its rationale, pass/fail rule and a negative control that demonstrates the relevant defect is rejected. Historical exceptions may allow listed failures but must not require the failures to persist.
  4. Cost and stop rule: give the exact command/prerequisites, named phases, elapsed deadline for each entire phase, callback cap when needed, estimated or measured command duration clearly labeled, and retained failure state. Initial runtime phases remain at most 60 seconds. Preserve the current two-rejected-probe/two-tool-timeout reassessment rule; no retry-until-pass, repeated random-route searches, hidden matrix or autonomous scope widening.
  5. Result classification: report product assertion failure, setup/observer failure, missing coverage and explicitly approved waiver/manual result separately. Any required missing coverage prevents acceptance; it is not a product-defect claim or a pass. Manual cases remain pending until the user supplies results.
  6. Approval and ownership: record user approval of the gating outcome, setup policy, target/tolerance, bounded work and automated/manual split. Identify owned files, existing harness, dependency order and retained evidence before Ready. Parent integrates and reviews; an executor cannot add a new gate, change the contract or repair unrelated debt without renewed approval.

Approval may be part of one ticket brief; no extra approval ceremony is required when the same card was explicitly approved there. Normal fixture mechanics that preserve the approved contract remain execution details. Material changes to the tested outcome, state-write authorization, target, cost/risk boundary or automated/manual split require renewed approval. Non-gating diagnostics are labeled and bounded; they cannot become release gates without approval.

  • Acceptance: all listed workflow artifacts convey the same contract, include one concrete card example and stop/escalation example, preserve existing hard limits/waivers, resolve local links/IDs, and pass scoped diff checks. No production/scripts/build output changes.

Dependencies/order: explicit user adoption approval → exact documentation assignment → direct parent edits → QA consistency/example/link checks.
