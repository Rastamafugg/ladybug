Approval brief

Objective and motivation

Give shared HUD fields one named layout definition and one safe value handoff, while gameplay and ranking remain owners of their values. Correct the Instructions page so its ×2, ×3, and ×5 indicators start inactive gray and turn blue only when the matching heart is earned. Match the approved arcade HUD reference for the named gameplay fields. Set all nine initial high-score records to 10,000 and put a newly committed score ahead of existing equal scores. After the runtime ranking table is initialized, the High Score screen must display the same record values held in that table. Before initialization, leave the current Tiled-authored fallback unchanged. The user has deferred correcting this and other Tiled-screen graphics; cold-fallback appearance is not an FEAT-013 gate. This is not a fix for historical Options/Credits crash reports.

Plain-language behavior

The provider copies values from the part of the game that owns them into a small shared low-RAM snapshot. Screens can read that snapshot while the game borrows a different bank for code or data. Small new wrappers call existing drawing routines and paint the selected hidden BACK image; existing damage replay and frame publication make it visible.

Gameplay and demo refresh player-owned fields as they change, including score, lives, stage, vegetable, multiplier, and EXTRA/SPECIAL progress bits. The shared snapshot reserves an eight-byte second-player value block in the same field order as player one: score, stage, lives, multiplier, SPECIAL bits, and EXTRA bits. The current one-player game leaves that block unused and hides the 2ND label and values; future two-player ownership and update rules remain out of scope. Copy each changed owner value after its update, including when completed word bits are reset. TOP is separate: it always means the highest record currently stored in the high-score table. A player's live score can pass TOP without changing it. TOP changes only after Game Over when a qualifying name entry is committed to the table, and the provider then rereads table row one. A higher score changes TOP after commit; a score tied with row one changes TOP's name after commit but not its numeric value; a tie below a higher leader leaves TOP unchanged. If no record is committed, TOP stays the same.

At boot, after boot data streams are retired, clear the snapshot and seed TOP from the table's initial first row before the first read. Seed all nine ranking rows to 10,000 when the runtime table is first initialized. Before runtime ranking is initialized, the High Score renderer keeps the current Tiled-authored rows visible; FEAT-013 does not change that fallback. After initialization, the renderer must show all nine runtime records in table order, including each seven-byte name and score; initially, all nine scores are 10,000, and later commits appear at their table positions. Keep the existing seven-byte CoCo record-name format; the nine-character arcade sample name does not widen it. Keep the name keypad, cursor, and ranking rows local to their screens. Preserve the existing Level Start rules: its score and stage preview are screen-local and context-dependent, so the shared snapshot must not overwrite them. Game Over continues to hold the final gameplay image.

After the core HUD changes, the later FEAT-011 route work must preserve gameplay-owned HUD values on EXTRA/SPECIAL, refresh a value only after its reward commits, and resync gameplay values before the first visible frame on return. Those intermission calls, costs, and visible checks are deferred until the routes exist; they are not part of this FEAT-013 candidate or its Ready dependencies.

The shared font is the collection of 8-by-8 pixel patterns for letters and numbers, with eight bytes describing each glyph. A mask is an 8-byte bitmap, one byte per glyph row, whose bits mark the pixels to draw. The tile dispatcher routes a tile code to either the graphic blitter or shared text-mask painter.

Reusable code versus new code

New runtime code is limited in this sketch to the provider/wrappers, snapshot initialization, and successful-record tail. The template reader/validation is new host code; its generated ROM cost is unknown.

Provisional placement is the resident free tail beginning at $DF8C, reached through PAR6 page $3E.
