Authoritative expected contract

The current user requirement is authoritative for this investigation: the default is three total Lady Bug lives, including the active Lady Bug. At the initial gameplay handoff, the rightmost of the three displayed life indicators must turn to face down, walk off-screen, then reappear walking upward into the maze start position. After that handoff, exactly two reserve indicators remain visible. This requirement supersedes the older wiki wording that describes “three reserve lives” and excludes the active actor (game/overview, lines 84–94); that page is stale for this specific count contract.

The expected natural count sequence is therefore: initial handoff leaves two reserves; a death with two reserves leaves one and starts a replacement; a death with one reserve leaves zero and starts the final replacement; a later death with zero reserves enters game over. The reported rightmost-marker motion belongs to the initial three-total-life handoff; the existing death walk-off history is an adjacent rendering pattern, not proof that the current initial path is correct.

Confirmed current source behavior

  1. Current state meaning and default: LIVES is direct-page byte $23, documented as “lives remaining” (src/main.s:180-214). init_game_state writes 3 to it and writes stage 1 (src/main.s:682-722). The active player is initialized separately, so the current state model treats LIVES=3 as three reserves plus an active Lady Bug. This is the confirmed default-count mismatch against the user’s three-total contract.
  2. HUD projection: draw_lives visits exactly three slots, indices 0..2, at HUD columns 33,35,37 and row 21. It draws slot i when i < LIVES and clears it otherwise (src/main.s:1264-1285); each marker is a fixed 2×2 authored tile shape (src/main.s:1315-1324). With the current initialization, the stage frame requests all three life indicators while an active player is also being initialized. There is no count-aware “rightmost marker becomes active” operation in this renderer.
  3. New-game presentation and handoff: boot defers gameplay initialization until the presentation level-start path (src/main.s:550-581). For a live credit/start, presentation_flow_tick sets live context and opens the level-start screen (src/presentation_runtime.s:183-199); after its hold, level_tick routes to live_begin (src/presentation_runtime.s:725-793), which calls init_gameplay (src/presentation_runtime.s:794-805). That initializer dispatches the main gameplay initialization and player setup. The current source has no initial-life handoff substate, no rightmost-slot selector, no south-facing initial walk-off, and no deferred conversion from three displayed lives to two reserves.
  4. Existing automatic maze entry: init_player seeds cell (12,22), framebuffer pointer $89EC, north-facing direction, and PLAYER_MANUAL=0 (src/main.s:2066-2093). While manual control is false, player_tick advances automatically; when it reaches (12,18), it sets direction and request to neutral and stops (src/main.s:2244-2275, src/main.s:2361-2373, src/main.s:2439-2484). This supplies an upward entrance for the already-created active player, but it does not perform the requested rightmost life-marker conversion.
  5. Natural death entry and current decrement: enemy contact sets DEATH_STATE=1, clears player direction/request, and starts enemy reset (src/enemy_runtime.s:360-379, src/enemy_runtime.s:522-528). The main loop dispatches death_tick while the state is nonzero (src/main.s:624-677). Current death states run the measured shrink/wing sequence, then dt_finish_wings enters state 3 with a 37-frame timer; dt_blank only counts that timer (src/main.s:3552-3665). At blank completion, dt_finish_blank tests LIVES before decrementing, decrements once, invalidates both player ledgers, calls init_player, clears the death state, and requests RF_LIVES|RF_PLAYER (src/main.s:3661-3679). Current behavior with default LIVES=3 permits three post-start replacements before zero, then a fourth death reaches terminal state; with the required post-entry reserve count 2, the same routine would produce the expected two replacements and then terminal game over. The death decrement ordering itself is therefore usable after the initial-count correction, subject to runtime verification.
  6. Stage advance ownership and count preservation: in the natural live path, normal_tick detects STAGE_PENDING, calls PRES_MAIN_NEXT_STAGE, records next-stage context, and opens level start (src/presentation_runtime.s:290-328). The installed main next_stage increments STAGE, resets maze/gates/entities/player/enemy, and does not write LIVES (src/main.s:724-745). When the level-start hold expires with PRES_CONTEXT_NEXT_STAGE, level_tick clears context and releases directly without calling live_begin or init_gameplay (src/presentation_runtime.s:725-737). Thus natural stage advance preserves the current reserve count; it does not reset the three-total-life session to three new reserves.

Confirmed defects, adjacent history, and uncertainty

Confirmed defect 1 — count: the current new-game state creates an active Lady Bug plus LIVES=3 reserve markers, yielding four life units against the requested three-total default. The rightmost marker is not consumed during initial entry.

Confirmed defect 2 — initial choreography: no current source path turns the rightmost of the three initial indicators south, walks it off-screen, and re-enters it upward. The active player is initialized directly below the maze and walks upward independently. The user-visible initial sequence is therefore missing.

Adjacent historical evidence: commit 2c6d3a4 had a dt_finish_wings → state 3 path that selected DIR_SOUTH, placed the player at the marker slot calculated from the pre-death count, moved it down for 24 ticks, then decremented and called init_player. That was a death replacement sequence, not the initial new-game handoff. Commit 5d7365e replaced it with the measured 37-frame blank and direct dt_finish_blank path. It is useful as an implementation pattern only; it does not establish current initial behavior.

Uncertainty: source inspection does not prove the exact current frame at which the three life icons are first published or the visual position of the separately initialized player. A runtime capture must confirm the initial publication boundary and ensure the correction does not reintroduce the historical A/B respawn ledger issue recorded by BUG-006.

Smallest discriminating verification after an approved repair

  1. Initial three-total handoff: use natural credit/start input and capture the level-start-to-gameplay boundary. Require the initial scene to expose three life indicators, then require the rightmost indicator to become the south-facing active entrant, move off-screen, and return north into the maze. At the first stable maze-start position, require exactly two reserve indicators, an active player, and a total of three life units. Risk covered: default count and missing initial choreography.
  2. Natural replacement count: force ordinary deaths through the natural DEATH_STATE path. Starting after the initial handoff at two reserves, require first death → one reserve plus replacement, second death → zero reserves plus replacement, and third death → terminal game over with no replacement. Risk covered: decrement timing, final-reserve handling, and active-versus-reserve conflation.
  3. Stage preservation: reach a live stage-clear boundary with a nonzero reserve count, require next_stage to increment STAGE without changing LIVES, and require the next level-start hold to take the next-stage context path without a second new-game initialization. Risk covered: accidental reset of session life state at stage advance.
  4. Adjacent framebuffer regression: run natural A/B publication after the initial handoff and after one replacement; require the active player to remain present on both owners while the expected reserve count remains stable (two after initial entry, one after the first replacement). Risk covered: interaction between the new marker handoff and BUG-006 owner-local player history.

These checks cover the distinct count, initial-animation, terminal, stage, and persistent-framebuffer risks. They are required runtime evidence, not current-revision passing evidence.

Repair boundary and residual risk

Candidate repair direction is to separate total-life/session state from reserve-HUD state at the live level-start boundary: retain the three-total default, convert the rightmost initial marker into the active entrant, and publish two reserve markers before normal control. Reuse the existing below-maze northward movement after the marker walk-off, but give the initial handoff its own explicit animation substate so it cannot be confused with death respawn. Preserve the current death decrement ordering only after initializing the post-entry reserve count to two. This is a repair proposal only; no implementation approval is inferred by this report.

Residual risks include the unverified current-revision pixels/timing, persistent A/B player-ledger publication after the new initial and replacement paths, the interaction with complete-profile presentation ownership, and the extra-life path (src/main.s:859-870) whose increment can exceed the three-slot HUD renderer. Those risks require separately scoped repair and QA work.
