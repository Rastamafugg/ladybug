Approval brief

Objective and motivation

Rewrite the project memory map as one informative narrative of the current code and its memory ownership. The existing page combines general map documentation with dated snapshots, experiments, proposals, and references to prior options. Those entries obscure the current account and can leave obsolete allocations looking authoritative. Keep only explanations and rationale that still help readers understand the current implementation; preserve historical detail through links to its canonical tickets.

Evidence and baseline

The baseline is repository HEAD be911f1e90fd41ae09ad619aee3ee148f61f1a6d on 2026-10-24. The target page has 50 section blocks and 51 second-level headings, mixing map topics with dated implementation snapshots and historical fitting proposals. The page itself is unchanged in the current worktree and is already linked from the implementation index. Current src/ and scripts/ files are clean relative to HEAD. Existing generated map and ownership artifacts have not been qualified as products of this source revision; no claim that their measurements are current is made here.

A focused source check found a concrete stale claim in the target's “Boot execution and legacy data-copy procedure” section: it labels direct execution from the 8 KiB cartridge code window as current. At this baseline, src/gmc_bootstrap.s runs its bootstrap from GMC bank 0, copies the loader to low RAM, stages the bank-1 runtime image, switches to all-RAM mode, publishes the staged image at $C000, and transfers to $C002. The source also marks $FE00-$FFFF as the forced-RAM/I/O region. The target already contains a separate obsolete self-copy investigation, and the lessons-learned page records that its earlier shadow-RAM model was disproven. This is a confirmed stale current-path description; the rest of the page has not yet received a complete source audit.

The source audit must use the current assembly and profile/configuration sources, including src/main.s, src/gmc_bootstrap.s and the active runtime modules, with scripts/build.sh and generated map/ownership outputs as corroborating evidence. A generated artifact is authoritative only after its source/build identity is established or it is regenerated from the current source.

Scope

In: rewrite wiki/internal/implementation/memory-map.html into a coherent current-state explanation; reconcile every retained address, size, owner, profile, overlay, and lifetime claim against current source and qualified build outputs; distinguish CPU-visible logical addresses, physical RAM pages, cartridge ROM source windows, and RAM copy destinations; retain relevant current rationale and link historical alternatives to canonical tickets. Keep the implementation index link if it remains accurate. Maintain the canonical ticket, ticket index, and dated project log.

Out: changing assembly, scripts, generated outputs, runtime behavior, memory allocations, build profiles, or product targets; rewriting linked tickets or raw reference material; adding memory-map tooling; and treating unresolved source/build disagreements as permission to modify code. A discovered code or tooling defect requires separate triage.

Scenarios and edge cases

  1. A reader needs to understand the current address-space layout and major owners from the page without reconstructing a timeline from dated fragments.
  2. Addresses reused across phases or mappings must be described with their owners and lifetimes so temporary overlays are not mistaken for simultaneous allocations.
  3. Cartridge source bytes, CPU-visible bank windows, and copied/decompressed RAM destinations must remain distinct.
  4. Profile-specific layouts and limits must be labeled by the profile that produces them; an old candidate fit must not appear as a current allocation.
  5. If assembly, build configuration, and a generated map disagree, the narrative must omit or qualify the unresolved claim and record the discrepancy for separate follow-up.
  6. Useful rationale from a historical proposal may remain only when it explains a current decision, with the canonical decision or ticket linked.

Options and recommendation

Adding a short summary above the existing dated sections would preserve the competing histories and leave two accounts of the map to maintain. Recommend replacing the snapshot stack with a topic-organized narrative, integrating only currently relevant rationale and linking historical evidence at its canonical ticket. This meets the requested single-narrative outcome while keeping detailed experiment records available.

Acceptance criteria

  1. The memory map reads as one current-state narrative organized by topic. It contains no dated activity-log or candidate-proposal sections; historical material is removed from this page or reduced to a current rationale with a link to its canonical ticket.
  2. The boot narrative describes the current GMC bank-0 bootstrap and bank-1 staging/publication flow, and labels the former direct 8 KiB execution and shadow-RAM self-copy accounts as historical, with the relevant canonical finding linked.
  3. Every retained factual claim about addresses, sizes, allocation limits, owners, profiles, mapped windows, source/destination locations, and temporal reuse is checked against current source and build configuration. Any generated map used is tied to this source revision or regenerated from it.
  4. The page distinguishes logical CPU addresses from physical pages and banked ROM source locations, and explains phase-specific aliases and lifetimes wherever the same storage is reused.
  5. No unsupported or unresolved claim is presented as current. Material source/build disagreement is recorded for separate follow-up rather than silently resolved by assumption.
  6. Existing useful internal links still resolve; the implementation index continues to link the page. The edited HTML uses the wiki shell and stylesheet, has unique IDs, and has no broken local file or fragment links.
  7. Only the approved wiki page and its necessary ticket/index/log records change. Source, scripts, generated build outputs, ROMs, capacities, and runtime behavior remain unchanged. No emulator run or gameplay test is required.

Verification plan and risks

  • Stale or incorrect allocation claims: audit retained addresses, extents, profile limits, and owners against assembly/configuration sources and source-qualified generated maps. This covers inaccurate current layout facts.
  • Stale boot execution model: trace the current bootstrap from bank-0 entry through loader copy, bank-1 staging, all-RAM publication, and the transfer to $C002. This covers retaining the superseded 8 KiB direct-execution description as current.
  • Incorrect temporal ownership: trace initialization, use, and retirement of reused regions through the relevant phase transitions. This covers aliases described as simultaneous or assigned to the wrong phase.
  • ROM/RAM location confusion: compare boot descriptors, loader/build layout, bank windows, and copy/decompression destinations. This covers source addresses being mislabeled as RAM or vice versa.
  • Unreadable or broken wiki page: check the page structure, unique IDs, local links/fragments, whitespace, and scoped diff. No gating test scenario is added, so DOC-014 test cards do not apply.

At proposal time, no build or complete current-source map audit had been performed. Existing generated maps record a different source revision, so this assignment creates source-qualified map evidence in an isolated build directory. No emulator run or gameplay test is included.
