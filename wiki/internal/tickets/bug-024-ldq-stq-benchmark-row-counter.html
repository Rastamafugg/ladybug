Approval brief

Objective and motivation

Repair the confirmed LDQ/STQ row-loop counter defect in the RSCH-004 benchmark, add a fail-closed scaling check to the existing runner, and regenerate the 1/2/4/8/16-row evidence. The intended outcome is valid row-dependent LDQ/STQ hot-path timing that can be compared with the portable byte-copy baseline. This ticket does not authorize a production optimization.

Evidence and baseline

The accepted RSCH-004 JSON, SHA-256 326902a5647cc0f4de72bad9eafa5bdd50cbfebf49d34c2fac76118d61f46edf, reports candidate LDQ/STQ medians of 11119 CPU cycles for every 1/2/4/8/16-row case. Correctness and guards pass, but the constant timing does not represent the requested work count.

RSCH-005 evidence, SHA-256 cee14d678e02850f8d0b65bab15c018facc40741804a710164fdd0be83929860, measures one LDQ at 8 cycles, one STQ at 8, one pair at 16, and the byte-equivalent copy at 38, with three identical samples and zero timeouts. It confirms the cause: q_hot_row loads Q_ROWS into B, then executes LDQ before DECB. Because Q is D:W and D is A:B, the second LDQ replaces B with source byte 5; the first row loads B=$86, so DECB produces $85 instead of decrementing the row count.

Observed versus expected

Reproduction: run python3 scripts/benchmark_6309_hotpaths.py --rows 1 2 4 8 16 --repeats 3 --timeout 5 against the current shared-workspace source. Observed: candidate LDQ/STQ is exactly 11119 cycles at every row count. Expected: candidate timing increases with row count, fits one fixed setup plus a stable per-row slope, and remains below the byte-copy baseline when correctness and identity checks pass.

Confirmed cause and discriminator

The cause is confirmed, not speculative. The loop counter is stored in a register owned by the measured instruction. The discriminating result is the RSCH-005 LDQ-only end state D=$1234, B=$34, combined with the isolated 16-cycle pair and the unchanged RSCH-004 reproduction. The repair must move count ownership out of A:B/D/Q; the corrected sweep must then scale with the requested row count.

Scope

In: replace the LDQ/STQ hot-path B counter in src/bench/6309_hotpath_benchmark.s with the existing direct-memory counter pattern; extend scripts/benchmark_6309_hotpaths.py to reject non-scaling row-count evidence; rerun and retain corrected evidence; synchronize this ticket, the ticket index, tooling page, and wiki log. Out: production assembly, TFM/OIM algorithm changes, XRoar source or timing behavior, assembler behavior, native mode, odd-address expansion, separate ROMs, loader/MMU/framebuffer ownership, gameplay, and hardware qualification.

Scenarios and distinct risks

  • One row: proves the final-iteration counter and branch boundary without relying on a taken-loop branch.
  • Two, four, eight, and sixteen rows: proves that the requested count controls executed work and that fixed setup is separable from a stable per-row slope.
  • Portable baseline versus 6309 candidate: proves the candidate comparison uses identical fixture shape, stride, source, destination, guards, and row count.
  • RSCH-005 isolated controls: guards the independent single-instruction timing and monitor boundary while the hot-path loop changes.
  • Authored/staged/live identity and repeatability: rejects stale ROMs, unexpected halts, missing markers, and host jitter before interpreting cycles.

Options and recommendation

  • Recommended: store Q_ROWS in RESULT_Q_STATUS before the loop and use DEC RESULT_Q_STATUS/BNE. The existing initialization code already uses this direct-memory pattern, and LDQ/STQ cannot alias the counter.
  • Rejected: retain B and save/restore it around each LDQ/STQ pair. This adds stack or transfer overhead to the measured candidate and obscures the intended operation cost.
  • Rejected: use U with LEAU -1,U. The project already rejected this pattern because LEAU does not establish the condition codes needed by BNE.
  • Deferred: redesign the benchmark around a new timing framework. The existing RSCH-004 runner is sufficient once count ownership and scaling validation are corrected.

Acceptance criteria

  • The Q hot-path loop no longer stores its row count in A, B, D, W, or Q; the baseline and candidate use the same direct-memory count and branch sequence.
  • All 1/2/4/8/16-row baseline and candidate cases pass live-byte, marker, halt, source/destination, guard, OIM, rejection, and baseline-byte-identity checks with three samples each.
  • For both baseline and candidate LDQ/STQ timings, medians increase strictly with row count. Per-added-row slopes from 1→2, 2→4, 4→8, and 8→16 agree within one CPU cycle after normalization.
  • The candidate LDQ/STQ median is lower than the portable baseline at every row count. Exact cycle targets are measured rather than projected.
  • The runner exits nonzero for a constant or non-scaling LDQ/STQ series, even if correctness and repeatability otherwise pass.
  • The unchanged RSCH-005 isolated command still reports boundary/LDQ/STQ/pair/byte medians of 2/8/8/16/38, all checks passing, and zero timeouts.
  • Corrected evidence records source/ROM/live/XRoar hashes, row counts, exact medians and slopes, repeatability, correctness, and the superseded RSCH-004 evidence hash.
  • No production source, release ROM, XRoar source, build input, capacity, or runtime behavior changes.

Dependencies, constraints, and risks

  • RSCH-005 is the cause authority and must remain passing unchanged.
  • The repaired RSCH-004 result supersedes only its invalid LDQ/STQ timing interpretation; historical TFM/OIM evidence and the original failing JSON remain retained.
  • The primary implementation risk is accidentally giving baseline and candidate different counter overhead. Source and runner checks must prove one shared counter sequence.
  • The primary evidence risk is accepting monotonic but nonlinear over-execution. The normalized slope assertion covers that risk.
  • Stop before exceeding the estimated 3% share or the 5% Compact ceiling. Reassess if either identified source file proves insufficient, a runtime probe times out twice, or the corrected result implicates XRoar or another subsystem.
