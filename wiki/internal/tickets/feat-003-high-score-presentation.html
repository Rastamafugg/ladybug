FEAT-003 High-Score Presentation and Name Entry internal

Complete the visible nine-entry high-score table and joystick-driven qualifying-score name entry removed from FEAT-002.

Approval brief

Objective and motivation

Finish the high-score behavior required by FEAT-002 without changing the approved seven-character name and three-byte score record format. The work is separated because the first complete visible renderer measured 203 bytes beyond the locked $1900-$1DFF module window, and final allocation must account for sound.

Evidence and baseline

  • Current revision passes the Plan A build with a 1280/1280-byte presentation module, 11398-byte cold payload, and 2053 GMC source bytes spare.
  • The current state slice stores nine records at $AF84, each containing a three-byte unsigned score and seven name bytes, and performs bounded insertion.
  • The rejected visible renderer used draw_tile_id, the resident digit helper, and a 9×7 display cache; it ended at $1ECB versus the $1E00 module limit.

Scope

In scope: visible seven-character names, visible decimal scores through 9,999,999, authored high-score row placement, coin overlay preservation, joystick traversal over the enter-high-score grid, immediate character append, END completion, strict qualification, descending insertion, ninth-entry truncation, and forced natural/integrated verification.

Out of scope: attract/instruction actor animation, sound runtime implementation, changes to the approved record format, battery-backed scores, resident-window expansion without renewed approval, and changes to normal gameplay rules.

Scenarios and edge cases

  • Render all nine rows with seven name cells and seven decimal digits, including zero values and a seeded 9,999,999 record.
  • Traverse letters, symbols, blanks, repeated cells, and END; append each visited character once and prevent writes beyond seven bytes.
  • Verify qualifying scores above the first entry, between entries, above the last entry, equal to an entry, and non-qualifying values.
  • Verify one insertion, lower-record shifting, ninth-record removal, held END behavior, interruption, and both framebuffer-owner start orders.

Options and recommendation

  1. Preferred: compact map-load or tile-patch rendering within Plan A, with a jointly reserved sound budget and at least 512 bytes of post-feature combined headroom.
  2. Alternative: expand the presentation module only as part of a combined high-score-plus-sound capacity revision. A 224-byte local expansion is insufficient for the proposed sound ceiling and release reserve.

Acceptance criteria

  • Visible names and seven decimal score digits match all nine session records, including a forced 9,999,999 value.
  • Name traversal and END insertion meet all scenarios without mutating incomplete entries.
  • The selected design passes module, stack, cold-payload, GMC-source, direct-page, and sound-reservation capacity gates.
  • Build, presentation proof, forced rare-path checks, and the integrated GDB/XRoar verification pass on the combined revision.

Assignment contract

  • Approved objective and non-goals: unchanged from the approved brief after explicit approval.
  • Owned artifacts: presentation runtime, presentation generator/verifiers, FEAT-003, linked ticket index/log, and generated evidence.
  • Implementation constraints: preserve the seven-byte name and three-byte score records; no unapproved resident, bank-3, frame-time banking, or sound ABI changes.
  • Required commands: scripts/build.sh build, scripts/build.sh verify-gmc, presentation proof, Python compilation, and forced/integrated high-score scenarios.
  • Commit: one bounded implementation commit after approval and Ready transition.

Verification and completion

Pending approval. Completion requires current-revision rendering evidence, name-entry evidence, capacity results jointly accounting for sound, and QA review.
