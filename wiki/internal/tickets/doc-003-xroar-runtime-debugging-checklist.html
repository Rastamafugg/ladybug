Approval brief

Objective and motivation

Add a reusable checklist to the canonical XRoar tooling page. It must guide a future investigator from exact artifact identification through bounded phase probes, natural-input reproduction, live-byte validation, cause discrimination, repair verification, and retained evidence without repeating the FEAT-002 and BUG-008 failures.

Evidence and baseline

RSCH-002 records that symbol intent was interpreted without first proving live-byte identity, deadlines expanded without valid marker semantics, and a hardware path received weight before software delivery and observation-tool defects were eliminated. BUG-008 records that forced event dispatch proved one real sparse-resolver defect but bypassed the natural credit-screen renderer, where a second register-preservation defect overwrote resident code. The current XRoar page documents commands and limitations but does not provide one ordered, reusable diagnosis checklist.

Scope

In: one checklist section in wiki/internal/tooling/xroar.html; links to the evidence ladder, BUG-008, RSCH-002, and relevant lessons; explicit natural-versus-forced input guidance; phase deadlines and stop rules; artifact/source/staged/live comparisons; register and call-contract checks; MMU/PAR and observation-tool validation; hypothesis ordering; repair and regression closure; ticket index and log updates. Out: game code, XRoar source, GDB scripts, new probe helpers, emulator automation, ticket-policy changes, and claims about private model reasoning.

Scenarios and edge cases

  • A natural keyboard path differs from a forced state or event-dispatch path.
  • GDB breakpoint installation races emulator execution or external XTest input.
  • A map symbol names expected code but live RAM contains loader data, stale code, or rendered pixels.
  • A corruption is observed during one phase but was written during an earlier screen or handoff.
  • A callee clobbers a register that its caller incorrectly treats as preserved.
  • A watchpoint, snapshot, timeout, or failed reattachment is an observation-tool limitation rather than target evidence.
  • A forced probe passes while the complete natural user-visible sequence fails.
  • An emulator or hardware hypothesis is considered before software, delivery, mapping, and tool candidates are separated.

Options and recommendation

Recommended: add the checklist as a named section in the existing XRoar tooling page. This keeps launch commands, GDB limitations, natural XTest input, and diagnosis order in one runbook without adding another navigation target. Alternative: create a separate debugging page and link it from XRoar; this provides more expansion room but duplicates context and increases link maintenance. No runtime or memory capacity changes occur under either option.

Required checklist sequence

  1. Record revision, dirty-state identity, build command, ROM hash, map files, emulator version, launch command, and exact natural reproduction.
  2. Define each phase, success marker, deadline, and timeout meaning before launch; keep the initial phase at or below 60 seconds and terminate exact owned processes.
  3. Install GDB breakpoints before releasing execution or sending XTest keys; distinguish real keyboard input from dispatcher or state injection.
  4. At the first unexpected boundary, compare authored bytes, packaged or staged bytes, and live destination bytes before interpreting the symbol or PC.
  5. Place code/data sentinels across preceding transitions so the first corrupting phase, not merely the first visible symptom, is identified.
  6. Validate MMU/PAR state, register ownership, stack state, routine clobber contracts, destination ranges, and the observation mechanism.
  7. Search exact corrupt-byte signatures through built payloads and calculate candidate write addresses before broad tracing.
  8. Rank software, build/delivery, mapping, tool, emulator, and hardware candidates; escalate undocumented hardware only with independent or authoritative evidence.
  9. Verify the minimal repair first through the complete natural sequence, then forced rare paths, capacity gates, and combined regression checks.
  10. Retain failing and passing markers, commands, deadlines, hashes, screenshots or framebuffer evidence, rejected hypotheses, capacity result, and residual risk in the owning ticket.

Required scenario walkthroughs

  1. Natural input race: a probe needs 5 then 1. Pass only if the checklist installs breakpoints before continuing and sending XTest input, identifies the events as natural emulator input, and does not substitute dispatcher injection.
  2. Mapped symbol mismatch: the PC equals a current map symbol but live bytes differ from the artifact. Pass only if diagnosis stops at authored/staged/live comparison before interpreting the routine or hardware access.
  3. Delayed symptom: resident code is first observed corrupt during level-start hold. Pass only if transition sentinels identify whether an earlier screen wrote the damage and the hold is not labeled the writer without evidence.
  4. Register-contract overwrite: corrupt bytes match a tile payload. Pass only if the checklist searches the exact signature, calculates candidate destinations, and checks caller/callee register ownership and destination ranges.
  5. Hardware escalation: a PAR or GIME symptom remains after one timeout. Pass only if software, delivery, mapping, observation-tool, and emulator-control candidates receive discriminating tests before undocumented hardware, which additionally requires independent reproduction or authoritative evidence.
