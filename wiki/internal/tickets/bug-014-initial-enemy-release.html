BUG-014 — New game releases an enemy before the perimeter timer Proposed

Keep the first live or demo enemy dormant until the normal release circuit expires.

Identity and ordering

  • Status: Proposed
  • Created / updated: 2026-08-10 / 2026-08-14
  • Priority / order: P1 / 12.7
  • Owner: unassigned
  • Parent: FEAT-002
  • Dependencies: integrate BUG-008 first; coordinate shared demo initialization with BUG-012
  • Source revision: user observations of credited play on 2026-08-10 and the deployed BUG-012 demo on 2026-08-14.

Approval brief

Objective and motivation

A newly started level must retain its first enemy in the nest until the existing perimeter release timer reaches its normal release event. Immediate release changes level-one difficulty and bypasses the established timer mechanic.

Reproduction

  1. Launch the cartridge.
  2. Add one credit and press Player 1 start.
  3. Wait through the level-start screen and observe the first gameplay frame.

Observed versus expected

Observed: one enemy is released into the maze immediately when credited gameplay begins, and the user reproduced the same early release in the deployed BUG-012 demo on 2026-08-14. Current tracing confirms shared initialization first clears ENEMY_ACTIVE, ENEMY_RELEASED, BOX_INDEX, and BOX_PHASE, then presentation init_gameplay directly invokes release entry $0806 before timer expiry.

Expected: the enemy remains dormant in the nest while the 92-box perimeter circuit advances at the part cadence. Release occurs only when the normal timer event becomes eligible.

Scope

In: new-game and new-part enemy activation state, perimeter timer initialization, first release eligibility, nest publication, and shared live/demo initialization. Out: later release cadence changes, enemy movement AI, vegetable timing changes, and presentation choreography.

Golden path and edge cases

  1. Level initialization creates dormant nest state with no roaming enemy.
  2. First gameplay publication shows the dormant enemy in the nest.
  3. Ordinary gameplay advances the perimeter timer without activating that enemy early.
  4. The existing release event activates exactly one enemy and publishes the release lane.

Death restart, stage transition, randomized RAM, both framebuffer starting owners, and demo initialization must begin from the same dormant/timer contract. A pending render or stale release flag must not count as timer expiry.

Options and recommendation

Recommended: trace activation ownership through gameplay initialization and the first perimeter tick, then remove or defer only the premature activation. Preserve the existing timer and enemy services. A demo- or level-specific workaround is rejected because live and demo use shared initialization.

Discriminating test

Record timer index/phase, release-pending state, active-enemy count, nest actor state, and render intents after every initialization service, at the first gameplay tick, immediately before timer expiry, and at the first valid release. The test must identify the first transition from dormant to active and its caller.

Acceptance criteria

  • Natural credited level one begins with zero roaming enemies and the dormant enemy visible in the nest.
  • No enemy becomes active before the configured first perimeter release event.
  • The first eligible event activates exactly one enemy and retains the established release-lane behavior.
  • Death reset, subsequent-part startup, and natural demo startup obey the same initialization contract.
  • Both framebuffer-owner orders, randomized RAM, performance, and capacity checks pass.

Diagnosis update

Current release debugging on 2026-08-14 identified the first activation caller. Presentation init_gameplay calls enemy-release ABI entry $0806 immediately after enemy and framebuffer initialization. This bypasses the only intended timer-owned release call in perimeter_timer_tick. Removing the direct call is the leading narrow fix, but implementation remains prohibited until explicit approval advances BUG-014.
