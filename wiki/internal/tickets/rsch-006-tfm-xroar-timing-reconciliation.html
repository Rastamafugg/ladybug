Approval brief

Objective and motivation

Resolve whether the large isolated TFM baseline is a valid XRoar cycle result, a marker/breakpoint boundary artifact, or a launch/live-ROM observation failure. The current evidence must be repaired or explicitly rejected before TFM can inform production optimization.

Current evidence

RSCH-003 recorded isolated TFM at 364937 baseline cycles versus 282 candidate cycles. RSCH-004 repeated the source-aligned TFM result at 126/1881 baseline cycles for 1/16 rows versus 64/889 candidate cycles, while the corrected LDQ/STQ evidence is now independent. A prior internal-marker probe reached copy_loop at 364084 cycles and its end at 365172, so the boundary interpretation remains unresolved.

The earlier source/executable mismatch hypothesis is not confirmed at the current revision. The tracked docs/reference/xroar/src/monitor.c defines read_cycles, the executable contains the read_cycles, event_ticks, and cpu_cycles strings, and the unchanged RSCH-005 command successfully reads the endpoint. A separate current RSCH-003 launch failed before timing because the live ROM window was stale, proving a startup identity race but not a TFM execution defect.

Scope

In: verify source/executable provenance for read_cycles; harden the existing live-ROM identity wait without changing the timing contract; compare marker-boundary, event-tick, and CPU-cycle measurements for one fixed TFM control and one source-aligned TFM case; retain failing and passing evidence; update the TFM recommendation. Out: production TFM adoption, production source, release ROMs, native mode, hardware qualification, separate ROMs, loader/MMU/framebuffer behavior, and undocumented hardware hypotheses.

Discriminating tests

  • Provenance control: confirm the executable method response schema and source/build identity before timing; a missing or partial response fails closed.
  • Startup control: run the existing fixed ROM after waiting for live prefix and benchmark-window identity; a stale window is classified as launch failure, not target slowness.
  • Boundary control: compare one TFM window with a no-op and a byte-copy control at the same marker shape; event-tick and CPU-cycle deltas must preserve the expected conversion.
  • Hot-path control: repeat the 1/2/4/8/16 source-aligned TFM sweep only after the first three controls pass; require stable incremental slopes and correct source/destination guards.

Acceptance criteria

  • Current source and executable provenance for read_cycles is recorded, or the mismatch is reproduced with exact hashes and a bounded repair.
  • Startup identity polling prevents stale live-ROM windows from entering timing evidence and retains a five-second per-phase deadline.
  • The TFM result is classified as valid, invalidated, or unresolved with a named cause and retained evidence; no unsupported speedup claim remains.
  • Any repaired TFM timing result includes event ticks, CPU cycles, marker addresses, static expectations, repeatability, and source/ROM/XRoar identity.
  • No production source, release ROM, XRoar semantic behavior, native mode, or separate-ROM policy changes.

Risks and stop conditions

The primary risk is mistaking a stale live image or breakpoint artifact for TFM execution cost. Stop after two observation-tool timeouts, two rejected probes, material expansion into XRoar semantics, or before the 7% estimate is exceeded. A protocol or emulator implementation change returns the work to Proposed with a revised class and ceiling.
