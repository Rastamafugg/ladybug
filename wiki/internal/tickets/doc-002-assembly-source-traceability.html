Approval brief

Objective, recommendation, and intended outcome

Create a two-layer documentation system. Hand-authored wiki pages remain authoritative for terminology, rationale, architecture, contracts, memory ownership, data layouts, and traceability. A generic build tool joins assembly source with the lwasm listing and symbol map to produce a disposable line-level HTML browser under build/source-reference/. This gives a reader a path from game behavior to exact addresses, emitted bytes, instructions, symbols, and source lines without manually duplicating generated addresses in the wiki.

Definitions and coverage rules

  • Controlled term: a Ladybug-specific or non-obvious hardware, memory, rendering, timing, packing, workflow, or data-layout term. Standard English does not require glossary duplication.
  • Module: one independently assembled source unit or generated payload with a defined address range, owner, imports, exports, lifetime, and capacity limit.
  • Routine contract: purpose, inputs, outputs, clobbered registers, memory reads/writes, side effects, invariants, callers, callees, and timing or size notes where material.
  • Basic block: one straight-line sequence entered at its first instruction and exited by a branch, call, jump, return, or fall-through boundary.
  • Memory structure: any fixed address, direct-page field, record, array, table, framebuffer metadata area, payload, stack interval, virtual range, or physical-page allocation.
  • Line-level source browser: generated HTML showing every assembly source line, its source file and line number, assembled address, emitted bytes, label, enclosing routine/basic block, and links to applicable instruction, routine, symbol, and memory documentation.
  • Documented: the item has one canonical definition, all other uses link to it, and automated coverage verifies that the definition still resolves. Merely appearing in a generated symbol list is not sufficient.

Evidence and baseline

  • Source structure describes module ownership, generated interfaces, the fixed jump ABI, and major call flow, but it does not catalog every routine or provide behavior-to-line traceability.
  • Memory map records major regions and many direct-page fields, but allocation descriptions, structure-field definitions, lifecycle rules, and source references are not represented through one uniformly linted schema.
  • Coding conventions requires contracts for non-trivial routines. Current sources are inconsistent: src/main.s contains many contract banners, while src/presentation_runtime.s has no complete Inputs/Returns/Side effects routine headers.
  • The build already emits lwasm listing and map artifacts for the resident runtime, enemy runtime, presentation runtime, and GMC bootstrap. These contain the address, byte, symbol, and source relationships required for a generated browser.
  • The release reference already provides one page per 6809 mnemonic. Generated instruction links can reuse that reference instead of repeating mnemonic definitions in every routine.
  • Descriptions have used terms such as resident, cold payload, PAR5 scope, framebuffer owner, save-under, render intent, GMC source interval, and presentation module without a single enforced controlled vocabulary. This allows architectural assumptions to appear before their definitions.

Scope

In: controlled glossary; hierarchical behavior-to-source guide; complete physical/virtual/cartridge memory atlas; module catalog; routine contracts and call graph; data-layout catalog; requirement-to-code-to-test traceability; generic lwasm listing/map parser; generated line-level HTML browser; documentation coverage manifest and lint; reusable assembly-project documentation template; wiki navigation, workflow, and build instructions; and initial coverage of all shipped Ladybug runtime modules.

Out: changing gameplay behavior; rewriting standard Motorola instruction reference pages; documenting third-party emulator or tool source line by line; replacing assembly comments with wiki prose; generating the hand-authored architectural rationale; requiring prose for self-explanatory local branch labels; and publishing the internal wiki as player-facing documentation.

Information architecture

  1. Glossary: one alphabetical page defining controlled terms, units, acronyms, ownership words, lifecycle words, and links to detailed pages. Hand-authored pages link the first material use of each controlled term.
  2. Behavior guide: each game state and user-visible sequence links to its state record, director transition, gameplay service, data records, and verification scenarios.
  3. Architecture and module catalog: one page records module boundaries, source and destination ranges, imports/exports, owners, lifetimes, call direction, mutable state, generated inputs, and capacity guards.
  4. Memory atlas: every cartridge interval, virtual address range, physical page, direct-page byte, stack interval, framebuffer allocation, fixed jump, copied module, and persistent record has one owner and one canonical definition. Each definition includes address, length in bytes, unit, mutability, initialization, lifetime, aliases, and source references.
  5. Routine catalog and call graph: every externally callable or non-trivial routine has the complete contract. Local basic blocks inherit the routine contract and receive a concise block purpose where control flow is not self-evident.
  6. Data-layout catalog: every record and table lists field offset, width, encoding, valid range, sentinel values, owner, producers, consumers, reset rule, and capacity formula.
  7. Traceability matrix: each approved ticket scenario links through behavior/state, module/routine, data structures, exact source ranges, verifier scenario, and retained evidence. Missing rare-path evidence remains a failed link, not a pass.
  8. Generated line browser: a clean build parses source, includes, listing, and map outputs and emits one stable HTML anchor per source line, symbol, routine, and address. Emitting and non-emitting lines are both shown. Standard mnemonics link to wiki/release/reference/6809/; project symbols link to their canonical hand-authored definition.
  9. Reusable template: document the minimum directory layout, source-comment contract, memory-manifest fields, generated-artifact interface, lint rules, and adoption sequence required to reuse the system in another bare-metal assembly project.

Proposed artifacts and boundaries

  • wiki/internal/implementation/glossary.html: controlled vocabulary.
  • wiki/internal/implementation/source-guide.html: top-down behavior, architecture, module, and traceability entry point.
  • wiki/internal/implementation/routine-catalog.html: routine contracts and call relationships, split by module only if page size becomes unusable.
  • wiki/internal/implementation/data-layouts.html: records, fields, tables, and lifecycle.
  • wiki/internal/implementation/memory-map.html and source-structure.html: normalized ownership and links to the new catalogs rather than duplicate definitions.
  • wiki/internal/implementation/assembly-project-template.html: reusable process and schema.
  • scripts/build_source_reference.py: thin generation CLI using explicit command-line inputs; no Ladybug addresses are hard-coded in the package.
  • scripts/verify_source_documentation.py: thin verification CLI for coverage, uniqueness, link, stale-address, and generated-output checks.
  • scripts/source_reference/: private generic package containing immutable typed records, source/listing/map parsers, normalization, coverage policy, stable-link construction, HTML rendering, and independent generated-output verification.
  • scripts/source_reference.json: project-specific source modules, listing/map inputs, wiki symbol anchors, exclusions, and coverage policy. Generated HTML remains under build/source-reference/ and is not hand-edited.

Scenarios, edge cases, and failure modes

  • A reader starts from an attract-mode behavior, follows the transition and memory ownership, opens the responsible routine, then reaches the exact assembly lines and 6809 instruction references.
  • A reader starts from a direct-page address, finds its width and owner, then finds every source read/write and every routine contract that names it.
  • A reader starts from a crash address or GDB program counter and resolves it to module, routine, basic block, source line, emitted bytes, and relevant memory structures.
  • An included source line, generated symbol, multiple labels on one address, data-only line, conditional-assembly line, macro expansion, non-emitting comment, and relocated copied module are represented without losing source provenance.
  • A source edit moves a routine or renumbers a direct-page field. Regeneration updates line addresses; lint rejects stale hand-authored numeric claims and duplicate ownership.
  • A new routine, fixed jump, direct-page symbol, persistent record, or generated ABI entry is added without documentation. The verifier fails and names the missing canonical definition.
  • A local branch label requires no separate prose when its enclosing documented basic block explains it. A local label referenced outside that block becomes a documented symbol.
  • A controlled term is used before definition or with conflicting definitions. Glossary/link lint fails.
  • A required ticket scenario has no trace to a verifier or current evidence. Traceability reports it as incomplete.

Options and recommendation

  1. Recommended hybrid: hand-author semantic documentation and generate address/byte/line relationships from lwasm artifacts. This preserves rationale while preventing address and line-number drift.
  2. Rejected manual line encyclopedia: duplicate every source line and address in hand-authored HTML. It creates immediate synchronization risk and is impractical as a reusable template.
  3. Rejected generated-only documentation: expose listings and symbol tables without contracts or rationale. It explains encoding but not ownership, intent, invariants, or game behavior.
  4. Rejected source comments only: comments remain necessary for local reasoning, but they cannot provide cross-module memory ownership, ticket traceability, global call flow, or controlled terminology by themselves.

Acceptance criteria

  • A clean documented build generates the line-level browser for every shipped Ladybug assembly module and resolves every emitted address in each configured listing to a source line or explicit generated/relocation record.
  • Every assembly source line appears in the generated browser. Every instruction line shows address, emitted bytes, enclosing routine/basic block, and a valid mnemonic-reference link; non-emitting lines are explicitly marked.
  • Every non-trivial routine has one complete contract. Every local label belongs to a documented routine/basic block, and every externally referenced label has a canonical catalog entry.
  • Every fixed address, direct-page allocation, copied module, persistent RAM record, physical page, virtual range, cartridge interval, framebuffer structure, stack boundary, generated ABI entry, and structured table field has exactly one documented owner and definition.
  • Every controlled term used in the new implementation documentation is defined in the glossary and linked on first material use. Standard 6809 mnemonics resolve to the existing release instruction reference.
  • FEAT-002 scenarios are traceable from acceptance criterion through state, routine, data, source range, verifier, and current evidence. Missing required scenarios make the documentation verifier fail.
  • The generator and verifier run from a clean checkout using documented commands, reject deliberately missing symbol/routine/memory definitions, and reject a stale listing or map whose material-source hash differs.
  • The reusable template contains no Ladybug-specific address requirement and can generate a minimal source browser for a supplied fixture project with at least two modules, one copied/relocated module, one data record, and one cross-module call.
  • Wiki link lint passes, new pages are indexed, the build workflow documents generation, and the completion report records coverage counts, exclusions, generated output location, command results, residual gaps, and one bounded commit.

Risks and controls

  • Documentation volume: generated addresses and line views remain build artifacts; only semantic contracts are hand-authored.
  • False completeness: coverage counts do not establish correctness. Acceptance also samples behavior-to-line, address-to-owner, and memory-write traces manually.
  • Parser coupling: fixtures cover include depth, conditional assembly, data lines, copied-module relocation, and multiple labels. Unsupported listing constructs fail explicitly.
  • Wiki policy: the hand-authored HTML rule remains unchanged. Generated HTML is confined to build/source-reference/; the wiki documents how to regenerate and interpret it.
  • Baseline control: document the current authored source regardless of known bugs. Later runtime changes are outside DOC-002; they use the delivered regeneration and stale-source checks after this ticket completes.
