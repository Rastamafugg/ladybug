FEAT-008 — Animate the added attract enemy

Proposed · 2026-09-30 · High-risk technical classification

Approval brief

Objective: preserve the user's added enemy in coco-attract-screen.tmx and animate it synchronously with the existing attract actors. This is an additional authored actor, not removal or replacement of the existing seven. The user clarified the addition is intentional and requested the same animation behavior.

Baseline: authored asset checkpoint bf3a2d9 adds raw sprite tile 101 at zero-based column 20, row 4 in Sprite Animations, with horizontal and vertical flip flags. At source revision c6135c0 the compiler rejects it because the position is absent from ATTRACT_ACTOR_EXPECTED_TILES. The current running ROM predates that asset checkpoint and displays seven actors. No runtime failure or eighth-actor performance result has been observed.

Scope: register this position and sprite family; preserve authored transforms; supply the family's existing palette mapping; extend the existing three-phase surface and destination records from seven actors plus twelve logo rectangles to eight actors plus twelve logo rectangles. Keep current phase holds, synchronization, title duration, logo behavior, and screen/credit/start handoffs. Correct the family's wrap frame: build_screen.py ENEMY_CODE_SETS selects sheet row 0, column 4 after rows 6/7, column 5. A simple row-only cycle would select an unrelated image.

Exclusions: gameplay enemy behavior, unrelated artwork or palette redesign, new animation renderer, new loader/MMU protocol, enlarged hard limits, keybinding behavior, sound, and BUG-058 performance optimization. Historical BUG-010 remains Done; this ticket adds a newly authored actor.

Capacity and risk: High-risk because the existing persistent-framebuffer animation uses tightly packed banked surfaces and compressed cartridge staging. At the last built menu-redraw artifact, decoded surfaces consume 7296 bytes and destination/phase records 44 bytes in the 8192-byte page-$3C allocation, leaving 852. The new actor projects +384 surface bytes and +2 destination bytes: 7726 total, leaving 466. These are layout arithmetic, not a new build measurement. The compressed title bundle currently consumes 1747 bytes in its 1792-byte $B880–$BF7F window, leaving 45; the additional compressed cost is unknown. Architecture must prove fit without overwriting tile patches at $BF80 or changing approved hard limits. If it cannot, return to Proposed with the measured failed fit and a bounded alternative before implementation.

Dependencies and order: complete this asset/compiler compatibility increment before the combined FEAT-005 keybinding build, because the authored attract addition currently prevents that build. Independent keybinding architecture may continue. Project-management routes this ticket to coding-architect; no delegation or separate worktree is required.

Acceptance: the authored screen compiles with exactly eight actors; all three phases use the intended sprite-family frames and transforms; the added actor occupies the authored footprint with no trails, missing pixels, or damage to adjacent title artwork; the previous seven actors and logo retain their phases and cadence. Both persistent buffers and a natural attract-loop return must pass. Credit/start interruption must preserve existing screen ownership. The integrated adaptive build, source audit and every unchanged hard capacity guard must pass. Retain phase/cadence and worklist timing observations; existing BUG-058 failures remain separate and cannot be represented as passing.
