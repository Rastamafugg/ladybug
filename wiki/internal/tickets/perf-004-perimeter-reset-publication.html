Approval brief

Objective and motivation

Natural death-to-reset currently redraws 92 perimeter boxes before publishing the nest reset. Retained PERF-002 closed-interval evidence reports 241720–242969 active cycles for that combined worklist, far above the 27000-cycle target. Symbol coverage identifies exactly 92 calls to draw_perimeter_box; this is worklist attribution, not a framebuffer-owner effect.

Evidence and baseline

At PERF-002 branch commit 3209025, represented by build/perf002-death-reset.json, twelve measured closed intervals cover zero enemies, four enemies, and vegetable state across framebuffer targets A and B. The minimum is 241720, the maximum is 242969, and every observation fails by at least 214720 cycles. Isolated structural-cache publication is 9801–11112 cycles, so PERF-003 common-actor work cannot plausibly remove the perimeter-dominated excess.

Scope

In: boot-time synthesis of the exact native perimeter-reset program from existing authored screen assets; candidate physical-page allocation; the bounded PAR5-restoring helper; FEAT-002 cold-payload reduction required to preserve future-sound headroom; A/B ownership/replay; and combined verification.

Out: changes to death cadence, gameplay rules, nest reset cache semantics, generic structural compositor behavior, gameplay-time ROM switching, sound implementation, high-score presentation, and PERF-003 work.

Scenarios and edge cases

  • Force isolated perimeter publication and natural death-to-reset for zero, four, and vegetable structural states.
  • Start with both framebuffer targets and reverse the starting order.
  • Prove boot-time page synthesis, candidate page $20 ownership, 92-box-equivalent exact pixels, old-footprint and ownership behavior, PAR5 restoration, death cadence, and compatibility with the retained generic path.
  • Prove cold-payload reduction, combined module/cold limits, source headroom before and after the reserved sound budget, and clean/warm presentation boot behavior.
  • Missing forced cases fail verification.

Recommendation and alternatives

At boot, synthesize the exact native reset program from the already-loaded authored screen_map/screen_tiles assets and write it to candidate physical page $20. Invoke it through the bounded low-RAM helper at $06B2-$07FF, mapping PAR5 to $20 only for the call and restoring $34 before return. Reduce the FEAT-002 cold payload by at least 524 bytes, targeting the projected 1409-byte exact-gameplay-tile reuse reduction. Do not use $28-$2B, which remain reserved for the compatibility compositor. No gameplay-time ROM switching is permitted.

Constraints and risks

  • The helper has at most 334 candidate bytes after the bank-0 proof destination.
  • Physical page $20 must be proven unused and must not overlap framebuffer, state, presentation, compatibility, or sound allocations.
  • Interrupt-visible state must remain outside the temporary PAR5 mapping.
  • Every exit must restore PAR5 to page $34.
  • The boot generator must remain inside the $0000-$07FF bootstrap allocation; cartridge source headroom does not relax low-RAM, physical-page, code-window, direct-page, stack, ABI, or compatibility limits.

Acceptance criteria

  • Each complete natural combined perimeter-plus-cache-publish worklist is at most 27000 active cycles, with target margin defined as 27000 minus measured cycles.
  • Every timed interval is closed from frame_render_impl to the next such boundary; tails are diagnostic only.
  • Exact pixels, 92-box semantic coverage, A/B and reversed replay, PAR5 restoration, cadence, diagnostics, total cartridge capacity, destination capacity, clean build, and compatibility verifiers pass.
  • Combined source demand leaves at least 2560 CPU-readable bytes spare before the reserved sound budget and at least 1024 after it; the hard minimum is 2048 before and 512 after sound.
  • Cold payload is at most 10874 bytes for the minimum 524-byte reduction, with the preferred target at or below 9989 bytes; module, combined module/cold, resident, and destination limits remain valid.

Capacity-resolution proposal

Recommended redesign: retain the PERF-004 native reset program and its timing behavior, but synthesize that program during boot from the already-loaded authored screen_map/screen_tiles data instead of storing 4484 payload bytes in the GMC loader source pool. Write the generated program to candidate physical page $20, which must be proven unused on the 512 K target, and change the bounded helper to map $20 while preserving PAR5 restoration to $34. The FEAT-002 cold presentation pages remain at $3A-$3D; the current PERF-004 destination collision is removed.

  • Source capacity: removing the 4,484-byte perimeter source leaves approximately 2,036 CPU-readable bytes spare after retaining the 19-byte helper and existing boot proof. Reduce the current 11,398-byte cold payload by at least 524 bytes to restore the FEAT-002 engineering target of 2,560 bytes pre-sound, or 1,024 bytes after the reserved 1,536-byte sound budget. The historical exact-gameplay-tile reuse projection of 1,409 bytes is the preferred target, but must be remeasured at implementation.
  • Boot ownership: add a bounded generator to the bank-0 boot region, using existing bank-1 screen assets as input. It must stay inside the $0000-$07FF bootstrap allocation, run before gameplay, write only the candidate page, restore PAR5, and leave the generated bytes hash-identical to the independent build-time oracle.
  • Runtime ownership: the existing low-RAM helper remains the only gameplay entry. The generated native program continues to write the exact Green-to-White perimeter patch, so the isolated 16,489-17,738-cycle evidence remains the target to remeasure after relocation.
