TOOL-001 — Bank-0 Overflow Loader Verification

Use free boot-bank capacity as boot-time source overflow for banks 1–3.

Approval brief

Objective and motivation

Do not reject a cycle-improving implementation solely because its source payload no longer fits its original GMC bank. Pack eligible overflow from banks 1–3 into unused bank 0, and have the relocated boot loader copy every declared segment to its final RAM destination before runtime. Continue requiring every behavioral, timing, diagnostic, runtime-memory, MMU, and compatibility acceptance test.

Evidence and baseline

At main revision ca8c2b0, the assembled bank-0 loader ends at $C16B, only 363 bytes from bank offset zero, while the CPU-readable bank interval ends at offset $3DFF. Banks 2 and 3 currently leave 939 combined CPU-readable payload bytes, and the bank-3 enemy module has a separate 4,096-byte low-RAM destination contract. These are current single-revision capacity observations, not performance measurements.

Scope

In: a fixed bank-0 overflow pool, generated source-segment packing, bank-0 overlay composition, boot copy descriptors, declared physical-page and always-mapped low-RAM destinations, capacity guards, XRoar proof, build documentation, and performance-ticket capacity policy. Out: gameplay-time cartridge switching, automatic relocation of arbitrary absolute 6809 code, weakening runtime destination-memory/MMU limits, use of inaccessible offsets $3E00-$3FFF, and physical-hardware certification.

Scenarios and edge cases

No-spill build; one and multiple bank-0 segments; exact pool boundary; one-byte total overflow; loader growth into the pool; bank-0 low-RAM proof copy; payload reconstruction across bank 2, bank 3, and bank 0; bank signatures; TY=1 handoff; normal runtime; malformed destination; bank-0 source overlapping loader; and unchanged gameplay-time bank-switch count.

Options and recommendation

Reserve bank-0 offsets $0800-$3DFF as a 13,824-byte overflow pool and enforce loader_end <= $C800. Keep bank 2 and bank 3 as primary generated-payload sources and use bank 0 only after those eligible intervals are exhausted. Overlay exact bank-0 source intervals onto the padded boot image. Extend the existing eight-byte copy descriptor so destination page $FF means an always-mapped low-RAM destination; other values continue to select PAR5. Retain a two-byte bank-0-to-low-RAM proof segment at $06B0-$06B1 so normal XRoar verification exercises bank-0 selection. Reject gameplay-time ROM switching because it adds hot-path cost and changes runtime ownership.

Acceptance criteria

The canonical build and verify-gmc pass; the delivered image remains exactly 65,536 bytes; boot code does not overlap offset $0800; no source segment enters offsets $3E00-$3FFF; generated reconstruction is byte-exact; the normal XRoar trace proves bank-0 selection and the low-RAM proof copy before TY=1; bank 1 runtime, banks 2/3 signatures and payloads, enemy runtime, sparse indexes, PAR5 restoration, and main-loop execution remain exact. Synthetic exact-boundary packing passes and a one-byte excess fails. Capacity reporting treats individual source-bank overflow as permitted when packing succeeds, while destination RAM, virtual mapping, stack, direct-page, and total CPU-readable GMC capacity remain hard gates.

Selected design

The packer emits a full bank-0 overflow template plus a manifest of exact occupied source intervals. The final composer first assembles and pads the boot ROM, verifies loader_end <= $C800, then overlays only manifest-declared intervals at or above offset $0800. Generated copy records may name source bank 0, 2, or 3. A destination-page byte of $FF suppresses the PAR5 write and copies to an always-mapped literal destination; all other records retain the current PAR5 copy contract. Flat resident or enemy modules are not split automatically: code moved out of its original destination must be an explicitly assembled segment with a stable ABI and a verified mapped destination. This distinguishes source-ROM capacity from executable-RAM capacity.
