Approval brief

Objective and motivation

Add a selectable 6809/6309 CPU option to the existing XRoar run paths, describe the four game build profiles and runtime flags on a new internal wiki page, and decide whether the project should publish separate 6309 ROMs. The immediate user-visible sequence is: choose LADYBUG_PROFILE, choose LADYBUG_CPU, build the unchanged ROM, launch XRoar with the selected CPU, and observe the same profile-specific game flow.

Evidence and baseline

scripts/build.sh currently accepts highscore-test, development, release, and complete through LADYBUG_PROFILE. Every active assembly invocation uses lwasm -9, and the production source modules declare pragma nodollarlocal,6809. cmd_run and cmd_tester_run launch xroar -machine coco3 without a CPU selector. The bundled XRoar manual supports -machine-cpu 6809|6309; lwtools supports -9/--6809 and -3/--6309. The current source audit finds no 6309-only mnemonic in src/.

Historical current-revision performance evidence shows why a blanket 6309 rewrite is not yet justified: a four-enemy trace is dominated by shadow-region copies and sprite blits, while the project also has strict MMU/PAR, copied-module, loader, direct-page, stack, and 29,666-cycle frame boundaries. These are observations from the existing repository evidence, not new measurements for this ticket.

Scope

In: one validated LADYBUG_CPU runtime variable, propagation to the normal and tester XRoar launch paths, fail-closed validation, a new wiki/internal/tooling/runtime-profiles.html page, links from tooling/build-workflow navigation, profile/CPU compatibility policy, and a bounded assessment of useful 6309 instruction candidates. Out: gameplay changes, loader/MMU changes, new 6309 opcodes in shipped source, changes to the 6809-compatible ROM image, native-hardware claims beyond the current 6809 target, and a separate ROM deliverable unless a later measured optimization ticket is approved.

Golden path

  1. Set LADYBUG_PROFILE to one of the four existing game profiles, or use the current default complete.
  2. Set LADYBUG_CPU to 6809 or 6309, defaulting to 6809.
  3. Run scripts/build.sh run; the build remains assembled in 6809-only mode and the launch adds -machine-cpu.
  4. XRoar boots the same 64 KiB GMC image and the selected profile reaches its first visible output and normal flow.
  5. Use LADYBUG_CPU=6809 as the compatibility/reference run and LADYBUG_CPU=6309 as the emulator CPU variant.

Scenarios and edge cases

  • Each of the four game profiles runs with both CPU selections; the required pairwise coverage is profile behavior versus CPU selection, not a redundant full Cartesian runtime suite.
  • tester-run honors the same CPU selector.
  • An invalid CPU value fails before build or launch and lists the accepted values.
  • The default 6809 path remains unchanged in command semantics and ROM compatibility.
  • The baseline source audit rejects accidental 6309-only instructions while the shipped build is 6809-compatible.
  • GDB runs report the appropriate target architecture when XRoar is manually launched with the selected CPU; a 6309 GDB session is not used as evidence that the ROM contains 6309-only code.
  • Cold and warm runs, random RAM initialization, XRoar extra flags, and the existing profile-specific auxiliary runtime remain documented without changing ownership.
  • A future 6309-only instruction must not enter the universal ROM, boot loader, interrupt path, or copied module without an explicit compatibility and hardware decision.

Options and recommendation

  • Recommended: runtime-only CPU selector. Add LADYBUG_CPU, pass it to XRoar, retain lwasm -9, and publish one ROM. This gives immediate 6309 emulator coverage without changing bytes, packing, MMU ownership, or native compatibility.
  • Deferred: make the assembler ISA selectable for the whole tree. Current source pragmas intentionally force 6809, so this would require an explicit conditional-ISA design and a complete 6809 regression guard.
  • Deferred: separate ROM builds now. A 6809-compatible ROM already executes on a 6309, so separate identical images add artifact and verification cost without a product benefit.
  • Candidate research: benchmark 6309 TFM on contiguous copy segments and consider LDQ/STQ or masked-memory operations only where a measured cycle/byte benefit survives current ABI, interrupt, and mapping constraints. The major measured bottlenecks are not all contiguous, so no instruction is accepted by inspection alone.

Acceptance criteria

  • scripts/build.sh run accepts LADYBUG_CPU=6809 and LADYBUG_CPU=6309, defaults to 6809, and passes exactly one matching -machine-cpu option to XRoar.
  • scripts/build.sh tester-run follows the same CPU policy.
  • Invalid CPU values fail closed with a deterministic diagnostic.
  • The build remains 6809-only and the current source audit reports no 6309-only instruction in the universal source path.
  • The standard 6809 build and existing profile verification remain passing; the 6309 XRoar launch reaches the same required startup marker and one natural profile path.
  • The new wiki page describes highscore-test, development, release, and complete, plus LADYBUG_CPU, XROAR_EXTRA, GDB/trace options, defaults, compatibility, and separate-ROM policy.
  • The ticket records the 6309 instruction assessment, rejected alternatives, artifact identity, and any residual hardware or emulator risk.

Assignment contract

  • Owned artifacts: scripts/build.sh, wiki/internal/tooling/runtime-profiles.html, wiki/internal/tooling/index.html, wiki/internal/tooling/build-workflow.html, wiki/internal/tooling/xroar.html, this ticket, the ticket index, and the project log.
  • Constraints: runtime-only CPU selection; retain lwasm -9, source 6809 pragmas, ROM layout, loader, MMU/PAR ownership, framebuffer protocol, and universal ROM identity. Do not add 6309-only opcodes.
  • Commands: bash -n scripts/build.sh; invalid-CPU fail-closed check; scripts/build.sh build; canonical 6809 verification; one natural highscore-test XRoar launch for each CPU if the local display/runtime permits; and local HTML-link validation.
  • Evidence: selected CPU diagnostic, build output, ROM hash comparison, source mnemonic audit, and concise runtime startup results. Generated build/ outputs remain disposable.
  • Commit: one bounded commit when it can be separated from pre-existing worktree changes; otherwise report the dirty-worktree constraint and leave unrelated changes untouched.
  • Non-goals: gameplay, loader/MMU, framebuffer, native 6309 hardware qualification, and separate ROM deliverables.

Verification plan

  • Static: shell syntax, accepted/default CPU values, source mnemonic audit, and local HTML-link validation.
  • Build: canonical 6809 build and generated capacity/layout guards.
  • Runtime: one natural highscore-test launch per CPU, with first-visible-output/startup marker and no missing required phase; tester launch with one CPU variant if tester coverage is available.
  • Regression: existing profile-isolation and GMC verification on the 6809 reference path; 6309 verification is an emulator-CPU compatibility check, not proof of native 6309 hardware support.
  • Future instruction candidates: retain a short benchmark result or explicit rejection for each candidate; do not retain large passing traces unless required for reproduction.
