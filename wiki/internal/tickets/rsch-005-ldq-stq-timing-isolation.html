Objective and motivation

Reduce the RSCH-004 LDQ/STQ anomaly to a confirmed timing cause or a narrowly bounded unresolved discriminator. The current candidate copies the correct bytes and passes guards, but reports 11119 CPU cycles for every tested row count, while the equivalent 6809 baseline scales from 108 to 1593 cycles. The constant candidate value is not valid evidence for a production optimization decision.

This ticket isolates the instruction window so setup, loop control, marker handling, breakpoint behavior, event-counter semantics, and XRoar’s HD6309 implementation can be evaluated independently.

Evidence and baseline

The current accepted RSCH-004 artifact is build/rsch004-6309/rsch004-6309-hotpath.json, generated from source hash 58c21c6fecb6935bf2185ce68dd602ac4b8c79bc9974b8866c8f9f9b1e3b79dd with XRoar hash bad8de1a7a5cb1be5f55ff9bbb213442b403bc83c1f833c343523d5c318f6dbf. Three cold-launch samples were identical for each case. Correctness, source preservation, destination guards, live benchmark-window identity, markers, and baseline 6809/6309 byte identity passed.

Observed CPU-cycle values are measured integer boundary deltas, not estimates: LDQ/STQ baseline/candidate are 108/11119 at one row and 1593/11119 at sixteen rows. The candidate result is therefore repeatable but rejected as timing evidence pending this ticket.

Scope and design

In: a diagnostic ROM or extension to the existing benchmark, single-instruction and minimal-sequence LDQ/STQ controls, byte-equivalent controls, marker and breakpoint-boundary checks, event-tick versus CPU-cycle comparison, live-byte/source/hash validation, XRoar HD6309 source inspection, and concise retained evidence.

Out: production assembly changes, separate 6309 ROMs, assembler changes, loader/MMU or framebuffer ownership changes, gameplay behavior, native hardware qualification, and modifying XRoar’s timing model to make the result pass. A source or emulator instrumentation change may be proposed only as a separately identified diagnostic artifact with its own provenance.

Diagnostic controls

  • Boundary control: identical setup and markers with no candidate instruction in the measured window. This establishes marker, breakpoint, and counter overhead.
  • LDQ-only control: preload the source address and execute exactly one LDQ before the end marker. Validate Q and untouched destination memory.
  • STQ-only control: preload Q outside the measured window and execute exactly one STQ. Validate destination bytes and source preservation.
  • LDQ/STQ pair: execute exactly one LDQ followed by exactly one STQ over fixed aligned addresses. Validate the same four-byte transfer used by the hot-path candidate.
  • Byte-equivalent control: execute the corresponding four-byte load/store sequence with the same source, destination, markers, and setup.
  • Repeat-count control: where needed, use separately unrolled 1/2/4/8-operation windows to determine whether the anomaly has a per-instruction slope or a fixed boundary component. Do not use a repeated internal breakpoint as the primary timing boundary.
  • Addressing control: retain aligned addresses first; add odd-address variants only if the aligned single-instruction result is not sufficient to discriminate the leading causes.
  • Correctness control: compare source, destination, guards, Q/register state, marker bytes, halt reason, and live instruction-window bytes before interpreting timing.

Competing hypotheses and discriminating results

  • H1 — fixed boundary contamination: the no-op control is near the 11,119-cycle value and LDQ/STQ deltas are small and work-independent. This indicates marker, breakpoint, or monitor overhead.
  • H2 — instruction-specific XRoar behavior: LDQ-only or STQ-only is anomalous while the no-op and byte-equivalent controls are normal. Inspect the corresponding HD6309 execution and cycle paths without changing them.
  • H3 — Q-register or memory-access accounting: one operation has a plausible fixed cost but the pair or unrolled slope is wrong. Compare Q contents, source/destination access count, event ticks, and CPU cycles at every boundary.
  • H4 — stale or mismatched artifact: live C000 prefix, measured window, marker, ROM hash, or executable hash differs from the authored/staged inputs. Fail closed and retain the mismatch; do not interpret the timing.
  • H5 — unresolved observation interaction: all controls remain affected by the same unexplained boundary. Record the last proven marker and stop rather than extending a timeout or claiming an emulator defect.

Speculation: the constant result currently favors a fixed timing-boundary or XRoar state interaction over a genuinely expensive LDQ/STQ instruction. This ticket must confirm or reject that inference with controls.

Scenarios and edge cases

  • One cold launch each for the boundary, LDQ-only, STQ-only, LDQ/STQ pair, and byte-equivalent controls under XRoar 6309.
  • At least three repeated samples for each fixed control; a timing result is valid only when samples are identical or have relative spread at most 1%.
  • All controls use the same fixed aligned source/destination addresses, guards, stack setup, CPU mode, and marker protocol.
  • One 6809-compatible control confirms that the measurement path itself remains executable without 6309 opcodes.
  • Any timeout, unexpected halt, marker mismatch, live-window mismatch, stale ROM, source mismatch, or tool mismatch fails the diagnostic case and is retained as evidence.
  • Odd-address or page-boundary variants are optional follow-ups only after the aligned single-instruction result identifies a remaining address-dependent hypothesis.

Acceptance criteria

  • The current 11119-cycle LDQ/STQ observation is reproduced or invalidated against a fresh source, staged ROM, live-byte, and XRoar identity record.
  • The boundary, LDQ-only, STQ-only, LDQ/STQ pair, and byte-equivalent controls execute with correct memory and guard results.
  • Evidence records event ticks and CPU cycles at each marker, exact measured instruction count, marker addresses, halt reason, CPU mode, ROM/source/XRoar hashes, and repeatability spread.
  • At least one competing hypothesis is discriminated by measured slope or fixed-overhead comparison. If no hypothesis is confirmed, the remaining discriminator and last proven boundary are recorded explicitly.
  • No production optimization recommendation uses the LDQ/STQ result unless the diagnostic timing is valid under the stated repeatability and identity rules.
  • No production source, release ROM, loader, MMU, framebuffer, gameplay, or XRoar timing behavior changes.

Dependencies, risks, and exclusions

  • RSCH-004’s src/bench/6309_hotpath_benchmark.s, scripts/benchmark_6309_hotpaths.py, and retained JSON are the starting point.
  • The primary risk is mistaking deterministic observation-tool behavior for CPU execution cost.
  • XRoar’s repository HD6309 implementation is an inspection target, not an authority for cycle correctness; emulator evidence remains unqualified without an independent timing source.
  • After two rejected probes, two observation-tool timeouts, or discovery that the cause expands into another subsystem, stop and reassess through project management before adding scope.
  • Production 6309 code and separate ROM builds remain excluded.
