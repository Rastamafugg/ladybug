BUG-067 — Diagnose the instruction row-entry colour-cycle wait Draft

2026-10-01 · P2 · Standard · Draft · RSCH-014 Step A

Approval brief

Objective and motivation

Identify the user-visible colour-cycle wait before Ladybug movement at each instruction row start, then remove exactly the redundant wait once its timing owner is confirmed.

Evidence, reproduction and cause

The current generator applies row offsets (0,90,180), explicit earliest gates reference_consumes[4]+90 and reference_consumes[11]+90, and a target-colour transition boundary. These are integer ticks on the generated instruction timeline. Removing the two explicit gates alone changes no event motion or consume tick: selected events remain E=129, A=515, L=1251 and heart_x2=1409; the next-screen tick remains 1896. It therefore does not remove the observed wait. Removing row offsets changes later events (L 1251→1155, heart_x2 1409→1313, heart_x5 1601→1409, skull 1681→1489) and next-screen tick 1896→1884. Current compiler-schedule evidence does not prove whether that offset is the reported redundant delay or a required arcade-timing delay. Current, no-gate and no-offset event records are retained in snapshot.json.

Scope

In: diagnose and remove one specifically identified redundant full colour-cycle wait before the first Ladybug movement at each affected row start. Out: changing actor speed/cadence, consume ordering, trigger-colour rules or broader instruction timing without an explicit measured target. No production edit is selected at Draft.

Design and prototype

Identify, per row, which generated gate actually holds first movement and compare its current event ticks with the arcade-derived target. Deleting the explicit +90 floors is only an output-identical cleanup; it cannot satisfy the visible-wait request alone. Removing row offsets is a behavior-changing candidate with the measured deltas above, not automatically acceptable or rejected. Select the smallest change only after its timing target is established.

Scenarios and edge cases

  • Record a current-versus-candidate timeline for all 16 events, including each row’s first motion tick, prior colour-loop boundary and all motion/consume tick deltas.
  • The selected candidate removes one confirmed redundant 90-tick colour cycle at each affected row start while preserving target-colour transition and consume order; any other schedule shifts are explicitly approved before implementation.
  • Natural instruction playback confirms the first movement after each affected row starts without the extra cycle. Prove current ROM/code identity, name a row-start phase marker and success marker, set a deadline no longer than 60 seconds, and report a timeout as inconclusive.
  • After the timing target is resolved and approved, run existing instruction/layer checks and the complete-profile build; retain the generated event table and natural-frame evidence.

Cost class, dependencies and risk

Class: Standard. The code area is bounded, but the cause and exact timing target remain unresolved and changing row offsets changes generated behavior. Dependencies: BUG-059/060 compiler integration and BUG-064 layout baseline. Coordinate with BUG-050 arcade cadence evidence; this ticket changes only the reported row-entry wait. The arcade schedule oracle and meaning of “one colour change loop wait” remain open.

Risk controls: no timing change until the current wait and target delta are discriminated. A missing natural row-start scenario is incomplete evidence. Any broader timing change returns the ticket to Proposed.

Assignment and verification contract

Owned artifacts after approval: scripts/build_presentation.py and its existing instruction schedule verification. Runtime files enter scope only if diagnosis places the wait outside the compiler schedule; that requires a class/scope review before implementation.

Required commands and scenarios: python wiki/internal/tickets/evidence/rsch014-A/capture_evidence.py; compare all 16 current/candidate motion and consume ticks plus event-table hashes; existing presentation/layer verifier; complete-profile scripts/build.sh build; one forced natural instruction playback with identity-proven code, row-start phase marker, success marker and deadline ≤60 seconds.

Evidence and commit: retain source/map/ROM hashes, current-versus-candidate event records, failing evidence and capacity deltas. One bounded commit only after explicit approval and Ready; no push or ticket closure by the execution agent. Parent owns integration and QA.

Completion report: commit, commands, measured tick deltas versus target, capacity/headroom, rejected experiments, residual risks, retained evidence and justified ticket status.
