2026-09-27 — Regression-aware optimization options

User requests additional ways to reduce cycles within existing memory budgets, with explicit protection against earlier size-reduction regressions. This is a High-risk architecture review under BUG-058, not approval to integrate the partial fit or introduce a new renderer. Production and the isolated two-file candidate remain unchanged.

Lessons that constrain the next fit

BUG-053 demonstrates that repacking assets can invalidate a literal graphic index: retain semantic identifiers generated from final assets. PERF-007 documents persistent validity state incorrectly placed in the low byte of RING_BASE: enumerate byte ownership and register clobbers, including each half of D. BUG-040 requires actor-free retained backgrounds and correct replay on both framebuffers. Earlier player-reuse guards cost more than the work they avoided; a mask-free sparse encoding saved storage but increased commands and cycles. Historical absolute cycle numbers need calibration before reuse; these structural failure mechanisms remain relevant.

Recommended fitting order and cost boundaries

  1. Specialize existing copy loops without changing their output or order. Inspect the phase-zero background restore, which currently branches to a common row tail and dispatches indirectly for each row. A local counted loop can remove repeated dispatch. First collect path frequency; compare identical restored bytes, pointer advancement and clobbers for all ring phases, including wrapped rows. Expected outcome is a local cycle reduction; magnitude and added bytes are unmeasured. The fitted enemy code has consumed its nine bytes of padding before the fixed tables, so even a small expansion requires a proven local space saving. Do not move the tables or remove overlap handling to force this fit.
  2. Select the cheapest existing capture path by ring phase. The repeated-strip experiment failed. Instead, measure one existing strip capture versus the faster full capture for each relevant displacement/column-phase class; use a full capture when it is actually cheaper. Both produce the same clean background, and full capture already normalizes ring state. Prefer a small fixed decision to new mutable cache state. Retain the existing dirty/invalid-background fallback. Success requires all decoded backgrounds and logical records to match, plus lower complete-worklist maxima; timing of the decision itself counts. No cycle or byte saving is yet established.
  3. Reduce sparse sprite command-dispatch overhead while retaining the stream format. Enemy drawing averages approximately 10,544 elapsed cycle equivalents in the fitted four-enemy fixture. Count run lengths and partial/opaque commands before changing the dispatch tree. Consider paired transfers and direct dispatch only for frequent cases; keep masks, palette values, painter order and framebuffer/stage semantics intact. Cost may be a small table or extra instructions, and both hot code and cartridge source must fit independently. Check every enemy/player/popup/death consumer touched by shared decoder changes, including transparency over nonzero backgrounds. This is potentially broader leverage than minor enemy-AI changes, but savings are unmeasured.
  4. Recover cartridge space through byte-identical immutable stream sharing, if extra optimized code needs it. A read-only packing calculation on revision 283be5c found 130 indexed enemy frames but only 98 distinct encoded streams. Sharing exact streams while retaining all 130 index entries packs into 17,383 bytes instead of 23,005, including 183 padding bytes: 5,622 fewer payload bytes. Every indexed stream compared byte-for-byte equal. This is a packing calculation, not a fitted ROM or measured GMC spare increase. It saves storage, not drawing cycles directly, and does not enlarge the low-RAM executable window. Use generated page/address entries, verify every consumer and all loader reconstruction records, and preserve the immutable/shared ownership contract. Do not alter the encoding to obtain this saving.
  5. If local kernels remain insufficient, fit precomputed draw work for the active sprite set. Static level setup can prepare native masked rows or compiled draw runs once for reuse during play; the user already permits static construction cost as technical debt. Begin with the current enemy type and player frames, not an assumed allocation for every game frame. Compare native-row and compiled-run alternatives before selecting one: native pixels still require transparency merging and may not be faster. RAM residency, generated code/data size, explicit MMU ownership, cache invalidation and handoff must be proven. This is a higher-risk design direction with unmeasured memory and cycle costs, not an approved architecture or existing fit. Preserve the current renderer as the reference and keep restoration/painter ordering.

Evidence required before recommending implementation

Fit one change at a time against a preserved ROM and a named patch. Require generated-symbol checks, exact asset/stream equivalence where applicable, explicit scratch/register lifetime and allocation checks, and source/staged/live artifact identity. Compare final pixels and semantic state on horizontal/vertical motion, turns, overlapping actors, gates and mutable collectibles, deaths/restarts and stage transitions. Force rare required interactions, then verify natural alternating-framebuffer sequences; neither isolated-owner tests nor a clean screenshot replace sequence acceptance. Rerun the combined build and calibrated complete-worklist timings after integration. Preserve the target of 27,000 and the current hard memory bounds. Timing coverage must confirm live enemy counts and include moving-player play; the stationary controlled fixture alone cannot establish acceptance.

Recommended order: first the local loop, capture-selection and decoder measurements; fit byte-identical stream sharing only when a concrete storage need exists; consider precomputed drawing after measured evidence shows the local paths insufficient. Selective actor omission or relaxed overlap/dirty checks are not the first recommendation, because they revisit the ownership and replay failures documented above. No unmeasured option is represented as meeting the target.
