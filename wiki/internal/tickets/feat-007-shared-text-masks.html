Authorize migration of ordinary 8×8 text across all six presentation screens and the gameplay HUD to a shared monochrome font with separately specified text colours. Objective and evidence

Store each distinct monochrome glyph shape once as an 8-byte, 1-bit mask, and select foreground colour when drawing text. Screen text and gameplay digits should share the authoritative font definition. The existing gameplay HUD already selects a drawing colour, but its digit masks occupy 32 bytes each; the unfinished BUG-035 stage panel has a separate 1-bit font. Consolidate these paths instead of retaining parallel font definitions.

Measured source baseline: HEAD 1e57c3eb97572e5fa3766d470bb41cc087646fd6 plus the hashed local working state in inventory.json. The current presentation union contains 262 distinct native images before two phase substitutions, exceeding its 256 logical-ID limit. Of these, 88 coloured alphanumeric images match 35 distinct binary shapes. Their pixel payloads compare as 2816 bytes versus 280 bytes of masks; this is a representation comparison, not a ROM-saving promise, because gameplay references, metadata, code and compression affect actual storage.

Retained earlier successful-build capacities are historical observations: resident 8174/8192 bytes, presentation module 1280/1280 bytes and instruction module 937/938 bytes. The current working source fails the atlas guard. Establish exact source identities and a reproducible comparison fixture before implementation; do not describe a stale ROM as current-source acceptance.

Current acceptance exception: see the user-approved BUG-036 split. Known name-entry defects and full interaction acceptance are non-blocking; shared-text coverage remains required.

  • Presentation: ordinary character-font labels, numbers and punctuation on attract/title, instructions, level-start, enter-high-score, high-score and game-over screens. Include names, scores, credits, part and bonus values, multiplier text, prompts and side-panel text.
  • Gameplay HUD: fixed labels and all existing dynamic character text, including score/top score, credits, part/bonus numbers and letter/multiplier displays. Preserve current event triggers, value formatting, leading-zero rules, positions, glyph shapes, timing and animations.
  • Colour contract: inventory every migrated text run and dynamic field with its location, glyph source, colour source and background behavior. Excluded: the graphic LadyBug logo and its animation, collectible/sprite artwork containing letters, 16×16 score-popup art, death animation, vegetables/enemies/player, maze/gate graphics, new screens, new game rules, global hardware-palette redesign, framebuffer-depth changes, loader/MMU protocol changes, monitor/web tooling, and an assertion that every currently unspecified colour already matches the arcade. Those graphics keep their existing rendering paths.

Recommended approach and alternatives

Use one authoritative monochrome glyph bank, including required punctuation and blank handling. Text records identify the character sequence, destination and foreground colour; dynamic fields select their current value and colour through the same interface. Draw static text during screen preparation and dynamic text only through existing update triggers. Keep the native 4-bit framebuffer. Explicitly clear or restore the destination background so shorter text and digit changes cannot leave stale pixels.

Remove migrated precoloured text images from the presentation maps and eliminate redundant HUD/stage font payloads. Text and graphic IDs must be unambiguous; do not silently reinterpret existing tile IDs. Exact record encoding, helper placement and bank access are assignment details that must pass the initial fit gate. A bounded transient expansion cache may be used only if its capacity and invalidation are proven; coloured copies must not become authoritative stored font variants.

Prefer this over expanding phase-slot substitutions: text is a large measured source of duplication and future recolouring should not consume extra slots. Screen-specific atlases remain a possible later response if the complete graphic specification requires them. Wider tile IDs or wholesale sprite-format conversion are excluded from this ticket.
