BUG-087 — Level speed progression Draft

Prepare an arcade-grounded enemy movement policy after identifying what drives the reported CoCo level-to-level speed change.

Objective and report

The user reports that gameplay appears to speed up at every level and requests arcade threshold research followed by preparation of a timer/enemy movement correction. This ticket separates border rotation timing, enemy movement cadence, player velocity, sprite animation dwell, and transient adaptive-rendering timing. The confirmed source mismatch below is a candidate defect, not yet a demonstrated cause of the CoCo report.

Expected behavior is the approved, selected Lady Bug arcade difficulty profile's enemy movement schedule across part start and elapsed time. The arcade tables do not produce a simple strictly increasing rate at every part boundary. Any CoCo repair must reproduce the selected source policy without changing the independent border timer, player movement, animation dwell, or adaptive-rendering cap behavior.

Baseline and confirmed source facts

Source baseline is fe160ae; the parent verified that the current core source files match the baseline build receipt. Arcade input identity and selected ROM bytes are recorded in the RSCH-014 Step D evidence, generated rate-policy model, and selected disassembly.

On local MAME 0.220, DSW0 bit 1 selects the Easy/Medium or Hard/Hardest rate table; MAME reports Easy as the default, with no local DIP override. The active part counter is incremented from zero to one before first play and again at each later transition. The arcade selector indexes the offset table with the active counter directly, so active Part N uses index N. The earlier counter-zero-as-Part-1 interpretation is rejected. Counter 51-255 uses offset 16; the arcade counter itself wraps 0xFF to 0x00. This is distinct from the CoCo's STAGE 255-to-1 progression.

Under the default Easy/Medium profile, stage-start codes are Parts 1-6: 0x10; 7-8: 0x12; 9: 0x10; 10-14: 0x12; 15-17: 0x15; 18-50: 0x18. Under Hard/Hardest they are Parts 1-2: 0x10; 3: 0x12; 4: 0x10; 5-6: 0x12; 7-8: 0x15; 9: 0x12; 10-11: 0x15; 12-13: 0x18; 14: 0x15; 15-17: 0x18; 18-50: 0x20. Codes mean average coordinate steps per enemy dispatcher: 0x10=1.0, 0x12=1.19921875, 0x15=1.5, 0x18=1.796875, and 0x20=2.0. Within each part, the index is min(15, part_offset + ($61B7 >> 4)). The model contains per-part offsets and every code-change threshold for both profiles.

The elapsed counter starts at zero. Timer $61B6 starts at 96 logical gameplay-loop calls, reloads at 60, and increments $61B7 at expiry until it saturates at 0xF0. The first elapsed bucket is reached after 996 loop calls; later buckets are 960 calls apart; bucket 15 begins after 14,436 calls. These source-derived units are not raw arcade frames. The main loop polls VBlank, but static code does not prove one enemy dispatcher call per VBlank. No post-vegetable rate branch was found.

CoCo src/main.s::reload_box_timer already matches the arcade border thresholds: Part 1 uses 9 box ticks, Parts 2-4 use 6, and Part 5 onward uses 3. CoCo src/enemy_runtime.s::et_find_movement instead gates on LAST_FRAME & 1 and applies fixed framebuffer movement deltas, with no part or elapsed-rate selector. This is a confirmed source-policy mismatch. Current frame-indexed CoCo behavior across a natural level transition has not been measured, so causal attribution to the user's report remains open.

Scope and competing explanations

In scope: identify whether a current CoCo natural level transition changes enemy movement or game-loop cadence; distinguish movement updates from player speed and animation; choose the target arcade DIP profile; and prepare a bounded enemy-rate design with cycle-capacity evidence. The candidate enemy update path is src/enemy_runtime.s. Include src/main.s only if tracing proves its part/timer initialization owns the required state. Include src/adaptive_runtime.s only if a current trace attributes the transient to that subsystem.

Out of scope: changing the border timer already matched to the arcade, changing player movement, changing actor pose dwell tracked in BUG-080, creating a generic speed cap, or duplicating the adaptive-rendering speedup report owned by BUG-058. A speedup that appears only during rendering recovery or a phase handoff belongs to that separate diagnosis until a trace proves an interaction here.

Retained timing-wiki evidence records four-enemy windows up to 28,800 horizontal cycles and 27,920 vertical cycles against the 27,000-cycle target. Raising enemy movement cadence may worsen the existing over-budget windows. The repair class is High-risk because it changes gameplay timing, shared enemy dispatch state, and work on a tight frame boundary; fit and preservation of accumulator/state ownership are material risks.
