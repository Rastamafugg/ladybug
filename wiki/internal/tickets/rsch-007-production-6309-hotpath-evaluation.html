Approval brief

Objective and motivation

Measure the repaired TFM and LDQ/STQ candidates against byte-exact equivalents of the current production player save-under and roaming-background routines. The result must identify which routine and phase, if any, produces a material recurring-frame reduction before any production 6309 implementation or separate-ROM decision.

Confirmed source evaluation

The current proxy sweep is not an exact production baseline. Its source and destination both advance by eight bytes and then both receive a 152-byte outer stride. Production save_player, restore_player, and roam_copy_fb_to_bg stride only the framebuffer side; the background side is linear. Production also uses four-byte PULU D,Y transfers or four word loads/stores rather than the proxy fixture’s byte-at-a-time baseline. Therefore the repaired TFM values 126/243/477/945/1881 versus 64/119/229/449/889 and repaired LDQ/STQ values 118/222/430/846/1678 versus 74/134/254/494/974 prove instruction and loop behavior, but cannot be applied as production speedups.

At source SHA-256 0cb9094f585303c543d9e145d7cd18d4099cc3475c172d70fb8329e0ab6e4d61, save_player and restore_player each copy 16 rows of eight bytes between a 160-byte-stride framebuffer and a linear 128-byte owner-local save-under buffer. At source SHA-256 894aab87cb14d76bca76d7012f95de9768744f34e1b568ce6c2a142d60793b19, roam_copy_fb_to_bg has the same full 16-row one-sided-stride shape. These are structurally valid TFM and two-LDQ/two-STQ candidates, subject to setup, loop, register, and return costs.

roam_capture_ring_row copies only two exposed rows during vertical movement. Its column phase zero is contiguous and eligible, but its short worklist and required final X value may make setup cost dominant. Rotated column phases reorder bytes and are not direct TFM candidates. Persistent roam_copy_bg_to_fb restores 16 rows: column phase zero is contiguous; phase four can be expressed as two reordered Q transfers; phases two and six allow only partial Q grouping; odd phases wrap at byte boundaries and require their existing mixed byte/word sequence. Nonzero row phase can split one logical restore into two calls, adding dispatch and setup cost.

TFM requires a fresh eight-byte count in W for every strided row and consumes pointer registers. LDQ/STQ uses Q=D:W, so candidate code introduces W/Q clobbers not named by the current 6809 ABI comments. Exact caller liveness and any preservation cost must be included. Foreground BACK construction, owner-local save-under selection, source preservation, no-FRONT-write rules, and the 160-byte framebuffer stride remain invariant.

Preliminary recommendation

  • Highest-value controls: exact 16-row save_player, restore_player, and roam_copy_fb_to_bg current-versus-TFM-versus-LDQ/STQ snippets.
  • Phase controls: exact roam_copy_bg_to_fb phase zero and phase four, plus one odd rotated phase as a non-applicable control.
  • Setup-dominance control: exact two-row phase-zero roam_capture_ring_row, preserving its returned X.
  • Current verdict: no production speedup is established. TFM and LDQ/STQ remain candidates only for the listed shapes; blanket replacement of roaming copies is rejected.

Scope and exclusions

In: add one exact-production-shape benchmark source and one runner; copy current instruction windows verbatim into the baseline; implement isolated TFM and LDQ/STQ equivalents; measure setup, row loop, one-sided stride, split-ring dispatch, required final registers, correctness, guards, source preservation, and repeatability; count exact routine invocations in named natural and forced production worklists using existing timing/probe infrastructure; project candidate cycle savings against the current 27,000-cycle engineering target and 29,666-cycle hardware frame ceiling; update benchmark guidance and ticket evidence.

Out: production assembly changes, conditional 6309 production paths, release ROMs, separate-ROM policy, native-mode entry, physical-hardware qualification, XRoar semantics, loader/MMU/mapping, framebuffer ownership/protocol, gameplay behavior, OIM/LDW work, and unrelated contiguous buffer copies.

Scenarios and edge cases

  • Player save and restore: 16 rows, eight bytes per row, exactly one strided framebuffer side and one linear owner-local side.
  • Roaming full capture: 16 rows with framebuffer source strided and ring destination linear.
  • Roaming restore: column phases zero and four, with row phase zero and one forced split-row case; one odd column phase proves non-applicability rather than reporting a missing optimization as a pass.
  • Vertical exposed-row capture: exactly two phase-zero rows with the production return-register contract.
  • Current production baseline bytes must implement the same source sequence and loop mechanics as the named routine; a byte-at-a-time proxy is invalid.
  • Aligned production-like addresses and one observed owner-address alignment variant; do not multiply owner, row phase, column phase, and actor count unless source evidence identifies an independent interaction.
  • Natural named worklists count player save/restore and one/four active roaming actors; forced phase-zero, phase-four, and split-row states cover required rare paths.
  • A stale live image, unexpected halt, timeout, identity mismatch, guard change, source mutation, FRONT write, incorrect return register, or unexplained repeatability spread fails the affected result.

Acceptance criteria

  • Each accepted baseline is linked to the exact current source window, assembled bytes, source hash, staged ROM hash, and live-byte identity; proxy baseline evidence is explicitly separated.
  • Exact current, TFM, and LDQ/STQ cycle medians are recorded for every applicable routine/phase with three cold samples, no more than 1% spread, event ticks equal to 16 times CPU cycles, and five-second per-phase deadlines.
  • Destination bytes, source preservation, surrounding guards, final pointer values, declared flags/registers, owner-local background state, and no-FRONT-write constraints pass.
  • The result records W/Q and MD effects and includes any required preservation/setup cost; a candidate that depends on an undeclared clobber fails.
  • Natural and forced worklists report observed invocation counts and project the measured routine deltas against the 27,000-cycle engineering target and 29,666-cycle hardware ceiling without attributing differences to framebuffer owner identity.
  • A production follow-up is recommended only if one candidate saves at least 1,000 cycles and at least 5% of a recurring named worklist, with no correctness/ABI failure. Results below either threshold are retained as measured but rejected as insufficiently material.
  • No production source, release ROM, XRoar behavior, native-mode policy, separate-ROM policy, loader/MMU/framebuffer protocol, or gameplay behavior changes.

Dependencies, risks, and constraints

RSCH-006 and BUG-024/025 are complete measurement dependencies. The main risks are overstating savings from a weaker proxy baseline, omitting per-row TFM setup, losing the production return-register contract, treating rotated ring phases as contiguous, or expanding a research result into a resident production path. The current complete build has previously reported resident pressure as low as 10 bytes, so any later production implementation is at least High-risk and requires a separate explicitly approved ticket. Stop after two rejected probes, two observation-tool timeouts, one material expansion into runtime ownership or build policy, or before the 10% ceiling is exceeded.
