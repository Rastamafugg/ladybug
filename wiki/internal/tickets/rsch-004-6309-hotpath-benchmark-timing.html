RSCH-004 — 6309 Ladybug hot-path benchmarks and timing validation Done

Benchmark TFM, LDQ/STQ, and OIM against representative Ladybug renderer work, investigate the XRoar TFM outlier, and establish a trustworthy timing method.

Objective and motivation

Determine whether TFM, LDQ/STQ, or OIM can improve actual Ladybug work without confusing isolated mnemonic speed with a valid renderer optimization. Repair the benchmark timing method so a measured result is tied to the authored source, staged bytes, live bytes, exact worklist, emulator CPU model, marker semantics, and repeatability evidence.

RSCH-003 established that the isolated TFM candidate measured 282 cycles against a 364,937-cycle portable baseline, while LDQ/STQ measured 18 against 40 and OIM 7 against 12. All correctness checks passed, but the absolute TFM baseline is an outlier and is not suitable for production decisions.

Scope and design

In: source-aligned hot-path benchmark fixtures, 6809-compatible reference routines, 6309 candidate routines, host-side correctness oracles, XRoar timing validation, marker and breakpoint semantics, event-tick/cycle recording, static cycle cross-checks, repeated length/count sweeps, and a recommendation for each instruction. Out: production opcode adoption, release ROM changes, separate 6309 ROMs, loader/MMU ownership, framebuffer ownership or publication protocol, gameplay behavior, and native hardware qualification.

Hot-path cases

  • TFM: benchmark the row-sized contiguous transfers inside the existing save_player, restore_player, roam_capture_ring_row, and phase-zero roam_copy_bg_to_fb shapes. Preserve the surrounding 152-byte framebuffer stride in the fixture; do not claim that one TFM handles the full strided rectangle.
  • LDQ/STQ: compare a four-byte transfer matching the existing PULU D,Y plus two stores in player and roaming save-under paths. Test aligned and unaligned addresses and source preservation.
  • OIM: compare masked partial-pixel merge work matching merge_sprite_byte/sparse_blit_fb. Cover high-nibble, low-nibble, mixed, zero, and fully opaque source cases; reject OIM where it cannot preserve the opposite destination nibble.
  • Context: retain at least one complete active renderer interval or named sub-worklist attribution so an instruction result can be translated into frame impact without replacing the existing timing contract.

Timing-method repair

  • Record both XRoar event ticks and reported CPU cycles at every boundary, together with marker address, halt reason, CPU mode, ROM hash, source hash, and XRoar executable identity.
  • Use only one start and one end marker per isolated case. Do not use a repeated internal-loop breakpoint as the primary timing boundary.
  • Add a count/length sweep with fixed setup and multiple repetitions. Fit the incremental cost and compare it with a static 6809/6309 cycle model; a single absolute result is insufficient.
  • Verify marker bytes and live destination bytes before interpreting a symbol. Compare authored source, listing/map address, staged ROM, and XRoar-loaded bytes where loading or relocation is involved.
  • Investigate the monitor implementation mismatch: the executable is XRoar 1.11 and exposes read_cycles/cpu_cycles, but the tracked docs/reference/xroar/src/monitor.c contains no corresponding method. Either align the binary and source or label the binary as an external measurement dependency.
  • Classify a timing result as valid only when repeated samples for the same fixed work agree within 1% or are identical integer counts after the measurement model is applied. Otherwise retain the result as invalid evidence and report the cause or unresolved discriminator.

Scenarios and edge cases

  • Source-aligned TFM row copy with 1, 2, 4, 8, and 16 row-byte lengths, including the outer framebuffer stride.
  • LDQ/STQ at aligned and odd source/destination addresses, with guards before and after both ranges.
  • OIM for both nibble orientations, transparent zero, mixed transparency, and opaque bytes.
  • 6809 reference and 6309 candidate under identical fixtures; baseline ROM bytes must remain identical across CPU modes.
  • Repeated cold launches and repeated in-process cases, with one start/end breakpoint pair per case.
  • Marker at entry before the first instruction and marker after the final instruction, including a control routine with a known static cycle range.
  • TFM source/destination ranges that end near a page boundary, without crossing the production PAR5 remap contract.
  • Incomplete, timed-out, or tool-mismatched runs are failures of the measurement method, not passing performance evidence.

Observed evidence and working hypotheses

The current RSCH-003 artifact was rerun successfully under WSL three times. Each result JSON has SHA-256 320b5eacc9574d85c141803f4497a91b7d6a7fbd050fc02750cc1acb6c775451; source hash remains d1d2adbc01ebcee72cc086cc4b163e2b32d005f1ab222d7efd92be9f19156601. Baseline 6809 results were identical in all runs: TFM 364937, LDQ/STQ 40, OIM 12, and LDW/STW 12 cycles, with all correctness checks true.

A bounded internal-marker probe reached copy_loop at 364084 reported cycles and the copy end at 365172, while the benchmark start was 235. This confirms that the current observation path is deterministic but does not explain whether the excess is executed CPU work, event-counter semantics, or breakpoint/marker interaction.

Speculation: the most likely immediate risks are a measurement implementation mismatch between the tracked XRoar source and the executable, or an observation-tool boundary effect around repeated addresses. The TFM instruction implementation itself is not confirmed as faulty. RSCH-004 must separate these before any production conclusion.

Acceptance criteria

  • TFM, LDQ/STQ, and OIM each have at least one source-aligned Ladybug hot-path fixture and a portable 6809 reference.
  • Every candidate passes byte, guard, source-preservation, register/flag, mapping, and footprint checks declared by its fixture.
  • Timing evidence records source/ROM/live-byte identity, CPU mode, marker semantics, event ticks, CPU cycles, repeated samples, static model, and tool identity.
  • The TFM outlier is either explained by a discriminating result or explicitly remains unresolved with the next discriminator recorded; no unsupported speedup claim is accepted.
  • The repaired timing method rejects missing markers, stale bytes, unexpected halt reasons, tool mismatch, and repeatability failure.
  • Results include a measured frame/worklist translation and a recommendation for each instruction: candidate for a separate implementation ticket, retain 6809-compatible source, or reject.
  • Full scripts/build.sh build remains passing and no production ROM, loader, MMU, framebuffer, or gameplay behavior changes.

Dependencies, risks, and exclusions

  • RSCH-003 harnesses and the current XRoar monitor build are the starting point.
  • Primary risks are incorrect marker semantics, stale or mismatched emulator binaries, unmodeled CoCo 3 memory timing, and applying a contiguous-copy result to strided or remapped data.
  • Results are emulator evidence until an independently validated timing source or hardware measurement exists.
  • Separate 6309 ROM builds remain excluded. They would require a new High-risk design covering distribution, fallback, hardware qualification, loader assumptions, and capacity.
