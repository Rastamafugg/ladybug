Approval brief

Objective and motivation

Add one internal tooling article that explains how Ladybug combines build checks, independent source and artifact oracles, focused regression verifiers, emulator execution, and measurement evidence. Give each maintained test entry point a short purpose statement and identify whether it is part of the ordinary build path or is invoked for a focused ticket. This fills a wiki gap: the build runbook explains commands and the Python-oracles article explains artifact authority, but neither gives a project-wide testing model and inventory.

Evidence and baseline

Baseline is repository HEAD 3dd3397f99b969539bb0f821e6b98cb1548bab2d on 2026-10-06. The tracked top-level scripts/ directory contains 74 verify_*.py entry points and one test_source_audit.py unittest module with 24 named test methods. The test scripts are unchanged in the current worktree. scripts/build.sh directly runs build-integrated verification and has a separate verify-gmc path for XRoar/GDB execution. Existing build workflow, Python build and oracles, and XRoar/GDB workflow pages are the source documentation baseline.

Scope

In: create wiki/internal/tooling/testing.html; link it from wiki/internal/tooling/index.html; document the testing approach, types of checks, build-integrated verification, emulator/runtime verification, evidence and artifact-identity rules, and the script-level purpose of all 74 top-level verifier programs. Name and summarize all 24 unit-test methods in test_source_audit.py. Classify the inventory by purpose and ordinary-build versus focused invocation.

Out: changing tests, scripts, runtime code, build behavior, acceptance criteria, or test outcomes; executing the emulator or the listed tests; enumerating every assertion or scenario internal to each verifier; and treating capture, benchmark, or diagnostic-probe utilities as pass/fail tests. Mention those utilities only to distinguish measurement/evidence from functional verification.

Scenarios and edge cases

  1. A contributor needs the short answer to what runs during scripts/build.sh build and what additional coverage scripts/build.sh verify-gmc adds.
  2. A ticket author needs to select focused source, asset, runtime, behavior, framebuffer, audio, profile, capacity, or performance checks without assuming all 74 verifier scripts run on every build.
  3. A reader must distinguish an independent oracle from the generator or source it checks, a forced state from a natural gameplay sequence, and a measurement/capture from a pass/fail test.
  4. A verifier that is ticket-specific or retained for historical regression coverage must not be described as a current default suite member unless the build workflow calls it.
  5. Missing required runtime phases or stale artifact identity must be described as incomplete/failed evidence, not a passing test.

Options and recommendation

Expanding build-workflow.html would mix operating instructions with the testing model and make the 75-entry inventory difficult to scan. Extending python-build-oracles.html would overstate Python artifact checks as the whole test strategy. Recommend one dedicated testing article linked from the tooling index and cross-linked to those existing runbooks.

Acceptance criteria

  1. The article explains the risk-directed approach: build-integrated gates cover generated artifacts and hard boundaries; focused verifiers cover named regressions; runtime checks use natural sequences plus forced cases for distinct rare-path risks; measurements and human observations are reported separately from pass/fail correctness.
  2. The article describes the roles and limits of build, verify-gmc, the XRoar/GDB round trip, and the existing oracle workflow. It does not imply that all ticket verifiers run in the default build.
  3. Every top-level scripts/verify_*.py file in the baseline inventory is listed once with a source-checked purpose and a clear category. All 24 methods in test_source_audit.py are named and briefly described. The page states its baseline revision and how the inventory should be refreshed.
  4. The tooling index links the new page. All local file and fragment links resolve, IDs are unique, and changed HTML follows the wiki shell and stylesheet conventions.
  5. Only the approved wiki page, tooling navigation, ticket lifecycle records, and log entry change. No source, scripts, generated outputs, ROMs, capacities, or runtime behavior change; no ROM build is required.

Verification plan and risks

  • Inventory completeness and stale descriptions: compare the catalog against the exact baseline scripts/verify_*.py and scripts/test_source_audit.py file set, inspect each module description and relevant build.sh call sites. This covers omitted or misclassified entry points.
  • Incorrect default-suite claims: review every “build-integrated” label against the current scripts/build.sh command path; describe all other verifiers as focused unless an explicit default call proves otherwise.
  • Broken navigation: parse the changed wiki pages, check unique IDs and local links, and run git diff --check.

No game build or test execution is needed for this documentation scope. If source review exposes a stale or failing test, record the finding and propose separate work rather than changing the harness under DOC-013.
