Approval brief

Objective and motivation

Use line feed (LF, byte 0A) as the only line ending for tracked text files in both the Git repository and developer worktrees. Make the policy apply regardless of each machine's Git setting, and prevent candidate source copies from inheriting carriage-return plus line-feed (CRLF, bytes 0D 0A) when their tracked sources are intended to use LF.

Evidence and baseline

At E HEAD 1a55c4ac45541d93e8396af133f8793d07ae5bb0, the E worktree is dirty. Its .gitattributes contains only *.sh text eol=lf and *.sha256 text eol=lf; no .editorconfig exists. Git configuration from C:/Program Files/Git/etc/gitconfig sets core.autocrlf=true. git check-attr reports text and eol unspecified for src/presentation_runtime.s. Its Git HEAD blob is LF-only, while the E working copy and the copied FEAT-010 successor source file are CRLF-only. The successor's checksum manifests are LF-only, as required by TOOL-016. This is a demonstrated mismatch between checkout/configuration and generated-package writing, not evidence of a source-code behavior defect.

The official Git attributes documentation states that unspecified text/eol attributes defer to core.autocrlf/core.eol, and that attributes can define normalization and checkout endings. The checked-in attribute policy currently covers only shell scripts and checksum manifests.

Scope

In: inventory all tracked paths and classify text, binary, and intentional exceptions; define explicit LF rules in .gitattributes; add .editorconfig with LF defaults for supported text editors; normalize tracked text in a clean isolated worktree; document the policy and candidate-copy expectations in the build workflow. Preserve TOOL-016's explicit LF checksum writer.

Out: changing any machine- or user-global Git setting; changing game logic, build outputs, ROMs, artwork, audio, PDFs, or other binary payloads; normalizing historical ignored repro/ packages or rewriting their identities; running game builds or runtime checks; applying a broad renormalization to the dirty E worktree.

Scenarios and edge cases

  • Fresh Windows checkout with core.autocrlf=true must keep tracked text at LF because repository attributes define the checkout policy.
  • Fresh WSL/Linux checkout must also show LF in both the index and worktree.
  • Existing tracked files whose Git blobs contain CRLF must be explicitly classified and normalized; text=auto alone must not be assumed to rewrite every historical blob.
  • Binary and format-sensitive files must remain byte-identical and receive -text or an explicit exception.
  • Editor-created and candidate-generated text files must end in LF; checksum manifests continue to use TOOL-016's byte-explicit writer.

Options and recommendation

Keep the current narrow rules: smallest change, but source checkout behavior continues to depend on machine configuration. Change global Git settings: affects unrelated repositories and does not travel with the project. Recommended: project-local .gitattributes plus .editorconfig, backed by an inventory and a one-time staged normalization in an isolated clean worktree. The exact attribute patterns and binary exceptions are to be frozen after the inventory, before Ready.

Acceptance criteria

  1. Every tracked text path has an explicit LF rule. A fresh Windows checkout with core.autocrlf=true and a WSL/Linux checkout both report LF for the index and worktree using git ls-files --eol.
  2. .editorconfig requests LF for text files supported by the project's editors; new source, HTML, JSON, shell, and text records do not acquire CRLF through normal editing.
  3. All binary and intentional exceptions are listed and remain byte-identical before and after normalization.
  4. The reviewed staged normalization contains only line-ending changes in the enumerated text paths plus the policy/documentation files. Content compared after normalizing CRLF to LF is unchanged.
  5. The dirty E worktree is untouched by the normalization operation. Historical frozen candidate manifests, commands, evidence, and hashes remain unchanged.
  6. The build-workflow page explains the distinction between tracked-file attributes and generated candidate files; checksum manifests continue to pass the existing TOOL-016 LF contract.
