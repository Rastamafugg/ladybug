Reusable architecture, project configuration, evidence and workflow standards; design only.

Objective and motivation

Define a shared home for engineering architecture and implementation standards, with each application retaining its own configuration, assets, acceptance decisions and resulting outputs. Models should be able to ask what constraints apply, what evidence supports a proposed change and which dependencies it affects without repeatedly reconstructing those facts from tickets and scripts.

Memory-layout planning is one capability of the framework. Other capabilities include build evidence, reusable workflow definitions and explicit integration contracts. The design must reuse existing Ladybug mechanisms where appropriate rather than introduce a second catalog or a general autonomous execution controller.

Baseline: knowledge currently spans the wiki, source-reference configuration, build guards, generated maps/listings, build receipts and ticket-specific checks. Repeated reconstruction and the source-order dependency exposed during the EXTRA/SPECIAL relocation discussion motivate the proposal. No measured time-saving baseline or current all-profile capacity result has been established by this filing.

Proposed design scope

  1. Ownership: define what belongs to the shared architecture project, a platform family such as CoCo 3/GMC, and each application.
  2. Configuration and outputs: define how projects declare regions, profiles, tools, workflows and local output locations, and how results identify their originating inputs.
  3. Memory and placement evidence: cover region allocations, reserve policies, routine locations, branch reach, fixed-address consumers, mapping/lifetime restrictions and verifier dependencies. Distinguish established coverage from unknown references.
  4. Workflow promotion: define how a locally discovered workflow becomes a reviewed reusable capability while project-specific assets and authority stay local. Shared process-based test/diagnostic execution contracts, including whole-run deadlines and child ownership, are cross-referenced to Master Project MP-0023; this ticket does not implement that runner.
  5. Versioning and migration: define pinned versions, compatibility rules, staged adoption and rollback before any repository extraction or project conversion.
  6. Incremental delivery: select a small first implementation candidate, proposed as a retained-build capacity report, without making the complete framework a prerequisite for delivering that report or Ladybug 1.0.

Excluded: implementing the framework, automatic code relocation, changes to game behavior, applying the intermission package, controller recovery repairs, new execution authority, runtime profiling, ROM builds, MAME/XRoar/GDB, project-wide migration, GitHub repository creation and commits. Future implementation requires separately approved bounded assignments.

Ownership and integration contract

Shared architecture project: common record formats, interpretation rules, implementation standards, workflow contracts, reusable readers/checkers and their independent examples. This is a proposed responsibility boundary; no separate project exists as a result of this ticket.

CoCo 3/GMC platform family: documented address-space conventions, physical-page/bank distinctions, hardware restrictions and reusable platform workflows. Platform defaults must identify assumptions; an 8 KiB window is not automatically an application's permitted allocation.

Ladybug and other applications: actual region assignments, profiles, tool locations, approved budgets, fixtures, game-specific scenarios, assets, exceptions and all resulting reports/evidence. The shared framework must not infer runtime permission from configuration or a previous passing result.

Integration: an application pins compatible framework and platform versions, supplies its reviewed local configuration and chooses its output directory. Generated evidence records the exact versions and inputs used. It cannot silently modify allocations, approvals or application configuration. Unknown fields or unsupported versions must not silently produce a success conclusion.

Existing Ladybug records to reuse

  • Memory map: authored allocations, lifetime/ownership notes, historical fits and limits.
  • Source guide and scripts/source_reference.json: semantic source configuration and generated-reference conventions.
  • scripts/source_reference/model.py, map_parser.py, listing_parser.py and normalize.py: existing representations/readers for symbols, bytes, calls and address identities.
  • scripts/source_reference/provenance.py: captures pre-assembly inputs and checks recorded artifact identities. Reuse its supported semantics; do not rehash old outputs and claim a new build.
  • scripts/build.sh: existing region guards. build/ladybug.map, build/ladybug.lst, presentation maps/listings, build/source-build-receipt.json and build/ladybug-sparse-layout.json: candidate retained evidence, not admitted as current by this ticket.
  • scripts/verify_enemy_runtime.py: concrete source-order dependency on the relative positions of apply_letter_pickup and add_special_score. Record this as a placement dependency example, not authorization to change that verifier.

Missing or fragmented capability: a consolidated profile-specific connection between applicable limits, occupied extents, branch reach and non-game consumers of layout. Completeness must not be inferred from a list of direct calls; indirect destinations, aliases and authored verifier assumptions may require explicit declarations.

Glossary and evidence meanings

Build and profile
A build is output from particular inputs and settings. A profile names a combination of settings. Different profiles can occupy different amounts of memory.
Region and physical capacity
A region is a named address interval with an owner and purpose. Physical capacity is the hardware space available, which may exceed this owner's permitted allocation.
Permitted allocation and required reserve
Permitted allocation is the maximum extent the owner may occupy. Required reserve is space deliberately kept unused under an identified policy. A missing reserve is unknown, not zero.
Occupied extent and unused tail capacity
Occupied extent runs from the region start to its established occupied end, including intervening bytes. Tail capacity is permitted allocation minus occupied extent. It does not imply internal holes are reusable. Reserve margin is tail capacity minus required reserve.
Address identity
An address plus the context needed to identify its bytes: CPU address, mapped physical page, cartridge bank/offset, and applicable phase where relevant. Equal CPU addresses need not refer to the same storage.
Placement dependency and branch reach
A dependency is a caller, fixed offset, mapping rule or tool assumption affected by movement. Branch reach is the permitted signed distance from the end of a branch instruction to its target.
Hash, provenance and frozen input set
A hash fingerprints contents. Provenance relates outputs to the inputs/tools that produced them. A frozen input set is a recorded, identifiable selection; it does not lock or alter files.
Fixture, control and independent expected answer
A fixture is a prepared example; a control checks a distinct success/failure condition. Its expected answer is established separately from the code being evaluated.
Report validity versus capacity outcome
A report is valid if its identities and calculations are supported. It may validly report an overflow. Missing or conflicting evidence cannot establish fit. Historical evidence may be valid for its named build without describing current source.

Promoting local workflows

  1. Describe the workflow encountered in an application, its problem, inputs, outputs, constraints and actual evidence. Retain application-specific material locally.
  2. Identify the universal rule and the parameters that differ by project. Separate hardware-family restrictions from application choices.
  3. Review at least one contrasting example or explicit non-applicable case before calling the rule reusable. Synthetic examples do not prove adoption by another real project.
  4. Publish a versioned reusable definition only after its meaning and independent checks are reviewed. A candidate local script does not become a universal standard by being copied.
  5. Let each application adopt a named version explicitly, retain its own outputs and verify compatibility. Promotion never carries execution or approval authority between projects.

Versioning and migration gates

Version common records, platform rules and implementations explicitly. Additive optional data must preserve existing meanings; incompatible field meanings or required behavior require a compatibility change and explicit consumer handling. Never silently reinterpret historical evidence using new limits.

Migration sequence: approve the ownership/design boundary; identify existing consumers and duplicated rules; freeze application configuration and baseline evidence; qualify compatible behavior on retained examples; approve one application pilot; compare old and new conclusions; retain rollback to the prior pinned version; only then consider broader adoption. Concrete migration commands, writable files and controls belong in a later assignment.

A separate repository is a proposed destination, not an initial dependency. Do not move code before its ownership, dependencies and compatibility are understood. Existing controller cards and their prohibitions remain authoritative; this framework does not adopt or replace them.

Small first implementation candidate

Propose one advisory report for resident code, resident assets and the presentation overlay from one identifiable retained build. Select the actual build/profile only after its supporting files and historical limits can be reconciled. If that is impossible, report the missing evidence; do not rebuild automatically.

Candidate inputs: build/source-build-receipt.json, build/ladybug.map, build/ladybug.lst, build/ladybug-presentation-runtime.map and build/ladybug-presentation-runtime.lst, with matching historical configuration and applicable limits. Today's scripts/wiki cannot automatically establish historical limits.

Proposed outputs: one reviewed application-owned region contract, one machine-readable capacity report and one concise control summary. Exact output paths remain unassigned. Use plain-language chat to explain results; defer a new HTML renderer unless existing presentation can be reused cheaply.

Initially report established extents and tail capacity only. Internal free-space recovery, complete placement analysis and the EXTRA/SPECIAL branch example are outside this small implementation candidate, while remaining within the larger architecture roadmap. No current intermission fit is inferred.

Design acceptance criteria

  • Every shared/platform/application responsibility has an identified owner; approvals, project configuration and resulting outputs remain application-owned.
  • Define the minimum configuration/output fields and meanings, including evidence freshness, address identities, unknown coverage and version compatibility.
  • Walk through one existing Ladybug capacity question and one placement-dependency question; identify which answers existing evidence supports and which require later capability.
  • Demonstrate workflow promotion and rejection of a project-specific assumption using reviewed examples; no claim of multi-project implementation without evidence.
  • Document migration stages, rollback and exclusions. No new 1.0 gate or framework dependency is introduced into game tickets.
  • Define the small first implementation assignment's remaining inputs, independent controls, output ownership and explicit stop conditions before requesting implementation approval.
  • Measure benefits before claiming them: baseline repeated file reads/manual lookup steps and contradictions found for selected questions; compare with traceable answers from the pilot. No time-saving percentage is invented.

Proposed checks and sign-off boundary

Apply DOC-014. These are design requirements, not approved executable cards. Revision/profile, frozen fixtures, hashes, exact commands, owner and writable paths remain unresolved; therefore nothing is Ready for dispatch.

  • Manual design review: check the ownership, glossary, versioning, workflow promotion and migration criteria above. Acceptance is an explicit reviewed design, not an implementation claim.
  • Future offline arithmetic controls: independently authored examples at a permitted limit and one byte beyond it, plus a separate reserve shortfall. Expected outcomes are exact; a valid overflow report is a successful measurement of a capacity failure.
  • Future offline evidence controls: mismatched artifact identity, missing boundary and conflicting address context must produce explicit invalid/incomplete evidence without a fit verdict. Historical evidence must not be labeled current.
  • Future retained-build check: manually establish selected boundaries from raw maps/listings before comparison with extracted results. A missing historical constraint stops the attempt without building or searching for a passing result.
  • Bounds and results: proposed whole-command ceiling 60 seconds for each future named offline phase, including nested work; duration unmeasured. Stop on expiry, retain last evidence, no automatic retries. Report setup failure, missing evidence, expected negative-control rejection and capacity failure separately.
