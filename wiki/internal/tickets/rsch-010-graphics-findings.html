Finding 1 — settled rotated gate redraw omission is source-confirmed

Observed report: after a gate rotates away from its load orientation, a collectible colour change can make one visual wall return to its authored position while collision continues to use the rotated state.

Confirmed source boundary: can_move writes the new authoritative byte in GATE_STATE, records the animation ID and queues a render only when the player pushes the gate (src/main.s:2698-2707). The final transition is queued by finish_gate_animation, and queue_gate_render stores only the current one or two render IDs, modes, and styles (src/main.s:3015-3043). After the frame, frame_render_impl clears RENDER_GATE_ID and RENDER_GATE2_ID (src/enemy_runtime.s:584-616).

A later colour transition sets RF_ENTITIES in bonus_color_tick (src/main.s:1804-1845). The background renderer then restores every entity footprint and draws every live entity (src/enemy_runtime.s:752-767; src/main.s:1543-1590). Footprint restoration resolves the current cell through MAZE_STATE and the authored screen_map tile (src/main.s:3709-3748), so it can write over a rotated gate union. The gate phase that follows is conditional on a nonzero queued render ID (src/enemy_runtime.s:801-836); it does not enumerate settled gates or reapply GATE_STATE.

The visual/logical split is also explained: gate collision reads the authoritative GATE_STATE parity (src/main.s:2563-2623), while the dynamic overlay reads that same state only when draw_gate_overlay or the transition compositor is called (src/main.s:2822-2860; src/enemy_runtime.s:2660-2694). Therefore a settled gate can remain logically rotated after its pixels are overwritten by an entity redraw. The exact report detail that only one wall is reset requires a runtime pixel capture, but the missing settled-state reapplication is confirmed by current source.

This is independent of BUG-005's accepted pending-gate case. BUG-005 demonstrated that a queued gate projection could be overwritten by a later entity/underlay pass and repaired the pending-intent ordering. Its completion evidence does not cover a settled rotated gate with RENDER_GATE_ID=0 and no current gate intent. The current source path above remains open for that case.

Finding 2 — yellow object above the spawner is unresolved

Confirmed producers: stage initialization creates six bonus entities (three hearts and three letters) plus two to six skulls according to stage. Each record is placed on any cell whose MAZE_STATE dot bit is set; place_entity has no exclusion for the cell above the den (src/main.s:1392-1473; src/main.s:1482-1527). The generated maze includes an initial dot at semantic cell (12,10), the cell directly above the spawner (build/ladybug_maze.inc:21-22, row 10 entry has $80 at column 12). A live heart or letter there is recoloured by BONUS_COLOR, including yellow (src/main.s:1592-1627), and its record is normally cleared only by coordinate-matched pickup (src/main.s:3368-3432).

The enemy nest is a second possible source of a persistent visual. On initial enemy rendering, capture_zone_bg copies the complete 16-by-32 nest framebuffer region into ENEMY_ZONE_BG (src/enemy_runtime.s:540-555; src/enemy_runtime.s:3206-3223). Every nest composition copies that retained background back into a compact stage surface, then draws active actors and the dormant actor or vegetable (src/enemy_runtime.s:2365-2442). The vegetable producer draws into the lower dormant half at ENEMY_ZONE_STAGE+128 (src/enemy_runtime.s:2408-2425; src/enemy_runtime.s:3147-3167), so source inspection does not identify an above-spawner yellow vegetable path.

The source does not prove whether the reported object is a live entity, a retained nest-background pixel, a vegetable drawn at an unexpected destination, or a stale framebuffer replay. It also does not prove why a visible live entity would fail pickup. The report remains unresolved rather than assigning the colour-cycle timing as a cause. The existing special synchronization for the above-den dot only runs after pickup at exactly (12,10) and copies a clean tile into ENEMY_ZONE_BG+60 (src/main.s:3832-3875); this is a relevant stale-background boundary, not proof of the reported failure.

Common cause assessment

The gate symptom has a confirmed shared class with BUG-005: a later background/entity or retained-layer pass can write pixels after a dynamic scenery state was established. The settled gate case is a separate missing replay path because no queued gate intent remains after transition. The yellow symptom may involve the same retained-background ownership class, especially ENEMY_ZONE_BG, but temporal correlation with collectible colour changes is insufficient to establish that link.

No platform, loader, MMU, or asset-generation defect was established by this source-only review. No source repair is authorized by RSCH-010.
