Approval brief

Objective and recommendation

Extend the release assembly tips with seven concise entries that explain how Ladybug moves packed assets through mapped memory, audio service, and the video pipeline. Keep the articles self-contained, use current source as project examples, and link to existing hardware references for canonical GIME, MMU, sound, and 6809 details.

Motivation and baseline

DOC-011 completed the first source-backed assembly-tip expansion. The current folder has six HTML pages: its index, DP conventions, register allocation, indexed addressing, shared routines, and hot loops. The release wiki already covers CoCo 3 sound, GIME, and the bare-metal memory map; internal screen-rendering, sound, and memory-map pages contain project-specific detail. The proposed practical topics are not yet available in the release tips. Source review baseline: 7b91d64c4cb7027d072d2a8f47a369abc526ded2. Findings in this ticket are source-backed examples, not new cycle or capacity measurements.

Scope

In: seven new self-contained release pages under wiki/release/reference/asm-tips/, updates to that folder's index, links to the existing public hardware and instruction references, source citations, and a dated internal log entry.

Out: assembly, build-generator, asset, audio, or verifier changes; new runtime protocols; new benchmarks or performance claims; changes to hardware-reference pages; internal mirrors of public articles; and reproducing the full internal rendering or audio design documents.

Proposed release entries

  1. asset-packing-sparse-streams.html — Explain host-side packing and boot-transport compression separately from the sparse representation consumed at runtime. Use the sparse-sprite and presentation builders, generated manifests, and boot loader as examples.
  2. mmu-pointer-lifetimes.html — Explain that a 6809 pointer names a virtual address whose physical backing depends on the current PAR mapping. Show bounded map, consume, restore, and call-return contracts; identify when a pointer cannot remain live across a remap.
  3. audio-storage.html — Trace authored/generated sound data through packed transport, boot installation, and runtime stream storage. Explain phase and mapping ownership for code, stream data, and scratch without treating one profile's generated layout as universal.
  4. audio-processing.html — Trace gameplay or presentation events through polling, queues, voice slots, command waits, mixing, and SN76489 output/shadow writes. Distinguish event admission and stream completion from verified output.
  5. screen-data-generation.html — Trace authored screen and graphic sources through the screen and presentation builders into packed tiles, sparse streams, descriptors, and final generated indices. Explain why consumers must use identities from the final packed output.
  6. sprite-blitting.html — Explain native packed-pixel addressing, sparse decode, transparency masks, clipping/bounds, save-under capture, and restoration. Use the existing player/enemy paths to show how overlapping actors constrain restore order.
  7. framebuffer-publication.html — Explain persistent A/B surfaces, owner-local metadata, rendering only into hidden BACK, and Vbord-owned FRONT publication. Show how this pipeline avoids full-frame shadow copies and why pixels and per-buffer history must stay paired.

Reader scenarios and edge cases

  1. A reader follows authored or generated data through packing, boot transfer, mapping, and its runtime consumer without confusing compressed transport bytes with runtime command encoding.
  2. A reader holds a mapped pointer only while its PAR contract is valid; a remap changes which physical page the same virtual address accesses.
  3. A reader distinguishes audio event admission, queued playback, mixer selection, register/shadow output, and physical listening evidence. Profile-specific code and generated layouts are labeled by the source path that emits them.
  4. A reader distinguishes authored screen coordinates, generated tile or descriptor identities, and final framebuffer addresses; repacking can change generated indices.
  5. A reader understands that packed-pixel writes need valid row and extent bounds, transparent pixels preserve destination nibbles, and restore order matters where actor footprints overlap.
  6. A reader updates the non-scanned framebuffer with matching owner metadata and recognizes Vbord as the publication boundary; a missing or incomplete BACK image is not a successful commit.
  7. Every article can be opened directly and understood without access to internal-only pages; links to those pages may add project context but cannot carry required public explanation.

Options and recommendation

A single broad media-pipeline article would mix host packing, MMU lifetimes, audio service ownership, pixel decoding, and interrupt publication. Separate pages make each contract findable and let the index connect the full path. Splitting memory/audio and video into separate tickets would reduce per-ticket breadth but duplicate source review and index integration. Recommend one bounded series ticket with seven named pages, source-specific examples, and one shared navigation and accuracy check.

Dependencies and order

Acceptance criteria

  1. All seven proposed pages exist under the assembly-tips folder, stand alone, contain at least one source-verified Ladybug example, state relevant limits or tradeoffs, and cite the source revision used.
  2. The packing article distinguishes host compression, boot transport, and runtime sparse decoding. The MMU article distinguishes CPU virtual addresses from PAR-selected physical pages and states the pointer lifetime at remap/call boundaries.
  3. The audio articles identify the current source/profile path and the storage-to-output stages. They do not claim audible delivery from queue admission or stream completion alone.
  4. The video articles distinguish authored data, generated identities, runtime blit/restore work, framebuffer-local metadata, and Vbord publication. They do not present project-specific ownership as a universal 6809 ABI.
  5. The assembly-tips index links all seven pages with accurate summaries. Public hardware facts link to the existing GIME, memory-map, and sound references rather than duplicating their catalogs.
  6. Source and generated-layout claims are checked against the current repository when implementation begins. Numeric cycle claims are used only when supported by the 6809 reference or identified measurements; projections and qualitative tradeoffs are labeled.
  7. HTML parsing, unique IDs, local file/fragment links, and direct-page review pass. No source, generated runtime artifact, ROM, capacity limit, or timing target changes.

Verification plan and risks

  • Source/profile accuracy: check each generator, emitted identity, selected build profile, loader handoff, and runtime consumer at the implementation baseline. This covers stale or profile-inaccurate examples.
  • Ownership-boundary accuracy: review MMU map/restore, audio service/mixer/output, and framebuffer/Vbord paths at their callers and callees. This covers pointers or work attributed to the wrong owner.
  • Data-format accuracy: compare raw/generated, compressed transport, and runtime sparse formats where each transition occurs. This covers the risk of documenting unlike encodings as interchangeable.
  • Reference usability: parse changed pages, check unique IDs and local links, and open each article directly. This covers broken navigation and missing context.

No ROM build is required for documentation-only work. If source review identifies a code defect, new runtime pattern, unsupported hardware claim, or performance measurement requirement, stop and return that work for separate scoping rather than expanding DOC-012.

class Page(HTMLParser):
    def __init__(self):
        super().__init__(convert_charrefs=True)
        self.ids, self.links = [], []
    def handle_starttag(self, tag, attrs):
        attrs = dict(attrs)
        if 'id' in attrs: self.ids.append(attrs['id'])
        if tag in ('a', 'link') and 'href' in attrs: self.links.append(attrs['href'])
cache = {}
def load(path):
    path = path.resolve()
    if path not in cache:
        page = Page()
        page.feed(path.read_text(encoding='utf-8'))
        page.close()
        duplicates = [key for key, count in Counter(page.ids).items() if count > 1]
        assert not duplicates, f'{path}: duplicate IDs {duplicates}'
        cache[path] = page
    return cache[path]
sources = sorted(tips.glob('*.html')) + [ticket]
