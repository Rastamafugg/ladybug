Static decode of the local MAME 0.220 Lady Bug program ROM; source policy is distinct from measured cabinet or CoCo frame rate.

Identity and method

Input identity: MAME 0.220 executable SHA-256 7fb5200f8c62d51ef39af168f0965196efbd53cc3d2b759d9db93118114760e4; ladybug program ROM ZIP SHA-256 2d62b0194495bea6fa765c733a60c431ce685ab1f965a999d463557ef416ddf8. The six main CPU members map consecutively at $0000-$5FFF. Selected bytes were disassembled with z80dasm 1.1.5 and checked against expected byte sequences by rate_policy_model.py. The generated model JSON retains member hashes, disassembler identity, selected code hashes, all part offsets, both full rate tables, and computed policy thresholds. Selected instructions are retained in rate-policy-disassembly.txt; the full ROM dump is not retained.

The official MAME 0.220 Lady Bug input definition maps DSW0 to the difficulty switch. Its difficulty options identify DSW0 mask 0x03, default Easy, with bit 1 set for Easy/Medium and clear for Hard/Hardest. Local mame -listxml ladybug reports the same mapping; the local ladybug.cfg has no DIP override. This identifies the local test default, not an unknown physical cabinet setting.

Part and elapsed-rate selection

The active part counter is stored at $606E/$606F. Reset initializes it to zero; the initial start increments it at $04D9 before play, and later part transitions increment it at $0662. $1F26 returns the active player's counter unchanged; $40F8 indexes the part-offset table at $0EA6 with that value, without subtracting one. Active Part N therefore uses table index N. Counter zero is prestart, not Part 1. This rejects the earlier off-by-one interpretation that mapped Part 1 to index zero.

For Parts 1-50, the index is the direct part counter; the table contains entries 0-50. Counters 51-255 use the constant offset 16 through the fallback path. The arcade byte counter wraps from 0xFF to 0x00; that behavior is separate from the CoCo STAGE rollover from 255 to 1.

The rate index is min(15, part_offset + ($61B7 >> 4)). Each rate code is a mean whole-plus-fractional coordinate-step count per enemy dispatcher; it is not a frame count. Code 0x10 means 1.0 step, 0x12 means 1 + 51/256 = 1.19921875, 0x15 means 1.5, 0x18 means 1 + 204/256 = 1.796875, and 0x20 means 2.0. The dispatcher computes a shared integer step count using an 8-bit fractional accumulator and applies that count to each active enemy. In the historical Part 1 sample, each coordinate step maps to one visible pixel.

At stage start under the local default Easy/Medium profile, Parts 1-6 use 0x10, Parts 7-8 0x12, Part 9 0x10, Parts 10-14 0x12, Parts 15-17 0x15, and Parts 18-50 0x18. Under Hard/Hardest, Parts 1-2 use 0x10, Part 3 0x12, Part 4 0x10, Parts 5-6 0x12, Parts 7-8 0x15, Part 9 0x12, Parts 10-11 0x15, Parts 12-13 0x18, Part 14 0x15, Parts 15-17 0x18, and Parts 18-50 0x20. Part 51-255 retains the saturated offset 16, subject to the arcade counter's 8-bit wrap. These are ROM policy values, not measured velocities.

The stage setup at $0730 initializes $61B6=0x60 (96 logical gameplay-loop calls), $61B7=0, and the fractional accumulator $61B5=0. On each timer expiry, $61B6 reloads to 0x3C (60) and $61B7 increments until it saturates at 0xF0. The first elapsed bucket change occurs after 996 logical loop calls; subsequent buckets arrive every 960 calls; bucket 15 begins after 14,436 calls. These are loop-call counts derived from the timer code, not raw MAME frames. For example, Part 1 under Easy/Medium changes from 0x10 to 0x12 at bucket 6 (5,796 calls); under Hard/Hardest it changes to 0x12 at bucket 3 (2,916 calls). The model JSON contains threshold changes for all indexed parts under both profiles.

Separate systems and unresolved attribution

The arcade border timer is separate: $35E3 selects 9 box ticks for Part 1, 6 for Parts 2-4, and 3 from Part 5 onward. CoCo reload_box_timer already matches these thresholds. The arcade rate selector has no post-vegetable rate branch. The rate-code bytes are not animation dwell targets; pose timing remains tracked separately by BUG-080.

Current CoCo source et_find_movement gates enemy updates using LAST_FRAME & 1 and applies fixed framebuffer deltas: one packed byte horizontally (two pixels) or 320 bytes vertically (two pixel rows), four movement steps per eight-pixel tile. No part or elapsed-rate lookup is present in this path. This confirms a source-policy mismatch with the arcade progression. It does not establish the cause of the user's CoCo speedup report: no current revision, frame-indexed CoCo trace across a natural level transition, or dispatcher-to-VBlank mapping was captured in this preparation. Player velocity and the separate adaptive-rendering transient in BUG-058 remain separate evidence questions. The timing wiki records four-enemy windows up to 28,800 horizontal and 27,920 vertical cycles against the 27,000-cycle target; reproducing arcade acceleration could increase this risk.

The retained historical sample historical BUG-050 Part 1 MAME cadence has endpoints at frames 1504 and 1528, a 24-pixel displacement over 24 MAME frame intervals, and an eight-frame pose hold. It is one Part 1 observation only. It does not measure later-part rate changes or prove whether pose selection follows elapsed frames or distance.

Verification limits

Reproduction command: wsl python3 wiki/internal/tickets/evidence/rsch014-D/rate_policy_model.py. It verifies the local MAME identity, ROM ZIP and code bytes, DIP tables, rate tables, part indexing, and the generated schedule. wsl /usr/games/mame -listxml ladybug reports the local DIP definitions. No game runtime probe, CoCo source modification, build, or emulated CoCo test was performed for Step D. A later natural level-transition probe must identify the staged artifact and live destination, use an explicit part/timer marker, have a deadline of at most 60 seconds, and state that timeout means the marker was not observed within that phase.
