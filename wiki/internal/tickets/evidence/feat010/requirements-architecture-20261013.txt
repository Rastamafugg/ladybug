Recommended user-visible flow

1. Cold boot initializes the authored Attract screen as the first presentation owner. Its first published FRONT must be fully hydrated authored art with Start selected and the selected-state treatment visible; no high-score/menu/coin overlay may appear first.
2. In title/menu Attract, up/down moves among Start, Options, and Credits/About. Return activates the selected row. Start begins gameplay exactly once at zero coin credits; it neither checks nor decrements the legacy credit byte. A fresh Return on the default Start row is sufficient to start.
3. Options and Credits/About remain local pages. Their own controls and Back behavior work; neither page receives automatic-loop preemption while active. Back returns to Attract with Start selected. Credits/About remains informational; it is not a coin-credit page.
4. If title Attract receives no menu action, preserve the existing 558-count title interval, then the existing Instructions and attract/demo cycle. Source increments the presentation interval counter and compares it with 558 in MODE_ATTRACT. Treat 558 as presentation-flow counter units; existing BUG-010 evidence describes a 558-frame title interval, but do not convert it to seconds or VBlanks without a measured clock relation.
5. A recognized fresh presentation-control edge during an automatic attract-loop phase other than title preempts that phase, requests Attract with Start selected, and is consumed. Holding the triggering key through publication must not select a menu row or start the game; release then a fresh Return starts. A fresh event during active Options/Credits/About remains local.
6. Game over and name entry retain ranking/name behavior. The resulting high-score screen is ranking-only after the menu moves. Its return path to the new menu requires a contract decision below. No coin-position layer or coin-count overlay is required on that screen.

Input ownership and unresolved contract questions

Current complete-profile flow consumes physical coin/menu events centrally in presentation_flow_tick before screen-local dispatch. MENU_EVENT is populated by the key scanner as a fresh edge for high-score and screens 6+, while Attract is not currently a menu owner. The design should establish title-menu ownership for Attract and automatic-phase preemption before phase-local processing, while keeping Options/About and keybinding pages local. Do not broadly write the shared D0 scratch byte outside owners that already own it; prior input work found phase-local D0 clobber risk.

Required held/edge rule: preemption responds to a fresh edge; the edge that caused the redirect is discarded before Attract menu dispatch. Existing previous-key state must prevent a held Return from becoming a second fresh menu event on entry. Define deterministic handling for simultaneous fresh directions/Return/Back, invalid or unmapped controls, and cold versus warm entry. Recommended minimal rule is existing menu scanner semantics (arrows, Return, Back/Escape); coin 5/6 remains outside the menu. The phrase “any input” is broader than the current menu event interface. Approval must state whether it means any recognized presentation-control edge or also joystick axes/fire/gameplay buttons and other sampled inputs. Do not claim literal any-input coverage until the scanner contract and verifier expose those inputs.

The parent has a user question pending: after navigating the Attract menu without selecting Start, should automatic instructions/demo resume after inactivity, or should the menu remain indefinitely? The currently recommended option is to restart the same 558 MODE_ATTRACT counter interval after each fresh title-menu input. Do not finalize that behavior until the answer arrives. Also resolve the ranking-only post-game screen: recommended simplest return is to keep ranking visible until a fresh presentation-control edge redirects to Attract Start, consuming that edge; an automatic timeout or implicit menu overlay is not in the current scope. This recommendation needs explicit approval because it changes how the ranking-only screen is exited.

- scripts/build_presentation.py currently requires a Coin Positions layer and validates twelve 2x2 high-score coin slots, their sparse destinations, and black underlay. The authored high-score map has removed this layer. Remove only this high-score coin-placement contract/overlay. Keep shared coin tiles or game coin behavior still used by other screens.
- scripts/shared_text.py currently extracts Start/Options/Credits at hardcoded high-score rows 20/21/22 and synthesizes ADD CREDITS. The authored Attract map places Start Game at columns 15–24 row 15, Options at columns 15–21 row 17, Credits at columns 15–21 row 19. Derive and validate the new authored spans and remove the synthetic coin prompt; retain Credits/About.
- scripts/build_presentation.py has ranking rows (2,4,5,6,7,8,9,10,11), name column 16, score column 27. These constants are tied to the prior art and must be recalculated against the authored ranking grid. The new art visibly places its heading at row 2, TOP at row 4, a first-place line at row 5, and ordinal labels through row 13. Rows 5–13 are only a map-derived candidate for nine dynamic entries, not an approved coordinate assumption. The assignment must verify each name/score destination and line stride against actual compiled art and the high-score writer, including first and last entries.
- src/presentation_runtime.s owns cold initialization, title/automatic modes, central preemption, menu dispatch, credit admission/debit, first screen publication, and transitions back to Attract. src/keybinding_runtime.s owns sampled keys and fresh-edge state. src/shared_text_stage.inc owns menu selection, row behavior, local Options/About/back, and credit prompt synthesis. scripts/build_presentation.py and scripts/shared_text.py own authored TMX extraction and generated menu/ranking destinations. src/shared_text_ranking.inc and demo/name flow consume ranking destinations. Verifiers with old source-string expectations must be retargeted semantically under new unique FEAT-010 paths; do not edit historical verifier reports, captures, or evidence.
- Coin art elsewhere (including instruction/game material) is not automatically part of the removed high-score placement contract. Gameplay HUD credit label and SPECIAL rewards are explicit exclusions and must remain byte/behavior equivalent for this task.

Risk class and architecture boundary

High-risk. Distinct risks are shared input arbitration across title, local modal screens, and multiple automatic phase owners; cold loader and first-FRONT publication; the game-over/name-entry handoff to a now ranking-only high-score screen; generated coordinates and removed compiler layer; and very small resident/asset headroom. The intended pattern stays inside existing presentation, key-scan, text generation, and map compilation paths. No new module, protocol, allocator, renderer redesign, mapping change, or increased memory/timing limit is authorized. Reclassify and return for approval if implementation needs one.

Likely touched production artifacts are the two authored TMX maps, scripts/build_presentation.py, scripts/shared_text.py, src/presentation_runtime.s, src/keybinding_runtime.s, and src/shared_text_stage.inc; ranking source or generated consumers may need changes only if updated generated destinations prove insufficient. This is an inventory, not a committed target list. BUG-122 currently overlaps src/shared_text_stage.inc; serialize implementation after its accepted integration or have the parent resolve the shared-file order. BUG-117's prior Start observer must be rerun and a new free-start observer gate added. BUG-120/058 evidence remains old-input evidence until the parent builds and verifies the combined approved source/art state.

Approval-ready recommendation and exclusions

Recommend moving the existing menu owner from High Score to Attract, preserving existing generated-text/menu patterns, removing only high-score coin placement/count/admission presentation, using existing title idle count, and routing automatic-phase fresh input through a single preemption point before phase-local work. Acceptance is measured by exact authored front/map and rank-cell checks, zero-credit Start with unchanged credit byte, consumed held redirect input, preserved 558-count natural path, local modal ownership, ranking return, and all three profile capacity gates above. Explicitly exclude gameplay HUD credit label and SPECIAL reward changes, coin/reward economy redesign, unrelated TMX art, audio changes, arbitrary performance work, and any new module/protocol or increased bounds.

Before the canonical ticket can become Proposed/Approved/Ready, the parent must incorporate the user's answer on menu idle resumption and decide the ranking-only postgame exit plus the meaning of “any input.” These are observable behavior questions, not execution details. After approval, the Ready assignment should name the fresh capsule/output paths, exact owned source files, dependency order, commands, retained artifacts, separate commit boundary, and completion report. No implementation approval is implied by this report.
