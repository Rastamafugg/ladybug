# BUG-121 corner-assistance regression: bounded source diagnosis

## Disposition

High-risk read-only diagnosis; production remains Proposed. The likely regression is source-local: after the current-cell perpendicular check fails, the new code holds immediately, so it cannot approach the next center where the requested turn becomes legal. This is strongly supported by the source change and the exact gap in the existing positive test, but the new user report has not been reproduced on a live, byte-qualified runtime. No production, wiki, build, emulator, or Git changes were made.

## Source comparison

Current `src/main.s:2884-2888` (`pt_try_late_turn`) tests `PLAYER_WANT` from the current aligned cell with `can_move`. A legal current-cell turn goes to `pt_begin_late_turn` (`:2887`, `:2889-2898`). A blocked request immediately branches to `pt_draw` (`:2888`), preserving pose and buffered request but preventing progress toward a different next-center junction.

The compared pre-fix source at `d8d0e94^:src/main.s:2872-2915` did three things after the current-cell test failed: at `PLAYER_STEP` 1 or 2 it unconditionally continued with `pt_advance`; at step 3 it temporarily shifted `PLAYER_CELL_X/Y` one cell along `PLAYER_DIR`, called `can_move` for the request, ignored the returned carry, restored the old logical cell, then unconditionally advanced. That code explains why the old behavior was more forgiving near a later junction, but its unconditional advance also caused the measured two-pixel drift in a corridor with no requested exit. It cannot be restored wholesale.

The accepted MAME rule supports both halves of the requirement. `movement_snap_reference.json:13-29` admits an ordinary corner request through a six-pixel offset and rejects at seven pixels. Its blocked-request section (`:51-113`) and RSCH-017 summary record stationary coordinates at 2/4/6 pixels for a closed vertical passage. The source/runtime causal hypothesis is therefore: **the fix removed all approach to an upcoming junction along with the unwanted no-junction drift**. Runtime confirmation remains pending.

The existing CoCo verifier misses exactly that case. `verify_movement.py:4-15` tests blocked no-exit north/west at steps 1/2/3 and south/east at step 3. Its positive case (`:17-25`) selects a perpendicular edge already legal from the current cell and admits it at step 3. It does not test “current cell blocks the requested turn; the next reachable center has that turn.” Its gate case (`:26-31`) covers an endpoint push from the current cell, not an upcoming junction.

## Concrete upcoming-corner fixtures from the canonical maze

`maze_nav` stores bits 0–3 for N/E/S/W. `can_move` enters the target cell using reciprocal masks from `cm_entry_masks` (`src/main.s:3262-3263`): N `$04`, E `$08`, S `$01`, W `$02`. In the following fixtures, “current” is `PLAYER_CELL_X/Y`; “next” is one cell in `PLAYER_DIR`; “current turn target” is the requested neighbor from current; “next turn target” is the requested neighbor from next. All listed next/current-turn/next-turn cells have `gate_owner=0`. The masks are the authored `maze_nav` bytes, not observed live bytes.

- North then East: current `(6,3)`, next `(6,2)`, next cell mask `$0E` admits the north approach (`$04`); current East target `(7,3)` mask `$00` blocks `$08`; next East target `(7,2)` mask `$0A` admits `$08`.
- South then West: current `(6,5)`, next `(6,6)`, next cell mask `$0F` admits the south approach (`$01`); current West target `(5,5)` mask `$00` blocks `$02`; next West target `(5,6)` mask `$0A` admits `$02`.
- East then South: current `(5,4)`, next `(6,4)`, next cell mask `$0D` admits the east approach (`$08`); current South target `(5,5)` mask `$00` blocks `$01`; next South target `(6,5)` mask `$05` admits `$01`.
- West then North: current `(9,4)`, next `(8,4)`, next cell mask `$07` admits the west approach (`$02`); current North target `(9,3)` mask `$00` blocks `$04`; next North target `(8,3)` mask `$05` admits `$04`.

These four fixtures exercise each `PLAYER_DIR` coordinate-offset branch and each requested-direction reciprocal mask once, across both movement axes. For each, inject the coherent pose only at the existing real `player_tick` entry marker, use `PLAYER_STEP=1,2,3`, preserve the actual mapped direction request, then observe through `pt_done`. The turn must progress along the old axis to the next center and accept the buffered perpendicular direction there. Matched no-exit controls remain RSCH-017’s cells `(12,15)` and `(12,16)`, mask 5 (N/S only): requests west while north at steps 1/2/3 must retain zero X/Y/step delta and update facing only.

## Smallest correction candidate and gate limit

Do not restore the unconditional old block. For ordinary, non-gate upcoming corners, the smallest bounded behavior is a read-only upcoming-center qualification: project the next-center cell using `PLAYER_DIR`; test the requested reciprocal edge from that cell using the existing `TEST_X/Y`, `test_cell_offset`, `maze_nav`, and `cm_entry_masks` representation; continue old-axis movement only when that exact edge is present; otherwise use the current `pt_draw` hold. Apply this at all three partial offsets so offsets 2/4 can approach a real upcoming junction, while no-exit corridors remain stationary. Once the center is reached, the existing current-cell `can_move` admits the buffered turn. This preserves direct current-cell turns and avoids consulting a synthetic arbitrary maze opening.

Dynamic gate handling is a bounded unresolved design point. `can_move` first dispatches gate-owned cells (`:3101-3104`); its `cm_pass_horizontal`/`cm_pass_vertical` cases (`:3147-3161`) read the current `GATE_STATE`. But `cm_try_rotate` can mutate `GATE_STATE`, set animation state, and queue gate rendering (`:3163-3245`). Calling it as an early lookahead at step 1 or 2 would move a gate side effect earlier than the old step-3 probe. A static `maze_nav` check alone is insufficient because `maze-format.html` documents four potential generated gate edges while runtime admits only the current orientation. The read-only current-open passage predicates can qualify those paths without mutation; a pushable endpoint is not currently exposed as a read-only “would admit” result. To keep gate timing, do not trigger endpoint rotation before step 3. Preserving a buffered step-1/2 request toward a gate endpoint therefore needs a source-qualified pure preview of the existing endpoint predicates or a bounded architecture decision; do not silently treat such a gate as a regular static corner.

## Projected capacity and later verification

The BUG-121 integration record attributes 65 resident bytes of recovery to deleting the old probe. The current assignment intake reports 65 bytes free in the default resident and 4 in nonadaptive. Restoring the old block consumes the entire default margin and exceeds nonadaptive by 61 bytes, yet still allows incorrect unconditional advance. A selective step-3 version needs carry preservation through logical-cell restoration plus an advance/hold split; a direct stack-CC pattern projects roughly 8 bytes beyond the old block (about 73 bytes total) before any step-1/2 read-only classification. That exceeds available default headroom by about 8 bytes and nonadaptive by about 69 bytes; early-corner qualification and gate preview add more. These are source-size projections, not assembled fit results. A smaller encoding or compensating resident reduction needs a coding-architect pass; do not claim fit from the old 65-byte recovery.

Later parent-owned probe can reuse the existing verifier and monitor mechanics: each phase is at most 45 seconds, each marker wait at most 10 seconds; success marker is byte-qualified `player_tick` entry followed by `pt_done` for the exact fixture. Timeout means that boundary/result was absent within that phase, not that movement code is slow. Record X/Y, framebuffer anchor, `PLAYER_CELL_X/Y`, `PLAYER_STEP`, `PLAYER_DIR/WANT/FACE`, `TURN_SNAP`, target/current gate state, and verify live bytes against the current candidate before interpreting execution. The four upcoming static corners distinguish missing approach; the matched RSCH-017 no-exit control distinguishes over-permissive drift; the existing aligned corner and gate-endpoint fixtures guard their current paths. Include an upcoming gate endpoint only after the side-effect timing/preview contract is resolved.
