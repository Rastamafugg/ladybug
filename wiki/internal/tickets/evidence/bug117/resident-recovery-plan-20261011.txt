Normal-mode ordering must cover both start paths. Initial entry selects the entry branch at `main_game_tick`. Replacement entry is selected inside `death_tick` from the ordinary `main_death` branch. After `death_tick`, test `INITIAL_ENTRY_STATE`; when `dt_finish_blank` has armed an entry wait or WALKOUT, use the same pre-render audio path in that callback. The path renders once and bypasses the ordinary post-render audio call and joystick read. This avoids a Vbord commit between first entrant render and first cue output. Initial trace: ENTRY_WAIT_STAGE remains set through RF_STAGE publication. On the first callback after the committed stage, DEATH_TIMER is zero, so decrement LIVES once. Replacement trace: dt_finish_blank reaches its blank timer at zero, decrements LIVES once, and invalidates PLAYER_BG_VALID plus both owner-ledger valid bytes as today. If published music is busy, set DEATH_TIMER to 1 and ENTRY_WAIT_STAGE, then clear DEATH_STATE. If idle, call marker_entry_begin immediately. The next ENTRY_WAIT_STAGE callback recognizes the sentinel and does not repeat the life decrement. Nonzero-to-zero DEATH_STATE remains no music-admission edge. Entry state keeps the ordinary death callback out of player/enemy/input work.

Register, storage and caller proof summary

The entry routines already have undefined A/B/D/X/CC outputs, and their top-level callers do not retain these registers. `hud_fb_address` takes only HUD_X/HUD_Y, clobbers A/B/D/CC, returns X, and does not modify the HUD coordinates. Each caller stores or consumes the returned X before loading its next values. `MUL` tile indexing clobbers A/B/D/CC, which are already consumed by the current shift calculation and blit call. DEATH_TIMER is the existing direct-page byte at $003A; it is not a new owner. INITIAL_ENTRY_STATE at $00A0 remains the sole lifecycle gate. HUD_X/HUD_Y at $0027/$0028 remain renderer scratch. No new persistent framebuffer or render-owner field is introduced. AUDIO_MUSIC_PUBLISHED_BUSY at the previously reviewed unused $02D4 byte remains audio-owned after boot table retirement; only the post-PSG writer updates it, and main reads it.

Branch and cycle risks

The helper placement is chosen so the clear and draw BSR calls can be short, but neither final displacement is measured. The entry call is LBSR by design. The existing state-dispatch branch to iet_maze_entry may cross the short-branch boundary after surrounding edits; no relaxation value is assumed. The replacement death branch to main_entry_render, the WAIT_STAGE waiter branches, and all adaptive callback branches also require assembler inspection. Any relaxed branch changes the byte ledger and must be deducted, not absorbed by a cap waiver.

The route-count seed costs six cycles once (`LDA #80`, `STA direct`) and the new DEC costs six cycles on each accepted WALKOUT step and each OFFSCREEN logical tick. This does not change event cadence, but adds foreground work on entry callbacks. The final Y=18 guard is projected as a four-cycle direct LDA, two-cycle immediate CMP and three-cycle short branch per maze-entry callback; the release check adds a direct TST, short branch and direct CLR only after the endpoint. The HUD helper adds its call/return cost to three existing address users; it is a code-size trade that may slightly lengthen those paths. The tile MUL itself is projected to save nine cycles against the current ten register shifts, not counting identical address loads/stores. These are instruction-level estimates, not worklist measurements. Both existing full worklist maxima already exceed 27,000 cycles; the candidate cannot be accepted on cycle performance without new measurements.

Rejected or deferred local options

Reading HUD_X at WALKOUT completion is rejected because draw_lives and HUD tile helpers mutate HUD_X/HUD_Y after marker_entry_begin. The count-80 seed avoids that stale-scratch dependency.

Using a HUD_X < 64 shortcut in address construction is rejected for this plan. The helper preserves the existing 16-bit coordinate arithmetic and therefore needs no unproven global caller bound.

Dropping the adaptive release barrier is rejected. Input acquisition precedes the entry callback; rj_request ignores held input while INITIAL_ENTRY_STATE is nonzero. Clearing state and continuing AD_BATCH could cause a normal tick to use stale/default control state.

Using only FB_RENDER_PENDING without tracing the render transaction is rejected. Here the source proof is specific: state 4 sets RF_PLAYER on the final movement callback, BACK composition arms pending, mainloop blocks another callback, and the IRQ changes GIME_VOFF1/owners before clearing pending. The proof must be rechecked after implementation.

The common decrement dispatcher remains conditional because short/long branch growth and handler control flow are unmeasured; its 12-byte point estimate is not booked. Moving code to another module, using new banking, changing loader placement, or drawing on persistent ownership to chase the remaining resident gap is outside this authorization.

Fit decision and next proposal

The bounded source-local plan is not fit-ready. Without the optional decoder rewrite, the point estimate projects nonadaptive +32 bytes and adaptive joystick +4 bytes beyond capacity; reserving both possible BSR widenings projects +34 and +6 bytes over. The four-byte decoder point estimate reduces those overruns to +28 and +0 bytes if both BSRs stay short, or +30 and +2 if they widen. No case proves positive assembly margin in all profiles.

Concrete next scope: parent-owned architecture review of resident source placement and existing module boundaries, before implementation. Baseline is the measured 8131/8192, 8167/8192 and 8192/8192 resident images plus the no-dispatch point estimate 8160/8192, 8196/8192 and 8224/8192, and risk-reserved estimate 8162/8192, 8198/8192 and 8226/8192. With the optional decrement chain, corresponding short-BSR point capacities are 8156/8192, 8192/8192 and 8220/8192; widening both BSRs gives 8158/8192, 8194/8192 and 8222/8192. A future engineering proposal may use 8160/8192 or less in all three profiles as a 32-byte resident-margin objective; that is a proposed engineering margin, not an approved acceptance target. The review must identify at least 62 additional resident bytes beyond the decoder-plus-BSR-risk candidate, 60 beyond the decoder short-BSR point estimate, 66 beyond the no-dispatch BSR-risk candidate, or 64 beyond the no-dispatch short-BSR point estimate, then assemble exact sources to measure branch relaxation and capacity. Retain the 4096-byte enemy runtime cap, 920-byte engine cap and 6656-byte page-$3D boundary. Evaluate only code already present in resident text and existing callable runtime modules; any module ownership, bank placement, loader/MMU or persistent-framebuffer proposal is a separate material scope requiring BUG-117 to return to Proposed for user approval. Main risks are cross-profile assembly conditionals, call displacement, enemy-runtime capacity, and shifted foreground cycles. Exclude behavior changes, new modules, new state bytes, BUG-121/RNG/maze changes, memory or timing waivers, and implementation until a new exact Ready assignment is reviewed.

If that wider source-only review identifies a candidate, the next fit gate should build exactly adaptive keyboard, adaptive joystick and nonadaptive keyboard from a clean scratch capsule; retain source-contract checks and all existing capacity guards; inspect final listings for every short branch and BSR; and record bytes and cycle worklists separately. Runtime checks remain later: initial and real-death replacement onset, same-callback cue-6 PSG output before visible pose, no duplicate cue-13 admission, preserved x33/x35/x37 route and every two-pixel pose, music-first and commit-first completion ordering, then input eligibility only after both gates.
