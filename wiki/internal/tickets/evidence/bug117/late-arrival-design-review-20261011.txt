BUG-117 late-arrival design review — 2026-10-11

Disposition
This is a source-only architecture candidate, not an implementation or fit result. BUG-117 remains Proposed; production main.s work stays serialized after BUG-121. The newest requirement permits maze arrival after cue 6 completion, sets no maximum lateness, and retains cue onset at the first automatic-entry boundary, visible 2-pixel cadence/route, column padding, input/collision/death suppression, and release only after both cue terminal output and final-pose IRQ commit. No intentional early-arrival/pose-wait schedule is selected.

Fresh cue proof and residual queue
`audio_music_busy` is `audio_music_count != 0 || audio_slot0 != $FF`; it is generic and currently private to the audio page. Under an observed empty music queue and empty slot 0, the existing cue-6 route is source-proven to accept a fresh request: ID 6 routes to the separate 8-entry music queue, is not a duplicate, fits count 0, and dispatches to slot 0 in the same normal or adaptive admission service. This avoids a cue-progress counter, but only if the quiescent precondition and same-service dispatch are verified. A false busy result before this edge is not cue completion.

The death-cue edge is specifically `AUDIO_GAME_DEATH != 0` while the saved `audio_poll_death == 0`; `audio_poll_gameplay` then queues cue 13 and saves the current death state. This is a 0→nonzero transition. `dt_finish_blank` later clears `DEATH_STATE` to 0 after the death sequence; that 1→0 clear does not enqueue cue 13. Therefore replacement entry does not itself create a same-service cue-13 admission. A cue 13 already queued or active from the earlier death-start edge is a separate possible residual, and current source alone does not establish that it remains at the replacement boundary.

The state-edge trigger must change from state 4 to state 2 in both `audio_tick` and `aas_admit`. These checks run before semantic polling. On initial entry, `live_begin` sets state 1 only after leaving presentation mode; `initial_entry_tick` waits for the stage render boundary before changing 1→2. On replacement, the game is live and `dt_finish_blank` selects state 2 or the proposed state 5. Thus the first live audio service seeing state 2 can enqueue cue 6 before `audio_poll_gameplay`. In adaptive mode, `audio_poll_valid==0` only causes the subsequent gameplay poll to snapshot its fields; it does not suppress this earlier mode-edge test. The receipt must verify state 2 is never entered while `PRES_MODE` is nonzero, and must show the edge, cue-6 admission, slot-0 dispatch, and first PSG output in order.

Minimal conditional no-preemption candidate: at an otherwise-ready replacement boundary, inspect qualified music state. If music is already idle, call the shared marker-entry helper directly; state 2 then admits cue 6 and the first walkout step follows the existing schedule. If an actual prior music item remains queued or active, keep the player hidden and locked until a post-output idle sample, then open state 2 so cue 6 remains first at the automatic animation boundary. Do not insert an unconditional pre-entry wait or treat clearing DEATH_STATE as a new cue event. Any residual-drain hold must use the ordinary audio service and preserve the existing one-life decrement. Queue preemption/suppression remains a larger alternative and is not recommended without renewed scope.

The music queue and effect FIFO are distinct. Cue 6 bypasses AUDIO_Q_COUNT and routes through the music queue. Credit cue 12 uses the effect route; a full effect FIFO does not consume music-queue capacity, and exclusive cue 6 owns the mixer. The existing music-busy predicate intentionally excludes AUDIO_Q_COUNT, pending credits, and effect slots. Retain those fields in the test receipt, inject a credit/global-input event during the hidden hold, and prove cue 6 still enters slot 0 and emits its first PSG values. Do not use audio_drain_busy as cue completion: it waits on unrelated effects and credits. Capture current and saved death fields to distinguish a prior cue-13 residual from a new 0→nonzero death event; verify entry suppresses new death transitions and that no other music ID enters during entry.

Normal trace: the live stage/entry boundary sees published busy=0, enters state 2, and admits cue 6 before gameplay polling; the first note dispatches to slot 0 and writes PSG output in that audio service. The HUD walkout is 28/20/12 logical steps for x33/35/37. Offscreen padding is 52/60/68 logical ticks while both owner ledgers retire, so common maze-entry start remains at 160 VBlank frames; the 16 two-pixel maze steps finish at frame 192. On-time cue end and final pose can coincide. Late-audio trace: preserve all 16 steps and their cadence; if the final pose commits first, state 6 holds control until the post-output byte reads idle. If music ends first, keep entry control-locked until the final render's IRQ commit. Replacement-residual trace: if the death-finish boundary sees published busy=1, decrement the life once, clear death ownership, and hold hidden in state 5 while ordinary music service drains existing queued/active music. Clearing death to zero is not a cue-13 edge. Once the published byte is zero, transition to state 2 and admit cue 6 at that boundary. Do not wait for the separate effect FIFO.

Completion transport and exact terminal ordering
`audio_music_busy` becomes false when `audio_advance_slot` sees the stream end, before `audio_mix`/`audio_mix_write` publishes the terminal PSG state. A=0/A=1 and pre-output checks therefore cannot release control. The concrete one-byte candidate is `AUDIO_MUSIC_PUBLISHED_BUSY=$02D4`: boot owns that address only as part of the $0287-$02E9 descriptor table, whose last consumer returns at `boot_streams_retired` before `audio_init_impl`; current runtime audio owns $02C0-$02D3, $02DC-$02DD, and $02DE-$02EF, with no current $02D4 reference. Add a foreground audio ownership audit for the new byte. The neutral `audio_init_impl` call to `audio_mix_write` runs after queue/slot reset and can publish the initial idle value before `AUDIO_INSTALLED` becomes nonzero.

Place one `JSR audio_music_busy; STA AUDIO_MUSIC_PUBLISHED_BUSY` tail at shared `audio_mix_write_done`, after all physical `SND_DATA` writes. Both normal `audio_tick` and adaptive A=2 call this writer; A=2 then reaches `aas_ok` and returns success A=0, while the full-tick caller restores its normal return state after the write. The status byte therefore has a single writer and remains stable between output services. The neutral `audio_init_impl` write publishes idle after queue/slot reset and before `AUDIO_INSTALLED` becomes nonzero. In adaptive mode A=0 may retire a note before the callback, but it cannot update this byte; terminal state remains busy until A=2 has written and published it.

The predicate is generic music busy, not cue-specific. Fresh-cue proof is bound to the empty music queue/slot0 precondition, state-2 admission, same-service dispatch to slot0 ID6, no competing music enqueue during entry, first PSG output, and later slot0/queue retirement. Cue 12 and ordinary effects use the separate effect FIFO; capture `AUDIO_Q_COUNT`, `AUDIO_CREDIT_PENDING`, and effect slots, but do not wait for them. This keeps the credit/effect route out of cue-6 completion while proving it does not interfere with the exclusive cue.

Static size path from the current build listing: this shared tail costs six bytes. Five existing short-reachable `LBSR` calls can be written `BSR` to recover five bytes: audio slot-base calls at $A1A4→$A218 (new displacement +114), $A1DD→$A218 (+57), and $A223→$A218 (-13); audio-advance call $A23F→$A24B (+10); audio-mix-slot call $A57B→$A5BA (+61; caller and target both move by the inserted tail). The first four are inside the 731-byte copied engine; the fifth is outside it. Static byte arithmetic projects engine 727/920 and page-$3D payload 6656/6656, with zero remaining pre-keybinding margin. Each BSR is behavior-equivalent and two cycles faster than its LBSR. This is not an assembled fit; all profiles and worklist timing still require the existing checks. No cue-progress counter or API return-register change is needed.

Entry and release schedule
Use the existing cue unchanged: 31 waits / 192 nominal ticks / 3.2 s at uninterrupted 60 Hz (source projection only). Preserve the source-derived column schedule: HUD x33/35/37 => 28/20/12 walkout steps => 56/40/24 projected ticks; offscreen totals 104/120/136 => relative padding 0/16/32; common maze walk-on starts at projected tick160; 16 sequential 2-pixel maze steps end at projected tick192. On the x320 transition into existing ENTRY_OFFSCREEN=3, set `DEATH_TIMER` to 52/60/68 using `52 + 4*(HUD_X-33)` and count it down on `PLAYER_TICK_PENDING` while checking both owner ledgers. `DEATH_TIMER` has no death owner after DEATH_STATE clears; initial init clears it and replacement blank reaches zero. Do not call `init_player` until both the pad is zero and both ledgers are invalid. If ledgers retire after the nominal pad, enter late without skipping a visible step. `init_player` at cellY22 and its render are not proof of first-visible pixels; verify actual first maze sprite publication separately.

Keep audio raw time separate from animation logical time. Adaptive A=0 consumes raw FRAMES delta, advances at most one note boundary per voice, and drops excess after that boundary; `audio_adaptive_late` records late service. Nonadaptive cue time advances once per `audio_tick` call. Movement consumes PLAYER_TICK_PENDING, derived from logical committed cadence (FB_SIM_SEQ in the nonadaptive path; AD_SIM_TIME parity in adaptive); the entry barrier prevents catch-up through transient steps. Do not use FRAMES delta to accelerate movement or skip intermediate poses. The common maze-onset/frame-192 endpoint are nominal projections from the existing movement cadence, not audio-clock gates. Audio lateness alone does not delay that logical route: the entrant may reach the final position before cue 6 ends, then stays control-locked until both music-idle publication and final-pose IRQ commit are true. Prior-music drain can delay the entry start; this is separately observed as start lateness. No maximum lateness, timing waiver, cue edit, cadence change, or deliberately slowed/early-arrival schedule is proposed.

Foreground-order trace and visible-onset gate
Normal initial 1→2 and residual 5→2 occur inside `initial_entry_tick` in the `main_game_tick` branch. In the same foreground turn, `main.s` then calls `render_frame`; `enemy_runtime.s` writes the BACK image and `framebuffer_finish_back` sets `FB_RENDER_PENDING`. Only afterward does normal main call `AUDIO_ENGINE_EXEC`; `audio_tick` observes state 2, enqueues cue 6, dispatches/advances/mixes it, and performs the first PSG writes. The framebuffer IRQ publishes any pending image at Vbord without checking the audio status. Therefore source ordering does not prove that the walkout cannot become visible before the first PSG write: a Vbord between `framebuffer_finish_back` and the later audio call can commit the image first. No current source guard serializes those two actions, and no timing measurement in this design establishes a safe sub-frame bound. Minimal candidate correction is to service audio once in the nonadaptive entry branch after `initial_entry_tick` and before `render_frame`, bypassing the common later service on that branch. This preserves the same state transition and callback, adds no cue-progress byte, and arms publication only after cue output; parent review must confirm the call-order/cycle impact before implementation.

Adaptive ordering is different and statically serialized. `adaptive_work` services A=0, then `AD_BATCH` invokes `adaptive_tick_binding`; the binding calls `initial_entry_tick`, returns a barrier while entry state is nonzero, and calls A=1 before returning to stop catch-up. A=1 sees the new state 2 and admits cue 6 in that same work call, before `adaptive_render`. The renderer writes only BACK; `adaptive_work` then performs A=2 (first PSG writes) before `AD_COMPLETE_EXEC` and `framebuffer_finish_back` arm pending publication. The IRQ is the only display commit, so this path proves no visible walkout before cue-6 output, though its back-buffer composition precedes output. For a residual 5→2 transition, if A=0 retires prior music this work call, the published byte remains busy until A=2; the state-5 check consequently waits for the next adaptive callback, then transitions and admits cue 6 in the same callback/A=1. If prior audio was already published idle at callback entry, it transitions and admits immediately. Normal mode uses the same prior-published-status rule; it transitions and admits within the same main foreground turn, with the publication-order gap above.

At the 16th maze step, store the pre-render `FB_COMMIT_SEQ` word in `TURN_SNAP:TURN_OLD` with `STD TURN_SNAP`, set new `ENTRY_FINAL_PENDING=6`, and render the final position. While this state is active, `player_tick` remains suppressed. Those turn scratch bytes are otherwise consumed only by normal `player_tick`; `init_player` clears TURN_SNAP before entry, and release clears both bytes before state zero so the saved sequence is never interpreted as a turn. Release only after (1) the published music-busy byte is zero, (2) `FB_RENDER_PENDING` is clear, and (3) current `FB_COMMIT_SEQ` differs from the saved word. `framebuffer_finish_back` only arms pending; `framebuffer_irq_impl` flips owners, clears pending and increments the sequence. Nonadaptive main advances one scheduled work item and tests at its next entry callback. Adaptive A=0 runs before its logical callback but cannot change the published byte; `adaptive_tick_binding` must return a one-callback barrier when final-pending clears so AD_BATCH cannot catch up in the release callback. This handles either completion order without shortening or retiming the route. Capture the final-step render intent, saved sequence, pending bit, owner flip, and sequence increment; do not treat the renderer's arm operation as the commit.

Add `ENTRY_WAIT_MUSIC=5` for a replacement only when the prior published music status is busy at death finish. Decrement LIVES once, clear the dead-player ledger as today, clear DEATH_STATE, and do not call marker_entry_begin yet. Keep the player hidden and locked. On a later callback with published busy=0, call the shared marker helper; the 5→2 state edge admits cue6 in that same normal/adaptive audio service. When status is already idle at death finish, retain the current direct helper call. For initial entry, keep existing ENTRY_WAIT_STAGE=1 through the stage image and do not decrement LIVES or call marker_entry_begin until published music is idle. This conditional pre-boundary drain preserves cue-first output without an unconditional wait.

The current adaptive persistent renderer already exits `actor_closure_draw` for ENTRY_WAIT_STAGE=1 and ENTRY_OFFSCREEN=3. Its generic player path can still compose an unknown nonzero state such as proposed ENTRY_WAIT_MUSIC=5 when PLAYER_BG_VALID is clear, so add state 5 to that early suppression guard. The nonadaptive renderer already requires RF_PLAYER, which the hidden wait state does not set. State2/4/6 remain visible as appropriate. Candidate source owners are now exact: `main.s` for boundary/state/padding/final commit checks, `audio_runtime.s` for the shared post-output publication and nonadaptive state-2 trigger, `adaptive_audio_service.s` for the A=1 state-2 trigger, `adaptive_active.s` for the adaptive release barrier, and `enemy_runtime.s` for hidden-wait suppression.

Fit and decision gates
The architecture has concrete transport storage and writer lifetime, but is not fit-proven. Current measured limits are audio engine 731/920, page-$3D payload 6655/6656, complete keyboard resident 8131/8192, adaptive joystick resident 8167/8192, and nonadaptive keyboard resident 8192/8192. The proposed six-byte post-output tail plus five one-byte BSR savings projects page-$3D payload at 6656/6656 and engine at 727/920; it leaves zero page-$3D margin and remains an unassembled byte/cycle estimate. Resident code changes have no proven recovery at all-profile limits, especially nonadaptive's zero-byte headroom. Do not raise limits or call this architecture implementation-ready until current-source all-profile builds and existing timing/capacity checks pass.

Candidate production owners are exact: `audio_runtime.s` owns `$02D4`, its single post-PSG writer, and nonadaptive state-2 edge; `adaptive_audio_service.s` owns the matching adaptive state-2 edge; `main.s` owns state 5/6, conditional boundary, padding countdown, saved commit sequence, and conjunctive release; `adaptive_active.s` owns the one-callback release barrier; `enemy_runtime.s` owns hidden wait/offscreen suppression if the persistent renderer still composes the player in those states. These are candidates only; no production source, build, wiki, or Git changes are made here. The next design gate is a source-level fit plan for every profile and cycle/worklist review, followed by implementation assignment only after the canonical ticket is approved and Ready. No runtime result, fit result, acceptance, or target waiver is claimed.
