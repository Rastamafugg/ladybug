# BUG-122 stage-19 release comparison: bounded source diagnosis

## Scope and result

Source-only diagnosis against the current candidate artifacts. No runtime probe was run and no production, wiki, build, or QA files were changed. The comparison failure does not establish that entity selection rerolled: the retained failure combines table equality and RNG equality, while the evidence omits both expected values. The source exposes two stronger questions to discriminate first: whether the observed state-4 entry can be reached through the context-2 release path, and whether RNG equality spans normal gameplay ticks before the entry trace begins.

## Source-qualified order

1. `src/presentation_runtime.s:365-392` (`normal_stage`) handles `STAGE_PENDING`. If `$51` is clear it calls `PRES_MAIN_NEXT_STAGE`, writes `PRES_CONTEXT_NEXT_STAGE` (value 2), and starts the level-start screen.
2. `src/main.s:1024-1046` (`next_stage`) consumes pending, increments stage, initializes maze/gates/color, calls `init_entities`, `init_player`, and `init_enemy`, then sets `RF_STAGE`. This is the expected entity-table initialization for advancing to stage 19.
3. `src/main.s:1747-1884` (`init_entities` and `place_entity`) clears `ENTITY_TOTAL`, chooses entities, and uses `rng_next` at lines 1793, 1806, 1819, and 1843. It writes entity records at lines 1873-1883. A second call is a credible cause of both changed table and RNG.
4. With this build profile, `src/presentation_runtime.s:400-429` routes `start_screen` through `init_gameplay`. At `src/presentation_runtime.s:872-883`, the LEVEL_START path returns early when `PRES_CONTEXT_NEXT_STAGE` is set. Consequently it skips both `gameplay_reentry` and `PRES_MAIN_INSTALL_PHASE_TILES` for this context-2 next-stage screen.
5. `install_phase_tiles_for_screen` at `src/main.s:4799-4809` calls `init_game_state`, which clears `INITIAL_ENTRY_STATE` to zero (`main.s:969-1001`), then initializes maze/gates/entities/player/enemy. That installer is gated behind the `init_gameplay` path skipped above; it does not set entry state 4.
6. At `src/presentation_runtime.s:801-813`, `level_tick` sees context 2, clears context and mode, and returns. It does not call `live_begin`. The only visible current-profile writer that starts entry at state 1 is `live_begin` (`presentation_runtime.s:865-883`); it sets `ENTRY_WAIT_STAGE=1` and clears mode. The later source state chain is `main.s:862-963`: state 1 to 2 (`:901`), state 2 to 3 (`:918`), state 3 to 4 after offscreen ledgers/player setup (`:934`), and state 4 to 0 on entry completion (`:957`).
7. A repository-wide source search for `INITIAL_ENTRY_STATE` found no other store in active renderer, enemy, adaptive, or generated presentation installer sources. Enemy/adaptive routines read it only. `init_game_state` clears it; entry state machine updates it; `live_begin` starts it. The obsolete duplicate presentation implementation is inactive under `COMPLETE_PROFILE=1`.
8. Adaptive loop ordering matters for RNG interpretation. `src/adaptive_active.s:165-171` handles nonzero entry state and branches to its barrier; the normal path calls `rng_next` at `adaptive_active.s:203-204`. `verify_bug122.py:1420-1424` first waits for mode 0 and entry state 4. `runtime.py:163-176` implements that wait by repeatedly running `q.go()`. Therefore normal gameplay ticks may call RNG during the pre-trace wait if execution is in state 0. The later `trace_entry` (`runtime.py:179-188`) runs while entry state is nonzero and skips the normal RNG path. RNG equality measured from publication through wait and trace can fail legitimately even if the entry trace itself has no RNG tick.

## What the evidence establishes

The verifier captures a published baseline at `verify_bug122.py:1405-1408`, checks three holds at `:1416-1419`, waits for mode 0/state 4 at `:1420-1424`, then asserts combined direct-table and RNG equality with the message “later-stage release rerolled entity selection.” It reads the table directly from physical page `$34` (`:308-319`) and RNG from physical page `$38` (`:322-323`). The failure JSON records the actual end table hash `32414d1cd37b4e38cb2fb81cbfbe7551b53c818b1cf7949329d2dce89630c7b1` and stage-19 context-0 end state (player cell 12,18; DOTS_LEFT 105; BONUS_LEFT 6; 12 records). It does not retain expected table/RNG separately or final RNG, so it cannot say which comparator failed.

There is also a source/path discrepancy: if `PRES_CONTEXT` is 2 at the level-start `init_gameplay` and remains so through the `level_tick` release, current source skips `live_begin`, while the verifier later requires state 4. The retained evidence is insufficient to show the exact execution path that produced state 4. This does not prove a product defect; the executed branch/context or observation boundary may differ from the assumed one. Release-prefix bytes and actual transitions have not been qualified from a live PC.

## Ranked causes

1. **Boundary/path mismatch (leading).** The assumed context-2 release reaches state 4, but the current source’s context-2 branch clears mode/context and returns without starting entry. Qualify branch/context and live bytes at release before interpreting later state.
2. **Legitimate RNG advance during `q.wait`.** If wait includes normal state-0 ticks after release and before state 4, the active adaptive normal loop advances RNG. The existing combined assertion cannot distinguish this from a reroll.
3. **Unexpected duplicate initialization.** If context gating differs in execution, an unexpected `init_gameplay`, `install_phase_tiles_for_screen`, `next_stage`, or `init_entities` call can rewrite table and RNG. Current source says the normal context-2 path should not do this after stage setup.
4. **Capture/helper/render clobber.** Lower-ranked: the table and RNG are separately read from direct physical pages, and reviewed rendering/entry-state code has no other entry-state store. Still unresolved because expected values and live release bytes are absent.
