BUG-043 — Credit accounting and display Ready

Updated 2026-09-26 · Ready · High-risk · Active-game repair approved; not assigned

Objective and motivation

Make each new 5 or 6 press add one credit, and show the current count consistently on the right HUD and high-score start instructions. Show one-player wording for one credit and one-or-two-player wording when at least two credits are available. Play one credit cue for each accepted increment. Preserve BUG-013's authored coin placement and saturation contract; do not use this ticket to reimplement the coin overlay.

Natural sequence: unattended attract → first credit edge → high-score screen with count one and one-player prompt → further distinct edges → count and prompt advance → valid start consumes the appropriate credit count → level start, demo/live gameplay and game-over HUD display the remaining count. Existing presentation key scanning owns global credit edges; screen-local renderers consume the resulting count. The high-score screen's static one-credit prompt is displaced by a count-selected prompt.

Evidence and cause boundary

Baseline: user report at clean source 516bdd3, rebuilt complete 6809/keyboard ROM SHA-256 9bd7daa97e8ad93f08b31e0258afb20d21593bf6189e34926ee7fcc0ddaea1a9. The build passes. This is source evidence plus a user visual report, not a new natural runtime capture.

src/presentation_runtime.s scans rising keyboard edges into PRES_EVENT, but its pft_ready branch masks both credit bits and calls add_credit only once for a nonzero result; simultaneous new 5/6 edges therefore count as one. add_credit saturates at generated PRESENTATION_COIN_SLOT_COUNT, currently nine in scripts/build_presentation.py, while approved BUG-013 requires twelve. The same presentation source draws only coin slots from PRES_CREDITS; no current dynamic credit-count or wording branch appears in the high-score render path. The count/display discrepancy is source-confirmed in those paths; other screen HUD pixels and audio behavior still require identity-proven runtime observation.

Scope, edge cases and proposed behavior

In: one increment per distinct newly pressed credit key, a single authoritative count capped at BUG-013's twelve slots, current count on applicable right HUDs, high-score prompt variant, start consumption, and one cue per accepted increment. Out: coin artwork/slot renderer, two-player gameplay implementation, battery-backed persistence, general audio priority, unrelated HUD palette corrections, and altered reset policy.

  1. At zero credits, publish attract without a coin or credit prompt.
  2. A new 5 or 6 edge adds exactly one; held keys add zero. Separate simultaneous new edges add two, bounded by the cap; alternating edges each add one.
  3. At one credit, show one-player wording. At two through twelve, show the authored one-or-two-player wording. Count, prompt and coin prefix update together on the first complete published screen.
  4. A valid player-one start consumes one credit; a player-two button is displayed as an arcade instruction but this ticket does not add a two-player runtime. Resolve button-two behavior before approval if it must start play.
  5. At twelve, further input does not change count, pixels or cue. Cold/warm reset begins at zero unless a separately approved persistence rule says otherwise.

Proposed cue rule: trigger the existing credit cue only after a successful increment; a simultaneous pair produces two accepted events. If the available cue service cannot queue both without loss, keep the input/count requirement and return the cue detail for an explicit audio design decision rather than silently coalescing.

Options, risks and acceptance

Recommendation: keep the global edge scanner and one count owner, enumerate the two event bits, then render count/prompt from that state at each screen publication. Duplicated per-screen counters are rejected because they can diverge after start or interrupted screen loads. Reuse current text masks and screen publication hooks. Hard module/cold capacities, audio service and persistent framebuffer ownership make this High-risk. Verification remains proportional to the named risks. Seek renewed approval only before changing BUG-013 coin scope, two-player behavior, reset policy or audio ownership.

  • Natural cold attract → first and second credits → player-one start: count, prompt, coins and cue agree on every published screen. Risk: cross-screen stale count.
  • Held, alternating and simultaneous edges; eleven-to-twelve and twelve-plus saturation: accepted increments are counted exactly once and cues match accepted increments. Risk: combined-bit collapse and overflow.
  • Credit during loading/demo and after game over: no lost count, wrong owner call, or stale HUD. Risk: pre-emption and renderer ownership.
  • Complete build, exact artifact identity, current module/resident/cold limits and bounded frame-cycle checks pass. Current baseline has resident 8191/8192 bytes, assets 7680/7680, presentation 1259/1280, helper 331/334, and GMC source spare 1239; these are measured current-build values, not headroom promises.

Use the BUG-013 coin-layer and credit-runtime verifiers, current presentation-flow checks and one natural GDB-MCP sequence. Do not multiply screen, input and framebuffer-owner combinations without a distinct risk. Implementation remains on hold until the assignment is Ready.
