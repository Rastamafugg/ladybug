Reader workflow and generated content

Build the complete ROM → capture the actual module/profile/artifact inventory → extract annotated source and assembled references → validate identities and coverage → generate HTML and JSON under build/source-reference/ → verify freshness and links. A reader opens an index, scratch object or retained-background record, follows its producer/consumer links, and sees the relevant source lines and explanatory contract.

  • Index records: semantic identity, generator/function, generated symbol/table, index domain and bounds, page/address or descriptor encoding, all resolved consumers, and unresolved indirect consumers. Distinguish a stable frame identity from a relocatable packed offset.
  • Storage records: symbolic base and width, byte interval, physical mapping/phase context, owner, initialization, live interval, writers/readers/address-taking, aliases and clobbers. Reuse is permitted only with a declared reason and compatible lifetime; the same CPU address in two physical pages is not automatically a conflict.
  • Background records: owner and extent, clean source, capture, restore, draw/publication order, validity and dirty state, invalidation/reset events, overlapping actors and framebuffer ownership, plus linked verifier scenarios.
  • Evidence labels: extracted fact, authored declaration, verified result, unresolved relationship. Missing or uncertain information must remain visible. An annotation is not proof that every control-flow path obeys it.
  • Educational examples: generated-index repacking, a two-byte scratch conflict, and background capture/invalidation across alternating framebuffers. Explain the relevant concepts once in existing wiki guides and link to the generated records.

Acceptance and risk-based verification

  1. Discovery/profile risk: every emitted complete-profile module is registered or explicitly excluded with a reason; distinct assemblies of one source retain distinct artifact and profile identities. New/unregistered modules fail the audit. Restore successful generation before interpreting coverage.
  2. Staleness risk: generation uses current revision, dirty-input hashes, assembler/profile inputs and artifact hashes. A changed source, generated index, module artifact or annotation makes existing output stale; stale/missing build provenance cannot be relabelled current by hashing it again.
  3. Index risk: named index producers and declared consumers resolve; bounds and generated-symbol relationships are checked where available. Seeded obsolete literal indexes at declared index-consuming sites are diagnosed. Do not flag every numeric immediate as an index.
  4. Storage risk: fixtures distinguish immediate addresses from memory reads, one/two-byte accesses, offsets, indirect unresolved accesses, intentional aliases and banked/phase-separated storage. The historical $009F/pointer-low-byte conflict is rejected; legitimate sharing is documented rather than reported as corruption.
  5. Retained-state risk: required background records have capture/restore/validity/invalidation/publication links that resolve to current symbols. Missing contracts and dangling lifecycle links fail coverage. Output explicitly distinguishes declared ordering from runtime evidence and retains natural sequence test links.
  6. Completeness and education: all discovered candidates in the selected categories are documented, explicitly excluded or visibly unresolved; no silent omissions. Required shipped records cannot pass with unresolved ownership. The three teaching examples explain the failure mechanism and link to current generated evidence. Source anchors update after a line insertion or symbol movement.
  7. Compatibility: retain existing source-reference tests and add focused mutations for the new risks. Source annotations emit no bytes; executable artifacts and the final ROM must remain byte-identical to the selected clean reference. Documentation checks are host tooling and add no game memory or frame-time cost. A full build regenerates/checks the audit; the existing documentation CLI also supports an explicit rerun.

Static extraction is deliberately limited. Complete runtime alias/lifetime safety is not promised by this ticket; unresolved pointer arithmetic and dynamic mapping require explicit review or linked runtime proof.
