FEAT-005 — Gameplay options Proposed

Add session-only custom-game settings through individually verified option increments, then integrate them behind one menu.

Status and ordering

  • Status: Proposed
  • Created / updated: 2026-08-28 / 2026-08-28
  • Priority / order: P2 / 19
  • Roadmap: Phase 9 — finished game and polish
  • Owner: unassigned
  • Dependencies: stabilize the current Phase 9 presentation path; complete a capacity/design gate before menu integration or alternate-maze delivery.

Approval brief

Objective and motivation

Add an OPTIONS entry that configures custom-game rules without changing the arcade-compatible default. Each gameplay option is implemented and verified as one bounded increment before it is admitted to the combined menu build. Correctness and observable evidence take priority over cycle or byte optimization; optimization begins only after the option's natural behavior passes.

Evidence and baseline

This proposal was prepared from the working tree based on revision 608f4d0 on 2026-08-28. The working tree already contains unrelated Phase 9 changes, so no build outputs or capacity figures from that tree are acceptance evidence for this ticket. Confirmed source contracts are: new games initialize three reserve lives; the HUD draws at most three reserve markers; the perimeter reload is stage-dependent; stages use one immutable 24×24 maze; and the entity table contains twelve four-byte records. Six bonus records plus the stage-dependent two-to-six static skull records consume eight to twelve records. The deployed runtime does not yet publish a gameplay fire-button or spacebar action.

The arcade-compatible baseline is three reserves, continue disabled, the existing stage-dependent perimeter cadence, static randomized skulls, no letter replenishment, and the original fixed maze. The unattended demo always uses this baseline, independent of custom settings.

User-visible golden path

  1. Boot enters the normal attract/title flow with arcade defaults initialized.
  2. The player opens OPTIONS from the title flow, moves between rows, changes values, restores all defaults, or returns without starting a game.
  3. Starting a new live game snapshots the selected values. Options cannot change during an active game.
  4. Each enabled rule affects only its defined gameplay owner. Death, next-part, game-over, high-score, and attract transitions retain a single owner and occur exactly once.
  5. Returning to attract after game over retains the selected settings for the current powered session. Cold reset restores arcade defaults.

Core option contracts

  1. Reserve ladybugs: values 0, 1, 2, or 3; default 3. The value is the visible reserve count in addition to the active player. The first increment does not exceed three because the current HUD has three marker positions. EXTRA may still add a reserve, but the visible count saturates at three unless a later numeric-HUD ticket is approved.
  2. Continue current part: OFF or ON; default OFF. After final death, ON offers one bounded continue prompt. Accepting retains the part number, score, and completed SPECIAL/EXTRA letters, but rebuilds the current part from its clean initial maze, entity, enemy, player, and perimeter state and restores the configured reserves. Declining or timing out follows normal game over. The number of continues remains an approval question.
  3. Perimeter speed: named presets RELAXED, ARCADE, and FAST; default ARCADE. Presets select explicit stage-band reload values rather than altering the 60 Hz simulation clock. Enemy releases and every other perimeter-owned event continue to derive from completed circuits. Exact relaxed/fast reload values require gameplay measurement before approval of the child ticket.
  4. Letter replenishment: OFF or a named interval; default OFF. A collected letter record becomes pending and, after its timer, is reused for a new letter at an unoccupied, already-blank placement candidate. Replenishment does not add a dot or increment DOTS_LEFT, never occupies a gate, nest, entrance, actor, or other entity footprint, and is cancelled by death reset or part transition. The recommended replacement remains in the collected letter's X/T/R, S/P/C/I/L, or E/A group so stage composition remains bounded at three letter records.
  5. Deployable skulls: STATIC or DROP; default STATIC. DROP removes randomized static skulls and grants charges equal to the normal skull count for the current part. A fresh edge from right joystick button 1 or Space places at most one active skull on the most recently vacated aligned corridor cell behind the player. Invalid placement does not consume a charge. The recommended Rally-X-like rule affects enemies but not the player, and removes the skull on enemy contact or timeout; player lethality and lifetime remain approval questions. Input scanning must preserve joystick-axis and presentation-key ownership.
  6. Maze set: ORIGINAL or CYCLE; default ORIGINAL. Alternate layouts are delivered last and must retain the 24×24 field, valid entrance and nest, connected reachable paths, bounded perimeter circuit, valid gates, and sufficient unique placement candidates. Each layout is generated and statically proven before runtime selection. Runtime integration must load one complete coherent set of visual, navigation, gate-owner, gate-state, dot, candidate, and demo-route data; it may not mix tables from two layouts.

Additional candidate options

  • Placement seed: RANDOM or FIXED, allowing reproducible stages and verifier captures without changing placement rules.
  • Starting part: choose part 1 or an unlocked/practice part; custom runs remain ineligible for the arcade high-score table.
  • Bonus-colour speed: adjust the red/yellow/blue letter-and-heart cycle independently of the perimeter timer.
  • Enemy pressure: a later preset can adjust active-enemy cap or release cadence, but it must not silently duplicate the perimeter-speed effect.
  • Stage-clear target: require all dots or a lower percentage for shorter sessions; this needs explicit treatment of remaining entities and scoring.

Recommendation: keep these as follow-up candidates. Placement seed is the lowest-risk addition and provides direct verification value. Starting part is useful for practice and QA. The remaining candidates materially change balance and should be considered only after the six requested options are measured.

Compatibility and score policy

ARCADE DEFAULTS restores every default in one action. Any non-default value marks the session CUSTOM. Recommended policy: custom sessions display score normally but do not qualify for the arcade high-score table; separate custom records are out of scope. Attract/demo behavior ignores custom settings. No battery-backed or disk persistence is introduced.

Scope

In: session-only option state, title-flow menu, default restoration, new-game snapshot, the six core option contracts, per-option focused verification, final combination verification, capacity reporting, and synchronized wiki/ticket evidence. Out: two-player options, save files or NVRAM, network features, sound options, cheats, numeric life-HUD redesign, custom leaderboards, wholesale gameplay-loop refactoring, and optimization before correctness evidence.

Delivery sequence

  1. Architecture and capacity gate: define option-state ownership, menu/cold-data placement, live-game snapshot, input-edge protocol, entity-record reuse, alternate-maze data selection, and hard size limits. This gate creates the exact child-ticket ordering and verification commands.
  2. Menu foundation: prove title → options → title/start flow, controls, default restoration, session retention, cold reset, and an arcade-default gameplay snapshot with no gameplay option enabled.
  3. One-option increments: reserves, perimeter speed, continue, letter replenishment, deployable skull, then alternate mazes. Each increment has one bounded ticket and commit, enables only that option over arcade defaults, and must pass its focused natural path before the next increment begins.
  4. Integration: combine only accepted increments. Verify arcade defaults first, then pairwise combinations chosen for shared owners: continue/reserves, perimeter/enemy release, replenishment/stage clear, dropped skull/enemy collision, and alternate maze/entity placement.
  5. Optimization: profile the accepted combined build, optimize only measured byte or frame pressure, and rerun the same behavioral evidence unchanged.

Smallest sufficient verification set

  • Menu foundation: natural title round trip and cold-reset/default snapshot cover state ownership and initialization.
  • Reserves: configured initial count, ordinary respawn, final death, and EXTRA saturation cover initialization and life-boundary risk.
  • Continue: decline, timeout, and accept from a natural final death cover the new terminal handoff and exact retained/reset state.
  • Perimeter speed: one completed circuit in each preset on one early and one late stage band covers reload selection and release coupling without a full mode matrix.
  • Letter replenishment: collect, wait, blocked candidate retry, replacement pickup, death, and part clear cover record reuse, placement validity, and lifecycle cancellation.
  • Deployable skull: input edge/hold, invalid cell, valid behind-player cell, enemy hit, timeout, zero charges, and keyboard/joystick equivalence cover input ownership, collision, and resource bounds.
  • Alternate maze: static generator invariants plus one natural complete part and one gate/enemy/entity forced path per layout cover coherent table selection and reachability.
  • Combined build: arcade-default natural game, the five pairwise shared-owner cases above, standard build/capacity guards, and real-hardware input confirmation cover integration without a redundant Cartesian matrix.

Risks and stop conditions

  • The resident and copied presentation modules are near hard limits in current Phase 9 work; menu code may require cold payload or a new bounded copied module rather than resident growth.
  • The twelve-record entity table is full on six-skull stages. Replenishment must reuse collected records, and drop mode must replace static skull records. Expanding the table changes gate replay/cache layouts and requires renewed architectural approval.
  • Fire-button/Space ownership crosses keyboard scanning, joystick sampling, attract pre-emption, demo input, and live gameplay. A new edge protocol is required before deployable-skull implementation.
  • Alternate mazes multiply semantic and visual tables and may change demo routes, gate counts, memory packing, and worst-frame worklists. Any loader/MMU or framebuffer-owner change returns the feature to Proposed.
  • Optimization that changes accepted behavior, option semantics, or evidence is separate work and requires a new or revised ticket.

Acceptance criteria

  • Arcade defaults reproduce the documented current rules and remain the cold-reset state.
  • Every included option passes its isolated natural path and named edge cases before combined integration.
  • Menu input is edge/repeat bounded; held or simultaneous inputs cannot skip rows, start twice, drop multiple skulls, or pre-empt the wrong owner.
  • Custom settings are immutable during a live game, retained across attract within the powered session, and excluded from arcade high-score qualification.
  • All required rare paths are forced; a missing required path is a failed verification, not a pass.
  • The combined build passes standard generated-data, ROM/GMC, memory-window, framebuffer, gameplay, presentation, and real-hardware input gates with current-revision evidence.
  • Performance and capacity are measured after correctness. A missed hard limit or steady-gameplay frame target remains a failed target and produces a follow-up rather than acceptance.

Approval decisions required

  • Approve or revise the six core option contracts and their delivery order.
  • Choose continue count: once per game, once per part, or unlimited.
  • Confirm that a dropped skull is enemy-only and temporary, or retain normal skull lethality.
  • Confirm that custom sessions cannot update the arcade high-score table.
  • Select any additional candidate option for the first feature scope; recommendation is placement seed only.

Approval advances only this umbrella outcome and ordering. It does not authorize implementation. The architecture/capacity gate must complete exact artifacts, commands, ownership, and child-ticket contracts before any child becomes Ready.

Assignment contract

Unassigned while Proposed. After approval, route first to coding-architect. Each child ticket owns one isolated option or the final integration, one bounded commit, exact production and verification artifacts, measured capacity, retained evidence, and a completion report. No child may absorb another option or optimize unmeasured code.

Verification and completion

No implementation or runtime verification has been performed. The evidence above is a requirements and source-contract audit only.
