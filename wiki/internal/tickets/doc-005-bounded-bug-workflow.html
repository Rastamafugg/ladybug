Approval brief

Objective and motivation

Keep correctness, artifact identity, natural-path verification, and hard capacity gates while preventing small bug fixes from consuming a disproportionate share of the user’s weekly token allocation. Replace the current one-size-fits-all bug process with explicit Compact, Standard, and High-risk classes; proportional verification; cumulative diagnostic stop rules; and budget checkpoints.

Evidence and baseline

The user reports that BUG-018 and BUG-019 each consumed approximately 20–50% of a weekly token allocation. This percentage is a user observation because repository artifacts do not contain authoritative token telemetry. Historical commit statistics show the work-shape mismatch: BUG-018 added 82 and deleted 11 lines in its production generator while adding 759 lines across two dedicated verifiers, 5,348 total insertions, four mode/owner captures, and four rejected probes. BUG-019 changed 37 assembly lines while adding a 454-line dedicated verifier, 6,303 total insertions, six focused captures, and six rejected probes. The repository contains 56 Python verifier programs totaling 15,243 lines at the audit revision. These are historical single-revision observations from commits 8a5747d and ac575f6, not projections or token measurements.

Natural process sequence

  1. Project management records the bug objective, confirmed knowledge, affected boundary, cost class, estimated weekly-token share, ceiling, and smallest sufficient verification set.
  2. The approval brief maps every scenario to one distinct risk and obtains explicit approval under the existing lifecycle.
  3. Diagnosis uses existing source, static checks, and shared verifiers first; cumulative rejected probes, timeouts, root-cause expansion, or budget pressure trigger reassessment.
  4. A Ready Compact bug defaults to direct parent implementation without delegation or duplicate integration verification.
  5. QA runs the focused discriminating test, natural golden path, relevant adjacent regression, standard build, and relevant capacity checks; it expands coverage only for a named independent risk.
  6. The completion record reports result versus behavior targets and budget ceiling, retains concise deterministic summaries, and records any approved exception.

Scope

In: exact synchronized changes to AGENTS.md, .agents/skills/project-management/SKILL.md, business-analyst/SKILL.md, debugger/SKILL.md, qa-reviewer/SKILL.md, wiki/internal/tickets/workflow.html, and wiki/internal/tickets/template.html; three bug cost classes; 5% and 10% default ceilings; High-risk negotiated ceilings; cumulative diagnostic stops; risk-to-scenario mapping; pairwise default coverage; direct Compact execution; a 200-nonblank-line Compact verifier escalation threshold; concise passing evidence; exact walkthrough verification; index and log synchronization.

Out: retroactive reclassification or deletion of existing tickets/evidence; runtime, assembly, scripts, assets, generated build artifacts, XRoar, Codex application-wide behavior, weekly-quota telemetry implementation, weakening artifact-identity or hard capacity requirements, automatic approval, changes to coding-architect, and implementation of a shared verifier framework.

Scenarios, edge cases, and failure modes

  • A palette/data correction with a confirmed cause, existing pattern, two or fewer production files, and no ownership or capacity-boundary change qualifies as Compact.
  • A renderer-ownership, persistent-framebuffer, cross-phase handoff, loader/MMU/mapping, unresolved corruption, or hard-boundary change cannot qualify as Compact.
  • If Codex cannot read the weekly quota meter, the estimate is labeled as such; user input is requested only as the ceiling approaches.
  • Two rejected probes or observation-tool timeouts force reassessment; a deterministic rerun after correcting identified probe mechanics does not count as a new probe.
  • A Compact bug whose cause expands into another subsystem is reclassified before more experiments or implementation.
  • Mode and owner combinations use pairwise coverage unless their interaction is a named risk; persistent-owner defects may still require a complete crossover.
  • A Compact verifier projected above 200 nonblank lines requires a revised estimate and user approval before creation; the limit is an escalation trigger, not a correctness target or permission to compress unreadable code.
  • Failed traces and evidence required for reproduction remain retained; large passing traces may be summarized only when deterministic hashes and results prove the same criterion.
  • Emergency authorization, explicit user requests for exhaustive verification, and High-risk work remain available but must record their ceiling and rationale.

Options and recommendation

Recommended Option A: implement the complete synchronized patch below. Expected outcome: Compact bugs target no more than 5% of weekly allocation and Standard bugs no more than 10%, with explicit approval before exceeding either. Success is measured by instruction-consistency checks and walkthroughs that reject BUG-018-style Cartesian over-verification and stop BUG-019-style cumulative probe expansion. Option B: add budget checkpoints only; this is lower-edit but leaves the mechanisms that create excess work unchanged. Option C: retain current policy; this preserves maximum uniformity but accepts the reported 20–50% per-bug cost. Option A is recommended because it changes both the budget signal and the process that consumes it.

Acceptance criteria

  • All seven target files contain consistent Compact, Standard, and High-risk definitions and no contradictory eligibility rule.
  • Compact and Standard default weekly-token ceilings are exactly 5% and 10%; High-risk requires an explicit user-approved ceiling.
  • The policy stops before exceeding a ceiling and after two rejected probes, two observation-tool timeouts, or one material root-cause expansion.
  • Compact eligibility excludes runtime ownership, protocols, loader/MMU/mapping, hard memory or timing boundaries, persistent-framebuffer interaction, cross-phase handoffs, and unresolved corruption.
  • Compact verification defaults to a focused discriminating test, one natural golden path, one relevant adjacent regression, standard build, and relevant capacity guards.
  • Every added scenario must map to a distinct risk; pairwise coverage is preferred over a Cartesian matrix unless the interaction is under test.
  • Compact work defaults to direct parent implementation and requires approval before adding more than 200 nonblank lines of ticket-specific verification code.
  • Passing evidence defaults to concise summaries and hashes while failure/reproduction evidence remains retained.
  • Five policy walkthroughs pass, HTML and local links pass, edited-file whitespace passes, and the diff contains no runtime or build-artifact change.

+- Each required verification scenario must name the distinct risk it covers. Prefer pairwise coverage over a Cartesian scenario matrix. Add the full matrix only when the interaction itself is a stated risk.
+- Reuse an existing verifier or shared harness before creating a ticket-specific verifier. A Compact bug may not add more than 200 nonblank lines of ticket-specific verification code without reporting the reason, reclassifying the cost estimate, and obtaining user approval.
