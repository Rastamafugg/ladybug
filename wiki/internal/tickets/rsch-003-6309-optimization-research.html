RSCH-003 — 6309 optimization research and test harnesses Done

Measure 6309-only instructions against Ladybug’s real copy, decode, and state workloads before accepting any optimized source or separate ROM.

Identity and ordering

  • Status: Done
  • Created / updated: 2026-08-29 / 2026-08-29
  • Priority / order: P2 / 20.1
  • Roadmap or source: implementation roadmap, performance lessons, and TOOL-004
  • Owner: parent agent
  • Dependencies: TOOL-004 runtime CPU selector and documentation; no dependency on gameplay feature work
  • Cost class / ceiling: Standard research/tooling estimate of 6–8% of weekly allocation under the default 10% ceiling. Integrating a 6309-only production path, changing loader/MMU ownership, or publishing a separate ROM reclassifies the implementation to High-risk with an explicit ceiling.

Objective and motivation

Determine whether HD6309 instructions materially improve Ladybug’s measured hot paths, and build reusable harnesses that can prove correctness and timing before source changes are accepted. The research must distinguish instruction-level benefit from broader representation, MMU, framebuffer-owner, and worklist effects.

Baseline

The universal source currently assembles in 6809-only mode and contains no 6309-only mnemonics. Existing evidence identifies byte movement, sprite decoding, save-under, and persistent framebuffer composition as the important costs; several paths are strided, cross page boundaries, or require PAR5 restoration. The 6309 emulator path is provided by XRoar’s -machine-cpu 6309; the reference path is the same ROM under 6809.

Candidate set

  • TFM for contiguous source/destination copies.
  • LDQ/STQ, and where appropriate LDW/STW or SEXW, for multi-byte state and pointer movement.
  • AIM/OIM/EIM/TIM for isolated masked memory operations.
  • 6309 register-stack and bit-manipulation instructions only if a measured hotspot and ABI contract justify them.

Scope and design

In: reusable 6809/6309 microbenchmark ROMs or modules, correctness oracles, cycle/byte measurements, candidate versions of representative copy/decode/state routines, source compatibility checks, XRoar trace integration, and a recommendation for or against production use. Out: unmeasured gameplay rewrites, changes to the universal ROM, loader/MMU/framebuffer protocol changes, native hardware qualification, and separate release ROMs unless a follow-up implementation ticket is approved.

Harness requirements

  • Run identical input fixtures under 6809 and 6309 CPU modes.
  • Compare destination bytes, source preservation, registers, condition codes, and sentinel regions after each candidate routine.
  • Cover contiguous copies, strided framebuffer rows, page-crossing ranges, PAR5 remapping boundaries, partial-mask writes, and interrupt-sensitive entry/exit contracts where applicable.
  • Record instruction count and XRoar cycle timing with a named phase, worklist, deadline, and artifact hash.
  • Fail if a candidate changes bytes outside its declared destination, leaves mappings or registers outside its contract, or cannot be assembled under the declared ISA.

Scenarios and edge cases

  • TFM candidate on aligned and unaligned contiguous buffers, including zero-length and boundary-length transfers.
  • Copy candidate across an 8 KiB virtual-page boundary, with and without a required PAR5 restore.
  • Strided framebuffer rows where a contiguous transfer is invalid; this scenario can reject an otherwise fast TFM result.
  • Masked byte candidate for both nibble orientations and values that preserve unrelated bits.
  • Register/stack candidate across IRQ/FIRQ entry, subroutine calls, and existing module ABIs.
  • 6809 build rejection of every 6309-only source variant and unchanged universal ROM hash for the unoptimized path.
  • Cold and warm XRoar runs with both CPU modes, including trace timing and random RAM where the harness uses entropy-sensitive state.

Acceptance criteria

  • At least one reusable harness executes under both XRoar CPU modes and emits machine-readable correctness and timing results.
  • Every evaluated candidate has a measured baseline, measured candidate result, workload definition, and byte/cycle delta; no result is inferred from mnemonic availability.
  • Correctness passes for declared destination, source, register, flag, stack, mapping, and sentinel contracts.
  • The harness explicitly records rejected candidates and reasons, including cases where MMU stride or ownership makes an instruction unsuitable.
  • The recommendation identifies whether any candidate merits a separate approved implementation ticket, remains 6809-compatible, or should be rejected.
  • No production source or ROM behavior changes are accepted by RSCH-003 itself.

Assignment contract

  • Approved outcome: implement only reusable benchmark harnesses and evidence. Do not change Ladybug production source, release ROMs, loader/MMU ownership, framebuffer protocol, or distribution format.
  • Owned artifacts: src/bench/6309_benchmark.s, scripts/benchmark_6309.py, wiki/internal/tooling/6309-benchmarks.html, this ticket, the tooling index, and retained ignored output under build/rsch003-6309/.
  • Verification command: wsl -d Ubuntu -- bash -lc 'cd /mnt/e/projects/ladybug && python3 scripts/benchmark_6309.py --timeout 10'.
  • Evidence contract: retain the machine-readable JSON, per-variant ROM/listing/map artifacts, source hash, tool versions, correctness results, cycle deltas, 6809 rejection diagnostic, and rejected stride/remap cases.

Verification and completion

The harness executed successfully twice at the approved revision. Source hash is d1d2adbc01ebcee72cc086cc4b163e2b32d005f1ab222d7efd92be9f19156601. Baseline 6809, baseline 6309, and candidate 6309 correctness passed for all four cases. Baseline 6809 and baseline 6309 ROM bytes were identical. Candidate assembly under lwasm -9 was rejected for TFM, LDQ/STQ, OIM, and LDW/STW.

Measured candidate deltas versus baseline 6309 were: TFM 282 versus 364,937 cycles (−99.92%), LDQ/STQ 18 versus 40 (−55.00%), OIM 7 versus 12 (−41.67%), and LDW/STW 14 versus 12 (+16.67%). The unusually large isolated TFM baseline is retained as measured XRoar evidence and requires a production-hotspot benchmark before use.

Evidence: build/rsch003-6309/rsch003-6309-benchmark.json. Any production optimization or separate ROM proposal must be recorded as a new or revised High-risk ticket.
