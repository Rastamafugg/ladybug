BUG-044 — TOP score authority Verification

2026-09-26 · P1 · High-risk · order after BUG-043 · candidate implementation; parent integration pending

Objective and motivation

Wherever TOP is displayed, show the name and score in the first committed high-score table record. A live player's score remains 1ST until name entry commits an eligible result; merely passing the standing TOP value must not change the TOP display. Preserve the ranked table's default and insertion semantics.

Natural sequence: start with default first record → score below and then above that record during live play while TOP stays fixed → game over → qualification and name entry → commit selected name and score into the table → every TOP display refreshes from the new first record if it changed. The ranked table is the new display authority; the independent live HIGH_BCD copy is displaced as TOP authority.

Evidence and discriminating cause

Baseline: user report at clean source 516bdd3, rebuilt complete ROM SHA-256 9bd7daa97e8ad93f08b31e0258afb20d21593bf6189e34926ee7fcc0ddaea1a9; no new live score capture. The current build passes. In src/main.s, add_dot_score, add_bonus_score and add_special_score copy every new SCORE_BCD into HIGH_BCD, and draw_hud uses HIGH_BCD for TOP. This directly explains the reported live-score tracking. The high-score helper in src/shared_text_stage.inc stores separate ten-byte ranked records at PRES_HIGHSCORE_BASE, with the first record holding the committed score and name. Its name-entry renderer also substitutes the pending score/name for TOP when insertion index is zero, before commit. That premature display is a separate source-confirmed path to the same symptom.

Discriminating test: seed a known first ranked record and a lower live score; cross the record's score without ending the game, then enter and cancel/complete a qualifying name. Record the three underlying byte groups and displayed TOP cells at each publication. A stale or live-score-driven TOP differs from the first committed record; a correct commit updates both together.

Scope, scenarios and proposed design

In: first-record score/name authority for TOP in gameplay, instructions, level start, demo, game over, high score and name entry where those fields exist; update at commit; default first record at session start; current 1ST score remains independent. Out: ranking order beyond existing insertion behavior, persistent storage, credit accounting, score-award arithmetic, colour/palette changes, and general name-entry movement.

  1. Initialize the table with the documented default first record and display that same name/value at TOP before play.
  2. During live score changes, keep TOP's name/value equal to the committed first record, including when 1ST surpasses it. No table mutation occurs before game over.
  3. During qualifying name entry, show the existing first record until END commits the new entry. Aborting or failing qualification leaves TOP unchanged.
  4. After commit, use record zero for every TOP name/value on the next complete publication. If the inserted rank is not first, TOP remains the previous first record.
  5. Demo and stage transitions do not mutate ranked records; session reset follows the existing table persistence policy.

Recommendation: read TOP from the existing ranked record at render/publication boundaries, with a bounded cache only if measured frame cost requires one. Reject an independent score-updated TOP variable because it recreates the divergence. Test first publication after commit and both framebuffer owners; do not infer owner-specific performance from unlike phases.

Acceptance, cost and risks

  • Natural credit/start → below/above TOP scoring → game over → qualifying name entry → END → high-score and next presentation: displayed TOP name/value equal record zero at each checkpoint; live 1ST remains its own score. Risk: premature promotion.
  • Nonqualifying and rank-two-or-lower inserts: no TOP change. Risk: wrong rank ownership.
  • First-record insertion updates all TOP surfaces once, without stale A/B publication or a partially updated name/score pair. Risk: persistent framebuffer and cross-phase handoff.
  • Current complete build, hard capacity guards and frame-cycle limits pass; report before/after resident, high-score helper, presentation and cold payload sizes. Current measured baseline: resident 8191/8192, presentation 1259/1280, high-score runtime 911/938, assets 7680/7680 bytes, GMC source spare 1239 bytes.

High-risk because table access crosses game-state, banked high-score, name-entry and persistent HUD owners with hard memory boundaries. Verification remains proportional to the named risks. Seek renewed approval before changing score rules, table format, bank mapping or ranked insertion behavior. Reuse FEAT-003, BUG-036 and current presentation-flow verification; add only the smallest first-record publication comparison and one natural qualification sequence.
