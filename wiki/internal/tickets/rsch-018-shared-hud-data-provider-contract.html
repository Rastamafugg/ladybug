RSCH-018 - Shared HUD data-provider contract Proposed

Created 2026-11-02 · P2 / unassigned · no implementation authority

Objective and motivation

Define one shared contract for how gameplay and presentation provide HUD values and how the HUD formats, colors, positions, and redraws them. The goal is consistent screen output while gameplay and ranking keep ownership of their own data.

The user reported that right-side HUD values and colors differ by screen. Current source places gameplay HUD drawing in src/main.s and presentation panel updates in src/shared_text_stage.inc. The visible layout is authored in Tiled and copied from the shared template to the affected maps. This proposal addresses the division of responsibilities before any code is changed.

Source baseline and confirmed user decisions

  • src/main.s contains draw_hud, score/vegetable/part writers, draw_lives, and life_marker_position. The source comment defines LIVES as reserve lives after the active player enters.
  • src/shared_text_stage.inc contains presentation screen writers, including presentation_panel_slice, which is called by stage_panel_slice and dispatches TOP or High Score panel work.
  • The shared tiled/coco-template.tmx supplies the HUD layout copied to seven screen maps. The current presentation build path generates screen data and color rules from those maps.
  • User direction: gameplay values need to be available at each gameplay update. Ranking records can be supplied at game/Attract initialization and refreshed only after a game-over flow changes them.
  • User direction: the life-award movement remains gameplay/event-flow work. After the award is committed, the HUD receives the new reserve count and owns which static life markers are lit. The 1.0 display has at most 12 markers; reserve count may exceed 12 and saturates at 255. A numeric count above 12 is future work.

These are source observations and user decisions, not build or runtime results. The current HUD inconsistency has not been traced field by field across every screen; that inventory is part of this research.

Proposed scope

In: inventory each HUD field by screen, data owner, source writer, map cell, format, color, and refresh event; define a compact, read-only provider/view contract; define when gameplay and ranking publish data; define the life-marker refresh around the existing award animation; define the single layout source and map-sync/build handoff; and account for mapping, framebuffer, code-size, and active-worklist timing constraints.

Out: changing score, ranking, or gameplay ownership; adding a numeric above-12 life counter in 1.0; changing the adopted EXTRA/SPECIAL rewards; implementing the shared renderer or provider in this ticket; changing Tiled art outside the agreed template-sync process; and building, testing, or running the game as part of this design ticket.

Recommended contract to evaluate

  1. Gameplay remains the authority for current score, reserve lives, stage, vegetable progress, and part value. It provides a fresh view on each gameplay HUD update, or a changed-field mask when the value changes; the HUD never writes back to those values.
  2. Ranking remains the authority for records and pending name/score. Provide its snapshot at game/Attract initialization and refresh it after a qualifying game-over/name-entry flow commits a changed record. Do not poll ranking data on every gameplay update.
  3. The HUD owns field layout, formatting, color selection, and pixels. It consumes copied values or a synchronous provider interface whose lifetime is valid across the selected memory mapping; it must not retain a pointer into a page that can be remapped.
  4. For lives, gameplay owns the one-byte reserve count and all award/loss changes; the HUD receives a read-only count and never changes it. A completed award increments once up to 255; at 255 it still completes the route/cue/animation but leaves the count at 255, so it cannot wrap to the zero game-over sentinel. A life loss uses the existing gameplay decrement and game-over path at zero. The event-flow owner controls the moving life animation. It commits the award only when that animation finishes, then asks the HUD to redraw the static row from the new count. The HUD lights min(reserve_count, 12) markers; the moving sprite temporarily covers slot 12 when all markers are lit, then disappears as the HUD redraw reveals the marker. A later numeric counter can use the same full count.
  5. Tiled template layout remains the visual source of truth. The build converts field markers and color properties into one descriptor contract, then synchronizes the designated maps; gameplay and presentation code must not keep independent copies of cell coordinates, formats, or colors.

Proposed snapshot address and handoff

Evaluate a 32-byte by-value HUD snapshot at CPU address $02A0-$02BF. The memory map records PAR0 initialized to map $0000-$1FFF to physical page $38; under that mapping, this range remains addressable while PAR5 changes. That is a condition of the proposed design, not proof that PAR0 is permanently fixed or that these bytes are free. This is a candidate only: the memory map does not mark the bytes free, and an older BUG-087 allocation analysis also mentions $029B-$02A0 as a candidate range. Before selecting this address, audit current symbols, scratch and stack use, boot/runtime lifetimes, confirm PAR0 remains mapped to $38 throughout capture and draw, and inspect the boundary byte at $02A0. If any live owner overlaps or the view does not fit in 32 bytes, select a different audited range; do not silently allocate over it.

The proposed provider copies named values into the snapshot while each source owner is accessible: gameplay publishes on a HUD update, while ranking publishes at initialization and after a committed record change. The renderer reads the copied fields and retains no pointers into PAR5-mapped pages. Routine names, byte offsets, and whether updates use a whole-record copy or a changed-field mask remain open design details.

Read-only low-RAM ownership audit

Audited the current E:\projects\ladybug worktree on branch main, HEAD 1a55c4ac; several inspected source/build files contain uncommitted changes, so this result describes the current worktree contents, not that commit alone. No build or runtime check was run.

  • The source declares no fixed game variable in $02A0-$02BF. On the lower side, the keybinding block ends at $029A and the rate helper owns $029B-$029F. On the upper side, audio storage begins at $02C0 and continues through its guard, status bytes, and service gateway. The current stack window is $1E00-$1FFF.
  • Menus share the presentation selection byte $E0; shared_text_stage.inc names it MENU_SELECT, and the Keybindings screen uses that same byte as its row index. The Keybindings screen uniquely needs five persistent gameplay key values plus scan/capture state: its declared 20-byte block is $0287-$029A, with key values at $0287-$028B, fixed-menu held state at $028C, $028D reserved, eight row samples at $028E-$0295, and five working bytes at $0296-$029A. This is additional keybinding data, not a separate menu-selection variable. General Attract/Options navigation bounds up/down at MENU_SELECT; Options also rejects indices 2 and above before indexing MENU_LIVES. Keybindings bounds normal navigation to rows 0–5, with row 5 returning Back and capture intended only for rows 0–4. Its capture writer nevertheless relies on that flow rather than checking the index at the write.
  • That capture path is the conditional indirect writer: src/keybinding_runtime.s sets X to KB_BIND=$0287, loads B from $E0, then stores one byte with sta b,x. The target is $0287+B; values B=25 through 56 would write into $02A0-$02BF. Normal screen entry clears the shared selection and normal navigation stays in range. I found no source path or recorded runtime incident that puts it out of range. An unrelated memory-corruption bug or unexpected capture entry could do so, but those are hypothetical, not observed causes.
  • Generated boot copy paths are bounded away from the range. scripts/build_sparse_sprites.py places its 8-byte copy descriptors at $0200 and rejects a table larger than 128 bytes, so it ends before $0280. It also restricts generated low-RAM payload destinations to $06B0-$07FF or the presentation window at $1900-$1E3F. The bootstrap consumes the copy table during boot; the compressed-stream table is separately staged at $1800-$187E and retires before runtime handoff. PAR0 is set to page $38 at boot/startup; inspected later mapping writes target PAR1–PAR5.
  • The older BUG-087 record's broad $029B-$02BF candidate and “no references” scan are historical, not current clearance: the rate helper now actively writes $029B-$029F, and the keybinding indexed store was not ruled out by that scan.
  • src/audio_runtime.s still comments that “Boot tables end at $02BF.” That conflicts with the current bootstrap table at $1800-$187E; the comment is stale evidence, not an owner declaration. It was not edited in this audit.
  • The non-shipped src/rom_probe.s is a one-off cartridge-window diagnostic, not part of scripts/build.sh's game build. Its purpose, fixed parameters, output format, capacity limit, and historical result are documented on the cartridge-window ROM probe page. Git history adds it on 2026-05-10 and extends it to scan $C000-$FEFF on 2026-05-12. The lessons-learned record documents an XRoar/GDB run on 2026-05-12 with 50 mismatches. Each mismatch is four bytes, starting at $0200; by calculation, 50 records occupy $0200-$02C7, including the proposed range. This span is an inference from the reported count and source record format; no matching low-RAM dump or exact ROM identity was found. The source-reference registry excludes the probe from shipped modules.

Assessment: The source-level indirect-reference and phase-lifetime review is complete. It found no intended shipped-game owner in $02A0-$02BF, but found a conditional keybinding write if the shared selection index leaves its normal 0–5 range. Thus the range is not cleared for allocation. Before selecting it, bound or independently verify that indexed write's input, narrow the source-reference ownership record to this subrange, correct the stale boot-table comment, and compare against a fresh build-generated destination map. The current E worktree is dirty, so this review does not certify commit 1a55c4ac or a linked artifact. No bytes were reserved or written; no build or runtime check was run.

For persistent A/B rendering, the proposed HUD draw joins the existing render-intent transaction. Source defines RF_HUD and RF_LIVES intents; framebuffer_queue_damage carries persistent HUD/life intents to the other surface, and the renderer paints the selected BACK surface. The vertical-border interrupt swaps FRONT and BACK only when FB_RENDER_PENDING says the BACK surface is complete. The shared HUD must therefore update or queue damage for the appropriate surface, never draw directly to FRONT, and let the existing publication point expose the completed frame. The exact call boundary and proof that both surfaces contain current HUD pixels remain to be designed.

Proposed Tiled color preview

Keep the template's black-and-white placeholder art and authored geometry as the layout source. Current source has two other color inputs: scripts/build_presentation.py's presentation_pen_map applies screen/map palette rules to authored tiles, while scripts/shared_text.py reads assets/arcade/text-colours.json for shared-text field colors and coordinate runs. These inputs have different responsibilities today and can overlap on visible HUD fields.

Proposed relationship: for HUD fields explicitly represented in the template, semantic field IDs and color properties in that template become the single authored field-color source. The generator derives the runtime field-color data and a Tiled-visible preview from the same properties. For any such field currently represented in text-colours.json or covered by presentation_pen_map, the design must choose migration or a generated consistency check; it must not leave two independently edited values or silently discard a needed rule. Keep JSON coordinate runs and palette rules for content outside the template-defined HUD fields unless the field inventory shows they should move too. The preview remains generated output, not a second hand-edited source. Property encoding and preview artifact format are proposals, not frozen implementation choices.

The exact snapshot address, byte offsets, refresh call shape, descriptor schema, framebuffer call boundary, and preview encoding are not frozen. The design must settle them after source-level ownership and mapping checks; no proposed address or preview counts as implemented or qualified evidence.

Required design scenarios and edge cases

  • New game and first visible gameplay frame: initialize all gameplay-owned HUD fields from the new game state.
  • Ordinary gameplay update: score, stage, part, vegetable, or lives changes are reflected on the next defined HUD refresh without a screen-specific stale value.
  • Life award and loss: after the moving sprite reaches its destination, gameplay commits one award and publishes the resulting count; the HUD redraw reveals at most 12 static markers with no duplicate sprite. Counts 12 through 255 show 12 markers. At 255 another award leaves 255; a normal loss decrements the reserve count and zero follows the existing game-over path.
  • Attract/High Score entry and changed record: ranking snapshot is present on entry, remains stable during gameplay, and refreshes after a record/name commit.
  • Screen/map transition and both persistent framebuffer owners: drawing uses the selected prepared BACK surface and does not publish an incomplete field update or write directly to FRONT.
  • Missing or stale provider data: the design defines a deterministic fallback to authored baseline values and never borrows a prior screen's state accidentally.

Acceptance criteria for the design ticket

  1. Provide a source-backed screen/field matrix naming the current writer, logical owner, map layout/color source, and refresh event for every HUD field in the target screens.
  2. Specify the provider/view schema, ownership, update cadence, dirty-field behavior, initialization, ranking refresh event, life-animation handoff, stale-data fallback, and error behavior.
  3. Specify how the shared Tiled template becomes build input and how generated descriptors replace duplicated coordinates/color rules.
  4. Audit the proposed $02A0-$02BF snapshot against live symbols, scratch, stack, and phase lifetimes; document the provider copy boundary and PAR5 expectations.
  5. Specify how shared HUD damage reaches the selected BACK surface, remains correct for both persistent surfaces, and is published only after the existing completion handoff.
  6. Specify template field-color ownership and its relationship to text-colours.json field values/runs and presentation_pen_map rules; define migration or consistency checks for overlaps and stale-preview detection.
  7. Account for current direct-page ownership and PAR mapping, persistent BACK/FRONT rules, the 1,280-byte presentation-module ceiling, and the 27,000 active-cycle target. Identify which figures are limits, estimates, or still unknown; do not claim timing or capacity passes without a build.
  8. Deliver a separate implementation boundary and least-cost verification plan. No code or map edits are acceptance for this ticket.

Options and risks

Recommended: centralize the HUD's drawing contract and use stable, read-only provider values while leaving gameplay and ranking state in their current owners. This reduces divergent drawing rules without making the HUD the authority for score or records.

Rejected for this proposal: moving all score/life/ranking state into a new HUD-owned state module. That duplicates or transfers authoritative game state, expands save/restart and screen-transition behavior, and adds unnecessary coupling.

Risks: banked modules may not share an address window at the same time; the proposed low-RAM range may overlap a live scratch, stack, or historical candidate allocation; persistent-framebuffer ownership requires redraws on the prepared BACK surface; Tiled layout or color-preview output can drift if generated from different metadata; and a common refresh routine may consume presentation bytes or cycles. The design must resolve the address audit and measure or bound the other effects before implementation is proposed.
