Approval brief

Objective and motivation

The attract title must show the complete arcade-referenced actor sequence using the existing gameplay sparse renderer and persistent framebuffer publication path.

Reproduction and measured baseline

  1. Launch the current integrated cartridge without input and allow boot to publish the attract title.
  2. Observe the complete title-state interval before instructions.
  3. Compare actor inventory, positions, source frames, phase durations, underlay restoration, and framebuffer publication with assets/arcade/attract_actor_reference.json.

Current CoCo baseline: src/presentation_runtime.s draws only two hard-coded actors at $661C and stale $2CA4, selects only frame values zero through three, redraws every attract tick without restoring four independent footprints, and holds attract for 360 ticks. The BUG-009 closure build at current main measures resident 8190/8192 bytes, assets 7144/7680, bank-3 runtime 4081/4096, presentation module 1214/1280, cold payload 9755/10874, combined module/cold 10969/14219, CPU-readable GMC spare 3743 bytes, and future-sound margin 2207/512 bytes.

Measured arcade oracle: a neutral-input MAME 0.220 capture records 1,800 consecutive BGRA32 frames. Complete title frames are 185 through 742 inclusive, a single measured interval of 558 frames. Four stationary actors animate synchronously. Phase zero lasts six frames because the complete title begins mid-cycle; phases one, two, three, and zero then repeat in eight-frame holds. Frame 743 is blank, frame 744 begins instruction drawing, and frame 745 is the first complete instruction frame. One capture frame maps to one CoCo 60 Hz Vbord tick. The capture command, raw hash, coordinate transform, four source-code sequences, crop hashes, and boundary hashes are canonical in the oracle.

The actors are upper-left Yellow at raw (64,16) / CoCo (56,112) / $661C; upper-right Purple at raw (152,32) / CoCo (72,24) / $2F24; lower-left Pink at raw (24,64) / CoCo (104,152) / $7F34; and lower-middle Green at raw (96,72) / CoCo (112,80) / $5238. Three sequences map entirely to existing enemy sparse indexes. Purple phases zero and one are absent; appending those two capture-proven frames changes the enemy payload from 22,683 to a projected 23,005 bytes, a 322-byte net increase, and remains inside physical pages $35-$37 with 1,571 destination bytes spare.

Scope

In: capture-backed inventory, coordinate transform, frame sequence, duration records, two capture-proven missing sparse frames, existing sparse drawing, four independent underlays, persistent-owner preparation, and focused natural/forced verification. Out: title map selection or artwork, instruction actors, gameplay actor behavior or indexes zero through 127, independent actor renderers, cold sprite pixels, sound, and BUG-011 through BUG-013 behavior.

Natural sequence, scenarios, and failure cases

  1. Prior screen remains complete while the attract screen is prepared without visible partial writes.
  2. Both persistent owners receive the same complete static title and phase-zero actors before the first title publication.
  3. The first complete title frame starts the 558-tick oracle interval: phase zero for six ticks, then synchronized eight-tick phases 1,2,3,0.
  4. At each phase change, restore all four old footprints, draw all four new frames through the existing sparse decoder, restore PAR5, and publish at Vbord.
  5. After tick 558, leave BUG-009 screen selection and the existing instruction-loading transition in control; the arcade partial-draw boundary is evidence, not a requirement to expose a partial CoCo screen.
  • Cold launch, warm reset, and the later natural attract-loop return must show the same interval.
  • Initial owner orders (front A, back B) and (front B, back A) must converge to identical title pixels and actor metadata.
  • Credit and start edges during owner preparation, phase restoration, the last title tick, and instruction handoff must pre-empt without a partial title, stale underlay, or lost edge.
  • A missing actor, wrong source code, wrong transform, wrong hold, changed static title cell, write to FRONT, missed commit, PAR5 leak, payload overflow, or absent natural scenario is a failure.

Selected design and rejected alternatives

Use the existing compatibility framebuffer at physical pages $28-$2B only as a pixel-identical hold surface while both persistent owners are prepared. Copy the current visible owner to that surface in bounded chunks, select it at Vbord, render the authored attract map into owners A and B through the existing map loader, capture four canonical 128-byte underlays at $B000-$B1FF, draw phase zero into both owners, then enter normal A/B Vbord publication and start the 558-tick timer. If preparation is pre-empted, retain the complete hold surface until the replacement screen publishes. Pages $28-$2B are already reserved compatibility storage and $B000-$B1FF is within documented free game-state RAM; no new runtime owner or physical allocation is introduced.

Append source sprites 6 and 7 with the oracle's horizontal transform to the existing enemy sparse list as indexes 128 and 129. Preserve indexes zero through 127 byte-for-byte. Store only four destinations, sixteen sparse indexes, and timing/underlay metadata in the existing presentation data path. No sprite pixels may enter the cold presentation payload.

Rejected alternatives are direct writes to the scanned FRONT owner, which reintroduce destructive sprite tearing; publishing an unsynchronized BACK owner, which reproduces the mostly-black failure; a second actor renderer or cold sprite atlas, which violates approved scope; and changing existing gameplay sparse indexes, which creates unnecessary gameplay risk.

Acceptance criteria

  • All four actors, source frames, fixed coordinates, and appearance order match the oracle for every title frame.
  • Phase boundaries match within one 60 Hz tick, total complete-title duration is 558 ticks, and no extra actor-visible pre-roll is introduced.
  • Every old footprint restores to the authored title pixels; both owner orders converge exactly and no static title cell changes.
  • Existing sparse indexes zero through 127 and all gameplay actor behavior remain unchanged; only capture-proven indexes 128 and 129 are appended.
  • No second renderer, cold sprite pixels, FRONT writes, missed commits, PAR5 leak, hard-capacity failure, or required-scenario omission occurs.
  • Every preparation and phase-change worklist completes within the 29,666-cycle hardware maximum; the engineering target is at most 27,000 cycles.
