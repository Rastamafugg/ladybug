BUG-005 — Gate replay after collectible colour change Verification

Preserve the current runtime gate orientation when a nearby collectible is recoloured.

Approval brief

Objective and motivation

When a bonus-colour transition redraws a collectible near a gate, the affected gate union must end in the authoritative GATE_STATE orientation on both framebuffer owners. The bug is visible now because queued gate damage and entity redraw use different publication phases.

Evidence and baseline

The current path can project a queued gate final through framebuffer_project_gate_only, then run erase_entity_footprints/draw_entities for RF_ENTITIES without a current gate intent. A forced XRoar snapshot using build/ladybug.rom and a gate-0 nearby-entity state produced a 19-byte difference in the gate union between the no-colour control and colour-cycle case on both owners. This is a single diagnostic observation, not an acceptance result; temporary captures are under /tmp/ladybug-debug-01.

Scope

In: ordering and publication of queued gate damage relative to collectible colour redraw, gate/entity overlap, both framebuffer owners, and replay regression coverage. Out: gate geometry, collectible art/palette definitions, movement rules, and a new renderer protocol.

Scenarios and edge cases

  • Pending final gate plus colour change with an overlapping heart, letter, or skull.
  • Pending diagonal followed by final gate and colour change across alternating owners.
  • Gate with no nearby collectible as a control.
  • Both gate orientations, neighbour unions, repeated colour cycles, and collected entities.
  • Natural replay after a gate transition, not only an isolated forced state.

Options and recommendation

Recommended: ensure any queued gate projection remains scheduled after current entity/underlay work, or reapply the authoritative gate union after that work. Preserve the existing generated transition streams and bounded entity cache. Reject broad full-screen redraws because they would alter the persistent-framebuffer budget and scope.

Acceptance criteria

  • Forced and natural colour/gate scenarios converge pixel-for-pixel with an independently rendered authoritative gate result on both owners.
  • No static maze tile or stale wall overwrites a current gate wall in the gate-plus-neighbour union.
  • Existing BUG-001, BUG-002, BUG-003, BUG-004, gate-cache, and no-overlap checks remain passing.
  • Current build, capacity, and framebuffer ownership guards pass; missing required scenarios fail verification.

Type-specific diagnosis

Observed: recolouring a nearby collectible can leave gate wall bytes in the wrong orientation. Expected: gate state is authoritative after every combined replay. Competing causes: stale gate intent, stale entity cache, or underlay ordering. Discriminating cause: the forced pending-gate control differs only by RF_ENTITIES; the colour case redraws entity footprints after the queued gate projection, confirming underlay ordering.

  • Constraints: retain generated transition payloads, bounded cache records, framebuffer ownership, natural A/B replay, and all existing capacity limits. Do not modify Tiled assets or unrelated dirty build/session files.
