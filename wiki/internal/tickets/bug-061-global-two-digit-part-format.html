BUG-061 — Render every PART value with two digits Draft

2026-10-01 · P2 · Standard · Draft · RSCH-014 Step A

Approval brief

Objective and motivation

Use a leading zero for single-digit PART values and reserve a two-digit field wherever the game shows a part label/value.

Evidence, reproduction and cause

The complete gameplay HUD already calls asset_draw_two_digits, which writes a leading zero for values 1–9. The shared stage-panel formatters in src/shared_text_stage.inc and src/shared_text_ranking.inc suppress a zero tens digit and emit one to three significant digits. STAGE is documented as 1–255 while FEAT-005’s selectable starting level is 1–99. Therefore the 01–99 case is source-confirmed, but the requested two-digit rule has an unresolved 100–255 display boundary.

Scope

In: static PART labels/field width and dynamic formatting on gameplay, level-start and any other screen that displays the current part. Out: changing stage progression, vegetable selection or clamping behavior without renewed approval.

Design and prototype

Reuse the existing two-digit digit renderer for all 01–99 paths and ensure every affected TMX field has two value cells. Do not choose saturation, wrapping, three-digit continuation or a maximum-stage rule for values over 99 until the user resolves that boundary. Preserve all current score, part selection and vegetable content.

Scenarios and edge cases

  • Values 1, 9, 10 and 99 display exactly 01, 09, 10 and 99 in every approved PART field; no stale third digit or one-cell shift remains.
  • All screen labels/value cells have consistent two-digit placement and colors; gameplay, next-level, level-start and other current-part displays agree.
  • The >99 behavior is stated by the user before the ticket advances to Proposed/Approved; no behavior is inferred here.
  • Current complete build, shared-text static checks and natural first-part plus stage-transition display pass after layer and FEAT-005 dependencies.

Cost class, dependencies and risk

Class: Standard. Dependencies: BUG-059/060 layer and static map contract; FEAT-005 SharedText reconciliation; explicit user resolution for values above 99. BUG-035/048 historical stage-panel work does not prove current dirty map formatting.

Risk controls: use only current-revision artifacts and exact authored target cells. A missing natural screen, build or edge scenario is incomplete evidence. Any change to outcome, behavior, dependencies or risk after approval returns this ticket to Proposed.

Assignment and verification contract

Owned artifacts after approval: Candidate src/main.s, src/shared_text_stage.inc, src/shared_text_ranking.inc, assets/arcade/text-colours.json and relevant Tiled maps, to be narrowed after the >99 decision. No production edit is made.

Required commands and scenarios: After approval: complete-profile scripts/build.sh build; existing shared-text and presentation verifiers; focused current-artifact checks for 01/09/10/99 plus the user-selected >99 boundary. Runtime phases must prove current ROM bytes and name success marker/deadline before PC interpretation.

Evidence and commit: retain concise current-map/source/ROM hashes, exact target-cell or event receipts, failing evidence and capacity deltas. One bounded implementation commit after explicit approval and Ready; no push or ticket closure by an execution agent. Parent owns integration and QA.

Completion report: commit, commands, measured results versus every target, capacity/headroom, rejected experiments, residual risks, current evidence paths and justified ticket status.

2026-10-01 — Part display recommendation; not a decision

Source baseline fe160ae has an eight-bit STAGE, 1–255. next_stage increments 255 through zero to 1; selecting a starting part is limited to 1–99 but natural progression is not. Recommendation: minimum two digits, showing 01–99 and the true 100–255 thereafter. This preserves progression and avoids a misleading saturated 99 or modulo-100 label. It is an explicit exception to the user's literal two-digit requirement and requires confirmation; do not silently adopt it. A strict two-cell field cannot represent all existing stages uniquely.

Standard class retained for the display proposal. Scope is formatting and necessary field clearance only; no stage, enemy, vegetable or option-range change. Target: every applicable screen shows the same true part with zero-padding below ten. Focused values 1/9/10/99 cover padding and digit transitions; 99→100 covers field expansion and stale pixels; 255→1 covers existing rollover and erasure. Combined build/fit and natural screen transitions remain required. BUG-059 and FEAT-005 integration precede current-ROM verification. User review request is not approval; BUG-061 remains Draft.
