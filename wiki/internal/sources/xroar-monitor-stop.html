2026-10-07 — Single-step acknowledgement precedes the durable stop

In coco3.c lines906–922, the emulation loop later consumes the requested steps, executes them, then calls monitor_mark_stopped with reason step. wait_for_stop at monitor.c lines1338–1378 waits for that durable reason/PC; clear_breakpoint at lines1245–1288 is halted-only. This is an observation-order correction; it changes no game code or acceptance criteria.

2026-10-07 — Normal monitor timeout does not stop XRoar

Source review at XRoar revision 66f010efb6b8521b000f00e75afd6a06f7d1599b (the already-ingested monitor.c SHA-256 remains 30c0d8f4ff69963eec0439c191e3993335d241fefc04da6950da5c4a7709de65) confirms wait_for_stop blocks on the run-state condition and sends a JSON response with reason="timeout" when its deadline expires; it does not change the emulator run state or terminate XRoar. coco3_run continues CPU execution while monitor state is running. Requests are serialized per client, so a long poll blocks later requests on that connection until the wait returns.

Therefore a missing wait response plus a missing monitor listener is not the normal no-breakpoint timeout result. The source cannot distinguish process crash, external termination, or transport loss. The fresh candidate mainloop sentinel confirms one new process survives a reachable stop, but does not reproduce the earlier long callback wait.
